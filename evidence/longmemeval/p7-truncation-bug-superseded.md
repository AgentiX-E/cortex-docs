# P7 发现 —— MR 检索框架丢弃了它大部分的证据预算

**状态**：根因经可复现实验确认。尚未改动生产代码。

## 1. 错在哪里

`truncateSession`（`natural-language-memory.ts:1615`）有一个预算记账
bug，使它几乎丢弃了整个每会话配额。这不是调参问题，也不是检索排序问题。
它是一个 `break`。

```ts
for (const turn of turns) {
  if (/\] user:/.test(turn)) {
    if (used + turn.length > maxChars) {
      truncated = true;
      break;            // <-- abandons the remaining budget entirely
    }
    kept.push(turn); used += turn.length;
  } else {
    const head = sliceCodePointSafe(turn, ASSISTANT_HEAD_CHARS);
    if (head.length < turn.length) { truncated = true; }
    kept.push(head); used += head.length;
  }
}
```

当一个用户回合放不下时，循环**终止**。每一个剩余回合都被丢弃，
包括那些每个只花 200 字符、本可放下的助手开头。函数返回时预算大量未花。

## 2. 测得的严重度

在运行 `34594513996` 的全部 316 个金标准会话上（`session_survival.py`）：

| 指标 | 值 |
|---|---|
| 完整出现在框架中的金标准会话 | **0 / 316 = 0.0%** |
| 主体长度中位数 | 14 746 字符 |
| 实际保留的字符数中位数 | **325** |
| 存活率中位数 | **2.2%** |
| 存活超过 50% 的会话 | **0** |

每一个金标准会话都被砍到其主体的约 2%。每会话预算为
2000 字符，因此保留约 325 意味着**每个会话大约 1675 字符（84%）的配额被丢弃**。
在每框架约 17 个会话上，每题约丢弃 28 000 字符的可用证据。

## 3. 可复现的最小复现

`/tmp/probe2.mjs`，镜像 LongMemEval-S 的回合形态（用户约 900 字符，
助手约 1400 字符），预算 2000：

```
session len 14202
result len  1143        -> 57% of the budget used
user turns kept: 1 of 6
```

第一个用户回合吃掉 901 字符（预算的 45%）。五个助手开头增加
1000。已用 1901 时，*下一个*用户回合（901）溢出 —— 而 `break` 丢弃了
该会话的其余部分，留下 857 字符预算未用，并丢掉 6 个用户回合中的 5 个。

这与真实数据完全吻合：实例 `0a995998` 在 14 601 字符的主体中只保留 283 字符（1.9%）。

## 4. 为何这解释了平台期

从 `mr_attribution.py`，121 个实例中有 22 个收到不完整的证据集，
其准确率为 63.6%，对照完整样本的 88.9%。错误分解为
`0.157 = 0.099 (retrieval) + 0.058 (extraction)`。

失效模式精确吻合：MISSING 但错误的例子全是**差 ±1 的计数**
（`3→2`、`2→3`、`4→5`、`2→1`）。模型不是幻觉，也不是算错 ——
它正确地枚举了一个证据集，而该证据集恰好缺失那些被丢弃回合所携带的那一项。

## 5. 为何这是一个 bug 而非一个设计选择

该函数自己的文档字符串陈述了其契约：

> “限定会话长度，同时保留承载事实的用户回合。
> […] 这会保持每个用户回合完整并限制助手回合。”

其意图是在预算内最大化保留的用户证据。`break` 做的恰好相反：
一旦某个用户回合放不下它即停止，即便预算大部分尚存。`ASSISTANT_HEAD_CHARS`
常量只有在循环被期待越过一个超大回合继续时才有意义 —— 否则这些编码成本毫无意义。
实现与其文档化的契约相矛盾。

还有第二个较小的缺陷：`ASSISTANT_HEAD_CHARS` 被计入 `maxChars`，
但文档字符串只把用户回合描述为受预算约束的资源。无论意图是哪一个，
当前代码对两者都收费然后提前停止，因此两种读法都未被满足。

## 6. 候选修复（待设计，尚未应用）

循环不得在第一个放不下的用户回合处终止。选项，大致按偏好排序：

1. **继续而非 break。** 跳过超大的用户回合并继续处理，使之后放得下的回合被保留。
   保持文档化的“保留每一个放得下的用户回合”契约。
2. **分别预算用户回合与助手开头**，使助手开头永远无法挤掉那些它们只为其提供上下文的用户事实。
3. 两者兼施，并保证至少一个用户回合总能存活。

无论选择哪一个，都必须明确陈述该不变量，因为当前代码没有任何本可捕获此事的测试：
需要一项断言“保留长度接近预算”或“每一个放得下的用户回合都在场”的测试，
且它必须对当前实现失败。

## 7. 对框架预算的下游影响

修复这一点会增加每个会话存活的文本，这会改变 `DEFAULT_MAX_AGGREGATION_CHARS`
（20 000）上的压力。每会话预算与框架预算相互作用，因此在修复之后、
触及框架预算之前，必须重新测量框架利用率。121 个框架中已有 105 个显示
`[truncated]` 标记，所以框架也在裁剪会话。

## 8. 这没有解释什么

11 个抽取错误（PRESENT 但错误，`$3,750→$8,750`、`4→6`、`3→4`）
仍是独立的问题 —— 先枚举再计数而没有强制台账。那是
P7 计划中的 P1，不受本发现影响。
