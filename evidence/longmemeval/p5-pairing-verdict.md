# P5 配对判决 —— 为何两个配置相同的实验臂出现了分歧，以及修复

**受测提交：** 缺陷为 `1ce76aa`；修复为 `20592f2`。
**证据：** 运行 `34389565513`（P3b）。97/127 与 99/127 两个数字记录在
`p3b-graph-verdict.md`（第 44–47 行），而非从产物读取 —— 见下文“来源”，
这是本判决的一项局限。
**承接：** `p5-verdict.md`，它把这个标记为一项未解异常，并把它定为任何进一步
特征工作之前的首要先决条件。

## 判决先行

**该异常是真的，其机制是 LLM 调用不可复现性遇上逐实验臂的缓存实例，且它已被修复。**
TR 引擎消融的两个实验臂解析到*同一*配置，却在同一次运行中得到 97/127 和 99/127。
它们出现分歧，是因为每个消融都分配了自己的查询扩展缓存，所以每个实验臂各发出
127 次独立的 LLM 调用，而托管端点在 `temperature=0` 下也不会跨调用为同一提示词
返回相同文本。

修复：每一对消融现在共享一个答案缓存（`20592f2`）。共享在构造上就是安全的 ——
缓存以完整渲染后的提示词为键，因此提示词不同的实验臂不会冲突。

**正是这一对产生了截至 P3b 每一份判决所用的运行内噪声底。** P3b 判决引用的恰恰是
这两个实验臂 —— `tr-deterministic-temporal` 的 97/127 与 `tr-no-graph-recall` 的 99/127 ——
称之为“配置上完全相同的系统”，并把那 2 道题的差距称为“同配置运行间漂移”，
并由此导出 **2 道题 / 1.57 pp 的运行内噪声底**
（`p3b-graph-verdict.md` 第 44–47 行）。那个噪声底正是 `p5-verdict.md` 所推翻的。
所以该噪声底不只是*像*一个缓存产物 —— 它就是一个。

## 来源（本判决的局限）

图召回消融报告**不存在**于 `p3b-graph-34389565513` 产物中：该产物包含主报告、
MR 消融、TR 引擎消融和 KU 双时间消融，但没有 `benchmark-tr-graph-*` 文件。
图实验臂在 `1ce76aa` 时尚未接入 `bench/run.ts`，因此它从未被上传。

因此，97 和 99 这两个数字取自 P3b 判决的正文，而非从产物重新导出，
且 97 由 `benchmark-tr-ablation-report.json` 佐证（TR 引擎 `featureAggregate` = 97/127），
而 99 在此无法被独立验证。真正能独立验证、且承载论证的，是下面的缓存共享对照 ——
它无需任何图实验臂就有意义。

教训正是本次迭代反复重学的那个：一个丢弃报告的产物通配，会静默地使结果无法恢复。
工作流的上传步骤已经正是为此通配 `benchmark-*.json`；缺口在于该实验臂根本没有产出文件。


**在确立这一点时我还犯了两个错误，都在此更正：**

1. 我声称存在一个“三个实验臂、一个配置、三个答案”的缺陷
   （TR 的 100 对 99 对 97）。错了。100 来自**主**报告，其特征系统跑在完整的
   500 道题样本上；97/99 来自只跑在 127 道 TR 题上的消融。样本不同，
   而主报告并不是对同一量的可比测量。
2. 我声称主报告的图消融显示了算术上不可能的 `30 repaired / 0 broken` 且总数不变，
   并称之为评分退化。错了。那一行是 **ABS** 能力码，而其对比是有意为之：
   基线实验臂有 `enableAbstention: false`，因此从不返回 `null`，而特征实验臂
   对全部 30 道弃权。`judgeScorer` 把 ABS 题评为 `answer === null`，
   所以 `0 → 30` 是弃权对比完全按设计运作，而非缺陷。

两个错误都来自阅读聚合数字而没有检查它们是在哪个样本、哪个能力码上计算的 ——
与 P4 代码修订混淆相同的失效模式。这个检查很便宜；我跳过了它两次。

## 证据链

### 0. 承载论证的对照（可独立验证）

下文其余一切都只是支撑性细节。这是承重证据，它不需要图实验臂，也不需要外部数字：

| 实验臂对，同一次运行 `34389565513` | 缓存 | 不一致 |
|---|---|---|
| 主报告：`nl-naive-baseline` 对 `nl-abstain-feature` | **共享**扩展 + 答案缓存 | IE、MR、KU、TR 上 **0 / 0**（470 道） |
| `tr-deterministic-temporal` 对 `tr-no-graph-recall` | **各自独立**，配置相同 | **2 / 127** |

两行都来自产物中的文件。共享缓存的实验臂在**全部 470 道题上的每一道**都一致。
没有配置差异但缓存各自独立的实验臂出现分歧。唯一的变量是模型是否被问了两遍同样的
问题 —— 这是工装的性质，而非任何模型或实验臂的性质。

### 0b. 该缺陷在当前代码中仍然存在，不只存在于 `1ce76aa`

在四次 `2c2c635` 运行（早于该修复的那几次）上检查配对不变量，
主报告的两个实验臂在**四次运行中的三次**违反了它：

| 运行 | 违规（非 ABS 不一致对） |
|---|---|
| `34492139716` | 无 |
| `34558715449` | TR 0 破坏 / 1 修复 |
| `34558717704` | KU 0/1，TR 0/1 |
| `34558719936` | TR 1/1 |

主报告的两个实验臂在 `2c2c635` 时已经共享了两个缓存，所以这是一个不同于 `1ce76aa`
且更有意思的失效：共享缓存是必要的，但**并不充分**。对调用序列的一次探测说明了原因 ——
在只共享答案缓存、不共享查询扩展缓存时，一道题产生**三次** LLM 调用：

```
CALL0 = expansion prompt   (not cached)
CALL1 = QA prompt          (cached)
CALL2 = expansion prompt   (identical to CALL0, not cached)
```

所以实验臂仍然会重新查询扩展提示词。在查询扩展缓存也被共享后，调用数降到两次，
每个不同提示词一次。`20592f2` 中的 `answerCache` 修复覆盖的是那些**完全**没有
缓存共享的消融实验臂；四次 `2c2c635` 运行早于它，不受它影响。

这就是为什么该修复的端到端验证是运行 `34582260187` —— 第一个在
`20592f2` 上的运行 —— 以及为什么不变量检查现在是分析器的一部分而非一次性检查：
违规出现在大多数运行中，却一直未被察觉。

### 1. 两个实验臂在配置上完全相同

| 实验臂 | `enableDeterministicTemporal` | `enableGraphRecall` |
|---|---|---|
| `tr-deterministic-temporal` | `true`（显式） | 未设置 → `false` |
| `tr-no-graph-recall` | 未设置 → **开启** | `false`（显式） |

`enableDeterministicTemporal` 除非显式为 `false`，否则为开启
（`natural-language-memory.ts:277`：`this.options.enableDeterministicTemporal !== false`），
而 `enableGraphRecall` 默认为 `false`。两者解析结果完全相同。

我是核查了这一点，而非假定它，且是在首先假定了相反情况之后才核查的；
`enableDeterministicTemporal` 的默认开启语义正是两个实验臂坍缩为一个配置的原因，
而实验臂名称或调用点中没有任何东西表明这一点。

### 2. 它们没有共享缓存

在 `1ce76aa` 中，`runTemporalEngineAblation` 和 `runGraphRecallAblation` 各自构建
自己的 `new Map<string, string[]>()`。缓存键是
`` `${promptBuilder.name}:${question}` `` —— 两个 TR 实验臂都使用
`buildTemporalQueryExpansionPrompt`，所以键本会*在*单个缓存内冲突，
但每个实验臂都从冷启动开始。谁也没有预热另一个。

### 3. 为何评判器不是原因

`createLlmJudge` 使用一个模块级 `judgeCache`，以完整评判提示词为键，
该提示词内嵌问题、预测与期望。同一三元组在一个进程内总是返回同一判决，
因此评分是可复现的，不可能产生这一分歧。已核查，非假定。

## 修复

`answerCache` 现在按每个消融声明一次，并传给两个实验臂，覆盖全部
五个消融外加主基准（12 个接线点，6 对）。

在构造上安全而非靠约定安全：`respondWith` 在**完整渲染后的提示词**上查找
`` cache?.get(prompt) ``（`natural-language-memory.ts:765-766`），因此：

- 提示词不同的实验臂产生不同的键，不会冲突 —— 处理组绝不会被遮蔽；
- 提示词逐字节相同的实验臂只被回答一次，这正是移除不可复现项的原因。

## 测试

`report-runner.test.ts` 中六项测试，由一个故意对重复提示词**每次都给出不同答案**的
LLM 驱动。一个确定性桩会让整个缺陷不可见，因此该测试模型必须不是确定性的 ——
这是此处的核心设计决策。

**经变异验证。** 移除缓存接线恰好失败于：

| 消融 | 实验臂共享提示词？ | 没有修复时会失败 |
|---|---|---|
| TR 引擎 | 是 → 失败 | ✅ |
| TR 窗口 | 是 → 失败 | ✅ |
| TR 覆盖 | 是 → 失败 | ✅ |
| KU 双时间 | 是 → 失败 | ✅ |
| MR 聚合 | **否** | ❌ 通过 |

MR 消融的实验臂在 `aggregationPrompt` 上不同，因此每个提示词都不同，
没有缓存条目被共享。因此它的测试断言的是它真正能够确立的较弱性质 ——
两个提示词模板都被行使到，所以对比是真的 —— 而不是我最初写的那个缓存命中主张，
那是假的。共享缓存对 MR 仍有益处，只要两个实验臂恰好发出同一提示词；
只是在那里它不是一项正确性保证，测试也如实说明。

## 范围与影响

**是测量完整性，不是准确率。** 没有任何实验臂的配置改变，因此每一个先前产物中的
每一个评分数字都未变。改变的是：对于四个实验臂共享提示词的消融，一次运行内的
实验臂比较不再静默地包含一个 LLM 不可复现项。

那 2 道题的误差在 `p5-verdict.md` 所测的约 23 道题的流动噪声底之内，没有改变任何判决。
它之所以重要，是因为 McNemar 设计假定实验臂*恰好*配对，而这是该假定第一次被
可证明地违反 —— 且有一个零成本、还能省下 LLM 花费的修复可用。
