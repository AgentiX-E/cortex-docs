# 同模型复跑三家竞品：机制已落地，四条事实先于任何分数

**结论先行。** 要在 Runner 上用与 cortex 相同的 DeepSeek 评测 Mastra / Mem0 / MemCog，缺的不是 workflow 而是三样东西：一个能把"同一个 LLM"变成可审计字段的计量代理、一个能容纳"检索即推理"系统的协议操作、以及三个各自真的能跑起来的驱动。三样都已落地并有测试；四条事实在任何分数产生之前就已经被这次适配推翻或确认。

**三家跑完之后的答复（细节在 §8–§10）。** 没有一家在相同上下文预算下赢过 cortex 自己的窗口，而最贵的两家买到的最少：MemCog 每题 **¥3.48**、其中 97% 花在建库；Mem0 每题 **¥1.37**、同一轮两题全输；Mastra 每题 **¥0.275**、把 112k 的原文整段读进去，换来 +6.7 点而 `p=0.73`。真正值得抄的不是某个机制，而是一个**形状**：MemCog 的可导航页面 + 两个工具 + 有界轮数——它只占 MemCog 自己账单的 2.8%。

## 1. 为什么"同一个 LLM"必须是一个 base URL，而不是一句承诺

一次比较里有**四个**模型位置，而 cortex 只占一个：

| 系统 | 模型在哪里被调用 | 该位置是否决定它的公开分数 |
| --- | --- | --- |
| cortex | reader（每问 1 次） | 否 —— 纯检索 |
| Mem0 | ingest 抽取（`infer=1`，每 turn 1 次） | **是** —— 94.4 的配置用它 |
| MemCog | 建库 5 步 **+** 导航 2–7 轮 | **是** —— 95.80 是整个循环 |
| Mastra | 答题 agent、Observer、Reflector | **是** —— 84.23 vs 94.87 只差 reader |

只设 `DEEPSEEK_MODEL` 的跑法，等于拿"DeepSeek 读的 cortex"去比"各家默认配置的竞品"。Mastra 的默认是 `'auto'`：有 Google key 时选 Gemini。这不是比较，是三个实验。

因此：**每个驱动的 `base_url` 都指向 `tools/competitor-sut/sut_llm_proxy.py`**，代理转发到 DeepSeek 并从响应里读 `usage`。已被测试钉死的性质（`tools/__tests__/test_sut_llm_proxy.py`，10 条）：

1. 请求体与响应体**逐字节**转发 —— 被测系统在解析它们，重新序列化就是换了一份数据；
2. token 从 `prompt_tokens`/`completion_tokens` 分项读，不用 `total_tokens` 加分项（那会重复计）；
3. `X-Sut-Label` 把账单按阶段拆开：`memcog/build` 与 `memcog/navigate` 是两行，因为"建库占九成"和"查询占九成"需要不同的修法；
4. 计数按模型分表，静默 fallback 会显示为两行而不是一个平均；
5. `stream: true` **转发**并在末帧结算 —— 见 §3，第一版拒绝它是错的；
6. 上游 4xx 原样透传并计 `failures`，不变成 200 空体。

`src/config/llm_config.py` 是四个空字符串。README 要求使用者自己取消注释示例。

**结论：任何 MemCog 复现都必然包含"复现者自己写的传输层"。** 我们这份也一样 —— `memcog_driver.py` 在任何人按名 import 之前 patch `core.llm_client.call_llm`，且补丁只含作者注释里那六行（无额外重试、不改进 prompt、不做解析）。manifest 原文写明这一点。

这不是论文的缺陷，而是"引用这个仓库的数字时，那个数字意味着什么"的一个事实。

### 2.1 而且它在 3.12 以下根本跑不起来，仓库没说

第一次真实派发死在 `manifest produced no response`。驱动 stderr 写着原因：

```
File ".../store_build/sources.py", line 75
SyntaxError: f-string expression part cannot include a backslash
```

PEP 701 在 Python **3.12** 才允许 f-string 替换字段里出现反斜杠。runner 是 3.11.18。于是模块 import 就炸，失败发生在 `main()` 之前，parent 把它报成"驱动死了"而不是"没人核对过的版本假设"——README 里没有任何最低版本说明。

两个后果，且超出这一个文件：

1. **竞品的运行时要求是它配置的一部分**。晚发现的代价是一个完整派发。`memcog_driver.py` 现在在低于 3.12 时 re-exec 进 `MEMCOG_PYTHON`，否则用一句话退出，同时点名版本、文件与 PEP；
2. 解释器**装在 job 的 3.11 旁边**而不是替换它——这次比较的其它每一步都在 3.11 上测量，换掉它就是实验里多一个变量。

## 3. Mastra 的 `agent.generate` 走流式，第一版代理拒绝它是我的 bug

第一版代理拒绝 `stream: true`，理由是"usage 只在末帧完整，逐 delta 累加会报一个没测量过的数"。理由对了一半：**不做累加**是对的，**拒绝**是错的。Mastra 每次 generate 都发 `stream: true` 与 `stream_options.include_usage`，拒绝的结果是三家系统里有一家完全跑不起来，且症状是**空答案**——一个会被读成"记忆系统坏了"的形状。

修法：逐块转发 SSE，从**带 usage 的那一帧**读取（赋值而非累加），一次会话计一次 `calls`（不是一帧一次），并记录 `stream_frames`，使得"流结束但没有 usage 帧"可见而不是静默为零。

## 4. 两个系统没有检索端点，协议因此长出一个可选操作

`MemoryProvider.answer?` —— 类型上可选、manifest 上可选、它的存在本身是一个关于架构的声明。

| 后果 | 断言位置 |
| --- | --- |
| `self` 系统**不会**再被共享 reader 读一遍 | 用一个会抛错的 reader 断言，而不是一个会记录的（同时调两条路径也能得到像样答案，只有账单会说话） |
| judge **仍然**是共享的 | 所以 accuracy 仍可比 |
| `ProviderScore.answerer` 记 `shared`/`self`/`none` | 表格对 `self` 行的 recall 列打印 `—` 而不是 `0.0%`（它没有排序列表，零是假陈述） |
| `ProviderScore.usage` 携带系统自身花费 | `null` 是"未测量"，不是"免费" |

为什么这个字段非有不可：Mastra 自己的消融是**同一记忆系统 84.23 → 94.87**，只换 reader。把 `self` 行和 `shared` 行并排打印总分会诱导读者去做那 10.64 点明令禁止的减法。

## 5. 派发之前的成本与时间算术

本地替身实测（不是语料）：120 turn（约 36k token）的一题，**9 次模型调用**（8 次观察/反思 + 1 次作答），耗时 **4 分 10 秒**。LongMemEval-S 每题约 550 turn，直接外推是每题 5–15 分钟。

| 臂 | 每问调用 | 每问 token（估） | 100 题 | 500 题 |
| --- | ---: | ---: | ---: | ---: |
| cortex（纯检索） | 1 reader + 1 judge | ~7.4k 上下文 + judge | ≈ 1.5M | ≈ 7.5M |
| Mem0 `infer=1` | ~550 抽取 + 2 | ~1.6M | ≈ 165M | ≈ 820M |
| MemCog | ~50 建库 + ~4 导航 | ~200k | ≈ 20M | ≈ 100M |
| Mastra OM | ~8 观察 + 1 作答 | ~36k | ≈ 3.6M | ≈ 18M |

按 DeepSeek 标价（¥2/M 输入 miss、¥8/M 输出）粗算，500 题列：Mem0 约 **¥1,900**、MemCog 约 **¥250**、Mastra 约 **¥60**，另加共享 reader/judge。

这张表里四个估计错了三个，而且错在两个方向，§8 是改正后的数字：MemCog 实测**每题 1,287,032 token、¥3.48**（是估计的 6.4 倍——表里猜"建库约 50 次调用"，实际是 665 次）；Mastra 实测 125,296、¥0.275（3.5 倍）；Mem0 实测 576,772、¥1.37（只有估计的三分之一，因为每题 haystack 是约 52 个 session，而不是 550 个待抽取的 turn）。按实测价，500 题列变成 MemCog 约 **¥1,740**、Mem0 约 **¥685**、Mastra 约 **¥138**。估计值留在这一节而不是被实测值替换：**一个被预注册、后来被证伪的数字，是"测量确实做了事"的唯一证据**。

**真正的约束不是钱而是墙钟时间**：500 题 × 5 分钟 = 41 小时，单 job（300 分钟上限）跑不完。所以首轮 100 题，500 题那轮需要分片。

这也是 `sut_infer` 默认仍是 `0` 的原因：`infer=0` 是**另一个系统**，manifest 会写明跑的是哪一个。

## 6. 首轮派发与它要判的问题

顺序：`sut=memcog` → `sut=mastra` → `sut=mem0&sut_infer=1`，均 `read_questions=100`，`sut_llm` 留空（继承 reader 的模型 id）。

每个数字要回答的问题都被刻意收窄。**不是**"cortex 是否比 MemCog 强"，而是：

1. MemCog 在同 100 题、同 judge、同模型下若领先 3 点以上 → 要抄的机制是**可导航结构与工具调用**，`DESIGN-MULTI-STEP-RETRIEVAL.md` 已有对应预注册；
2. Mastra 若领先 → 要抄的机制是**压缩代替检索**（阈值化的 Observer/Reflector），这是本仓库从未测过的方向，账本里最近的亲戚是 `[thing 3]`；
3. Mem0 `infer=1` 对 `infer=0` —— 抽取消融一旦这个臂存在就是免费的，而它是唯一能回答"事实抽取在这个语料上到底买到了什么"的测量。

**输掉的竞品也回答了一个问题**，这正是"跑他们的代码"而不是"读他们的表格"的意义：§2–§4 的四条事实，全部产生于任何一道题被评分之前。

## 7. 遗留风险（已知且未解）

| 风险 | 状态 |
| --- | --- |
| MemCog 建库是**逐 session** 五次 LLM 调用，500 题可能 250 万次调用 | 已按 100 题首轮；若建库主导，下一步是建库缓存（同一 haystack 在题间复用） |
| Mastra OM 的 30k 阈值决定它到底是"压缩记忆"还是"摘要器" | 可由 `MASTRA_MESSAGE_TOKENS` 覆盖，manifest 记录实际值；首轮用 Mastra 自己的默认 |
| Mastra 的 vendor harness / ingest 顺序未知，94.87 不可复现 | 只复现**机制**，不声称复现数字；报告按 `self` reader 降级，不做 A 级比较 |
| MemCog 的判分器是它自己复制的官方模板 | 不采用它的判分；只取它的 prediction，交给共享 judge |
| 流式转发没有背压控制，慢客户端会拖住代理线程 | 单线程顺序跑，无并发；若分片并发需要改成 select |

## 8. 首轮实测：同 judge、同模型、同一批题

三次派发在同一个 judge、同一个 DeepSeek、同一份抽样上产出了数字。样本都小——Mastra 30 题、Mem0 与 MemCog 各 2 题——所以下表每一行都带 `n`：30 题里差 2 题就是一枚硬币。

| 臂 | n | 准确率 | 调用/题 | prompt token/题 | ¥/题（目录价） | 它的上下文是什么 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| `mastra`（自答） | 30 | **70.0%**（21/30） | 2.0 | 125,296 | 0.275 | 自己的生成器，观察日志 + 原文 |
| `cortex-session`（共享 reader） | 30 | 63.3%（19/30） | 1 reader + 1 judge | 33,270 | 0.067 | 整 session，预算 8 turn |
| `lexical-reference`（共享） | 30 | 63.3%（19/30） | 1 + 1 | 34,974 | 0.070 | 同 session 的词法 top-k |
| `cortex/trim-2.8k`（共享） | 30 | 56.7%（17/30） | 1 + 1 | 2,799 | 0.006 | 2.8k 字符窗口 |
| `mem0` `infer=1`（共享） | 2 | 50.0%（1/2） | 51.5 | 576,772 | 1.37 | 抽取后的事实，向量 top-k |
| `memcog`（自答） | 2 | 50.0%（1/2） | 667 | 1,287,032 | 3.48 | 模型写的页面，模型再读回来 |

每一行的成本是**这条臂自己**在每题上的花费：读该臂的 `usage`，减去同一标签下这个 job 之前的基线（§8.4）。MemCog 那行是唯一必须从 job 账本里重算、而不是直接取产物的，两者差 4 倍——见 §8.3。

配对检验就在产物里，所以比较是逐题而不是两个比率相减：

```
cortex-session   -> mastra   n=30  +5/-3  delta +6.7%   p=0.7266  不显著
cortex/trim-2.8k -> mastra   n=30  +8/-4  delta +13.3%  p=0.3877  不显著
```

### 8.1 Mastra 的观察记忆在它自己的默认阈值上没有压缩

这个臂被派发来测的机制是"压缩代替检索"：Observer 把旧消息折成观察，Reflector 合并，agent 用观察日志 + 近期窗口作答。`messageTokens` 留 Mastra 自己的默认 30,000，语料约 115,000 token。

账本记录的是**真正进入模型的东西**：90 次作答产生 **180 次调用，每次作答 2 次**，而这两次并不对称：

| | 每次调用的 prompt token |
| --- | ---: |
| 小调用（180 次中的 90 次） | p25 7,765，min 5,884 |
| 作答调用（另外 90 次） | 中位 **112,144**，p75 116,635，max 118,781 |

也就是说**作答调用带的是原文，不是压缩日志**：115k 语料上中位 112k token，等于什么都没压。这个 70% 是一次**全上下文阅读**外面套了一层记忆接口，它该和 `cortex-session` 的 33k、`cortex/trim-2.8k` 的 2.8k 并排读，而不是和 cortex 的预算臂当成同一上下文预算来比。

这个读法改变了"该抄什么"。"压缩代替检索"不是那 +6.7 点的来源，**上下文体积**才是，而 cortex 已经有这个旋钮（`maxPromptCharsByRoute`）。Mastra 真正提供的信息是战利品的尺寸：3.8 倍上下文，+6.7 点，n=30 下不显著。

### 8.2 Mem0 的抽取是表里最贵的上下文，而且两题都输了

`infer=1` 在 ingest 阶段每 session 一次模型调用——两题的 haystack 就是 103 次调用——而抽取提示本身携带对话原文，所以账单是**每题 576,772 prompt token**：整个 115k 语料的 5.0 倍、`cortex-session` 33k 的 17 倍、2.8k 窗口的 206 倍。它答对 1/2。同一批两题上，cortex 每一条臂都答对 2/2。

不是样本量问题的那部分在这里：**换三种读者提示，答案不动**。同一份 `mem0` 上下文在 `con`、`dispatch`、`dispatch2` 下都是 1/2；而 `cortex-session` 是 2/2 → 1/2 → 1/2，`cortex/trim-2.8k` 稳定 2/2。当一个插入能力子句的提示对某条臂毫无作用、对另一条臂有作用时，差别在两条臂**放进 reader 的东西**里。

这个臂的 recall@k 是 0.0%，而这个数字说的是**指标**而不是 Mem0：命中判定的条件是片段文本里含有一个金标 **turn**，而抽取出来的事实不是 turn。这个指标根本看不见抽取型系统，能读的只有它的准确率列。

### 8.3 MemCog：每题 129 万 prompt token、¥3.48，其中 97% 花在"问题被提出之前"

MemCog 是唯一必须重建成本而不是直接读产物的臂：它的产物写着 `¥13.91`、每题 `2,799,803` token，而这两个数描述的是**两条臂**（§8.4）。job 账本才是第一手材料，而它切得很干净——四轮跑是顺序执行的，每次回到 `q1` 就是一轮的开始：

| job 里的第几轮 | 调用 | prompt token | ¥ | ¥/题 |
| --- | ---: | ---: | ---: | ---: |
| 检索步 | 1,312 | 2,471,285 | 6.71 | 3.36 |
| 阅读 `con` | 1,363 | 2,677,061 | 7.19 | 3.60 |
| 阅读 `dispatch` | 1,336 | 2,600,276 | 7.01 | 3.51 |
| 阅读 `dispatch2` | 1,328 | 2,547,637 | 6.90 | 3.45 |
| **job 合计** | 5,339 | 10,296,259 | 27.82 | 3.48 |

每轮 2 题，103 个 session、1,037 个 turn 的 haystack。所以**一题 = 1,287,032 prompt token、667 次调用、16 分钟**；而拆分说明钱去哪了：

| 阶段 | 调用 | prompt token | 占比 |
| --- | ---: | ---: | ---: |
| 建库 build | 5,319 | 10,005,968 | 97.2% |
| 导航 navigate | 20 | 290,291 | 2.8% |

这就是全部结论：**MemCog 花掉的钱里 97% 买的是库，2.8% 买的才是那个值得抄的推理**。分摊到 session 是每个约 24,300 prompt token，分摊到 turn 约 2,400。导航——在库写出的页面上做 2–7 轮模型调用——正是 `DESIGN-MULTI-STEP-RETRIEVAL.md` 描述的那部分，而它在两题上只花了 20 次调用，也是表里最便宜的东西。

为什么数字波动这么大：MemCog 答对 1/2，和 `mem0` 一样，而 `n=2` 无法把它和表里任何一条臂区分开。它自己那一轮里的配对是 `lexical-reference -> memcog  +0/-1  −50.0%  p=1.0000`、`cortex-session -> memcog  0/0  0.0%`——两个方向各一题，这正是 n=2 的价值。它的 `recall@k` 是 0.0%，理由和 Mem0 相同——命中要求片段含金标 **turn**，而模型生成的页面不是 turn——所以只有准确率列有内容。

不过这几条臂的配对带出一个交叉验证：自答系统根本不看 reader 提示，所以它的分数必须在 `con` / `dispatch` / `dispatch2` 上**不变**，而它确实没变——两次转换都是 `0/0 no change`，同一时期 `cortex-session` 在第二对里动了一题。也就是说，三个 reader 臂并不是一个会漏进"不读题的臂"的变量。

这两题真正确立的是价格：**是 `cortex/trim-2.8k` 2.8k 窗口（¥0.0056）的 621 倍、`cortex-session`（¥0.067）的 52 倍、Mastra（¥0.275）的 12.7 倍**——而且共享臂的 `¥/题` 只算 reader 输入，所以这几个倍数都是差距的**下界**。

### 8.4 派发过程暴露的四个缺陷，和它们的共同点

四个都不是关于竞品的，都是关于"跑出了一句它没测过的话"，或者"为一个没人会读的产物付了钱"。

**崩掉的 harness 是一个绿色步骤 + 一个空文件。** 九个测量步骤写成 `node ... | tee 产物`，而管道报告的是最后一条命令的退出码。于是 run 45011910491 **成功**结束，阅读表 0 字节，成本报告写着"阅读阶段没写 json"。harness 其实在 import 时就死了，死在第一行输出之前。现在九个步骤都加了 `set -o pipefail`；此后同类失败会显示为红叉——第二个缺陷正是这样被发现的。

**一个没有任何步骤创建过的目录。** `MASTRA_STORE` 在三个阅读步骤里指向 `<workspace>/.cache/mastra/store.db`，而在两个真正 ingest 的步骤里都没设。于是 ingest 用了驱动的 `/tmp` 默认值，没有任何步骤创建 `.cache/mastra/`，libsql 对阅读阶段回答 `ConnectionFailed("...: 14")`——SQLITE_CANTOPEN，读起来像权限或损坏，两者都不是。现在模型/代理/两个存储的变量统一放在 job 的 `env`，驱动自己创建被交付路径的父目录，而 live 往返测试故意传一个父目录不存在的路径。

第二个更小但同类：Mem0 的 DeepSeek 工厂无论模型是否可达都会构造 `OpenAI` 客户端，而检索阶段不携带 `DEEPSEEK_API_KEY`，驱动把 `""` 传了进去，于是以 `Missing credentials` 死在 import。那条路径上没有任何东西读这个凭据——代理会用自己的上游 key 覆盖 `Authorization`。现在 loopback base URL 会拿到显式的 `proxied` 占位符，manifest 记录用了哪个占位符，而任何非本地 URL 仍然什么都不给。

**一个属于整个 job 而不是某条臂的成本列。** 计量代理每个 job 只起一次，跨检索步和三个阅读臂一直活着（阅读本身也要它计量），所以它的 `/stats` 计数是 **job 级**的，而 `DRIVERS` 里每个驱动都原样上报这个计数——驱动这样上报是对的，把它算到某一行的头上是错的。MemCog 是第一个撞上的臂，而且算术是精确闭合的，不是凭感觉：

| 量 | 值 | 出处 |
| --- | --- | --- |
| 那行记录下来的 | `5,148,346` prompt token | 它的 `competitor-read.json` 里的 `usage` |
| 检索臂 + `con` 臂 | `5,148,346` prompt token | 账本里的 `2,471,285 + 2,677,061` |
| 一条臂两题的真实花费 | `2,574,173` prompt token | 账本按每次回到 `q1` 切分 |
| 那行印出的每题成本 | `¥13.91` | `usage ÷ 2 题` |
| 一题的真实成本 | `¥3.48` | `¥27.82 ÷ 8（四轮 × 两题）` |

另外两行是**碰巧**干净的，而这个"碰巧"值得写下来：Mastra 的 ingest 只写存储（它自己的进度行写着 `0 call(s)`），Mem0 的检索步则死在第二节那个凭据缺陷上，所以 `con` 臂开始时这两个标签下都还没有花费。MemCog 的检索步要用模型建库，于是它是三家里唯一在阅读臂上报时、标签下已经有别的臂花过钱的一家。

为此改了两处，下一轮不需要再做考古：适配器在驱动可能花钱之前先读一次 `/stats?prefix=<name>` 作为基线，从每次读数里减掉，读不到就判这条臂失败（没有基线的 job 级计数报的是 job 的价格，不是臂的价格），若驱动上报的调用数比基线还少也判失败（说明它数的不是代理的数，这条臂无法归属）；报表的金额列从 `own ¥` 改成 `own ¥/q`，因为它紧挨着 `own tok/q`，而在一个"每题"表头下印一个总数，在 n=30 时就是 30 倍的错。`tools/competitor-sut.mjs usage-scope` 是这三种情况的自检，进度行也从 `cumulative` 改成 `since launch`——同一个缺陷的上一层。

**一个没人会读、却已经建好了的库。** 工作流的顺序是：先对被测系统跑一次"只检索"的阶段，再跑三条阅读臂；而**每一个阶段都会重新拉起驱动、重新 ingest**——协议是 `mode: isolated`，每题之前 `reset`，后一个阶段没有任何状态可以继承。这种重复并没有测到阅读阶段没报的东西：阅读阶段为被测系统写下的行本身就带 `recallAtK`、`recallAllAtK` 与 `mrr`，top-k 相同——`--budget-tokens` 只裁剪本仓库自己的臂。所以第一步买到的是隔壁那张表的第二份副本：run 45011905117 在这一步为两题花了 **¥6.71 与 39 分钟**，紧接着 `con` 臂把同样两个库又建了一遍。

现在只要阅读阶段会测同一个系统，这一步就跳过，并且用单独一行说出来，而不是把一个被点名要求的系统的行悄悄省掉。仍有两种情况会跑它：纯检索派发（`read_questions=0`），以及显式臂列表里写的是**别的**系统——那是阅读阶段不会带上它这一行的唯一情形。第二处跳过的价值比看上去大：按 Mem0 实测每次抽取 4.7 秒，三十题要跑约两小时的 ingest，而那份重复会把派发顶到 job 300 分钟的上限上，一点余量都不剩。

这一步内部还有第二处跳过，理由不同。当它真的运行时（纯检索派发），自答系统在这上面没有任何可贡献的东西：Mastra 与 MemCog 的 `search` 按设计返回 `hits: []`，它们唯一能印出来的 recall 是 0.0%，那是**仪表**的陈述。对它们按 manifest 里的 `answers: true` 跳过；之所以按声明判而不是加一个 workflow 输入：标志位是多一个可以填错的东西，而"这个系统会不会自己作答"本来就已经被读出来用于决定能不能调 `answer`。Mem0、Letta 和 reference 驱动仍然跑这一步，因为它们有排序列表，recall 列对它们是测量。

这个改动的账目后果最好在下一张账单之前就说清楚：自答臂的**每题成本里包含一次建库**，这不是失真——那就是"孤立地回答一道题"的真实价格，也是其他所有臂被要求遵守的同一协议。它真正意味着的是 `read_prompts` 会把这个价格乘以臂数：三提示扫描等于把同样两个库建三遍，所以 MemCog 的 reader-提示比较是**每题 ¥10 量级**的实验，不是 ¥3.48 的实验。

| 系统 | 按本次实测，它到底在做什么 | 对 cortex 的判定 |
| --- | --- | --- |
| Mastra OM | 每题 2 次调用，作答那一次中位 112k token：全上下文 + 一份观察日志 | **抄预算，不抄机制。** +6.7 点是上下文体积买来的；`maxPromptCharsByRoute` 是更便宜的杠杆，该做的实验是窗口扫描，不是引入 Observer |
| Mem0 `infer=1` | 每题 51.5 次调用、577k prompt token（语料的 5 倍）把 session 变成事实，然后两题全输 | **不抄抽取。** 它是表里贵两个数量级的上下文；`infer=0` 消融是那个便宜的对照，用来说清"抽取本身没用"还是"只是太贵" |
| MemCog | 每题 129 万 prompt token、667 次调用、¥3.48，其中 97.2% 建库、2.8% 导航，两题答对 1 | **抄接口，不抄建库。** 可导航页面 + 两个工具 + 有界轮数是比看上去更小的改动（`DESIGN-MULTI-STEP-RETRIEVAL.md`），而那正是这张账单里的 2.8%：两题一共 20 次调用、290k prompt token。建库才是让这条臂成为 `cortex-session` 52 倍的原因，而它买到的答案在 n=2 上与一枚硬币无法区分 |

三家都没有证明的一件事：**在相同上下文预算下**有机制能赢过 cortex 自己的窗口。那正是下一轮该跑的实验——把所有臂的 reader 输入固定在 33k token，看观察、事实、导航能不能在**同一个信封内**赢过逐字 session。

## 10. 五个必答问题的当前答案

1. **三家能不能在同一模型上被测？** 能，三家都已在同 judge、同 DeepSeek 上产出过数字。MemCog 的约束不是钱（100 题约 ¥348）而是墙钟：每题 16.9 分钟，单 job 300 分钟上限约合 17 题，所以 100 题要按 `--offset` 切 6 片。
2. **"同一个 LLM"是否可审计？** 是。`X-Sut-Label` 把每次调用记到系统与阶段上（MemCog 的标签还带题号 `memcog/build/q1`），账本随产物上传，每个数字都能回溯到调用行；金额由账本按带日期的价目表换算，只有一处换算代码。
3. **准确率差距是多少？** n=30 上 Mastra +6.7pp（McNemar p=0.7266，不显著）。n=2 上 Mem0 是 1/2，而同一轮三条 cortex 臂都是 2/2；MemCog 也是 1/2，而那一轮 `cortex-session` 同样是 1/2——两题分不出任何东西，能分出的只有价格。
4. **成本差距是多少？** prompt token/题：2,799（2.8k 窗口，¥0.0056）／33,270（整 session，¥0.067）／125,296（Mastra，¥0.275）／576,772（Mem0，¥1.37）／1,287,032（MemCog，¥3.48）。MemCog 那 129 万里 97.2% 是建库，只有 2.8% 是导航。
5. **该抄什么？** 预算先于机制：先把窗口给够（Mastra 的 +6.7 点来自 3.8 倍上下文，不来自 Observer）；不抄 Mem0 的抽取，也不抄 MemCog 的建库；要抄的是 MemCog 的**接口形状**——可导航页面 + 两个工具 + 有界轮数，也就是它自己账单里的那 2.8%。

## 11. 下一次派发：在跑之前先把判据写下来

cortex 自己的臂没法搬到 Mastra 的信封里——每题 112k token 是阅读表里任何一行的 3.8 倍——但 **Mastra 的可以搬到 cortex 的信封里**。`messageTokens` 是决定 Observer 多久压缩一次的阈值，在厂商默认的 30,000 上它基本没起作用：作答调用读到的是语料**加上一份长到和语料一样大的观察日志**。把这个数调低就是一个数字的事，而它把这张表现阶段做不出的比较变成可以做的：**同一个机制，放进 33k 的 prompt 预算内**，在同一批题、同一个 judge、同一个模型、同一份抽样上对 `cortex-session`。

所以派发参数是：`sut=mastra`、`sut_mastra_message_tokens=3000`、`questions=30`、`read_questions=30`、`read_prompts=con`、`offset=0`。对照组不是新的一条臂：它就是 §8 表里已有的那条 30 题 Mastra 行——同一份抽样、同一批题，所以配对是题内的，唯一移动的东西是那个阈值。

| prompt token/题 | 准确率对 `cortex-session` 的 63.3% | 能确立什么 |
| ---: | --- | --- |
| ≤ 40,000 | ≥ 63.3% | 压缩能在信封内成立、并在信封内赢过逐字 session——**去建那个压缩器**，机制是可迁移的 |
| ≤ 40,000 | < 63.3% | 一旦必须塞进信封，压缩就输——只抄预算旋钮，Observer 不进 cortex |
| > 40,000 | 任意 | 这个阈值控制不了上下文，因为观察日志压过了它——Mastra 的贵是结构性的，不是阈值问题 |

第三行没有退路：如果阈值降到十分之一、prompt 仍然高于 40k，那这个系统的价格没有任何可调之处，§9 里"抄预算不抄机制"的判断就从推论升级为实测。

这个实验无法了结的两件事，现在就写下来，免得被读进结果里。它是 n=30，所以差两题仍然是一枚硬币——63.3% 对 63.3% 的结局叫"分不出来"，不叫"相等"。而且它只动了厂商自己配置里的一个数字：它回答的是"这个机制能不能活在 33k 的信封里"，不是"Observer 是否优于一个好窗口"——后者只有 cortex 自己实现一版才能回答。

## 12. 归一化列确立了什么，以及对"显而易见的读法"的三处纠正

`tools/sut-cost-report.mjs` 现在印出这张表一直缺的那一列：**每百万"系统导致的读取 token"能换多少分**，并用 `--reference <臂>` 把每一行都对某一条点名的臂定价。分母是**系统总量**——reader 读到的，加上系统为产出它而花的——这个选择本身就是全部论证，因为对抽取型系统来说这两半差三个数量级。

30 题那一轮：

| 臂 | prompt tok/q（系统） | 准确率 | 分 / 百万 token | 与 `cortex-session` 打平需要 |
| --- | ---: | ---: | ---: | --- |
| `cortex/trim-2.8k` | 2,799 | 56.7% | 202.57 | 5.3% |
| `cortex-session` | 33,270 | 63.3% | 19.03 | —（参照） |
| `lexical-reference` | 34,974 | 63.3% | 18.10 | 66.5% |
| `mastra` | 125,296 | 70.0% | 5.59 | **不可能（238%）** |

同一条命令在两题那两轮上读出 `mem0 不可能（1745%）`、`memcog 不可能（3892%）`。这两行各只有一枚硬币的准确率，而结论不在乎：**需要超过 100% 准确率才能打平的行，无论它的准确率最终是多少都打不平**，所以这个排序与样本量无关。这是比 n=30 的配对检验更强的陈述，也是"抄不抄"这个决定该站的地方。

### 12.1 分母本身就是那个发现

若只用 reader 的上下文作分母——也就是厂商以"每题上下文"发布的那个数——同一条命令会把 **Mem0 排到第一：1,392.76 分/百万 token**，是它实际名次的 39 倍，因为它每题只交给 reader 359 个 token，却花掉 603,503 个 token 把 session 变成事实。一个只报小分母、不报大分母的工具不只是美化抽取，它**把排序倒过来**。所以这一列的名字是"系统导致被读取的量"，而不是"reader 看到的量"。

### 12.2 我们比的这条臂不是发货臂

`cortex-session` 是基线。发货配置——`cortex-memory`、六路由 room map、`relevanceTopK=256`——在 500 题 × 四轮上是 **91.25%、每题 7,448 token**（`landscape.json`，run 44017278305），supersede 那一臂是 91.35% / 9,241。所以上一轮结论的诚实写法是：**没有任何一家被测竞品能打平 cortex 的基线臂**；而发货臂既比那条基线高 28 点，又比它便宜 3.6 倍。也就是说，"该不该抄某个机制"这个问题，我一直是对着错误的对照组问的；修法不是再派发一次，而是**把产品臂接进同一个 harness**。

### 12.3 Synap 不是"在上面且够不着"

95.6%（478/500）、**每题 7.4K token**，作答模型 Gemini 3.8 Flash，judge 是 gpt-4o。对 cortex 的 91.25% @ 7.4K 是 +4.3 点；而本仓库实测：换 judge 会把它自己 467 条已记录答案移动 **−3.21 点，13 降 0 升**。一个落在 3.2 点仪表带内、且两边 reader 不同类的 4.3 点差距，**不可判定**——两个方向都不可判定。

"闭源"也不等于够不着。它的仓库公开了每一条逐题记录（检索到的记忆、写下的答案、judge 判定）、作答 prompt、两份 run manifest 和 `bench/` harness。**答案级重判**是现成且便宜的：不做 ingest、不要 reader、不派发，用我们的 judge 把它的 500 条重判一遍。这比 race 更强，因为它把 reader 从比较里整个移除了。闭源挡住的是"跑它的系统"，挡不住"读它的机制"和"重判它的判定"。

## 13. 两个实验回来了，落的是预注册的第三行

### 13.1 Mem0 在 n=30：抽取账单第一次量在三十题上，而不是两题

§12 里那行 n=2 的 Mem0 是一枚硬币。同一个臂，与其它行同一批题：

| 臂                  |  n | 准确率 | ctx tok/题 | own prompt tok/题 | own ¥/题 | 调用/题 |
| ------------------- | -: | -----: | ---------: | ----------------: | -------: | ------: |
| `lexical-reference` | 30 |  70.0% |     34,974 |                 0 |    0.070 |       0 |
| `cortex-session`    | 30 |  60.0% |     33,270 |                 0 |    0.067 |       0 |
| `cortex/trim-2.8k`  | 30 |  53.3% |      2,799 |                 0 |    0.006 |       0 |
| **mem0 `infer=1`**  | 30 |  63.3% |    **407** |       **544,477** |    1.295 |    47.9 |

两个加粗的数字是同一个机制的正面与背面。Mem0 交给 reader **每题 407 token**，为产出它们花掉**自己的 544,477**：30 题共 1,437 次模型调用，每存一个 session 一次，每次读入约 11.4k prompt token、写出约 537 completion token。这 1,437 次调用**全部**是 `add`；Mem0 的 `search` 一次模型都不调。所以这个臂贵，不是因为它在做难事，是因为**它付钱让模型写记忆，一个 session 付一次，不管将来有没有问题需要那个 session**。

归一化后是**每百万 token 1.16 分**，对 `trim-2.8k` 的 190.43 和 `cortex-session` 的 18.03。要靠准确率打平 `cortex-session`，它需要 983% 的准确率。配对检验对 `cortex-session` 是 `+2/−1, p = 1.0000`——不可区分，而这正是 30 题样本能给出的最强结论。

### 13.2 Mastra 在 `messageTokens=3000`：§11 的第三行

§11 那张预注册表有三行，这次落的是没有兜底的那一行：

| 每题 prompt token | 结果                                   | 它会确立什么           |
| ----------------: | -------------------------------------- | ---------------------- |
|         ≤ 40,000 | —                                      | 没有发生               |
|         ≤ 40,000 | —                                      | 没有发生               |
|      **> 40,000** | **120,221（原 125,296）**              | **阈值不控制上下文**   |

阈值降十倍，prompt 只动 **4.05%**，准确率动 **−3.3 点**（70.0% → 66.7%，21/30 → 20/30）。§9 给 Mastra 的判词——"抄预算，不抄机制"——**撤回**：没有预算可抄，因为阈值控制的那个数不是大的那个。

### 13.3 机制不是不可调，是瞄着另一种协议

调用日志说清了 120,221 token 去了哪里，而答案不是"观察日志长到了语料大小"（那是 §9 在没有逐调用记录时的推断）：

- **30 题共 60 次调用**：恰好每题两次，交替"大—小"；
- 30 次大调用**全部 ≥ 100k**（最大 118,781，该组最小 116,189），30 次小调用**全部 < 10k**（中位数约 2.1k）；
- 两者都标 `mastra/answer`，因为驱动从模块变量取 label，而 Observer 恰好是在作答相位里触发的。`mastra/observe` 出现**零**次：`ingest` 期间没有任何观察，`settled()` 立刻返回，因为没有待处理项。

所以大调用是作答 agent 读整份 transcript（约 480 轮、约 117k token），小调用是 Observer 压缩未观察窗口（≤ `messageTokens`，这才是阈值真正限住的量）。大调用在前。**一个在它所本可以缩短的答案之后才发生的观察，缩短不了那个答案**；而在 `mode: isolated` 下每题都是新 thread、一次 ingest、一次作答，压缩出来的形态没有任何东西会去读。降低阈值不是"没能帮上"，是在这个协议下**不可能帮上**。

这把"抄不抄"这个问题重新定义了，而不是关掉它。Mastra 的观察式记忆是为"会继续的对话"造的——观察的产物由下一轮读。LongMemEval 的 isolated 协议是相反的形状。机制本身可能值得有；这个臂证明不了它，任何阈值也证明不了。

**能确认这个读法的预测**（跑之前登记）：`mode: shared` 下——三十题共用一个 thread——同一个臂的第 2..30 题应当明显比第 1 题便宜，因为每题的观察会成为下一题的输入。若没有发生，说明 Observer 压根没运行，66.7% 就是一个披着观察式记忆 manifest 的全量上下文臂。

这个结论有两件事它**不**说。它不说 Mastra 的 94.87% 是错的——它的 harness、prompt 与 ingest 顺序仍未公开。它也不说 cortex 该跳过压缩：它说的是 cortex 需要的压缩必须**发生在答案之前、作用在答案将要读的东西上**——那正是 `cortex/trim-*` 在字符层已经做的事，也是语义压缩器在 token 层必须做的事。

### 13.4 本轮在 cortex 里发现的两处缺陷，其中一处会随版本发出去

既然写下了"产品臂才是对照"（§12.2），就该查一下产品臂从发布入口到底够不够得着。够不着。

`registered-arm.ts` 存在的理由就是"产品可能为一个配置公布数字、却发另一个配置"。它用给 `assembleMemory` 加默认值的方式修好了 `promptContract` 和 `ask` 两个字段。第三个字段 `relevanceTopK = 256` 拿到了常量，**没有读者**：`assembleMemory` 把 `options.index` 原样转发，于是 `SearchIndex` 解析到自己模块的默认值 **64**。也就是说，`docs/USER-MANUAL.md` §6.6 告诉用户写的那句"给我那个被测量过的臂"的裸调用 `assembleMemory({ llm, storage })`，**只评分了 91.25% 那次读数所覆盖候选的四分之一**，第六十位之后的 turn 拿到未评分的下限。

更糟的是它**不可观测**。`SearchCensus` 报了 turns、terms、vectors、embed 调用和查询数，没有一项随宽度变化。64 的产物和 256 的产物在读者能看到的每一个字段上一模一样。所以修法是两行加一个字段，而且必须一起：

- `assembleMemory` 在调用方未命名时从 `REGISTERED_ARM.relevanceTopK` 解析 `index.k`，遵循两个指令杠杆已有的规则：一个拒绝命名"臂"的组装根，并不因此就没有臂；
- `SearchCensus.k` 报这次检索**实际解析**的宽度，于是"这题排了 256 个 turn"和"这题排了 64 个"不再打印出同一份产物；
- `registered-arm-width.test.ts` 走用户的三步（assemble、`remember`、`askStored`），从**跑过的那次检索**的 census 上读宽度——因为一个只测 option 的测试，会和一个永远没走到索引的调用方意见一致。

它改变了上面所有数字里的什么：**什么都没有**——那些行是 `cortex-session`（一个不建索引的裸 provider）与竞品臂。它改变的是产品发货时对着的那个数：`reader` profile 文档里的 91.25% @ 7,448 token 是在 256 下测的，而在这个提交之前，装配出来的是 64。
