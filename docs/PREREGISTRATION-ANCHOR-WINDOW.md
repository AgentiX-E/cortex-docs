# 预登记：`anchor-window` 证据单位（第 132 轮）

> 本文件写在**派发之前**。它登记的是一个**已实现、已登记、从未有读数**的机制。它的价值不在于新颖，
> 而在于它是本仓 **⑯ 缺口的一个具体实例**：能力在代码里、在配置面上、在转发表里都有，唯独没有一次
> 花钱的读数。派发成本按上一轮实测登记为 **≈14.1 CNY / 127 分钟**。

---

## 1. 为什么是这一项，而不是又一个候选

`anchor-window` 在 `packages/cortex-memory/src/prompt.ts` 里是 `RelevanceUnits` 的第四个取值，
`selectByAnchorWindow` 有实现、有 12 条单元测试、有半径 0 与 `turn` 单位的等同性断言；
`packages/cortex-memory/bench/run-ablation.ts` 的 `RELEVANCE_UNIT_FORWARDING` 是
`Record<RelevanceUnits, …>`，所以它编译期就必须被转发；`bench-memory-arm.ts` 接受这个值；
workflow 的 `cortex_memory_relevance_units` 输入把它一路送到 `CORTEX_MEMORY_RELEVANCE_UNITS`。

**全链路通，一次读数也没有。** `04-execution-tracking-report.md` 最后一次提到它是 **§17,924**，
而该文件已写到 **§27,000 行之后**——也就是说它被登记完之后，在随后约 9,000 行的迭代记录里
**一次都没有再出现**。它不是被否证的，是被遗忘的。

这正是 `semanticCarry` 教训的另一面：那一次五环节里缺了「臂能请求」这一环，机制永远不执行；
这一次五环节齐全，缺的是**第六件东西**——一次派发。二者在产物上的表现都一样：产品侧没有数字，
所以默认值不会动，用户拿不到。

## 2. 机制的一句话形状

房间买的是**锚点 + 它自己会话内的 ±2 邻域**，作为**一个不可分割的块**；锚点按相关性降序走，
放不下就**先缩窗口再缩锚点**（radius → radius−1 → … → 仅锚点），最后一级等于 `turn` 单位自己的
决定，所以紧预算下它永远不会比 `turn` 少交付。

来源是 Chain on Demand 的 `cod/expand.py`（`seeds K=60`、`pool K=200`、`expand window ±2`）。
本仓不照抄它的锚点预算，而是用**字符房间**替换——因为 `turn` 单位已经给每一条轮次打了分，
在这个排序上无界地走锚点，等于同一个选择加上邻域。

### 2.1 它要修的是哪一种失败

`§13.283` 第一次量了这个臂的金标轮召回：**6,520 / 7,516 = 86.75%**，`MR` 更高，**97.11%**。
残留不是排序失败——**53 个缺失的 `MR` 轮次分布在 34 道题上，`goldRanks` 全部是 `-1`**，
即信号从未给它们打过分。它们是**已经得分的锚点的邻居**，落在字符切割的另一侧。
**前缀在任何宽度下都买不到它们**，因为加宽前缀买的是更多**被排过序**的轮次。

这是 `anchor-window` 与 `retrieval-anchored` 的分野，也是 `§13.257` 的代价所在：
后者把邻域**放回池子**，让它们带着锚点分数的衰减比例参与排名，于是顶掉了本来排在它们前面的命中，
`MR` 丢了 8 题。前者把邻域**和锚点一起买断**，邻域不参与排名，因此**没有「挤掉谁」这回事**。

## 3. 这次派发能测什么、不能测什么

### 3.1 先写下地板的约束

`§11.13` 用本仓自己的数据量出**跨派发分辨力地板 = 0.70 点**（未受处理的参考侧 27 小时里
882 → 896 格）。这次是单变量派发、跨派发比较，所以：

> **任何小于 0.70 点的总体效应在这次设计里不可判。** 判据因此不写在总体准确率上，
> 而写在**能力级**（`MR` 121 题，1 题 ≈ 0.83 个能力点 ≈ 0.2 个总体点），并要求**题级符号检验**同向。

### 3.2 上限是多少

`MR` 现有错误 **19.75 题**（101.25/121）。缺金轮的 34 道题里，一部分已经答对，所以
**可救的上限低于 34**。若机制如解释那样工作，转化率的合理预期是 20–40%，
即 **+7 至 +14 题**。这比 0.70 点地板高一档，所以这次设计**有能力**判读一个真实效应。

### 3.3 不能测什么

- **不能测半径**。±2 是参考实现的冻结值，也是产品默认值，workflow 已在 24/25 个输入上限，
  所以半径不是变量。这次派发测的是「**这个单位**有没有用」，不是「哪个半径最好」。
- **不能测与 `retrieval-anchored` 的交互**。那是第二个变量。
- **不能测非 `MR` 能力**。它们是多会话路由之外的路线，机制按构造不触及，所以它们是**内部对照**。

## 4. 判据（读数之前写死）

| # | 判据 | 阈值 | 失败的含义 |
| --- | --- | --- | --- |
| **A1** | 机制确实执行 | 500 题里 `promptDigest` 与基线**不同的题 ≥ 90**（`MR` 121 题的下限读数） | 机制存在而交付未动 → **运行作废**，不是「无效」 |
| **A2** | 越界检查（前置条件） | `IE`/`KU`/`TR`/`ABS` 的 `promptDigest` **逐题不变** | 跨出了多会话路由 → **运行作废**，先修实现 |
| **A3** | `MR` 准确率 | 均值 **≥ 104.25**（即 +3 题），且题级 `up − down ≥ +3` | 效应在地板下或方向相反 → 不切换 |
| **A4** | `MR` 交付轮数 | 中位数**上升**且 `evidenceChars` 上升（房间买的是深度） | 若交付轮数不变而提示变了 → 机制改的是排序不是邻域，**解释错** |
| **A5** | 成本 | prompt token / 题 ≤ **7,822**（基线 × 1.05） | 用 5% 以上的 token 买准确率 → 按成本轴重新登记，不得单独通过 |

A1/A2 是**前置条件**，不是结果判据：机制的设计已经保证它们在成立的那一侧（`selectByAnchorWindow`
只被 `relevanceUnits === 'anchor-window'` 分支调用，而该分支只在 `buildSessionPrompt` 的 plan 上
出现）。它们失败只有一种解释——实现与声明不符。

## 5. 两个可否证的预测（写在派发之前）

> **P1**：若 `MR` 出现退步，退步的题**必属于缺金轮的 34 题之外**。机制只增加证据，
> 一个证据更全的窗口让读者答错，只能是它被无关邻居带偏——那说明邻域是噪声源，
> 于是「邻域恢复」这条线要改的是**邻域的选取条件**，不是半径。
> 落在 34 题之内 → 机制的解释成立但方向错了（更多证据让读者更犹豫），这条线应当整体放弃。

> **P2**：若机制有效，增益应集中在**缺金轮的 34 题**上。若增益均匀分布在其余 87 题，
> 那么有效但不是因为「补齐邻域」——这会把解释从「召回残留」改成「交付顺序」，
> 而后者是另一个机制（顺序轴已由 §13.279 测过并否证）。

两条都不影响 A3 的判据，但它们决定下一轮沿着哪条线走。
