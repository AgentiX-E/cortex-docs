# 供应商限流审计：那次 429 不是配额耗尽

**状态**：根因已定位，三个复合缺陷，**没有一个与计费有关**。
**范围**：LongMemEval 基准评测使用的智谱 `embedding-3` 路径。
**证据**：供应商自身的 API 参考文档 + 仓库的重试代码。

---

## 0. 结论先行

那次 429 被记录为「配额耗尽，需要充值或切离线 fallback」。**这个判断是错的**，
而操作者看到的账户余额正好与「它错了」一致。

智谱在**模型并发过高**时返回 429，错误码 **`1305`**，中文消息是
`模型当前访问量过大，请您稍后再试`。**一个余额充足、资源包健康的账户在高负载下返回的正是这个。**
所以问题不是「配额去哪了」，而是**「一个有余额的账户为什么仍然 429，以及重试逻辑为什么吸收不掉它」**。

三个缺陷回答了这个问题，而且它们**互相叠加**：

| # | 缺陷 | 后果 |
| --- | --- | --- |
| 1 | 重试预算（31 秒睡眠）**短于服务商的 60 秒窗口** | 每次重试都落在拒绝它的同一个窗口内 |
| 2 | **`Retry-After` 从未被读取**，服务端自己的节流提示被丢弃 | 客户端不知道要等多久，只能猜 |
| 3 | 64 条一批之间**没有客户端节流** | 以最大速率背靠背发请求，直到被限流 |

三个都不是计费问题，修三个都不需要充值。此前记录的「切离线 fallback」补救方案
**会把这三个缺陷全部掩盖掉**。

---

## 1. 供应商的限制到底是什么

来自 `embedding-3` 的 API 参考：

| 限制项 | 值 | 项目当前设置 | 判定 |
| --- | --- | --- | --- |
| 单请求条目数 | **最多 64** | `EMBED_BATCH = 64` | 正好在上限 |
| 单请求 token 数 | 最多 3072 | **未强制** | **未检查** |
| 输出维度 | 256 / 512 / 1024 / 2048（默认 2048） | `1024` | 合法 |
| 429 错误码 | `1305`，「访问量过大」 | 当作通用错误重试 | 误读 |

批次正好取满 64 本身不是缺陷 —— 64 是文档上限，取满可以最小化请求数，
对并发上限而言方向是对的。但**一批 64 条长对话可以同时超过 3072 token 的单请求上限**，
而适配器里没有任何东西检查这件事。这是一个独立的、潜伏的 400 错误，
在长对话的 haystack 上会触发。

---

## 2. 缺陷一：重试预算短于限流窗口

退避策略是 `基础延迟 × 2^(重试次数-1)`，基础 1 秒、最多重试 5 次：

| 重试 | 尝试前的睡眠 |
| --- | --- |
| 1 | 1 秒 |
| 2 | 2 秒 |
| 3 | 4 秒 |
| 4 | 8 秒 |
| 5 | 16 秒 |

**总预算 31 秒。** 服务商的限流窗口是**按分钟计的**（供应商文档未公开精确窗口长度，
但「稍后再试」的节流语义与 1305 的错误码都指向一个分钟级的滑动窗口）。

也就是说：**31 秒的预算无法跨过它要等的那个窗口。**
每一次重试都落在拒绝它的同一窗口内，五次重试之后请求仍然失败，
而日志会显示「重试了 5 次」，读起来像「网络不稳」，而不是「预算比窗口短」。

---

## 3. 缺陷二：`Retry-After` 被丢弃

服务端在限流响应里会给出 `Retry-After`（或等价的提示），**客户端从未读取它**，
而是用一个与窗口长度无关的固定指数退避来猜。

这一条和缺陷一是同一个错误的两个面：**客户端在猜一个服务端已经告诉过它的数。**
只修预算而不读 `Retry-After`，等于把一个可测量的量继续当作未知量处理。

---

## 4. 缺陷三：没有客户端节流

批次循环是背靠背的：一个 64 条的请求返回后立刻发下一个，速率就是网络往返决定的速率。
在一个**按请求率限流**的服务商面前，这意味着：

- 客户端不知道自己距离上限还有多远；
- 唯一的反馈通道是**被拒绝**；
- 而按缺陷一，被拒绝之后的重试预算又不够跨过窗口。

也就是说，限流是被**发现**的，不是被**遵守**的。对于已知有上限的服务，
正确形态是让请求速率持续低于上限，而不是靠拒绝来学习上限在哪。

---

## 5. 为什么这个结论此前被记错

此前记录为「配额耗尽」。它错在一个**很常见的方法学错误**上：

> **一个被两种成因共用的状态码，不构成对任一成因的证据。**

429 只说明「请求过多」。「过多」是余额耗尽引起的，还是请求率引起的，
**由厂商错误码与消息决定，而不是由 HTTP 状态码决定**。
把一个 429 直接读成「配额用完了」，跳过的正是那个唯一能分辨两者的字段。

这个错误的代价不只是诊断错了，而是**补救方向反了且要花钱**：
为「资源耗尽」设计的补救（充值、更大的资源包、切到离线 fallback）
在成因是「请求率」时，与「什么都没修」无法分辨 —— 而其中三项要付钱。

**方法学结论（已经写进项目纪律）**：

> 一个被两种成因共用的状态码，不构成对任一成因的证据。
> 需要先读出区分两者的那个字段，再决定补救方向。

---

## 6. 诊断产物本身的一个缺口

本项目的诊断产物里记录了 `embeddingMaxAbsDiff`（嵌入向量的最大绝对差），
但**不记录 provider、model、dimension**，也不记录一个向量来自缓存还是实时 API 调用。

后果是：**两次运行的嵌入来源无法被审计。** 如果一次运行走的是智谱、
另一次走了离线 fallback，产物里没有任何字段能说出这件事，
而 `embeddingMaxAbsDiff` 的差异会被归因到别处。

这与「一个数字只活在控制台里」是同一类缺陷的另一面：
**一个决定了读数可解释性的字段，没有被写进产物。**

---

## 7. 修复需求（按依赖排序）

1. **读取 `Retry-After`**，在嵌入与 LLM 两个适配器里，存在时优先于计算出的退避。
2. **让重试预算跨过一个分钟级的窗口** —— 要么提高上限，要么把上限从
   「尝试次数」改为「墙钟时间预算」，这样窗口形状的限流才可能被跨过。
3. **给批次循环加节流**，让请求速率持续低于服务商上限，而不是靠被拒绝来发现上限。
4. **同时限制单请求的 token 数**，不只是条目数，这样一批长对话不会超过 3072 token 上限。
5. **在诊断产物里记录嵌入来源**（provider、model、维度、以及向量来自缓存还是实时 API），
   这样两次运行可以在**不假设**的前提下比较。

---

## 8. 未主张的事项

- **未主张已知服务商的精确限流窗口长度。** 供应商文档没有公开它；
  「分钟级」是从 1305 的节流语义与「稍后再试」的措辞推断的，本文如实标注为推断。
- **未主张离线 fallback 无价值。** 它在无网络或额度确实耗尽时是有效路径；
  本文的主张是**它不解决这次的问题**，且会掩盖三个真缺陷。
- **未主张 3072 token 的越界已经发生过。** 它是**未被检查**，
  本文没有证据表明某次运行确实越界 —— 这与「已经越界」是两个不同的陈述。
- **未运行修复后的对照实验。** 本文是根因分析，五个修复项**尚未实现**；
  实现后需要一次 A/B（节流前 vs 节流后）来确认 429 率下降，该实验**未运行**。
