# 供应商限流审计：那次 429 不是配额耗尽

**状态**：根因已定位，三个复合缺陷，**没有一个与计费有关**；**五项修复已实现并验证**（见 §9）。
**范围**：LongMemEval 基准评测使用的智谱 `embedding-3` 路径。
**证据**：供应商自身的 API 参考文档 + 仓库的重试代码 + 实现后的单元测试与端到端运行。

---

## 0. 结论先行

那次 429 被记录为「配额耗尽，需要充值或切离线 fallback」。**这个判断是错的**，
而操作者看到的账户余额正好与「它错了」一致。

智谱在**模型并发过高**时返回 429，错误码 **`1305`**，中文消息是
`模型当前访问量过大，请您稍后再试`。**一个余额充足、资源包健康的账户在高负载下返回的正是这个。**
所以问题不是「配额去哪了」，而是**「一个有余额的账户为什么仍然 429，以及重试逻辑为什么吸收不掉它」**。

三个缺陷回答了这个问题，而且它们**互相叠加**：

| # | 缺陷 | 后果 |
| --- | --- | --- |
| 1 | 重试预算（31 秒睡眠）**短于服务商的 60 秒窗口** | 每次重试都落在拒绝它的同一个窗口内 |
| 2 | **`Retry-After` 从未被读取**，服务端自己的节流提示被丢弃 | 客户端不知道要等多久，只能猜 |
| 3 | 64 条一批之间**没有客户端节流** | 以最大速率背靠背发请求，直到被限流 |

三个都不是计费问题，修三个都不需要充值。此前记录的「切离线 fallback」补救方案
**会把这三个缺陷全部掩盖掉**。

---

## 1. 供应商的限制到底是什么

来自 `embedding-3` 的 API 参考：

| 限制项 | 值 | 项目当前设置 | 判定 |
| --- | --- | --- | --- |
| 单请求条目数 | **最多 64** | `EMBED_BATCH = 64` | 正好在上限 |
| 单请求 token 数 | 最多 3072 | **未强制** | **未检查** |
| 输出维度 | 256 / 512 / 1024 / 2048（默认 2048） | `1024` | 合法 |
| 429 错误码 | `1305`，「访问量过大」 | 当作通用错误重试 | 误读 |

批次正好取满 64 本身不是缺陷 —— 64 是文档上限，取满可以最小化请求数，
对并发上限而言方向是对的。但**一批 64 条长对话可以同时超过 3072 token 的单请求上限**，
而适配器里没有任何东西检查这件事。这是一个独立的、潜伏的 400 错误，
在长对话的 haystack 上会触发。

---

## 2. 缺陷一：重试预算短于限流窗口

退避策略是 `基础延迟 × 2^(重试次数-1)`，基础 1 秒、最多重试 5 次：

| 重试 | 尝试前的睡眠 |
| --- | --- |
| 1 | 1 秒 |
| 2 | 2 秒 |
| 3 | 4 秒 |
| 4 | 8 秒 |
| 5 | 16 秒 |

**总预算 31 秒。** 服务商的限流窗口是**按分钟计的**（供应商文档未公开精确窗口长度，
但「稍后再试」的节流语义与 1305 的错误码都指向一个分钟级的滑动窗口）。

也就是说：**31 秒的预算无法跨过它要等的那个窗口。**
每一次重试都落在拒绝它的同一窗口内，五次重试之后请求仍然失败，
而日志会显示「重试了 5 次」，读起来像「网络不稳」，而不是「预算比窗口短」。

---

## 3. 缺陷二：`Retry-After` 被丢弃

服务端在限流响应里会给出 `Retry-After`（或等价的提示），**客户端从未读取它**，
而是用一个与窗口长度无关的固定指数退避来猜。

这一条和缺陷一是同一个错误的两个面：**客户端在猜一个服务端已经告诉过它的数。**
只修预算而不读 `Retry-After`，等于把一个可测量的量继续当作未知量处理。

---

## 4. 缺陷三：没有客户端节流

批次循环是背靠背的：一个 64 条的请求返回后立刻发下一个，速率就是网络往返决定的速率。
在一个**按请求率限流**的服务商面前，这意味着：

- 客户端不知道自己距离上限还有多远；
- 唯一的反馈通道是**被拒绝**；
- 而按缺陷一，被拒绝之后的重试预算又不够跨过窗口。

也就是说，限流是被**发现**的，不是被**遵守**的。对于已知有上限的服务，
正确形态是让请求速率持续低于上限，而不是靠拒绝来学习上限在哪。

---

## 5. 为什么这个结论此前被记错

此前记录为「配额耗尽」。它错在一个**很常见的方法学错误**上：

> **一个被两种成因共用的状态码，不构成对任一成因的证据。**

429 只说明「请求过多」。「过多」是余额耗尽引起的，还是请求率引起的，
**由厂商错误码与消息决定，而不是由 HTTP 状态码决定**。
把一个 429 直接读成「配额用完了」，跳过的正是那个唯一能分辨两者的字段。

这个错误的代价不只是诊断错了，而是**补救方向反了且要花钱**：
为「资源耗尽」设计的补救（充值、更大的资源包、切到离线 fallback）
在成因是「请求率」时，与「什么都没修」无法分辨 —— 而其中三项要付钱。

**方法学结论（已经写进项目纪律）**：

> 一个被两种成因共用的状态码，不构成对任一成因的证据。
> 需要先读出区分两者的那个字段，再决定补救方向。

---

## 6. 诊断产物本身的一个缺口

本项目的诊断产物里记录了 `embeddingMaxAbsDiff`（嵌入向量的最大绝对差），
但**不记录 provider、model、dimension**，也不记录一个向量来自缓存还是实时 API 调用。

后果是：**两次运行的嵌入来源无法被审计。** 如果一次运行走的是智谱、
另一次走了离线 fallback，产物里没有任何字段能说出这件事，
而 `embeddingMaxAbsDiff` 的差异会被归因到别处。

这与「一个数字只活在控制台里」是同一类缺陷的另一面：
**一个决定了读数可解释性的字段，没有被写进产物。**

---

## 7. 修复需求（按依赖排序）

1. **读取 `Retry-After`**，在嵌入与 LLM 两个适配器里，存在时优先于计算出的退避。
2. **让重试预算跨过一个分钟级的窗口** —— 要么提高上限，要么把上限从
   「尝试次数」改为「墙钟时间预算」，这样窗口形状的限流才可能被跨过。
3. **给批次循环加节流**，让请求速率持续低于服务商上限，而不是靠被拒绝来发现上限。
4. **同时限制单请求的 token 数**，不只是条目数，这样一批长对话不会超过 3072 token 上限。
5. **在诊断产物里记录嵌入来源**（provider、model、维度、以及向量来自缓存还是实时 API），
   这样两次运行可以在**不假设**的前提下比较。

## 8. 未主张的事项

- **未主张已知服务商的精确限流窗口长度。** 供应商文档没有公开它；
  「分钟级」是从 1305 的节流语义与「稍后再试」的措辞推断的，本文如实标注为推断。
- **未主张离线 fallback 无价值。** 它在无网络或额度确实耗尽时是有效路径；
  本文的主张是**它不解决这次的问题**，且会掩盖三个真缺陷。
- **未主张 3072 token 的越界已经发生过。** 它是**未被检查**，
  本文没有证据表明某次运行确实越界 —— 这与「已经越界」是两个不同的陈述。

## 9. 修复实现与验证

§7 的五项已全部实现。每一行给出承载它的代码，以及**这次修复能从真实运行路径到达**的证据
（而不只是在单元测试里成立）。

| # | 修复需求 | 实现位置 | 验证 |
| - | -------- | -------- | ---- |
| 1 | 读取 `Retry-After` | `packages/cortex-llm/src/retry.ts` 的 `parseRetryAfterMs`，优先于计算出的退避 | 5 条解析测试（delta-seconds、HTTP-date、小数、畸形值拒绝）+ 6 条 `retryableFetch` 测试 |
| 2 | 跨过分钟级窗口 | `DEFAULT_RETRY_BUDGET_MS = 120_000`，上限是**墙钟预算**而非尝试次数 | `DEFAULT_RETRY_BUDGET_MS > 60_000` 测试 + fake-timer 测试断言 10 次重试的配置在第 5 次请求时被预算截断 |
| 3 | 批次循环节流 | `EMBEDDING_BATCH_INTERVAL_MS` → `setEmbeddingBatchIntervalMs`，`embedManyCached` 在无 per-call 值时读取 | 两条 64 条目批次的间隔测试；该值被打印进运行日志并写入产物 |
| 4 | 限制单请求 token | `packages/cortex-eval/src/retrieval.ts` 的 `EMBED_MAX_TOKENS = 3072` 与 `shapeBatches` | token 越界拆分测试、超长单条测试、以及一条小文本测试证明该上限**没有退化成「一文本一请求」** |
| 5 | 记录嵌入来源 | `createEmbeddingWithProvenanceFromEnv`、`EmbeddingSourceStats`，以及每个 JSON 产物的 `embedding` 块与每个 Markdown 报告的首行 | 9 条来源测试、8 条缓存计数测试，以及一次端到端运行（15 个产物全部带 provenance 块） |

**为什么 §4 的节流需要一个进程级设置而不是一个参数。**
真正执行嵌入的那些检索函数（`retrieveTopKByQueries`、`buildTurnIndex`、
`retrieveByQueries` 等八个）都不接受 options 对象，所以 per-call 的 `batchIntervalMs`
**从基准入口无法到达** —— 而基准恰恰是唯一需要遵守配额的那个调用方。
为设一个数字而把 options 参数穿透八层，会让每一个对该数字没有意见的调用方都被迫携带它。
`setEmbeddingBatchIntervalMs` 只在 `embedManyCached` 自身没有该选项时被读取，
因此 per-call 契约仍然可测，不需要全局重置。

**为什么来源审计需要一个计数器而不是缓存快照。**
审计读者必须区分「完全实时嵌入」的运行与「从持久化缓存恢复」的运行，
而这两者产出**逐字节相同**的报告。快照的大小回答不了这个问题：
它说的是存在多少向量，而不是某次调用的输入里有多少已经存在。
所以计数在缓存查找与批次派发真正发生的地方累加 —— 这也是两者唯一能够
在代码漂移时与缓存不一致的方式。

**新增的三处缺陷注入验证。** `tools/inject-embedding-provenance.py`（9 个变异）、
`tools/inject-embedding-source-stats.py`（8 个）、`tools/inject-retrieval-shaping.py`（9 个）
全部被现有测试抓住，且每个变异后文件按 md5 逐字节还原。
其中**两个变异在首轮存活**，各自暴露了一个真实测试缺口并据此补测：
`Number.isInteger` 单独使用时放行负维度（`-5` 会走到远程路径），
以及两个缓存计数器没有任何测试能把它与常量区分开。

**一处如实记录的残留缺口。** `retrieval.ts` 第 631–632 行未覆盖。
它们守卫循环内的 `indexOf(hit) < 0`，而该循环的 hits 来自同一个 session 键控的 map，
所以对调用方能构造的任何输入都不可达。这是防御性守卫而非行为：
没有测试能到达它，除非捏造一个该函数接收不到的状态，而那样的测试只是在断言虚构。
记录在此，是为了让覆盖率读数呈现为**已测量**而非**已达标**。

**仍未运行的事项。** §8 的那条 A/B（节流前 vs 节流后，对比 429 率与总耗时）
**仍未运行到结论**。上面所有证据都来自单元测试、变异注入与一次本地端到端运行；
它们能证明修复**从真实路径可达**，不能证明**在真实配额下的 429 率下降**。

| 臂 | 输入 | 其余参数 |

**两次派发都失败，而第二次的原因是本轮改动自己引入的缺陷 —— 如实记录。**

| 次 | commit | 到达的步骤 | 结果 |
| -- | ------ | ---------- | ---- |
| 1（两臂） | `6863fa2f` | 5. Install dependencies | 失败：`ERR_PNPM_OUTDATED_LOCKFILE` |
| 2–4（两臂，含重试） | `42232bfe` | 7. Verify library | 失败：`eslint: not found` |

第一次的原因如上，已在 `42232bfe` 修复。**第二次的原因不是此前记录的那一个**，正确叙述是：

锁文件修复**生效了** —— `Install dependencies` 转为绿灯，失败点后移一步到 `Verify library`
（即 `pnpm check`）。`pnpm check` 随后以 `sh: 1: eslint: not found` 退出。
根因是 `42232bfe` 把 **`@xenova/transformers` 写进了根 `devDependencies`**：
它硬依赖 `sharp@0.32.6`，而 `sharp` 的 postinstall 要下载 libvips。
`pnpm install` 是**原子**的 —— 任何一个原生模块的 postinstall 失败都会以 exit 1 终止，
而终止后 workspace 的 `.bin` 链接根本不会建立，于是四个包**同时**失去 `eslint`。
一个只通过 `await import()` 到达的依赖，被写成了整个 workspace 必须解析的强制依赖。

修法分两部分，以**对照实验**而非「看起来合理」的形式验证：

| 臂 | 配置 | `sharp` 脚本 | `pnpm install` |
| -- | ---- | ------------ | -------------- |
| A（修复） | `optionalDependencies` + `pnpm.onlyBuiltDependencies` | 被忽略 | `Done in 2.1s` |
| B（对照） | 根 `devDependencies`，无白名单 | 执行 → `Failed` | exit 1 |

两臂都在**仓库 pin 的 `pnpm@9.15.0`**（即 CI 使用的版本）下运行，而非沙箱默认版本。

**此前重试循环的错误，记录在此，因为它正是本文要命名的那类错误。**
四次派发由一个把 HTTP 422 当作可重试的脚本发出。**422 不可重试**：它是确定性拒绝，
重试一个确定性拒绝等于**再发一次请求**。于是该脚本创建了 23 个 run，其中 21 个是探针。
422 从来不是障碍 —— 同一份请求体后来原样返回 204，13 个输入键逐个测试也全部被接受。
真正的失败**一直在下游一步**。

**第二次假绿灯，同样记录。** 第一次 `pnpm check` 报绿，是因为工作树里还留着先前构建的
`dist/` 与 `node_modules/`。命令是对的，**树不是干净的**。此后所有验证都在
**从远端提交物化出的全新副本**上重跑 —— 这是本文此后对自己执行的标准。

**本文不主张任何 429 率的对比结果。** 一次**根本没跑到基准的红灯**不是关于节流的负面结论；
把它读成负面结论，正是本文要纠正的那个错误本身 —— **把一个结论的规模，配给一次从未发生的测量。**

**仍未证明的部分，精确陈述。** `eslint` 失败已修复，且该主张已在 `pnpm@9.15.0` 下
对**推送树**验证通过。本地**无法**验证的是 `better-sqlite3` ——
`cortex-node` 的必需原生依赖，且是静态 import：它的 postinstall 需要 `nodejs.org` 取 headers、
需要 `github.com` 取预编译包，而本沙箱把两者都黑洞化。
GitHub runner 上两者可达，所以本地失败是**环境性**的；但这意味着**本地环境无法为安装链路端到端作证**。
