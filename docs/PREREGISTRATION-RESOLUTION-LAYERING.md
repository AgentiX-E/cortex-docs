> 写作时间：**派发之前**，`resolution.ts` 已实现并测试，`CORTEX_MEMORY_RESOLUTION` 已接线。
> 本轮**没有派发**：智谱 embedding 账户余额耗尽（`code 1113`），任何需要实时向量化的运行都会在
> 中途死掉（见 `PREREGISTRATION-TURN-WINDOW-MATCH.md` §6）。判据先写下来，等能跑时不许改。

## 1. 这条机制要修的是哪一个数

`C1` 要求每题 prompt token ≤ **6,000**，现状 **7,448**（`S16`，`44017278305`），差 **19.5%**。
两条已被量过的成本路都付了准确率：

| 路线 | 账单 | 准确率 | 出处 |
| --- | ---: | --- | --- |
| 房间表（48,460 / 24,000） | 9,168 → **7,448**（−18.8%） | **−1.15 点**（题级 −1，p = 1.0） | `44017278305` |
| 宽度计划 `coverage=0.9` | **5,660**（−27.1%，已低于 6,000） | **−4.00 点** | `43259830582`（200 题） |

兑换率 **−1 点 / 6.8% 账单**；`C1` 的 22.7% 直线定价 **−3.3 点**，而实测 −4.00 更贵，因为宽度计划
切掉的是**事件**。骨架不可压：产品入口组装一条提示 **27,268 字符，指令 207（0.76%）**。

所以 `C7` 不改房间、不改选择器、不改指令：它改**一条轮次变成什么文本**。长轮若与问题有词汇重叠，
保留匹配周围的窗口（上限 1.5 × 宽度 = 600）；若无重叠，压成「首句 + 含数字的句子」一行（0.6 × 宽度
= 240）；短轮原样（≤ 400）。平均长度下降，前缀搜索（未改）自然装下更多轮次。

## 2. 五条判据

对照 = 注册臂（`maxTurnChars=400`，`resolution=raw`），实验臂 = 同一宽度 + `resolution=layered`。
**同一个 job、同一份语料、同一批问题**——`§11.13` 量过跨派发地板 **0.70 点**，小于它的效应只有
同 job 配对才判得动。

| # | 判据 | 阈值 | 为什么是它 |
| --- | --- | --- | --- |
| **F1** | 机制确实执行 | ≥ **90 / 500** 道题的 `promptDigest` 变化（限定两侧 `promptVariants == 1`） | `anchor-window` 的教训：先证明机制跑了，再读分数。两侧单变体是跨运行比较 `promptDigest` 的前提（`PREREGISTRATION-ANCHOR-WINDOW.md` §7.4.1） |
| **F2** | reach | 非受帽路由（`IE` / `KU` / `ABS`）逐字节不变 | 分层挂在 `maxTurnChars` 上，`#capReaches` 是唯一决定 reach 的地方；0 变化即证明它停在原地 |
| **F3** | 密度（假证条款） | `MR` 的 `roleCensus.total` **中位数上升 ≥ 20%**，且 `promptChars` 中位数变化在 **±2%** 内 | 这是本机制唯一的「真的装下了更多事件」证据。同样的字符数、更多的轮次 = 密度；字符数一起缩 = 宽度削减，读数作废 |
| **F4** | 准确率 | **主判**：`MR` 均值 ≥ **101.25**（不退）且 `up − down ≥ −3`；**通过后**再读 `MR` ≥ **104.25** 且 `up − down ≥ +3` | 主判是「不亏」，副判是「赚」。本战役已有五次「读第二遍」机制被否证（`tally` −9.5 / `spec` −7.8 / `audit` −6.10 / `selfConsistency` 86.2 / `item-ids` −2），把「赚」写成唯一判据会让每一次负结果都变成一次无效派发 |
| **F5** | 成本 | ≤ **7,416** token/题（不升） | 这条机制的**全部理由**是成本；它若让账单上升，无论准确率如何都不采纳 |

`F3` 是 `§14.133.2` 的假证条款，写在派发之前：**`eventsFitted` 中位提升 < 20% 就关闭这一族**，
不跑全量。这条比 `F4` 更早判决，也更便宜（200 题 × 2 重复，2.85 CNY 起）。

## 4. 三个可否证的预测（写在派发之前）

> **P1：收益应集中在 `record` 占比高、且金标含数字的题上。** `F3` 通过而 `F4` 只持平，说明
> 「多装轮次」没有换成「多答对题」——那会把下一步推到**轮次粒度**（一条长轮是否该拆成多条），
> 而不是继续调形态上限。

> **P2：`TR` 的方向与 `MR` 同号或更好。** `TR` 的答案就是日期，而 `record` 保留「首句 + 含数字的
> 句子」，日期句几乎必然含数字。若 `TR` 反向，说明 `record` 的首句优先在日期题上把日期句挤掉了——
> 这是一个可修的实现缺陷（操作数优先的顺序已实现，见设计 §3.3），不是机制无效。

> **P3：`promptChars` 应几乎不变（±2%）。** 因为两条臂填同一个房间、用同一个前缀规则。若 `promptChars`
> 显著下降，说明分层实际起到了「宽度削减」的作用（例如 `excerpt` 分支几乎没有命中，全部走 `record`），
> 那么 `F4` 的读数就不能归因于密度，必须按宽度削减重新解释。

不是「分层无效」。

### 7.1 为什么 20% 在这个宽度上是不可达的，而不是差一点

分层只改写长度超过 `maxTurnChars` 的轮次。受帽路由上够到 cap 的是 **5.8%**（`MR` 348/5,983；
`TR` 134/2,642 = 5.1%）。要让同样的字符装下多 20% 的轮次，需要被压缩的部分释放约 **20% 的字符**；
5.8% 的轮次即使全部压到地板（0.6×cap）也只释放约 5–7%。实测 +6.7% 已经贴住这个上限。

### 7.2 为什么 `TR` 会反向

`excerpt` 的上限是 **1.5×cap = 600**，比它替换掉的 400 **大**。在问题词出现在多数轮次里的路由上，
"变宽"的轮次多于"变窄"的轮次：同样的字符装下更少的轮次。`TR` 正是这种路由（答案是日期，问题词
普遍出现），23 降对 5 升不是噪声，是机制在该路由上的方向。

§5 记下的"第一版把分层叠在 cap 之上是自相矛盾的"这一判断，在另一个方向上重新出现了：
1.5×cap 在多数轮次共享问题词的路由上，就是一次**宽度增加**穿着分层的标签。

### 7.3 理由也一起被否证了

本机制的全部动机是 `C1`（7,448 → 6,000 token/题）。但它的设计是"把省下的字符花掉"：房间不动，
提示长度 −0.09%。**即使 `F3` 满分，账单也不会动。** 一条以成本为理由的机制，在结构上不可能降低
它自己的成本——这一条与密度读数无关，写在派发之前就成立，只是当时没人把它算进去。
