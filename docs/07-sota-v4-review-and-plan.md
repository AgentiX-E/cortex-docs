## 0. 结论先行

1. **报告通过审核。** 核验的 12 条 A 级断言 **12 条成立**，其中 3 条是逐字级（`_sessions` 未读、嵌入缓存键含原文、判官 `source: 'reader'`）。它的核心判断——"91.05% 是测量系统的分数，不是产品的分数"——由 `CortexMemoryOptions` 的 28 个字段无一为 `Storage`、`DisclosureSession` 零非测试实例化、`Fact` 零构造器等事实共同支持，没有一条被证伪。
2. **但它的第一步错了。** 报告说 `Δ_judge` 未知、需新建脚本重判 2,000 条。仓库已有 `tools/judge-regrade.mjs` 与一份跨模型重判读数（`judge-sensitivity.json`，467 题）：**净 −15 题 / −3.2 点，且是单向严格化（artifact 独对 13、重判独对 0）**。按报告自己的判据（±2 点），**口径修正已经被触发**，报告却把它写成"未知"。
3. **四处修正，其中两处改变排期**：① `Δ_judge` 已有同族读数，跨 provider 那一步的成本从"两天"降为"半天 + 一次重判"；② 登记臂的 `index: null`，所以擦除缺口是**真实缺陷但不在 91.05% 里**，该排 P1 不是 P0；③ `unrun` 是 8 条不是 7 条；④ `relevance` 字段实名是 `relevanceSignal`。
4. **路线不变，顺序微调**：R1（产品化，约 720 行，零派发）仍然是第一位；但 I1（判官口径）之所以仍在最前，理由从"未知所以必须先测"改为"已知 −3.2 点，所以必须先决定这个数算不算数"。
5. **cortex 目前不是 SOTA。** 准确率 SOTA 是 **Maximem Synap 95.6%**（不同读者），同读者条件下可复现前沿 85.8–86.5%（cortex 91.05% 已在其上）；成本口径 SOTA 是 **Mem0 ≈6.8K token/题**，cortex 9,201。本计划瞄准的是报告定义的 **B+C 组合**：`accuracy ≥ 93% ∧ billedPromptTokensPerQuestion ≤ 6,000 ∧ 能力归属全在产品侧`。
6. **审核期间第三格跑完，它改写了 `S10` 的表述（§13）。** 三格齐备后三项配对**严格可加**：只标记 **−4.75**、只窗口 **+7.25**、捆绑 **+2.50**。上一轮写的"捆绑非劣、增益未证明"仍然字面成立，但它把两件稳定的事加在了一起——逐轮看，**标记四轮全负、窗口四轮全正**，而它们的和正正负负。这一条同时给 I6（行内 superseded 渲染，同类"插入元信息"机制）一个 −4.75 量级的先验预警，以及一个必须做的控制（交错执行，见 §13.6）。

## 1. 审核方法

三条规矩，避免"审核"退化成"重述"：

1. **只用仓库现状判定**。报告引的行号、字段、run id 一律回原文件复验；行号漂移算通过（只允许 ±10 行），内容不符算不通过。
2. **区分"断言错"与"断言不全"**。前者要撤回，后者要补，两者对计划的含义不同。
3. **禁止用报告内部的自洽当证据**。例如报告说"39 条门里 7 条 `unrun`"，这句话只有跑一遍 `acceptance-check` 才算核验过。

## 3. 四处修正

### 3.1 修正一：`Δ_judge` 不是未知，是 −3.2 点，且单向

`cortex-docs/evidence/longmemeval/judge-sensitivity.json`（`auditRun 43164165343`，源 `43140878641`）：

| 量 | 值 |
| --- | ---: |
| 重判题数 | 467（排除 30 弃权 + 3 多会话） |
| 翻转 | 2（0.43%），up 2 / down 0 |
| artifact 独对 | **13** |
| 重判独对 | **0** |
| 并列 | 2 |
| artifact 判官 | `deepseek-chat` @ temp 0（`source: reader`） |
| 重判判官 | `deepseek-v4-pro` @ temp 0（`matchesArtifact: false`） |

三点必须一起读：

1. **翻转率极低（0.43%）而分数下降 3.2 点。** 两个数字不矛盾，它们量的是两件事：翻转率量"同一判官的抖动"，净变化量"两个判官的严格度差"。13 单向对 0 反向说明这不是噪声，是**系统性的更严格**。
2. **这个方向与"同源偏袒"相反。** 同源判官会偏爱自己措辞（放松），更强判官更严格（收紧）。实测净 −3.2 意味着**严格化效应盖过了同源偏袒效应**——所以"同源偏袒带来的分数虚高"其量级**小于 3.2 点**，是一个上界，不是一个未知。
3. **它不能替代跨 provider 重判。** 两个判官同属 deepseek，厂牌这一轴没有动。报告 §6.1 的核心关切（判官与被测同源）依然成立，只是它的量级已经有一个上界。

**对计划的影响**：I1 从"探查一个未知量"改为"给一个已知量做跨厂牌确认"。它的出口条件也变了：

| 原判据（报告） | 修订后判据 |
| --- | --- |
| `Δ_judge` 落在 ±2 点内则口径洞小，否则重述历史 | 已有同族读数 −3.2 点，**口径修正已触发**；跨 provider 读数的用途是回答"其中多少是严格化、多少是同源偏袒"，而不是"要不要修正" |

### 3.2 修正二：擦除缺口不在当前分数里

`arm-config-baseline.json` 的 `index: null`。这意味着产生 91.05% 的那条臂没有打开 `index.reuse`，所以 §5.5 的缺陷（嵌入键含原文、无 delete 路径）**不是一个被测量的机制的一部分**。

它仍然是缺陷，而且按产品口径比按分数口径更严重：一个卖"你的数据可以删掉"的产品，删行而留下明文键，是这句话的一半。所以它留在计划里，但排在 **P1（产品）** 而不是 **P0（口径）**，且它的验收是**安全断言**（擦除后 `get(keyOf(text))` 为 `undefined`）而不是**分数断言**。

### 3.3 修正三：`unrun` 是 8 条

`node tools/acceptance-check.mjs` 实测：

```
39 criteria — 28 pass / 3 aim (R1, S3, C1) / 8 unrun / 0 fail
unrun: D1 S6 S7 S8 S9 S11 C3 P1
```

报告写"7 条 `unrun`"，而它自己列出的清单就是 8 个（`D1`、`S6`/`S7`/`S8`、`S9`、`S11`、`C3`、`P1`）。这是计数笔误，不影响任何结论——**但它说明"报告里的计数要复验"这条规矩是必要的**，因为这份报告的其他计数（26 行账本、44 个错、15 题上限）都被下游计划直接引用了。

顺带确认报告没提的一行：**3 条 `aim` 未达成**（`R1 -1 of ≥1`、`S3 83.1% of 85.0%`、`C1 9201 of ≤6000`）。`aim` 是非阻塞状态，但它是"产品还没到目标"的三个具体位置，应当出现在每轮汇报里。

### 3.4 修正四：字段实名

`relevance` → `relevanceSignal`（值 `retrieval-anchored` 正确）。同类：报告 §3.2 第 17 行写"`relevanceFor` 注入（`bench/run-ablation.ts:970`）"，实际注入点在 `cortex-memory/bench/run-ablation.ts`（不在 `cortex-eval`）。两处都是引用精度问题，不是判断问题。

## 6. 迭代计划 I1–I8

每个迭代：**目标 / 验收方法 / 测评集 / 成本 / 可否证条件**。一次迭代结束必须有一条可跑的出口命令，否则它不算完成。

### I1 · 判官口径跨厂牌确认（R0，约 0.5 天）

| 项 | 内容 |
| --- | --- |
| **目标** | 用**与读者不同 provider** 的判官（GLM 系）重判已归档答案，得到 `Δ_judge^{cross}`，并与已有的同族读数（−3.2 点）对照，分离"严格化"与"同源偏袒" |

## 10. 风险、停止规则与明确放弃

### 10.1 四个真实风险

| 风险 | 概率 | 缓解 |
| --- | --- | --- |
| `corpus.ts` 读放大让 `askStored()` 在 10⁵ 行不可用 | 中 | 自带 `(sessionId, ordinal)` 次级索引；用 10⁵ 行 fixture **计时**而非估算（I4 出口条件） |
| 抽取器在真实语料覆盖率 < 90% | 中高 | 离线先跑（不需要模型），不到 90% 不进基准（I8 硬门） |
| 跨厂牌判官让历史数字下移，被误读为"退步" | **高（已有 −3.2 点）** | 在 `RETRACTIONS.md` 写成"口径修正"，同时给两个口径的对照；不删旧数 |
| 双时态接线后 `assemble` 排除本该保留的事实 | 低中 | 保留 `historical` 分支（`asOf` 存在时不排除），用 L6 反转集验证 |

### 10.2 停止规则（提前写死，避免事后找理由）

1. 任何机制在**配对、四轮、端点地板之上**未达判据 → 写 `RETRACTIONS.md`，保持默认 `off`，不留在默认路径。
2. 任何迭代若无法满足"关掉时字节同一" → **不合并**，退回设计。字节同一性是 R1 唯一不可谈判的东西。
3. 任一次派发若 `arm-config` 逐字段 diff 出现**多于一个**变化字段 → 该派发只作筛选，不作读数。

### 10.3 明确放弃（写下来，才不会被下一个人重新捡起）

| 放弃 | 理由 | 何时可重议 |
| --- | --- | --- |
| 追公开榜第一 | 榜首靠更强读者；读者轴换一次 ±7–10 点，比任何机制都大 | 有人为"同读者第一"付费时 |
| 图数据库 / 多跳 | 本仓库 `MemoryGraph` 已测负（77.95→70.87，p=0.039） | 有注册的多跳臂与其判据时 |
| 写时 LLM 抽取 | `DB-Bench` 与仓库 −19.62 双向反证 | `C1` 约束解除后（抽取是成本不是准确率） |
| 第三个判官 | 同源问题未修，加第二个只加一个不确定 | `J1` 通过之后 |
| 把 `retrieval-anchored` 搬进产品 | 会把产品变成仪器副本；正确动作是给产品自己的排名一个读数 | `S9`/`S11` 读数之后，按读数决定搬**等价物** |
| 在 n=72 上声明 KU 个位数提升 | 分辨率地板 11.05 pp | KU 有 ≥200 题的第二仪器（L4/L5 接入）之后 |

### 13.2 三项配对，且严格可加

| 对比 | 变量 | 配对 delta | 不协调对 `b/c` | McNemar `p` | baseline 噪声标尺 | 差分中的差分 |
| --- | --- | ---: | --- | ---: | ---: | ---: |

**可加性是精确的**：−4.75 + 7.25 = +2.50，与实测的捆绑值逐位相同。这不是巧合，是配对均值差的线性恒等——但它有实质含义：**「捆绑 +2.50」不是一个效应，是两个反向效应之和。**

三项单独看都未达显著（`p = 1.0 / 0.281 / 0.377`），且都小于端点地板 17 题，所以按 §8 的口径，**一项都不能写成"提升"**。但方向可读，而且方向之间不矛盾：

- **窗口正向**：+7.25（扣掉未受治疗系统的重绘后 +11.00），点估计是三项里最大的。
- **标记负向**：−4.75，但 `b=9 / c=8` 近乎对称、`p = 1.0`——这更像"标记不改变正确率"，而不是"标记有害"。点估计为负是因为 9 比 8 多一题。
- **两者相加才是捆绑值**：所以"锚定窗口不比 head 切法更差"这句话是对的，但它是**两项抵消后的净值**，把 +7.25 藏在了 −4.75 后面。

### 13.3 与外部受控臂的同向印证

MemStrata 的受控臂把两件事分开量：**同预算、仅换选择方式 = 7.6 点；同选择、只加体积 = 0.2 点**（`arXiv:2610.05343`）。本仓库这一组给出同向的数：**"切在哪里"（选择）+7.25；"切了怎么标"（呈现）−4.75**。

两个来源、两套实现、两个数据集，都指向同一句判断：**在固定预算下，"选什么"值钱，"怎么标"不值钱**。这比任何单一读数都可靠，因为它是一次**跨源复现**。

### 13.4 对 I6 的修订（这是本次审核唯一被读数改写的迭代）

报告 §5.3 提出行内 superseded 渲染——给被取代的轮次尾附 `[superseded by a later statement on <date>]`。它的形态与本轮的标记格**同类**：都是往证据里插入一段读者原本没有的元信息。而标记格的点估计是 **−4.75**。

所以 I6 必须改两处：

| 项 | 原计划 | 修订后 |
| --- | --- | --- |
| **预期** | KU 四个陈旧孪生题配对 ≥3 题修复 | 不变，但**增加一条前置预警**：任何"往证据里插入元信息"的机制，在本臂上的先验点估计是 −4.75（同类形态），所以 I6 的收益必须**超过**这个先验才算机制有效，而不只是"超过 0" |
| **前置实验** | 无 | **零派发，已完成**（见 §13.6）：标记格的 −4.75 是**四轮全负且单调加深**（−1 / −4 / −6 / −8），不是抖动。所以预警成立且要加强：I6 的收益必须超过 −4.75 这个已有量级的呈现代价 |

### 13.6 前置检查的结果：四轮全负，且单调加深

三份证据文件里有四轮逐题的布尔掩码，逐轮算 delta 即可，零成本：

| 对比 | r0 | r1 | r2 | r3 | 均值 | 极差 | 四轮符号 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| **只标记**（none → ellipsis） | −1 | −4 | −6 | −8 | −4.75 | 7 | **四轮全负** |
| **只窗口**（head → match） | +7 | +9 | +5 | +8 | +7.25 | 4 | **四轮全正** |
| 捆绑（两者同时） | +6 | +5 | −1 | 0 | +2.50 | 7 | 正正负负 |

三件事从这个表里出来，每一件都改变了上一轮的表述：

1. **分离之后，两个分量都比它们的和更稳健。** 捆绑的四轮在正负之间摇摆（极差 7、符号两正两负），而两个分量各自**四轮同号**。原因不神秘：捆绑是两个反向效应之差，差的方差是两份方差之和——报告 §6.4 用同一份 artifact 记过这件事（`2/9 p=0.0654` vs `16/5 p=0.0039`）。**一个看起来读不出东西的对比，可能只是因为它把两件稳定的事相加了。**
2. **−4.75 不是抖动。** 四轮全负（−1 到 −8），随机抖动出现四轮同号的概率是 1/8。所以"标记不改变正确率"这个解释要撤回，改成"标记有可复现的负向关联，量级 1–8 题"。
3. **但单调性要单独说明，不能算进结论。** 四轮是顺序执行的，−1 → −4 → −6 → −8 的单调加深也可能是顺序效应（API 负载、缓存状态、速率变化）。区分它需要**交错执行**（ABAB 而非 AABB），这是一个具体的、下一次派发就能带上的控制，零额外成本。在它做之前，−4.75 应读作"可复现的负向"，而"越到后面越差"应读作"待归属"。

### 13.7 这条读数对产品默认值提出的问题

产品规则是：`match` 强制 `ellipsis`——一个切了却不标记的窗口，读者不知道被切过。这条规则的理由是**读者知情权**，它是对的。

但读数是：带标记比不带标记**低**（四轮全负）。于是这里有一个必须写明而不是绕过的张力：

| 立场 | 依据 | 代价 |
| --- | --- | --- |
| 保留强制标记 | 读者知情权；不标记的窗口是"静默截断"，而仓库已经有一条 `S10` 的判据专门反对静默截断 | 四轮全负的点估计，均值 −4.75 题 |
| 允许 `match + none` | 读数支持 | 放弃知情权，且会让"标记"从机制降为可选装饰 |

**本轮不建议改这条规则。** 理由是：3.6 节的第三条发现说明这个负值的归属还没定（可能是顺序效应），在没有交错执行的对照之前改产品默认值，等于用一次未归属的读数去推翻一条有原则支撑的规则。正确的顺序是**先归属，再决定**。

这条张力本身值得留在文档里，因为它是一个"原则与读数冲突"的实例，而这类冲突通常是下一轮最容易做错的地方——两种错误方向都很有吸引力：为了分数悄悄允许静默截断，或者为了原则假装读数不存在。

### 13.5 一个工程闭环值得记下来

上轮为第三格加的 `marker` 双侧记录（`arm.marker: {control, treatment}`），在这一轮第一次救了场：没有它，`turn-window.json` 与 `turn-window-window.json` 都会写 `window: head → match`，而它们一个是捆绑、一个是纯窗口——**两份证据文件会长得一模一样**。这条字段的价值不在它被写下的那天，而在它第一次区分两个对比的那天。

## 14 I1 执行记录（第 109 轮）：判官的三处仪器缺口，与一条被证据撤回的迭代项

### 14.1 为什么 I1 不是「跑一次重判」

计划把 I1 写成「用 GLM 重判已归档答案，读 `Δ_judge^{cross}`」。真正动手时发现，这条派发在此之前**不可达**，而且是三处独立的静默缺口：

| # | 缺口 | 后果 | 修法 |
| --- | --- | --- | --- |
| 1 | `judge-audit.yml` 只导出 `DEEPSEEK_API_KEY`，且 preflight 按名字检查它 | 一个 `zhipu:` 判官会通过一项为它**不用**的凭据写的检查，然后在 ~500 题上收 401 | 新增 `tools/judge-credential.mjs`：凭据由**判官所选 provider** 决定，通过 `reader-provider.ts` 的声明表解析，不打印值只打印长度 |
| 2 | `parseJudgeResponse` 对不认识的回复返回 `false` | 判官若用别的回复格式（`**Yes**, the response matches.`），508 次判官调用全部被判为「否」，跨厂牌差距 = 整个判官信道的宽度，且读起来像「对手更严」 | `parseJudgeVerdict` 在判决旁报告「是否读懂」；`createLlmJudge` 通过 `onUnrecognised` 暴露；读数记录 `judge.parse` |
| 3 | 两读数的比较没有算术工具 | 「≤1 不可检出 / >5 须拆半」写在计划里，却要人肉比对两个 JSON | 新增 `tools/judge-cross-vendor.mjs`：三道拒绝 + 三个状态 |

第 2 条是本轮最重要的发现：**它不是判官的问题，是解析器与判官格式不匹配的问题**，而两者在读数里长得一模一样。修复只加字段、不改判决——`parseJudgeResponse` 对既有调用者返回的布尔值与改动前逐位相同，这也是历史读数仍可比的前提。

| 未读懂回复 | —（当时无此字段） | **0** | — |

### 14.7 I3① 撤回：`answer()` **不**转发 `sessions`

计划 §6 的 I3 第①项写的是「`answer()` 转发 `sessions`（或显式抛错）」。实现、测试、全绿之后撤回，原因是可测的：

| 事实 | 出处 | 后果 |
| --- | --- | --- |
| 加载器为**每个**实例都构造 `sessions`，`context = sessions.flat()` | `longmemeval-loader.ts:158` | 不存在「没有会话视图」的题目 |
| 兜底分支调用 `answer(q.question, q.context, q.sessions)` | `benchmark.ts:1031` | `IE` 与非偏好单会话题型（**467 题中的 150 题**）都会带上非空 `sessions` |
| `answerSessions` 用的是多会话聚合提示词 | `memory.ts` | 转发即把这 150 题的提示词换掉 |

### 15.2 四个状态，每条都由三条事实推出

## 16 I5 执行记录（第 111 轮）：擦除的第七个表面，与一次被读数推翻的判断

### 16.1 为什么 I5 不是「给接口加一个 `delete`」

计划把 I5 写成三件事：`EmbeddingCacheStore.delete()`、默认键改 `sha256(text)`、`forget()` 同时删行与删向量。做完之后它们是对的，但**把它们当成分开的三个改动会做错方向**，因为三者只在一个前提下成立：

| 事实 | 出处 | 后果 |
| --- | --- | --- |
| 缓存键是 `${fingerprint}\u0000${text}` | `cache/embedding-cache.ts`（本轮之前） | 键**就是**那句话：每个被嵌入过的句子都有一份明文副本，在一个披露边界不知道的表/文件里 |
| 存储接口只有 `get`/`set`/`size` | 同上 | 副本**没有任何删除路径**，不是「忘了调用」，是接口上不存在 |
| `keyOf` 是调用方覆盖的，指纹是 memo 私有的 | 同上 | 即使外部拿得到 store，也**重构不出键**；擦除必须由持有键函数的对象来做 |
| 产品侧没有任何会话配置向量存储 | `DisclosureSessionOptions`（本轮之前） | `forget()` 清空五张表、四条读路径全空，而 `get(keyOf(text))` 仍然返回那句的向量 |

所以真实的缺陷叙述不是「少了一个方法」，而是：**这个仓库一直在测量「擦除是否完整」，而它的表面枚举少了两项，且这两项在当时不可擦除。** 那一轮之前，`C7=0 / C8=0` 是真的，它量的是它枚举到的五个表面。

### 16.2 七个表面，与两种不同的泄漏形状

计划写的「5 → 7（行、键、向量）」在实现时被读数改写。七个表面**不是同一种量**：

| 表面 | `kind` | 泄漏长什么样 | 怎么读 | 擦除前 | 擦除后 |
| --- | --- | --- | --- | ---: | ---: |
| `private-facts` / `shared-facts` / `cards` / `releases` / `erasures` | `row` | 行里出现那句话 | 序列化后计次 | 1+2+1 | 0 |
| `embedding-keys` | `keys` | **键本身就是句子** | 键字符串里计次 | **0** | **0** |
| `embedding-vectors` | `vectors` | store 仍能回答「这句存过吗」 | `held([句子])` | **2** | **0** |

第二行是这次唯一的计划修正，而且它是一个**可证伪性质**的分界：键表面在擦除**前**也必须是 0，因为键已经是摘要——它不是「擦除有没有生效」的读数，而是「键的构造有没有退回去」的读数。一个「前后都是 0」的数在没有守卫时**和仪器坏掉无法区分**，所以它单独配了一条空转守卫：

> 键表面在擦除前必须有条目（`rowsBefore > 0`），否则「键里没有原文」是关于一个空链表的话。

这就是为什么普查不是「加两个数」：**加入一个恒为 0 的表面会削弱整张表**，除非它带着自己的控制器。

### 16.3 键改摘要：`erasure.ts` 反对过它，而反对的理由有一半仍然成立

`erasure.ts` 的判定 2 写着：**擦除记录不得保存摘要，因为一个可猜测句子的摘要是离线猜测的神谕。** 那条判断是对的，而它同时是「缓存键也不该摘要」的最强论据。本轮把它推翻，理由必须精确到**生命周期**，否则就是双重标准：

| | 擦除记录 | 缓存键 |
| --- | --- | --- |
| 生命周期 | 设计上**比句子长**——它是删除日志，一年后还有人读 | 与它指向的向量**同寿**；`forget()` 一次删两者 |
| 存活时有害性 | 只有神谕 | 明文键是**完整副本**，比神谕更糟 |
| 删除后 | 记录仍在（设计如此） | 两者都不在 |
| 结论 | 不得摘要 | 摘要**严格更弱**：存活期泄漏从「副本」降到「神谕」，删除后为零 |

平台论据（入口不能 `import node:crypto`）也仍然成立，只是它有一个第三解：**在包内同步实现**。`cache/sha256.ts` 是 190 行、零 import、纯函数；`sha256.test.ts` 用两组权威校验它——NIST 的五个公开向量（含一百万个 `a`，唯一能抓住多块状态链错误的那个），以及**与 `node:crypto` + `TextEncoder` 的差分测试**，语料专挑能打坏编码器的字符串（星光面、孤立高/低代理、NUL、BOM、55/56/63/64 四个填充边界）。**平台实现是裁判。**

还有一个断言是这次刻意加的：`sha256.ts` 的源码里不得出现任何 `import` 语句。它的存在理由就是「这个入口不能有 Node 内建」，未来一次「顺手改成 node:crypto」的编辑会在这里红，而不是在某个消费者的打包里、晚一个发布。

## 17 I4 执行记录（第 112 轮）：产品终于持有语料，以及被组合暴露出来的第七次

### 17.1 为什么这不是「给 `CortexMemoryOptions` 加一个 `storage` 字段」

计划写的是四件事：`corpus.ts`、`CortexMemory.remember/askStored`、`assemble.ts` 三 profile、OPFS 作为语料后端之一。四件都是对的，而**把它们读成四个独立特性会做错方向**，因为这一轮真正的对象是三条同时成立的事实：

| 事实 | 出处 | 后果 |
| --- | --- | --- |
| `answer(question, context[])` 的语料是**实参**，每次由调用方交来 | `memory.ts` | 产品不持有任何状态，一个问题结束就忘 |
| `CortexMemoryOptions` 28 个字段，没有一个是 `Storage` | `types.ts`（本轮之前） | 集成方拿到一个类，**没有已知能跑的装配**——唯一非测试构造住在 `bench/`，而 `files: ["dist"]` 不发布它 |
| `DisclosureSession` 有 store 没有 reader，`CortexMemory` 有 reader 没有 store | 两者构造签名 | 两个对象**零组合**，能力账本第 10、13、15 行因此全是 `blocked` |

所以这一轮的交付物不是「加存储」，是**把已经存在的能力接成产品**，并给每一次搬家配一条「关掉时字节同一」的断言。判据不是「有没有 storage 字段」，而是：`assembleMemory({profile:'full'})` 之后，一个客户能不能 `remember` → `askStored` → `forget`。

### 17.2 数据模型：两处对计划的修正，都是「同一事实不要写两遍」

计划 §22.38.2 给了 `StoredTurn` 的草样，这一轮**删掉了它的一个字段、发现了它不必需要的另一个**：

| 计划草样 | 实现 | 为什么 |
| --- | --- | --- |
| `hash: string // md5(text)` | **没有这个字段** | 它是**同一事实的第二份表示**：重放比较的是原文与原文，精确且无碰撞；存摘要只是多一个会和原文分叉、并且每次读都要重新校验的字段。而这个仓库唯一需要保存原文的地方就是语料本身——一个读不懂自己 transcript 的记忆不是记忆 |
| 需要一个全局 `seq` 让顺序可复现 | 行里**没有** `seq`；顺序是 `(会话到达序, ordinal)`，前者住在 `corpus.session` 索引行里 | 计划担心的是「`query` 不保证顺序」，这个担心是对的（`sql.ts` 的 `kvQuery` 没有 `ORDER BY`），但结论应该是**把顺序变成数据**，而不是在每一行上再抄一遍顺序。到达序只有一处：`corpus.session.seq` |

次级索引的形状也是被读数定下来的：`Storage.query` 的 `keyPrefix` 在三个后端上都**先物化再切片**（`selectPage`），所以「按前缀读一个会话」是一次全表扫描。`corpus.session` 因此不是普通的 `(sessionId, ordinal) → id` 表，而是一行一个会话、带 `ordinals: number[]`：`session(id)` 是一次点查加 k 次点查，k 是该会话的轮数。**这是产品侧唯一一处为了绕开端口能力而做的结构决定**，写在 `CorpusSessionRow` 的注释里。

### 17.3 这一轮真正查到的缺陷：`CortexMemory` 把调用方的 store 换成了自己的

`assemble.test.ts` 的第一版 `full` 冒烟测试里，`removed.vectors` 读 **0**——而那句话刚才确实被索引嵌入过。原因在 `CortexMemory` 的构造函数：

```ts
// 本轮之前
if (index?.embed === undefined || index.reuse === false) { this.#indexOptions = index; return; }
this.#embedStore = new MemoryEmbeddingCacheStore();      // ← 调用方传的 store 被丢掉
this.#indexOptions = { ...index, store: this.#embedStore };
```

两个方向同时错，小的那个先发生：传一个持久 store（文件、数据库）的调用方**静默地**得到一个内存 Map，他买的重启复用从未发生。大的那个是这一轮才暴露的：`assemble.ts` 的 `full` profile 造**一个** store 交给两边——索引和披露边界——**因为擦除必须能到达索引写过的条目**；而 store 被换掉之后，边界的擦除器指向一个永远没人写的 Map。

于是上一轮 I5 修好的东西，在组合处被抵消了：行全删、读路径全关、`removed` 逐项计数、`vectors: 0`。**I5 的普查看不见它**，因为普查直接构造 `SearchIndex({ embed, store })`，从不经过产品的构造器——**仪器量的是机制，而缺陷在接线**。修法是一行：`index.store ?? new MemoryEmbeddingCacheStore()`，外加一条断言把这个约定钉住（索引的 memo 与本装配的 memo 必须组合出同一个键；`SearchIndex` 若哪天命名了自己的 space，这条会红）。

这条发现的形状值得单独说：**前一轮的验收通过，并不等于这一轮的组合成立**。`removed.vectors` 是唯一能看见它的读数，而它只有在端到端路径上才有值。

## 18 I6 执行记录（第 113 轮）：把标记搬到读者遇见它的地方，以及一次只有组合才看得见的落空

### 18.1 为什么这不是「再加一个 `conflicts`」

计划里 I6 的目标写得很干净：`SupersededRendering = 'off' | 'mark' | 'collapse'`，默认 `off`，只改被替换那一轮的渲染，不动判定。**执行时最容易走错的方向是把它实现成 `conflicts` 的第二个开关**——同一批语句、同一个侧块、换一种排版。那样做会得到一份漂亮的实现和一次毫无信息量的派发，因为 `conflicts` 侧块已经被价过：审核期间到达的第三格读数（§13）把「只标记」定在 **−4.75**，四轮全负、单调加深（−1 / −4 / −6 / −8）。

读那份读数的解释写在 `conflict.ts` 自己的注释里，而且它是**位置**的解释，不是措辞的解释：侧块插在证据**之后**，读者读到它时答案已经成形；而 §13.6 里被价过的第三句（"若问的是以前的状态，较早的语句就是答案"）恰好证明了这一点——一句话把读者推向较早的值，代价是三个本该答对的问题。所以 I6 真正要改的不是「说什么」，是**在哪里说**：

| | `conflicts`（侧块） | `supersededRendering: 'mark'`（行内） |
| --- | --- | --- |
| 位置 | 证据与问题之间，独立一段 | **那一轮自己的渲染里**，语句之后 |
| 内容 | 两条语句 + 日期 + 一句条件句 | 一句括号从句，**不点名任何值** |
| 读者要做的事 | 回头重做一次比较 | 在读到该语句时就知道它已被替换 |
| 已登记读数 | −4.75（四轮全负） | **未派发**（本轮 0 派发 0 CNY） |

「不点名任何值」是关键的一条：一旦标记写出「后来是 1300」，它就变成了侧块的分布式版本，继承侧块的读数而不是检验自己的假设。

### 18.2 本轮唯一的真缺陷：`askStored` 走的正是被 `conflicts` 排除的那条路由

第一版实现把 `conflicts` 的触及范围原样抄了过来——四条平路由，排除 abstention 与 multi-session。理由在当时看起来成立：「一个比对照多触及一条路由的实验臂，在一个以单变量为全部价值的运行里是两个变量」。

然后是组合把它打翻了。`assembleMemory` 给客户的**唯一**提问方法 `askStored` 走 `answerSessions`，也就是 **multi-session**。一个在 multi-session 上被排除的标记，在产品里就是「包里有这个机制，组合根永远看不见它」。

这正是用户第 ⑯ 条要求的那类失败，而且它有一个很恶劣的性质：**每一份单元测试都绿**。`superseded-inline.test.ts` 的四路由断言会通过，覆盖率会是 100%，账本会把 `#5` 从 `gap` 翻成 `product`——而客户拿不到。抓到它的是 `assemble.test.ts` 里那条走 `remember → askStored` 的断言，并且在变异测试里确认过：把 multi-session 的接线撤掉，`assemble.test.ts` 与 `superseded-inline.test.ts` 同时红 4 条。

顺带说明 `conflicts` 当初排除 multi-session 的理由**为什么不迁移**：那条理由是「把会话压平成一块会毁掉这个 builder 唯一的意义」。标记不是一段，它附在**块内的某一轮**后面，边界一个都没动；它也不点名值，所以不构成「邀请作答」（abstention 的排除理由）。abstention 因此仍然排除。

### 18.3 判定不重复：标记读的是 `conflict.ts` 的选择

`supersededTurns` 不重新做语句选择。它调 `conflictStatements`，拿它返回的**证据顺序**列表，比较各条的值签名，把除最后一条之外签名不同的那些交给渲染。最后一条是「当前值」，理由不是约定而是构造：块按证据顺序打印，而排序阶段只在块被计算**之前**置换，所以没有路由能把一个乱序列表交给它。

这样做的收益是**两个人口不能分叉**：如果标记自己选一遍，侧块会打印一对、标记标另一对，而同时开着两个机制的一次运行会让读者看到一组没有标记的语句。代价也立刻出现在机械读数上——`conflictStatements`、`valueSignature`、`ConflictOptions` 三个导出**在这一轮离开了孤儿账本**，因为它们从「只有自己和测试在用的导言」变成了「被 `superseded.ts` 调用的产品入口」。导出普查因此从 1208 涨到 1215，有调用者的从 719 涨到 726，而孤儿总数 **489 一动没动**（三进三出）。

### 18.4 标记计入证据预算，而侧块不计：这是个取舍，不是疏忽

`insertRelatedStatements` 在 `fitToBudget` **之后**跑，所以侧块的约 1.2k 字符落在房间之外，带着它的 prompt 可以超过 `maxPromptChars`。对一个独立的段落这是可接受的；对一个**住在证据内部**的标记则不可接受——把标记从长度算术里藏起来，会让一次运行报告一个自己装不进去的房间，而房间正是成本读数的分母。

所以标记被计入。代价必须写在明处，而不是留给审阅时被发现：

- **交付集合不变时，差值恰好等于标记长度 × 被标轮数。** 这是第 ② 条验收的算术形式，测试按字节断言（删掉标记后与对照逐字节相同，长度差恰好 `SUPERSEDED_MARKER.length`）。
- **交付集合可能变。** 一个离预算只差一个标记的 prompt，开着标记会少交付一轮。这条被**刻意构造**成一条测试（用 `maxEvidenceChars` 把房间卡在三与二之间），而不是留到派发时才发现。

第三条相关的取舍是 `collapse`：它把那一轮换成「标签 + 有问题的那一句」，所以它**只有在该轮比那一句更长时才省字符**；一轮本身就是一句话时，它多花一个标签的长度。测试把两个方向都断言了（短轮 +17 字符、长轮显著变短），因为一个只会省字符的臂不是机制，是一个假设。
