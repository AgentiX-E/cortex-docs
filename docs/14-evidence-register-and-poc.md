# 证据登记与 POC 实验

> 面向 AgentiX-E/cortex。内部设计文档。
> 本文的作用只有一个：**文档里每一个量化结论，都能查到它是怎么来的，以及它有多强。**
> 凡是没有落在下表里的数字，视为未取证，不得进入白皮书或路线图。

---

## 0. 证据分级

| 级别 | 含义 | 可否单独支撑设计决策 |
| --- | --- | --- |
| **E1 实测** | 本项目 POC 或基准运行产出，命令可复跑 | 可以 |
| **E2 论文** | 同行评审或公开预印本，方法可查 | 可以（外部有效性需注明） |
| **E3 官方文档** | 引擎/运行时作者的一手文档 | 可以（用于能力与限制） |
| **E4 厂商自述** | 项目 README、模型卡、博客 | 只能用于"它声称什么"，不能用于"它有多好" |
| **E5 二手综述** | 第三方横评、汇编 | 仅作线索，必须回溯到 E1–E4 |

`[POC-n]` = `poc/p0n-*`；`[实测]` = `docs/07` 记录的基准运行；其余按下表出处。

## 2. 四个 POC

### 2.1 `p01-browser-storage` — OPFS 是否真的持久

**方法**：持久化 profile 启动两次。第一次写 10,000 行（480 字符 payload，带 tag 索引，单事务）→
`wal_checkpoint(TRUNCATE)` → 全表回读并算 FNV-1a 摘要 → 关闭浏览器进程。第二次**新进程**读同库、
再算摘要。摘要与行数同时相同才算持久。

**结果**：摘要 `128079214` 两次一致，行数 10,000 两次一致；写入 56,850 行/秒；checkpoint 1 ms；
点读 0.047 ms；tag 查询 3.2 ms；10k 全表回读 60 ms；profile 10.9 MiB；向量扫描见 §1 第 3 条。

**为什么这个 POC 不可替代**：文档能说"支持 OPFS"，但只有进程死在中间才能证明"数据真的在盘上"。
**它证明不了**：Safari（VFS 同类风险）、多标签页并发写、配额耗尽时的行为。

### 2.2 `p02-vector-scan` — 精确扫描到底多贵

**方法**：确定性 PRNG 生成单位向量；f64/f32/int8+scale 三种存储；20k/60k × 384/1024；
每格 40 次查询取 p50/p95；两次预热丢弃；top-k 用固定缓冲插入。

**结果**：见 §1 第 5 条。**方法上的两个教训**写在脚本 docstring 里：簿记伪装成算法（第 6 条）、
以及 dtype 被误读成性能变量。

**它证明不了**：wasm SIMD 下的 int8；多线程；真实 embedding 的相似度分布（本 POC 用随机向量，
所以召回质量无法评估，只能评估成本）。

### 2.3 `p03-federation` — 边界能不能被钉住

**方法**：一个 `FederatedStorage`（表前缀决定 store）+ 两个**真实** `Storage` 实现（tag/ttl/前缀查询/
分页/可回滚事务）。九条断言覆盖：路由、行级隔离、`origin` 标注、删除作用域、ttl 独立、
跨库事务拒绝、未知 scope 拒绝、单库事务回滚。

**结果**：9/9 PASS。

**方法上的自我纠错**：首版有一条 `async () => true` 的断言（不可能失败），已删除；
首版把带前缀的表名直接传给子库，导致 `queryAcross` 查不到东西，修正为"前缀是路由标记、不是命名空间"。

**它证明不了**：速度；真实跨库一致性（那正是被拒绝的能力）。

### 2.4 `p04-triage-rules` — 规则层是否守得住，以及它守多少

**方法**：
1. 从 `[实测]` 的基准产物里提取 6,000 条真实用户语句（LongMemEval-S），启发式抽出 **1,138 条候选事实**；
2. 分层抽样 60 条（48 随机 + 12 含工作线索）；
3. **先**按公开政策（私有：健康/金钱/家庭/职业状态/第三方/凭据；共享：组织对象）人工标注，
   **再**写规则，避免循环；
4. 指标：false-share（私有→共享）、false-private、coverage、三次一致率、10 轮稳定性。

**结果**：见 §1 第 8–10 条；per-rule 分解见 `poc/results/p04-triage-rules.md`。

**它证明不了**：LLM 提议层（需 provider）、真实用户在多卡片队列里的行为、非英语语料。

**已知偏差**：标注者一人、n 小、语料是"助手对话里的用户独白"（比真实口述更完整、更少俚语），
所以 24.2% 的上界既反映样本量也反映语料风格。

## 3. 尚未取证的部分（必须写明，否则就是过度承诺）

| 缺口 | 为什么重要 | 关掉它需要什么 |
| --- | --- | --- |
| **Safari 上的 OPFS-AHP** | PGlite 文档明确说同类 VFS 在 Safari 撞 252 句柄上限；若我们也撞，则 iOS 用户只能用 IDB 降级 | 一次 Safari 探针：安装 SAH pool、写 1 万行、读回；失败则记录实际句柄上限 |
| **wasm SIMD 下的 int8** | 目前的"int8 只省内存"结论只对纯 JS 成立 | 一个 wasm 内核（或 sqlite-vec/duckdb 的内建算子）跑同一批向量 |
| **LLM 提议层的稳定性** | CIMemories 的 25% 波动是外部结论；我们自己的提议器没测 | 同一输入 ×10 次，测 scope 建议的一致率；需 provider |
| **端到端 false-share** | 规则层只管 27%，其余靠人；人会不会点"接受"是行为问题 | 可用性实验（n≥20），测"100 张卡片里的误接受率" |
| **本地小模型的质量** | 0.5B–1B 在 48k 字符证据上的表现未知 | 需在浏览器里跑同一批 LongMemEval-S 题并与云端读数比对 |
| **多标签页并发写** | 两个标签同时写同一 OPFS 库的行为未测 | 双页并发写 + 崩溃恢复实验 |

## 4. 复跑与审阅

```bash
cd poc && npm install
npm run p01 && npm run p02 && npm run p03 && npm run p04
```

- 每个脚本把结果同时写 `results/*.json`（原始数）与 `results/*.md`（文档引用的表）；
- 每个脚本的 docstring 说明"能证明什么 / 不能证明什么 / 方法上曾错在哪"；
- `p01` 的 `POC_ROWS` 环境变量可改规模；`CHROMIUM_PATH` 可指向其他 Chromium。

**审阅清单（任何引用 POC 数字的段落都应满足）**：

1. 数字能在 `results/*.json` 里找到同名键；
2. 表里带 p50/p95 或上界，而不是只有均值；
3. 标注了运行环境（Node 版本 / 浏览器 / 单线程）；
4. 若结论跨运行时，两个运行时的数字都给出（如 §1 第 4 条）；
5. 负结果与"未测"被明确写出，不被措辞掩盖。
