**本期最重要的三个读数，都不是"分数"**：

1. **共享侧几乎是空的**：真实运行展示过的 59,675 条轮次里只有 **0.52%** 可共享，**63.6%** 的问题
   一条都没有。于是"共享知识靠过滤得到"这条叙事被实测推翻，共享库必须由**卡片**产生 —— 这是
   一轮**架构级**的修正，来自一个此前没人问过的问题（`[POC-7]`）。
2. **CI 是测量装置的一部分，而不是便利**：仓库设为 public 之后，macOS 与 Linux 两条链**一次跑通**，
   Safari 与 Hub 语料两个"本机测不了"的缺口同时关闭；而在它之前，两次失败都不是能力问题
   （作业根本没启动）。
3. **端侧的性能不是"引擎快慢"，是提交次数**：同一批 2,000 行，逐条写 **178–211 行/秒**、单事务
   **11,442–12,763 行/秒**（**54–72×**，三次运行）。这条读数把"批量写必须走事务"从建议变成契约，也解释了为什么原型
   （单事务写 10,000 行）与产品（每笔一次提交）看上去差两个数量级 —— **它们测的不是同一件事**。

## 2. 已关闭的假设

五轮实验逐一关闭，且**每一轮都关掉的是整条路径而不是单个参数**：

| # | 假设 | 怎么测的 | 读数 | 判定 |
|---|---|---|---|---|
| 1 | 问题与证据的词不匹配 → 加查询扩展 | 每题生成 3 条扩展查询，单变量 | 121 题产出、347 短语、0 拒答；MR 84.75 vs 84.25；**修 12 坏 12** | **证伪**（不是"没生效"，是"生效且抵消"） |
| 2 | 单次采样有方差 → 投票把它花掉 | 同题采样 3 次严格多数 | 一致 120 / 192 / 172（**75% 的题上有分歧**）；MR 86.2，净 **+1** | **证伪**（误差是**偏差**不是方差：37 道错里 15 道 under、其中 12 道差 1） |
| 3 | 提示词形状 → aggregation | 换多会话聚合的写法 | MR 87.5、弃答 16，但 **TR 94.2→72.8、IE 136.2→127.5** | **运行作废**（fallthrough 返回对照组块，撤掉了 merging sentence） |
| 4 | 证据打包单位 → session | 按会话而非按轮检索 | 窗口只动 6 turn / 640 字符；MR 85.2→82.5、TR 97.0→92.0 | **关闭**（未处理路由 −5 > 处理路由 −2.7） |
| 5 | 重排能回收排序损失 | 同 SHA 两臂 A/B | Δ +1.33 / −1.33 pp，p 均 0.7539；可回收上限 **11 题 = 2.2 pp** | **无效**（默认关闭） |

## 3. 测量仪器

仪器的存在理由：这一轮最多的缺陷不在产品里，而在**测量层**。以下是已建成的部分。

| 仪器 | 防的是什么 | 证据 |
|---|---|---|
| **`--audit` 七项**（roster / census-unit / budget / reach / vote / expansion / roles） | 一次运行内部两个字段互相矛盾（`vote=0/0/0`、触达表与 fallthrough 不一致、普查数咨询次数） | 复现两个历史缺陷；CI 上传后 `if: always()` 运行 |
| **reach 不变量**（8 ask × 6 路由，单条） | 触达表与实现的漂移 | 突变检验红 3 条 |
| **普查单位**（`#recordOutcome`，每题一次） | 按调用计数（投票轮 2,968 vs 应 2,000，超 968 = 484×2） | 4 条测试，3 条修复前为红 |
| **噪声底**（同配置复跑 + 逐题配对） | 把噪声当效应 | `--stability`：MR −2 / TR −4；状态层 11.8% 会变 |
| **双向断言闸**（dispatch input ↔ 产物字段） | 配置无法抵达测量 | 三次注入验证 |
| **产物自审 + 拒绝清单** | 门禁惰性 | 明确拒绝两项候选检查（`evidenceTurns > k`、turn > cap），因为它们会在**正常运行**上触发 |
| **发布规则命中计数**（`[POC-6]`） | 结构性零：被测机制从未触发，零被当成上界 | 命中 0 时 leak 列输出 `NOT MEASURED` |
| **冻结泄漏行**（`regress.mjs` + `regressions.json`） | CI 抓到的缺陷回潮 | 13 条历史泄漏行，12 条可判、1 条因文本截断单列 |
| **CI 链本身**（`poc-platform-probes.yml`） | "本机测不了"被当成"无法测量" | 两条链的结果提交到 `ci-results`，与主分支分离 |

> **一条被拒绝的检查也是设计。** 会在好运行上报红的检查，会教读者跳过输出 —— 比没有检查更糟。

## 4. 缺陷登记簿

按子系统分类。**没有一个能靠读码发现** —— 全部由"运行/重读真实产物/核对两个产物之间的一致性"发现。

### 4.1 报告与守卫子系统（连锁，同一轮）

| # | 缺陷 | 发现方式 | 教训 |
|---|---|---|---|
| 1 | 守卫的**爆炸半径**：前置条件检查放在它所保护的工作之后，触发时丢弃全部已完成报告 | 靠运行（11 分钟失败） | 代码**单独看是正确的**，缺陷在它与其他部分的位置关系里 |
| 2 | 覆盖度是**侧信道**：`coverage` 与 `report` 并列返回，渲染器拿不到 | 靠验证修复 | 修复 #1 把 permissive 变成默认，**把响亮失败换成了安静的错误数字** |
| 3 | 报告**无法从 JSON 重读**：`NaN`/`±Infinity` 序列化成 `null`，重渲染抛 `TypeError` | 靠重渲染归档产物 | 归档件是唯一耐久记录；**无法重读的报告无法被辩护** |
| 4 | 侧信道的第二个实例：`retryFires` 同样并列返回 | 靠审计"已声明的缺口" | **如实声明缺口是有价值的** —— 这个缺口是真的 |

### 4.2 测量层

| # | 缺陷 | 发现方式 | 教训 |
|---|---|---|---|
| 5 | **覆盖率门禁读的是噪声**：同一代码 12 次运行得 5 个不同结果，跨度 0.76pp | 第三次看到同一异常时不再解释它 | **"重跑一次就好了"是危险信号** —— 需要重跑才正常的数字不是证据 |
| 6 | **召回曲线的分母静默缩小**：曲线对 428 题算、报告对 500 题算，两个产物都没说 | 核对产物之间的能力项计数 | 排除**规则**正确，缺陷在排除**沉默**；产物内部自洽、对外误导 |
| 7 | **`vote=0/0/0`**：产品总暴露 `voteCounts()`，控制组发布了一份虚假普查 | 读产物 | 三者和为 0 视为**未测量**，不是"零投票" |
| 8 | **触达表与 fallthrough 不一致**：报告说触达，代码没触达 | 对照两组字段 | 与 #7 同类：**一次运行内两个字段互相矛盾** |
| 9 | **普查数咨询次数而非问题数**：投票轮 2,968 vs 应 2,000 | 算术对不上 | 单位错会伪装成"效应" |

### 4.3 数学核心（真实 BUG，在查测量问题的路上被撞出来）

| # | 缺陷 | 发现方式 | 教训 |
|---|---|---|---|
| 10 | **`sinkhorn` 收敛检测器恒真**：`uPrev` 是 `u` 的别名且 `u` 被原地修改，残差恒 0 | 补覆盖率缺口时顺手验证 | 一个**恒真**的判据，表现为静默的"已收敛" |
| 11 | **`logGamma` 对所有负非整数返回 NaN**：反射公式漏 `\|sin\|` | 追"守卫既然可达，是什么把它们带到的" | 真实 BUG 可以在**追一个测量问题**的路上出现 |
| 12 | **`binomialCdf` 在小 `p` 下返回无效值**：连分数在收敛域外求值，且破坏单调性 | 为守卫写性质测试时断言单调性 | 返回值**看似合理、不是 NaN**，误差在函数最确定处最大 |
| 13 | 修复 #12 时引入**无限递归**风险：边界比较用非严格 `>=`，在不动点 `a==b, x==0.5` 上 | **密集网格**的性质测试 | 「性质测试 > 点检查」最干净的一次实证 |
| 14 | **遗忘时钟量纲错误**：默认配置下 `consolidate` 删除全部记忆 | 读实现 + 复算 | 一个"看起来在衰减"的公式，量纲错了就是删除 |

### 4.6 三类方法假阳性（比任何单个缺陷都重要）

| 假阳性 | 我做了什么 | 为什么它是假阳性 |
|---|---|---|
| **探针扰动被测对象** | 往守卫体里插计数器，统计命中 | 插入动作本身改变了可达性，于是"实测"只确认了原假设。**该结论带着验收表进了仓库，是错的** |

## 5. 方法学教训（可复用的八条）

1. **零不等于零率**：0/12 必须报 Wilson 上界（24.2%），不能写"从未发生"。
2. **基准的簿记可能伪装成算法**：`p02` 首版 f32 比 f64 慢 2.3 倍，原因是 top-k 每命中即 `sort()`。
3. **会在正常运行上报红的检查比没有检查更糟**：它训练读者忽略输出。
4. **诊断正确不蕴含处方正确**：63.08 pp 排序损失成立，重排能回收它不成立（上限 11 题）。
5. **单次运行无法支撑 <5 题的声称**：噪声底 MR −2 / TR −4，且这是下界不是区间。
6. **修好了可达，不等于修好了可判别**：值抵达了决策点，但决策点不可达/不可判定，是同一种失败的两个阶段。
7. **配置的性质由最近一次"采纳配置"的运行给出**；被证伪的运行只贡献机制结论。
8. **回归即回滚**：图扩散激活 TR 77.95%→70.87%，理由是"理论上应该有效"；重排两臂 ±1.33 pp。
   两者都被实证否决。

## 7. 未取证缺口

### 7.1 三条阻塞项：全部关闭

| # | 缺口 | 关闭方式 | 读数 | 仍有边界 |
|---|---|---|---|---|
| **G1** | Safari 上的 OPFS-AHP | 仓库设 public → macOS runner 拿到 → `safaridriver` 驱动真 Safari | `sahPool: true`、`vfs: opfs-sahpool`、1,000 行 72 ms、checkpoint 1 ms | 单会话、无重启、未测并发/配额 |
| **G2** | 规则层 leak 的**比率** | 不再靠人工标注：`ai4privacy/pii-masking-200k` 提供 3,000 条"必然私有"的行，跑规则层 | leak **1/3,000 = 0.19% 上界**；coverage **87.5%**；两轮修补 16 → 4 → 1 | 语料是标识符类，不是职场作用域；后者仍只有 n=60 的 24.2% |
| **G3** | 真实题库上的端到端双库 | `[POC-7]`：把规则用在一次真实运行**已展示给读者**的 59,675 条轮次上 | 可共享 **0.52%**；**63.6%** 的问题共享窗口为空 | 产物只记 rank、不记 gold 身份，故不报"丢了多少准确率" |

**G2 的关闭方式值得单独说**：原计划是"再标 600 条"。实际做的是**换问题**——leak 不是 recall 的
函数，而是"发布规则命中私有行"的频率，于是任何"必然私有"的语料都能测。3,000 条语料来自公开
标注、不是我们写的，也不是模型写的（CIMemories 的标签是 GPT-5 生成的，用它等于让被告当法官）。
三轮之后 leak 从 16 降到 1，而这 15 个修掉的缺陷**没有一个**能被 60 条标注集发现。

### 7.1.1 为什么 G2 不能只用一次数字就宣布"安全"

`1/3,000` 的那一条，文本在语料里就是截断的（"…Home Loan Account with I"），标识符不在字符串里。
它被**按泄漏计入**（保守方向），而不是被剔除。剔除会让数字好看，也会把"我们看不见的东西"从
分母里删掉 —— 这正是 #28 那条"结构性零"的同一类错误，只不过方向相反。

### 7.2 设计侧未取证（6，不影响架构，只影响承诺强度）

| 缺口 | 需要什么 |
|---|---|
| wasm SIMD 下的 int8 | 一个 wasm 内核（或 `sqlite-vec`/duckdb 内建算子）跑同一批向量 |
| LLM 提议层的**跨供应商**稳定性 | 提议层不产出 scope（第 9 步），因此原先那条"测 scope 建议一致率"随之作废；剩下的是"同一输入在同一 provider 上是否复现" —— 本机 0.5B + greedy 可复现，**商用 provider 的批处理非确定性仍未测**（无 key） |
| 端到端 false-share（含人） | 可用性实验 n≥20，测"100 张卡片里的误接受率" |
| 本地小模型质量 | 浏览器里跑同一批 LongMemEval-S 题，与云端读数比对 |
| 多标签页并发写 | 双页并发写 + 崩溃恢复实验 |
| 输出侧泄漏 | 输出审查层本身未被设计 |

**声明纪律**：G1/G2 未关之前，不得对外发布"浏览器可用 / 隐私安全"的整体声明（03 §10.2）。

#### 七个缺陷，每一个都是测量发现的

| # | 缺陷 | 怎么发现的 | 严重度 |
|---|---|---|---|
| 1 | `SqliteStorage.transaction` **从未发过 `BEGIN`**：body 抛错时早先的写留在库里，而调用方被告知事务失败 | 写"回滚"测试时，断言 `inside` 不存在——它存在 | **高**（静默数据错误） |
| 2 | 前缀过滤用 `LIKE`：`_`/`%` 当通配符、ASCII 折叠，`ID:` 会返回 `id:...` | 给两个引擎写同一批断言时想到 key 里会有分隔符 | 中（错答案） |
| 3 | `(table_name, expires_at)` 无索引而清理每次读写都跑 → 批量写 O(n²)（161 行/秒） | 浏览器套件第一次报"178 行/秒"，与 POC 的 56,850 差两个数量级 | **高**（性能退化） |
| 4 | 关闭 storage 不终止 Worker，池仍装着 → 同页第二次打开装不上第二个池，**静默降级 IDB** | 浏览器套件里"写 2,000 行"跑在 idb 上，而同一页的矩阵刚在 opfs 上通过 | **高**（静默降级） |
| 5 | Worker 模块加载失败时谁都不回消息 → 页面永久挂起 | 写"失败的 sqlite URL"用例时，`describe()` 永不 settle | 高（挂死） |
| 6 | `?sqlite=` 当 URL base，相对路径抛 `Invalid base URL` | 套件第一次红：`OPFS storage is unavailable: Failed to construct 'URL'` | 中（误导的错误） |
| 7 | 浏览器套件在 OPFS 失败时把 IDB 结果贴上 `opfs` 标签 | 第 6 条让 OPFS 失败，套件却报了 23 条绿 | 中（测量自欺） |

**第 3 条与第 7 条值得单独记**：前者是"只在批量时出现"的性能缺陷，正确性测试永远看不见；
后者是**测量装置自己撒谎**——它当时报告 23/24 通过，而那份"通过"属于另一层。两条都只能由
"在真实平台上跑、并且把标签当成前置条件"抓出来。

**一个被实验否掉的优化**：先猜是 `journal_mode` 不是 WAL，加 `PRAGMA journal_mode=WAL` →
201 行/秒（与 178 同量级）；再加 `synchronous=NORMAL` → 249（仍在噪声带内）。瓶颈不在同步策略，而在该 VFS 用
回滚日志、每笔都必须完整提交。于是**不加 pragma**，改为把 `journal_mode` 放进 `describe()`，
让"为什么单条写这么慢"在读数里自解释；并把"批量必须走事务"写成 API 契约（差 54–72×）。

### 9.7 第 4 步：`cortex-ai` 的三种依赖画像，与两个"默认值"缺陷

`cortex-llm` 改名 `cortex-ai` 并拆成三个入口。结构上的要点不是名字，而是**依赖画像**：

| 入口 | 需要什么 | 谁会用 |
|---|---|---|
| `.` | 只有 `fetch` | 只调 HTTP 的服务、边缘函数 |
| `./local` | `@huggingface/transformers`（optional peer） | 离线 Node、带权重的浏览器 |
| `./web` | `globalThis.LanguageModel` | 有内置模型的浏览器 |

守卫按画像逐个走闭包：`.` 与 `./web` 禁止触达 peer，`./local` 是**正对照**。合成一个入口的代价
不是"包大一点"，而是每个只调 HTTP 的服务都被迫带 ONNX runtime 与 90 MB 权重。

#### 两个缺陷，都由"真权重 + 真比对"抓出

| # | 缺陷 | 怎么发现 | 严重度 |
|---|---|---|---|
| 1 | **默认 dtype 变了**：v2 默认量化权重、v4 默认 fp32。照默认升级，向量维度对、单位长度、**与已存向量不可比** | 一致性脚本里两条臂都跑，发现 v2 默认臂只有 0.988（15/15 低于 0.999） | **高**（静默不兼容） |
| 2 | **重排空转**：`text-classification` 对单标签做 softmax，所有候选 score 恒为 1.0 | 用真交叉编码器打分，三个截然不同的候选都返回 1.0；读原始 logits 得 1.954 / −4.028 / −5.625 | **高**（功能等于没有，但报告成功） |

**第 1 条的读法要精确**：升级本身**没有**改数学。同权重、同 dtype 下，发货适配器与 v2 的
**min cos = 1.000000**（15 条，0 条低于阈值）。会动的是默认值——所以处理方式不是"重建索引"，而是
**把 dtype 钉死在代码里**，并把 v2 时代的向量记为必须重嵌。

**第 2 条更值得记**：同一个缺陷在 v2 下是**响亮的失败**（管线按输入嵌套返回，适配器解析抛错并回退），
在 v4 下形状正好对上契约，于是变成**沉默的成功**。换版本把一个可诊断的故障变成了不可诊断的故障 ——
这类"修复过程中新引入的静默"只有端到端跑真模型才能发现，单元测试永远看不见（它们供给的是形状正确的
假数据）。

#### 覆盖与注解

`cortex-ai` 现在 **100/100/100/100**，并且**一条覆盖率抑制都没有**：两个 peer-loading shim 原先各带
一个 `c8 ignore start`，现在通过**注入模块加载器**被测穿（`dtype`、`pooling`、`env`、`logits` 全都能
直接断言），`resolveTransformersModule()` 则对**真装的 peer** 调一次。注解是被**删除**的，不是被改写
理由的。

### 9.9 第 6 步：卡片队列，以及它第一次运行就抓到的东西

`CardQueue` 落进 `cortex-core`：`proposed → accepted | edited | dismissed`，`accepted/edited → stale`，
`stale → accepted`（`refresh`）。`dismissed` 是唯一终态。五条设计规则各自被代码与测试守住
（02 §5.5.1 有对照表）。但这一步真正值钱的不是这张状态机，是它**第一次运行就抓到的两个问题**。

#### 问题一：一条政策句没有被执行

`credential` 的政策句写着 **"never stored, not even as a card"**，而写侧一直把它**私密存下来**。
两份产物里，写侧是弱的那一份，却也是被执行的那一份——这正是本项目一直在防的"文档承诺 > 代码行为"。

修法不是改政策句（那正是用户被告知的东西），而是加 `retention: 'never'`：命中它的句子被分类、
被报告（`stored: false` + `withheld`）、**不被写**。60 条语料没有凭证句，因此三项读数一位未动。

#### 问题二：三句最普通的健康事实，没有任何规则命中

"全部接受"这个消融（每张卡都点同意）在第一次运行时发布了 **3/12** 条 gold-private：
"incorporate more walking into my daily routine"、"reducing my intake of added sugars"、
"longer walks in the morning"。**私有召回只有 9/12**，而这 3 条漏判全是日常运动与饮食措辞。

这一条比它看起来更重要：**"边界是 fail-closed" 是规则的属性，不是队列的属性。** 队列只要有人不看
就点同意，就是一条绕过规则层的发布路径。POC-5 量到过同一个数（A4 3/12），当时归因于"`defer` 默认
共享"；现在归因更准确：**规则的召回不满，`defer` 的私有默认是唯一的兜底，而卡片正是绕开兜底的那扇门。**

#### 修补：先量三份语料，再改一个词

按既定纪律，改规则之前先测。三个候选在一次运行里同时测量：

| 方案 | 私有召回 | 60 条 coverage | 13 条冻结回归 | 1,467 条 coverage |
|---|---|---|---|---|
| 现行表 | 9/12 | 26.7% | 0/12 泄漏 | 28.6% |
| `walk(ing|s)?` | 11/12 | 30.0% | 0/12 | 28.9% |
| **`walk|sugar|calorie|intake`** | **12/12** | **31.7%** | 0/12 | **29.2%** |
| 再加 `stretch(ing)?` | 12/12 | 31.7% | 0/12 | 29.2% |

选了第三行：它把召回补满，而加 `stretch` **没有任何增量**，所以不加。false-share（0/12）与
false-private（4/8）在 60 条上均未变，说明这不是"把可共享的句子误判成私有"换来的召回。

**一处必须写下来的副作用**：`third-party` 从此在 60 条语料上一次都不触发——它唯一命中的那句
"a 5 km walk with my colleagues" 先被 `health` 抓住。判定不变（两边都是私有），但**归因变了**：
审计链现在会说"健康"而不是"第三方"。这种漂移不会体现在任何指标上，只能靠逐条看。

**剩下的 1/8 不可达**：`g42`（同上那句）被判私有，于是**永远不会有卡**，也就永远不会被发布。
这是队列的一个边界——它只能提升"规则判为 defer"的东西，不能把规则判私有的东西变成问题。
"用户能不能主动分享一条被判私有的记忆"因此是一个真正的产品问题，答案是**能**，但它需要一条
与卡片不同的路径（显式授权 + 更强的警告），不是本步的范围。

#### 四条较小的决定，每条都由一个"会为错误理由通过的测试"逼出来

| # | 问题 | 现在的做法 |
|---|---|---|
| 1 | `list()` 的排序**从来没有被执行**：内存存储本来就按 key 排序，删掉 sort 测试照样绿 | 加一个**逆序返回**的存储替身，让存储的顺序是错的 |
| 2 | `Admission` 用 `stored: boolean` + 可选 `withheld`，三处 `?? 'unknown'` 是死分支 | 改成判别联合：`stored: false` 一定带 `withheld`；剩下的一处由**注入矛盾分类器**覆盖 |
| 3 | 设计里的 `redactions` / `confidence` 若照抄，会是永远为空 / 恒为 0.5 的字段 | **不实现**，并在 02 §5.5.1 写明理由：一个恒为 0.5 的字段是没人能审计的承诺 |
| 4 | `expire()` 遇到没有 `decayAt` 的 accepted 卡片会怎样 | 不扫它。那是上个版本写下的行，一升级就把所有已确认事实撤下，比不撤更糟 |

### 9.10 第 7 步：输出侧——设计里最后一个没被覆盖的泄漏面

写侧把库分开了，但**回答是另一件事**。共享任务里的读者可以让模型复述一条它五轮前见过的私有事实；
那条事实不在窗口里，它在**答案里**。`docs/02` §6.3 一直写着"本设计不宣称安全"，因为这一面没人管。
这一步把它管上，用的是**写侧那张表**。

| 检查 | 判据 | 60 条上的读数 |
|---|---|---|
| **O1 范围扫描** | private 规则命中共享草稿 → 拦 | **12/12** gold-private 被拦 |
| **O2 归因** | 每条 `[[id]]` 必须落在窗口内；共享草稿必须至少一条 | 未知引用 / 无引用各一条 finding |
| **误拦** | 已发布的事实被写成草稿 | **0/4** |

**"0 误拦"比"12/12"更重要。** 一个漏报的守卫是假承诺；一个把正常回答拦下的守卫，会在第一周被
关掉，之后就什么都不保护。所以两条数一起报，缺一条这个功能就不该上。

#### 让它可用而不是烦人的那一处：豁免

共享任务**合法地**引用一条共享事实（包括提到钱的）不该被拦。所以当窗口里有一行 shared 记录、其
文本**包含**被命中的那个句子时，finding 标 `excusedBy: <id>` 并**保留在报告里**。守卫不判断"这句
话安不安全"，它问"写侧是不是已经决定了"，并把推理过程一起交出来。判据是**包含而非相似度** ——
会猜的守卫要么放过太多（不再是守卫），要么放过太少（被关掉）。

#### 三处"测试为错误理由通过"的地方

| # | 问题 | 现在 |
|---|---|---|
| 1 | 报告若按**命中的词**截取，`money` 命中的是 `spent`，"这句话包含：spent"对读者毫无意义 | span 扩展到句子边界（`.` `!` `?` `:`）；**换行不算**，草稿按 80 列折行 |
| 2 | 四个 `?? ''` / `?? 0` 是死分支：循环边界内 `draft[i]` 不可能是 undefined，`matchAll` 永远带 `index` | 用 `charAt` 与一次显式 cast 去掉，而不是留在报告里当"防御性代码" |
| 3 | 私有任务里若也拦范围命中，用户连自己的账单都不能问 | 私有任务只保留 `never-retained`（凭证仍拦，因为草稿会被存/贴/日志） |

两次注入都红：去掉豁免（两条红）、把凭证当成普通范围命中（一条红）。

#### 它买不到什么

**改写与概括**。"我的卡号是 4111…" 被说成"我的卡尾号 4111"时，O1 看不见，O2 也看不见。
所以这一层的承诺只能是**"减少了部分泄漏"**。把 §6.3 的 `0/12` 当成输出侧的读数，正是这份报告
一直在防的那类替换 —— 那 12 条量的是**存储**。

#### 这一步没做的

| 项 | 归属 |
|---|---|
| **O3 密文回显**（窗口之外的私有行逐字复现 ≥N 字符） | 需要私有行的指纹索引；P2 |
| `TriageProposer`（LLM 提议原子事实） | 需要 provider；它只改**卡片内容**，不改边界 |
| 跨会话记忆残留（模型在上一轮见过私有行） | 需要会话级隔离，属于编排层 |

### 9.11 第 8 步：O3，以及它补上的那 44 条

O1 跑规则表，所以只看得见规则命中过的句子——60 条里 12 条。其余 **44 条是 `defer`**：没有规则
有意见，靠"默认私有"待着；草稿复述其中一条，O1 报**干净**。这是剩下最大的洞，而且它之所以不可见，
恰恰因为其它部分都在正常工作。

O3 不需要意见，只需要**行**：字符 n-gram 重叠（默认 32），比对全部私有行。

| 检查 | 覆盖的私有行 | 60 条读数 |
|---|---|---|
| O1（规则） | 12 | 12/12 |
| **O3（回显）** | **56** | **56/56** |
| 误拦 | — | **0/4** |

**为什么不用相似度**：embedding 会把"我的卡被拒"和"我的卡没通过"判成同一句，而对近似句开火的
守卫会被关掉。代价写在付出它的地方，**并且被一条测试钉住**：改写（"卡号 4111…" → "尾号 4444"）
**抓不到**。哪天它真能抓到，是那条测试先红，而不是让读者以为它一直能。

**三个工程决定**：① 先把窗口内 shared 行的 n-gram 从私有语料里**减掉**（O1 豁免在 n-gram 粒度上
的同一句话）；② 空白折叠后比对（草稿 80 列折行），归一化串带**位置映射**回到原文，所以 finding
指向调用方手里那份草稿；③ 大小写只在比较时折叠，不动文本，映射因此不会失效。

**成本**（实测，单次扫描）：100 行 **0.94 ms**、1,000 行 **11.1 ms**、5,000 行 **67.5 ms**
（**这三个数在第 11 步被证明不可复现，见 §9.14**；同一份实现换一份语料实测是 2.1 / 32 / 332 ms）。
原文保留，因为"一张追不回来的表长什么样"比数字本身更有用 ——
线性，因为语料每次重建。一个用户几百行时是亚毫秒级，不值得优化；5,000 行时形状已经不对，
需要持久索引（P2）。**这张表不写成"可扩展"**。

两次注入都红：去掉白名单扣除、把阈值抬到无法命中。

#### 这一步没做的

| 项 | 归属 |
|---|---|
| 持久 n-gram 索引（万行级） | P2，需与存储层协商 |
| 改写/概括检测 | 需要语义对齐，且与"不误拦"直接冲突；目前明确不做 |
| `TriageProposer` | 下一步；只改卡片质量，不改边界 |

### 9.13 第 10 步：接线，以及三个只有跑起来才出现的缺陷

第 9 步结束时，`TriageProposer` **没有任何调用方**。第 10 步把它接进一条真实路径：写侧 → 卡片 →
提议 → 发布 → 读侧，由 `DisclosureSession` 固定顺序，由 `tools/triage-demo.mjs` 用九次独立的
进程调用跑出来。

#### 三个缺陷，没有一个是单层测试能看见的

| # | 缺陷 | 症状 | 修法 |
|---|---|---|---|
| 1 | **一个引擎装不下两个库** | 会话最初只收一个 `Storage`，指望表前缀分住两半。`FederatedStorage` 把前缀当路由标记**剥掉**，两半写进同一张 `facts` 表；第一次共享查询把私有行带出来，`ReadSideAssembler` 当场抛 `ScopeViolation` 并点名 key | 会话要求两个 `Storage`（两个文件）。这条失败现在有一条测试守着 |
| 2 | **`./local` 没有生成能力** | 想用真模型跑链路时才发现：离线入口能嵌入、能重排、能回答，**唯独不能提议**。第 9 步引入了一个只吃模型的组件，而"离线"那条入口产不出模型 | 新增 `createLocalLLM`，与嵌入共用 `preparePipeline`（同一个 `dtype` 钉法，同一处 `env` 写入） |
| 3 | **审计面丢掉原句** | 发布原子后：卡片 `text` 被改写、私有行被 `promote` 删掉，**没有任何地方记录"他原本说了什么"**。而导出是本产品唯一的审计面 | `KnowledgeCard.sourceText`（开卡写入、永不改写）+ 导出在措辞变化时多一列 `source` |

第 3 条是这三个里最有价值的：**代码每一行都对**，`edit()` 改用词、`promote()` 搬行、
`toMarkdown()` 打印卡片，三处合起来才产生"原句不存在了"。任何按函数写的测试都不可能发现它。

### 9.14 第 11 步：O3 的成本，以及一张追不回来的表

#### 先说那个追不回来的表

第 8 步的记录写着 O3 的成本是 **0.94 / 11.1 / 67.5 ms**（100 / 1,000 / 5,000 私有行），来源是
"本机脚本"。这一轮去复现它时发现：**脚本没有入库，语料也没有保存**。同一份实现，在一份每行约
200 字符的合成语料上重测，读数是 **2.1 / 32 / 332 / 834 ms** —— 比表里的慢 5 倍。

两个数都不假，但它们**不可比**：没有人能说清第 8 步那份语料有多长、有没有重复、归一化过没有。
这不是数字错了，是**测量没有被交付**。所以本步的第一件事是把 `test/echo/run.mjs` 连同语料生成器、
样本数、p50 一起入库，并在表头写明"同一份语料、两版实现"。

#### 判据与结果

步骤判据（03 §10.2 第 2 项）是**万行级 p95、召回不变**。结果：

| 私有行数 | 第 8 步实现 | 第 11 步实现 | 倍数 | 过滤器 | 判据 |
|---|---|---|---|---|---|
| 100 | 2.1 ms | **1.6 ms** | 1.3× | 0.1 MB | — |
| 1,000 | 32 ms | **20 ms** | 1.6× | 1 MB | — |
| 5,000 | 332 ms | **71 ms** | 4.7× | 4 MB | — |
| 10,000 | 834 ms | **133 ms** | 6.3× | 8 MB | ❌ **未达成** |

召回：同一行文本在 5,000 行语料上被复制，两版实现各自找到 **153** 个匹配窗口，**逐条相同**。
`OutputGuard` 的 60 条读数（56/56 拦下、0/4 误拦）在改动前后一位未动。

**为什么没达成**：形状仍是线性——每次扫描仍然读完所有私有行。真正的次线性需要一个**被持有并被
增量维护**的索引。按本步的测量，这样的索引（hash → 行 id 的开寻址表）在 5,000 行上要 **18 MB**、
10,000 行上 **36 MB**；降到 9 MB 也会在每一次写入时面对"重建 vs 陈旧"的选择，而**陈旧的方向是静默
的**：漏一行就是漏一条泄漏，且报告会显示"干净"。这笔交易被记录成债务，没有采纳。

#### 三个实现要点，每个都对着一个失效

| 点 | 失效 |
|---|---|
| 滚动哈希的幂用 `Math.imul` 循环算，**不用 `Math.pow`** | `Math.pow(P, 31) >>> 0` 取的是双精度数的低 32 位，而尾数早在 2^53 就截断了。结果：同一个窗口在不同位置得到不同哈希。**一切仍然是确定性的**，`contains` 却对大多数拷贝回答"没有"——这正是"结构性静默"那一类。原型里它活了十分钟，现在是第一条断言 |
| 过滤器只说"可能"，命中必须 `String.includes` 复核 | 布隆过滤器有假阳性；不复核就是**误拦**。复核次数与假阳次数都计数，所以"过滤器变差"会显示为一个数，而不是一次没人解释的变慢 |
| 语料与草稿共用同一套归一化 | 一边折叠空白一边不折叠，过滤器会把整份语料判成"干净"——又一次静默 |

#### 两次注入

| 注入 | 结果 |
|---|---|
| 幂改用 `Math.pow(P, w-1) >>> 0` | **4 红** |
| 信任过滤器、跳过 `includes` 复核 | **3 红** |

`cortex-core` **470** 条测试，语句/分支/函数/行 **100/100/100/100**（`echo-corpus.ts` 单独同）。

大小写与空白折叠、短于宽度的窗口被拒、空语料、位数组按窗口数而非行数增长、复核计数、
以及一条随机语料上的**无假阴性性质测试**。

### 9.16 第 13 步：A3 的仪器，以及在开跑之前就发现它测不出东西

#### 先说清楚这一步**没有**产出什么

没有 A3 的读数。一次点击都没有。原因不是没时间，是**在准备阶段就发现这份处理没有剂量**——
详见下面第三节。这一步产出的是：判据第一次**可以被计算**，以及一个**说明现在收数会白收**的读数。

#### 判据此前根本算不出来

A3 从计划写下那天起就写着"接受率差 ≥10pp、n≥20、配对"，但仓库里**没有任何代码能计算它**。
一个没人能求值的判据是句子，不是测试。`scoreA3` 把它变成算术：

| 输出 | 值 |
|---|---|
| 每臂 | 接受数（编辑算接受、另计）、Wilson 95% 区间、编辑数、决策时长中位数 |
| 配对表 | `both` / `onlySource` / `onlyAtoms` / `neither`，以及 `pairCount` |
| 检验 | **精确 McNemar**：`2·P(X ≤ min(b,c))`，`X~Binomial(b+c, 0.5)`，封顶 1 |
| 判定 | `atoms-better` / `source-better` / `no-difference` / `underpowered` / `unpaired` |

17 条测试，全部对着手算值：`10:0 → 2/1024`、`1:9 → 22/1024`、`5:5 → 1`（对称即 p=1）、
`0:0 → 1`（**没有不一致时答案是 1，不是 0**——把未定义统计量报成小数字，是零结果变成发现的
最常见方式）、对称性、封顶、以及"最后一票覆盖前一票"的续跑规则。

#### 仪器：三个命令，一次冒烟

```
node tools/a3-review.mjs prepare --out /tmp/a3/cards.json --limit 20 --llm local
node tools/a3-review.mjs review  --cards /tmp/a3/cards.json --decisions /tmp/a3/decisions.jsonl
node tools/a3-review.mjs score   --decisions /tmp/a3/decisions.jsonl
```

`prepare` 用真模型把 20 句变成 20 张卡（每张带模型实际拆出的原子）；`review` 每张卡呈现两次、
**偶数张先原句、奇数张先原子**（疲劳落在两臂上，而不是落在"第二个"）；`score` 打印上表。

管道冒烟：把 45 个 `a` 灌进 stdin，得到 40 条决策、20 对、`NO-DIFFERENCE`（p=1.0000）。
**这是管道测试，不是测量**——那些"接受"是我用 `yes` 灌的，任何人都不该把它当成读数。

冒烟还抓到一个真缺陷：第一次要 20 张卡只得到 **18 对**。原因是 `prepare` 先按 gold 标签筛
`defer`，而其中两句在**现行表**下已被判私有、不建卡——于是"要 20 张"实际只拿到 18 张，
判定随即变成 `underpowered`。`--limit` 现在数的是**卡片**，不是候选句。

#### 最重要的读数：处理强度（20 张卡）

| 两臂呈现 | 张数 | 例子 |
|---|---|---|
| **完全相同**（单原子 = 原句） | **14** | g02、g06、g08、g12、g13、g17、g19、g21、g22、g23、g25、g29、g30、g32 |
| 只差一个开场白（单原子） | 5 | "By the way, …" → 去掉；"Yeah, …" → 去掉；"Each had its own unique charm, but …" → 去掉 |
| **真的被拆开（≥2 原子）** | **1** | g04（3 条） |

也就是说：如果现在收 40 次点击，其中 14 次的两臂给受试者看的是**同一段文字**，5 次只差一个
"By the way"，只有 1 次在测"原子 vs 段落"。这样得到的读数会是一个关于 **0.5B 模型不擅长切分**的
结论，而不是关于**卡片该不该显示原子**的结论。

**这就是"处理强度"这个门槛的价值**：它把一次注定无效的实验挡在了 40 次点击之前。

#### 测试与门禁

`cortex-eval` 新增 17 条（`a3.test.ts`），包内覆盖率维持 100/100/100/100；`pnpm check` exit 0。

| 项 | 归属 |
|---|---|

| 真机界面 | `review` 是终端交互；网页版属于产品化 |

### 9.17 第 14 步：把"用哪个模型"变成一份记录，然后在离线入口里找到两个 HTTP 客户端

这一轮的问题是三个连在一起的：**0.5B 是什么、为什么不用 DeepSeek 或智谱、该不该有一个配置项并比较
两种配置**。完整答案在 02 §4.5；这里只记测量过程与结果。

#### 为什么要做配置，而不是"再加一个开关"

第 13 步结束时，两组数字躺在同一份文档里却**无法区分**：它们来自同一个 checkpoint，但如果其中一组
来自 API 模型，读者没有任何字段可以看出来。配置如果只是脚本里的 `if (flag === 'local')`，它带来的
不是可选择性，而是**两个不可比的读数**。所以这一轮做的是一个纯函数
`resolveLlmProfile(request, env) -> LlmProfile`：它的输出可以被打印、被存进 `cards.json`、被写进
`proposal.provider`，而且**结构上装不下 key**。

#### 四条决定，四次注入

| 注入 | 结果 |
|---|---|
| `remote` 缺 key 时**回退到 local** | **6 红** |
| 空字符串当成"已设置"（`!== undefined` 而不是 `present()`） | **1 红** |
| 去掉 `https` / loopback 检查 | **1 红** |
| 让 `./local` 重新 import 回 HTTP 适配器 | 守卫失败，**并同时点名两个文件**；包内测试 1 红 |

第二条值得单说：`CORTEX_LLM_API_KEY=` 在 shell 里是**导出了但为空**，`??` 会接受它，于是运行期拿一个
空 key 去请求。这不是假想的边角——CI 里未配置的 secret 通常就是长这样。

#### 实测一：本地推理 0 次网络请求

`packages/cortex-ai/test/profile/network.mjs` 在 import 任何模块**之前**接管 `globalThis.fetch`，
把每个请求归到阶段：

```
{ "model": "onnx-community/Qwen2.5-0.5B-Instruct", "dtype": "q4",
  "loadMs": 6869, "inferMs": 9751, "loadCalls": 0, "inferCalls": 0,
  "verdict": "no request during inference" }
```

**为什么要分阶段**：`@huggingface/transformers` 自带 `fetch`（冷启动要下权重），所以"依赖里没有 HTTP
客户端"这个说法本来就不成立。产品承诺的不是那个，而是**权重在磁盘上之后，推理不发一个请求**。一个
笼统的总数会把这两件事混成一件。

#### 实测二：守卫的新规则在真实树上失败了两次

给 `tools/entry-guard.mjs` 加**文件级禁令**（原来只匹配裸模块名，无法表达"这个入口不得触达我们自己
的 HTTP 客户端"）之后，第一次运行就失败：

| 轮次 | 守卫点名 | 原因 |
|---|---|---|
| 1 | `./local`、`./web` → `src/retry.ts` | `parseJson` 定义在 `llm/openai-compatible.ts`，两个离线入口都从那里 import |
| 2 | 仍然 `./local` → `src/retry.ts` | `CrossEncoderReranker` 与远程重排器同住 `rerank/rerank.ts`，而 `./local` 再导出它 |

修法是两处搬家（`src/json.ts`、`src/rerank/cross-encoder.ts`），旧名字仍从原模块再导出，调用方无感。
**两处的运行期请求数一直是 0**，所以这个缺陷永远不会变成一次泄漏，只会变成一个装着用不上的 HTTP
客户端的离线包——而 `local` 的承诺正是"那句话离不开这台机器"。修复后 `./local` 的闭包从 7 个文件减到
6 个，`bare` 只剩 `@huggingface/transformers` 与 `@agentix-e/cortex-core`。

#### 实测三：v2 与 v3，只改一条切分规则

第 13 步的剂量门槛没过（1/20），于是这一轮先问一个更便宜的问题：**是提示词没说清，还是模型做不到？**

| 项 | v2 | **v3** |
|---|---|---|
| 拆成 ≥2 条（处理） | **1 / 20（5.0%）** | **1 / 20（5.0%）** |
| 单条、有改写/裁剪 | 5 | 4 |
| 单条、与原句相同 | 14 | 15 |
| 覆盖度均值 / 最小值 | 0.920 / **0.416** | 0.932 / **0.296** |

**净零掩盖了三处反向移动**：

| 卡 | v2 | v3 |
|---|---|---|
| `g00` | 1 条 | **2 条**（"…using Python" + "So I'm interested in applying…"） |
| `g04` | **3 条** | **1 条**（丢了后两条） |
| `g18` | 裁掉 "By the way, speaking of TV shows," | 保留 |

`g04` 是新的失效类别：原子仍然逐字接地，闸不会拦（也不该拦），但**提议没覆盖整句**。闸管风险、不管
完整性——第 9 步写这句话时举的例子是"合法但无用"，这里是"合法但不全"。

**可复现性**：把提示词临时改回 v2 重跑一遍，20 张卡的原子与第一次**逐字节相同**。所以 v2 与 v3 的

### 9.18 第 15 步：把远端档从"未测"变成实测，而它一次就把剂量门推过了

第 14 步的三种配置里有两行是空的（local 1.5B 权重没取全、remote 没有 key）。这一轮把第二行填上：
`measure-models.yml` 在 CI 上带着 org secret 跑，**第一次真正执行**就给出了 A3 一直以来缺的那个数。

#### 仪器第一次运行是失败的，两处

| 失败 | 原因 |
|---|---|
| 60 条语料读数、embedding 读数 | 两步都把**绝对路径**传给 `--out`，而脚本里写的是 `join(HERE, out)`。`join('/a', '/b/c')` 是 `'/a/b/c'`，于是文件被写进包内一个不存在的目录，ENOENT |
| 判定 | 同一次 dispatch 里，A3 dosage 那一步**成功**了——它用 `dirname(config.out)` 直接处理绝对路径。两个脚本、同一行错 |

修法是 `resolve` 而不是 `join`（绝对段会替换），并把这个机制写在出错的那一行上方。**一个从没被执行过的仪器，
第一次执行就会暴露自己的假设**——这正是第 10/12 步反复记录的那件事，只是这次发生在工具上而不是产品上。

修好之后第二次 dispatch：**四个作业全绿**（远端生成、embedding、提交读数、密钥卫生）。

#### 读数一：剂量门第一次通过

| `remote` deepseek-chat | **15** | 5 | 0 | **75.0%** ✅ |

是容量问题，而容量是可以买的。

#### 读数二：六十条语料，配对比较

同一份 60 条标注句、同一版提示词、同一套闸：

| 项 | `local` 0.5B q4 | `remote` deepseek-chat |
|---|---|---|
| 产出可用提议 | 45 / 60 | **52 / 60** |
| 保留原子 | 48 | **89** |
| 候选 | 51 | 98 |
| 无法解析 | 0 | 0 |
| `failed:empty`（模型返回空） | 0 | 1 |
| 每句耗时 | 5.88 s（CPU） | **0.91 s** |
| 拒绝分布 | `health` 10、`money` 4、`ungrounded` 3、`too-short` 2 | `health` 12、`money` 5、`career-status` 1、`family` 1 |

配对：两边都成功 43、**只在本地成功 2**、**只在远端成功 9**、两边都失败 6 → 精确 McNemar **p = 0.065**。

三件事值得单独说：

1. **`ungrounded` 从 3 变成 0**。大模型没有编造用户没说过的片段；它的拒绝全部来自规则（健康、金额、
   职业状态、家庭），也就是说**闸的两种失效在远端只剩一种**。
2. **`too-short` 从 2 变成 0**：本地模型那两条"原子"短到没有信息量，远端没有产生这种东西。
3. **p = 0.065 不是 p < 0.05**。按预注册的门槛，这一条**不能说"远端更好"**，只能说方向一致、且不一致的
   9:2 全部倒向远端。单次 dispatch、单模型、`temperature: 0` 但在供应商侧不保证逐字节复现——这些都在下面
   的边界里。

#### 读数三：embedding 真的到了厂商，而不是悄悄回退

`cortex-eval` 的 `createEmbeddingWithProvenanceFromEnv` 在没有 key 时会回退到 256 维 hash 向量，并把这个
事实写进 provenance。CI 上 key 在，于是这一步同时验证了"到了厂商"：

```
{ "provider": "openai-compatible", "model": "embedding-3",
  "baseUrl": "https://open.bigmodel.cn/api/paas/v4", "dimensions": 1024,
  "seconds": 1.49, "cosineRelated": 0.9172, "cosineUnrelated": 0.5489 }
```

向量长度 1024 = 声明的维度（hash 回退是 256，这个差别在每一个下游检索分数里都是不可见的，除非有
provenance）。工作流里有一条断言：`provider` 必须等于 `openai-compatible`，否则**失败**——因为
"benchmark 用 hash 向量跑完、日志里写着 embedding" 正是 provenance 存在的理由。

#### 读数四：密钥没有出现在任何产物里

`hygiene` 作业把两个 secret 的值拿去 `grep -rqF` 全部产物，命中就失败并列出文件（`-q` 保证值不会经由
匹配行进入日志）。结论：两个 secret 在所有产物中**不存在**。这不是政策声明，是一条会红的检查。

**关于"设计阶段是否完美"**：9 条门槛 **9/9 ✅**，缺口清单为空。剩下的五条限制写在
03 §10.1.1，判断标准是"测出来与预期相反时，架构要不要改"——五条都不需要改架构，只影响阈值、
UI 和排期，因此是**边界**而不是**缺口**。
