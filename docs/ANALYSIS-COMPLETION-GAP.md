# 36 倍生成差额的归因：一次 0.09 CNY 的派发把"待定性"变成"可判定"

> 状态：**已定性**（运行 `44676731032`，2026-11-20）
> 结论先行：那 36 倍差额属于 **`ask=verbatim-scope` 这一份契约**，而该契约已因准确率被否证；
> 产品默认契约的交付比是 **3.66 字符/生成 token**，接近 3.5 的经验上限，**不存在**"provider 计费了调用方看不见的生成"。
> 因此约束⑰ 的读者侧成本杠杆不在"生成"，在"证据字符数"。

---

## 1. 待定性的原始形态

`S17`（运行 `44642788342`，121 道 `MR`，4 次重复）的产物里有两个数：

| 侧 | calls | completion tokens / call | 交付字符 / 答案 |
| --- | --- | --- | --- |
| feature（`verbatim-scope`） | 495 | **2,938** | 513 |
| baseline（`verbatim-acts`） | 706 | **82** | 未捕获 |

同一个客户端、同一个 provider、同一个 `thinking: {type: 'disabled'}`、同一个 harness，两侧的
每次调用生成量差 **36 倍**，而 feature 侧交付的字符只值 **146 token**（按 3.5 字符/token）——
**95.01% 的生成没有变成答案**。

第 139 轮把这件事写成了三个候选，并明确说"artifact 无法区分"：

| # | 候选 | 若成立，修法 |
| --- | --- | --- |
| A | provider 在计费推理 token，调用方看不见 | 换 provider 参数或降 `thinking` |
| B | 契约让模型写没人读的工作稿 | 改契约，需要预登记 A/B |
| C | 生成被输出上限截断，答案根本没写完 | **缺陷**：每个被截断的答案都是一道被判错、且任何提示词修改都救不回的题 |

三个候选的后果完全不同：A 是账单问题，B 是设计权衡，C 是正确率漏洞。

## 2. 把三个候选分开需要的最小派发

不需要 121 题。三个候选在**一次普通派发**里就分得开，只要那次派发跑的是**默认契约**：

- 若默认契约的交付比也在 0.2 附近 → A 成立（provider 行为）；
- 若默认契约的交付比正常、只有 `verbatim-scope` 异常 → B 成立（契约）；
- 截断率由新插桩 `truncatedCalls` 直接读数，与交付比无关。

于是派发 `semantic-carry.yml`：`capability=all`、`limit=6`、`ablation_runs=1`、`shards=1`、
`windows=2`、`pairing=carry`、`fact_timeline=0`、`budget_cny=3`。

投影 **0.09 CNY**（6 corpora × 2 windows = 12 题，输入 96% 命中缓存）。实际运行 5 分 50 秒。

## 3. 读数

运行 `44676731032`（shard job `136090260490` 成功，merge job 失败 —— 见 §6）：

| 字段 | 值 |
| --- | --- |
| calls | 38（baseline 14 / feature 14 / 判官与 setup 10） |
| prompt tokens | 213,422（**96.73%** 来自 prefix cache） |
| completion tokens | **3,017** |
| 交付字符 | **11,038** |
| **交付比** | **3.66 字符 / 生成 token** |
| 重试 | 0（38 次全部首次成功，0 次 429） |
| 每侧 completion / call | baseline 103、feature 112 |

`3.66` 与 `3.5` 的经验字符/token 比一致。**没有未交付的生成。**

三个候选的判定：

| 候选 | 判定 | 依据 |
| --- | --- | --- |
| A：provider 计费不可见推理 | **否证** | 同一 provider、同一 `thinking=disabled`，交付比 3.66 |
| B：契约工作稿 | **成立** | 差额只出现在 `ask=verbatim-scope`；`verbatim-acts` 侧 82 completion/次 |
| C：截断 | **未发生**（本次） | `finish_reason` 从未是 `length`；且 `truncatedCalls` 插桩已上线，后续每次派发都会自动报 |

## 4. 为什么这不是"换个说法"，而是改变了下一步

`verbatim-scope` 的准确率已经被否证（−2.48 点、`p=0.5078`、证据只有 15/121 相同、6 处回退）。
本轮补上的是**成本侧的第二条否证理由**：它同时让每次调用多生成 35 倍。

这意味着 `RETRACTIONS.md` 里那条记录不该只写"准确率不成立"，还要写"成本侧同样不可接受"——
两个独立的失败模式指向同一个结论，比一个失败模式更硬。

更重要的是，它把约束⑰ 的读者侧杠杆**移到了正确的位置**：

| 成本构成（`S17` feature 侧 495 次调用） | 占比 |
| --- | --- |
| prompt（12,831 token / 次） | **主导**，且 75.5% 命中缓存 |
| completion（2,938 token / 次） | 全部是契约工作稿，契约已被否证 |

所以"降成本"不可能靠改生成策略（默认契约已经只剩 112 token/次），只能靠**每道题读进去多少字符**
（`room` 48,460）。而 room 曲线（`evidence/longmemeval/room-curve.json`）已经测过缩小的准确率代价。

## 5. 截断插桩：为什么它必须存在，即使这次读数全是 0

`answerChars` 只能回答"多少账单没变成答案"，不能回答"为什么"。而"为什么"决定修法：

| 机制 | 修法 |
| --- | --- |
| 契约让模型写工作稿 | 改契约（需 A/B） |
| 生成在上限处被切断 | **缺陷**：答案从未存在 |

一次被截断的调用在其余每个字段里都与正常调用无法区分：它 `${calls: 1}`、有计价、有部分文本
（所以 `answerChars` 非零）。只有 provider 自己的 `finish_reason` 能把它分开。

实现三个决定：

| 决定 | 理由 |
| --- | --- |
| 计在 `UsageSnapshot.truncatedCalls`，不塞进 `LlmUsage` | `finish_reason` 与 `usage` 是同一个响应体的两个块；一条"被截断且无 usage 块"的响应必须两个事实都留下 |
| 只在 `=== 'length'` 时 +1 | 该字段在线上格式里可选，"没说"不等于"说被切断"；把缺字段当截断等于把猜测写进唯一的缺陷判据 |
| observer 转发第二个参数 | 侧级快照才是臂报的数；只让进程总数知道截断，会让每个侧读数都声称 0 截断 |

报告侧：表格里**总是**印一行（`calls the provider cut off at its output limit`），因为"没有截断"与
"这个构建不测截断"不能是同一份文档；只有真正发生时，才多印一行解读，把它命名为缺陷而非读者的失败。

## 6. 顺带发现的缺陷：最便宜的 screening 档在最后一步被拒

`ablation_runs=1` 的派发在 merge 阶段必然失败：

```text
refusing: a shard does not carry 1 `baselineCorrectByRun` bitstrings,
so its verdicts are not aligned with the repetitions the report declares.
```

根因是两侧对同一件事的约定不一致：

| 组件 | 约定 |
| --- | --- |
| `ablation.ts` | `runs > 1` 才写 `*.CorrectByRun`（1 次重复时它与镜像字段重复，而"两个必须一致的数组就是两个可能分叉的数组"） |
| `merge-ablation.mjs` | 无条件要求 `runs` 个位串 |

后果不是"少一个读数"，而是**最便宜的 screening 档不可用**：整段人群答完、付完钱、在最后一步被拒。
成本上它把每次 screening 从 1 次重复推到 2 次（翻倍），正确性上它让"先 screening 再正式"的流程
只能靠人记住不要用 1。

修法不是"改成必须写"（继续拒），也不是"1 次也写"（制造第二个表达），而是**重建**：1 次重复只有
一个可能位串，artifact 已经用布尔镜像记录了它。三条守卫同时加上：

1. 镜像缺席 → 拒绝（空位串会读成"每道题都错"）；
2. 镜像不是布尔 → 拒绝（`"1"` 被 `=== true` 读成 `false` 会把满分运行报成 0%，而文档里没有一个字说为什么）；
3. 重建出来的位串仍要通过原来的 roster 对齐检查。

并且**记录**哪些 shard 走了重建（`merged.parts[].bitstringsFrom`）——读的向量与重建的向量来自不同字段，
跨两次 merge 比较的人不该靠推断。

6 条测试（1 条绿路径 + 1 条记录 + 1 条"多重复时不记录" + 3 条拒绝），27 条 merge 测试全过。

## 7. 这一轮的教训

| 教训 | 形态 |
| --- | --- |
| "待定性"往往不需要更大的一跑，只需要一次**能把候选分开**的小跑 | 0.09 CNY 的 12 题派发否证了 A、确认了 B、排除了 C |
| 计量单位的错配会伪装成"未知" | 36 倍差额读到第三轮才定性，因为前两轮只有"计费"，没有"送达"，也没有"为什么结束" |
| 一个组件里成立的理由，在另一个组件里可能不成立 | `ablation.ts` 的"不写重复字段"是优雅的；`merge` 的"必须有"也是必要的；两者相遇时，最便宜的路径先死 |
| 守卫的价值等于它抓住的东西 | 这次是它抓住了我的派发，而不是我的派发抓住了它 |
