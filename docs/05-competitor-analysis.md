# 竞品分析：谁在同一个赛道上，以及哪些数字可以放在一起

> 本文的每一个数字都能在 `AgentiX-E/cortex` 的 `tools/competitor-ledger.json` 里找到同名条目，
> 由 `node tools/competitor-ledger.mjs` 生成表格、`--check` 校验、`--gap` 判定我们能否与之排名。
> **台账是数据，本文是读法。** 两者冲突时以台账为准，并且这条冲突本身是一条缺陷。

## 0. 一句话结论

LongMemEval-S 上公开可查的数字从 **51.8 到 94.4**，跨度 42.6 点，而这个跨度里**大部分不是系统差异**：
同一个 Zep 被三份来源读成 90.2 / 79.8 / 71.2，同一个 Mem0 自报 94.4、同 harness 读成 56.0。
所以我们**不宣称任何跨来源排名**，只做三件事：登记可比条件、在自己 harness 内比较、把可复现的对手
拉进自己的 harness 跑。

## 1. 可比性是一个六元组，不是一个数据集

两个数字可以放在一起排序，当且仅当它们在下列六项上全部一致：

```
dataset | variant | scoring | answer model | judge | harness
```

- 前两项说**问了什么**；
- 第三项说**一次预测怎样变成一个分数**——一条答案，还是 k 条里对一条就算对，还是 k 条投票；
- 中间两项说**谁答、谁判**；
- 最后一项说**谁的流水线决定了什么进入答题模型**——检索、截断、什么叫"答对"都在这里。

`harness` 必须进键，而不是从中间两项推出来：两个 harness 可以有相同的答题模型和裁判，
却在检索深度、截断策略、判正规则上完全不同。`scoring` 进键的理由是同一个理由往上提一层：
**同一个 harness 可以对同一批系统同时印出一列单答案和一列 k 中之一**，那是两个问题。

`--gap 83.0` 在 51 条台账上给出的结果是**没有可比组**，并点名 26 个并列最近的组**差的是同一组字段**：

```
83 has no comparable group.
  26 group(s) are equally near, none shares all six fields, and every one differs in the same
  3 field(s): answerModel, harness, judge.
```

这个"没有"就是诚实答案；换成"83.0 排第二"就是把 harness 的事实读成系统的事实。

### 1.1 `scoring` 是第五个字段缺的那一项，它的证据是一次 1.4 分之差

Supermemory 在 2026 年 3 月公布过两个数，同一篇博客、同一批 500 题、同一批阅读器与搜索代理：

| | 配置 A | 配置 B |
|---|---|---|
| 分数 | **98.6** | **97.2** |
| dataset / variant | LongMemEval / S | 同左 |
| 答题模型 | 同左 | 同左 |
| 裁判 | 同左 | 同左 |
| harness | 同左（同一团队、同一篇发布） | 同左 |
| **分数怎么来的** | **8 个专门化提示变体各答一次，任一对即算对** | **12 个变体投票归并成一条答案** |

六个字段里前五个完全相同，两个数字却差 1.4 点。把它们排序，排的是"给八次机会能到多少"对
"给十二次机会归并成一条能到多少"，读出来的却会像是系统差异。

**这正是最危险的一类行**：五元组的设计原则一直是"宁可把可比的表拆开，不可把不可比的表合并"，
而这一行错在相反方向——**两个数字可以在五项上全同却仍不可比**，也就是说五元组不只是粗，
它是**不完备的**，而不完备恰好在两个数字看起来最接近时隐身。真正差得远的行（7B 阅读器 38.2
对前沿模型 95.8）从来不在危险里，因为答题模型那一项早已把它们分开。

中文报道在 2026 年 3 月传过的"99% 刷爆 SOTA"就是这一行的 98.6 四舍五入，同时有三件事成立：
①它是"八中之一"而不是准确率；②厂商在同一篇里说明这**不是**他们的生产引擎，生产引擎是本台账
已登记的 84.6（`supermemory-published/gpt5`）；③至少一份转述把这次发布描述为**戏仿**——
针对"记忆基准能被做成什么样"。三条都不是删掉这一行的理由，都是这一行必须带 `scoring`、`kind`
和 `note` 的理由。台账不裁决厂商是否在开玩笑，它只保证：**不管对方发布了什么，都不能被顺手和
我们的数字排在一起。**

### 1.2 这个告诫本来就在文档里，只是文档管不了它

`cortex/docs/SOTA-LANDSCAPE.md` §2 的 Supermemory 行一直挂着这句注：

> advertised ~99% is an 8-variant ensemble

也就是说这件事**早就知道、写得对、而且写在册**。它**做不到**的是任何事：不能被检查、不能被印在
分组旁边、拦不住 `--gap` 把这一行报成"近"，更不能在下一行忘了写时被发现。这就是**告诫**与
**条件**的区别，也是这一轮以改 schema 而不是补一段话收尾的原因。

一般形式：**只活在一份文档里、而不活在消费这个数字的产物里的限定条件，会在第二个消费者那里丢失。**
本仓已经撞过四次同一形状——覆盖率注解 gate 看不见、`wired` 标志消融跑器从不读、总体没人事先点名、
现在是评分规则。四次的修法都是把限定条件搬进**做决定的那件东西**里。

加字段只有在字段有活干时才值得，所以同一轮把让它有活干的行也加了：

| 系统 | 分数 | scoring | 登记它的用途 |

| PlugMem | 90.2 | `single` | 台账里**代码可获取**的最高分（Apache-2.0，arXiv:2603.03296），唯一能被换成一次测量而不只是引用的竞品数 |
| MEMTIER | 38.2 | `single` | 唯一的 7B 阅读器行，让 57 点的阅读器效应留在同一张表里可见 |

- **MemCog 的表是拼的，只有它自己那一行是现测的。** 论文写明 baseline 行来自 Latimer et al. (2025)
  与 Sen et al. (2026)，不是重跑。于是它印的"95.80 对 Mastra 85.71"不是配对差——Mastra 自报

  这是 §3 那个模式第三次被独立确认，也是第一次拼装在论文里被写明而不是被推断。
- **PlugMem 复刻的是一个写入路径主张，而这正是本仓最近六十步在做的事。** 它的机制是**在摄入时**
  把命题（关于世界的事实）与处方（关于行为的指令）分开，再按高层概念与意图路由检索，最后把召回
  单元压成一句任务指令。前一半就是这个臂反复没能否掉的零假设：**记忆系统写什么比怎么排序更重要**。
  PlugMem 是那个主张带着代码站在 90.2 的地方。

### 1.4 换模型这一轴上的竞品与文献：一个控制实验、一个网关机制、一份八态 taxonomy

前三节讲的是「谁的分数高」。这一节讲的是另一条轴，而它此前完全没有出现在本文件里：**用户把
cortex 接到自己的模型上之后，会发生什么**。这一轴上的对手不是记忆系统，是网关与测量框架。

#### 一、唯一一份控制实验（arXiv:2609.05339）

**Goyal & Ray, *Does Your Agent's Memory Survive a Model Upgrade? A Controlled Study of Memory
Portability*, 2026-09-04, 18 页, under review, cs.AI / cs.CL / cs.IR。** 同一段历史四种存法，48 段
合成历史 + 随机答案码（所以预训练里答不出来）、每题 160 问、**精确打分，全程不引入 LLM judge**、
两个 <10B 开源模型、**双向**换模型：

| 存法 | 换 writer 后 | 备注 |
| --- | --- | --- |
| LC-RAW（逐字长上下文） | 基线 | 与本 arm 同形：原始轮次，无存储 |
| KG-fixed（固定 schema 图） | **+0.0004 ± 0.0020** | 不确定度是效应的五倍，即「没测到位移」 |
| NOTES（模型压缩笔记） | **+9.91 / −13.28**，按方向 | 多数 agent 框架的默认存法 |
| RAG 全量重嵌 | 可得 **+11.90** | |
| RAG 50/50 混合索引 | **+4.96** | 放弃大部分收益，而**每次调用都成功** |

诊断分解同样是可借用的方法：NOTES 的亏空 **80%（0.467±0.014 / 0.584±0.013）发生在写入阶段**，
RAG 的亏空 **81%（0.364±0.012 / 0.450±0.012）发生在检索阶段**——同一个症状，两个不同的产地。
修复侧：**只靠存储修复在 48 个用例里全部达不到 90% 恢复目标**；保留原始历史后，一个方向上
48 例恢复 34 例。

对本产品的三条直接结论写在 §7.0 / 白皮书 §6.1.7.6：**方向是主导变量而我们方向盲**；
**embedding 是比 reader 更硬的锁定**；**保留原始历史这条我们已经满足**（artifact 保留 `turns`）。

#### 二、唯一一个把「降级」做成产品的对手：LiteLLM health-check routing

它不是记忆系统，但它是 `DegradationGuard` 最近的一个已上线同类机制：后台循环探活、失败节点移出
路由池、`allowed_fails_policy` 按错误类计数、`health_check_ignore_transient_errors` 忽略 429/408，
**冷却到期自动放回**。差异就是本设计的全部立足点：

| | LiteLLM | `DegradationGuard` |
| --- | --- | --- |
| 观测对象 | 存活（401/404/5xx、超时、`max_tokens=1` 完形） | 合规（空答案、回声、无法识别的弃权） |
| 能得出的结论 | 这个端点挂了 | 这个 reader 产不出解析器要读的东西 |
| 恢复 | 冷却后自动 | **按构造没有** |
| 粒度 | deployment | reader（按路由） |

它的双向恢复对它要回答的问题是对的；本设计要回答的是另一个问题，而**四个信号里没有一个能说出
「这个 reader 的输出又变得可读了」**，所以自动回升会是「对着正在修的信号做优化」。

#### 三、唯一一份把「静默失败」列全的 taxonomy：Datasumi 的八态

`valid` / `schema_invalid` / `malformed_json` / `provider_refusal` / `content_filtered` /
`truncated` / `tool_call_instead_of_result` / `timeout`。它的核心论断与本项目独立得到的结论一致：

> **一个把所有情况都转成 HTTP 200 加一个空对象的网关，把它们藏起来不给所有人看，包括它的运营者。**
> Compatibility proxy 换来的是「纸面上的可移植性，回归由客户发现」。

对照本设计的四个信号，八态里的映射是：`provider_refusal` / `content_filtered` → `parse-failed`；
`timeout` → `deadline-exceeded`；`schema_invalid` / `malformed_json` → `parse-failed`；
`tool_call_instead_of_result` 不适用（本 arm 无工具）。**真正缺的是 `truncated`**，而它恰恰是最
容易静默扣分的一态：在输出上限被截断、但前段已经有可解析答案的回复，会被当成一个正常答案计分。

#### 四、judge 的可靠性文献，是任何「通过 judge 测出来的换模型效应」的上界

- 同输入成对判定翻转率 **11–14%**，六家 judge、三家 provider、29 个任务，**跨代未改善**
  （Yagubyan，GroundLM 2026）；约需 **11 次重复**才能稳定一个判定。
- 预注册审计 52,988 次请求：同窗口 Spearman **0.400**（门槛 0.90），次日逐字节重放 0.78（门槛
  0.99），**四家 provider 中位 0.74–0.88，无一家达到 0.99**；换 provider 不修复。
- 21 家 judge、约 541,000 次判定：test–retest >0.95 与位置偏置 >0.10 **同时存在**（「一致地错」）；
  exact match 与 Cohen's κ 之间 **33–41 pp** 的虚高。

cortex 的第一档打分是**精确匹配**而不是 judge，同 prompt 翻转 **4.8%**（§13.194.4），比上述数字
好一个量级——这正是该项研究把 judge 完全排除在外的同一个设计选择。**但第二档是 judge，而任何
通过第二档读出的换模型效应都继承那 11–14%。**

#### 五、这一节对竞争定位的影响

**零。** 它不改变任何对外数字，也不改变「我们不是 SOTA」这个判断。它改变的是**锁定叙事**：在
「换模型后还能用」这条轴上，行业里能被引用的证据只有上面这些，而**没有一家记忆系统公布过自己的
换模型可移植性**——它们公布的是 LoCoMo / LongMemEval 的分数。这是本项目可以做第一的地方，而且
它恰好是用户提的四条要求里最难的那条。

### 1.5 同一个阈值，能恢复时安全，锁存时有害——而竞品全都落在能恢复那一侧

§1.4 把 LiteLLM 当成最近邻。这一轮量出一件更要紧的事：**两家的阈值看起来是同一个数，风险却不在
一个量级，差别只有一条——恢复。** LiteLLM 的 `allowed_fails_policy` 计满即把节点移出路由池，
**冷却到期自动放回**；`DegradationGuard` 降档后没有任何方法回去。于是同一个「N 次失败」的规则，
在前者是「换个节点，一分钟后再试」，在后者是「这个部署从此改用更小的上下文预算」。

把这件事算出来，是本轮最有价值的一个数字。设每窗触发概率为 `p`、一次评测跑 25 个窗口（500 题）：

| 每窗触发率 | 单窗即锁存 | 要求连续两窗 | 差额 |
| --- | --- | --- | --- |
| 5.0%（设计容差） | **72.26%** | **5.58%** | 13.0× |
| 13.0%（实测离散度） | 96.92% | 30.80% | 3.1× |
| 30.0% | 99.99% | 84.17% | 1.2× |
| 95.0%（每call都失败） | 100.00% | 100.00% | 1.0× |

**一个按 5% 每窗校准、一次动作即永久的闸门，会在一次评测里误伤 72% 的正常部署。** 竞品没有踩到
这个坑，不是因为它们的统计学更好，而是因为**它们的动作可撤销，于是误报的价格是分钟级的**。
可撤销把「假警报」从产品事故降级成运维噪声，所以它们可以只数次数。

这一条改写了本节的定位叙事：**「我们的守门器更严格」不是卖点，「我们知道锁存让阈值不能是同一个
数」才是。** 有恢复的动作只需校准检出延迟；无恢复的动作还必须校准**累计**误报，而累计误报是
`1 - (1 - p)^n`，随部署时长单调上升，任何「每窗 5%」的说法都盖不住它。

补救办法不是把阈值调高（那会同时废掉检出），而是**要求持久化**：一窗触发只是上膛，连续两窗才
动作。代价精确到可报价——每个真坏掉的 reader 多花 20 次调用（40 而非 20），而每 call 都失败的
reader 在 25 窗内的检出概率仍是 **100%**。这条改动落在 `GUARD_PERSISTENCE = 2`。

文献侧借的是 SPC，不是竞品：控制图用**平均运行长度**（ARL = `1 / p`）标定，而定义它的每一份材料
都同时警告运行长度分布高度右偏、只看 ARL 会误导。`1 / p = 20` 窗读起来像「每 20 窗一次」，实际是
「活过 20 窗的概率 27.7%」。**锁存型报警是引用 ARL 不只是不精确、而是方向反了的那一类。**


### 1.6 同一个 benchmark，5 分钟和 4 小时测的不是同一个量

本轮的问题是一个运行跑了四个多小时是否正常。查竞品时撞见一件更要紧的事：**在同一个
LongMemEval 上，公开数字的墙钟从 5 分钟到"数小时"都有，而那不是一个工程水平差，是三个不同
的测量。**

| 来源 | 墙钟 | LLM 调用 | 指标 |
| --- | --- | --- | --- |
| MemPalace（ChromaDB raw） | **约 5 分钟** | **0** | Recall@5 **96.6%** |
| Awareness Memory（daemon 路径） | **35 分钟** | **0** | Recall@5 **96.0%**（4.2 s/题） |
| Haki 公开 harness | "**several hours** and a few USD" | 500 × ~40 次抽取 + 作答 + judge | QA 准确率 |
| 本仓 | **300–335 分钟** | 4000 次 reader + judge | QA 准确率 **89.80%** |

前两行是**检索召回**：把 500 题的 haystack 建成索引，看标注会话有没有进 top-5，**一次 LLM 都
不调用**，所以 4.2 秒一题是必然的。后两行是**端到端问答**：检索 + 组 prompt + reader 作答 +
判分，每题 1.76–5.02 秒×8（2 arms × 4 repetitions）。

**所以 96.6% 与 89.80% 之间那 6.8 点不是能力差，是任务差**，把它们并排放进一张没有口径列的
表，是这一节存在的原因。Awareness 自己的榜已经标了这句警告——"MemPalace 96.6% is Recall@5 only,
not QA Accuracy"——说明这个混淆在公开榜上是真实发生的，不是假想。

三条结论：

1. **4 小时是端到端评测的正常量级，不是我们的缺陷。** Haki 公开 harness 对同一数据集的措辞是
   "expect several hours"，且明确把那当作预期而非异常。我们 306–335 分钟的差别来自 repetitions
   （4 次，用于区分处理效应与采样噪声），而 Haki 单次作答。**四倍重复换来的是"差异是处理的还是
   采样的"这个问题的答案**，这个问题上公开榜大多数数字根本没回答。
2. **快，靠的是不调用 LLM。** 任何把墙钟压到分钟级的方案，压掉的都是 reader 调用——也就是被测
   对象本身。这不是优化，是换题。
3. **对标时必须写口径。** 我们对外报 89.80% 是 QA 准确率（`41284575092`，四次 89.40–90.40%）；
   按同一口径的 SOTA 是 agentmemory V4 的 96.20%（481/500，Claude Opus 4.6 作答、GPT-4o 判分、
   seed 42），差 **6.40 pt**。同一口径下我们 **领先 Raw-RAG 的 87.5% 2.30 pt、领先 memoricai 的
   85.8% 4.00 pt**——这两家此前都在本仓所有历史产物之前。Recall@5 的 96.6% 不与任何 QA 数字可比。

### 1.7 工程侧的两条可直接抄的做法

**一，`num_concurrent` 的默认值是 1。** lm-evaluation-harness 的 API 后端把并发做成了显式参数，
**默认串行**，文档推荐 2–4（理由是避免触发限流）。本仓的评测循环同样串行——**这不是落后，是这一类
harness 的常态**，因为瓶颈在 provider 的往返而不在本地算力。差别在于它们有一个我们没有的东西：
`--use_cache`（SQLite 响应缓存），崩溃重跑不必重新付费。

**这一条我们不该抄，而且理由要写下来。** 在 `temperature: 0` 下缓存第二个 repetition 的响应会
让 artifact **无法区分"确定性 reader"与"重放"**——而四次重复存在的唯一目的就是回答这个问题
（run `40722772896` 的四个总分是 407 / 414.5 / 414.5 / 423，不是同一个数）。缓存在这里是
**改变被测对象的变更**，不是性能开关，需要注册而不是提交。

**二，数据集按内容钉住。** Haki 的 harness 在每次运行前校验 sha256，文件不同就**拒绝运行**。本仓
的 workflow 下载 `resolve/main`——一个**可变指针**，且不做任何校验。上游改一个字节，同名的两次
运行就是两个总体，而 artifact 不会说。**本轮修了一半**：artifact 现在带
`datasetFingerprint`（`sha256:<hex>`，渲染在数据集名正下方），所以两次运行能不能比是**可查的**，
不依赖任何人事先记过哈希。**另一半没修**，而且不能从这里修——拒绝需要在文件上取到期望值，环境里
没有该文件，现在写任何摘要都是猜。代价必须说清：**已归档的十七份产物（含 89.80% 那份 headline）
永远不会有摘要**，所以本仓任何数字都无法回溯到产生它的那个文件；能力只从下一次派发开始。


### 1.8 一个 94.6% 的公开高位，以及它为什么不能照抄

本轮挖到三份对本项目**直接可用**的一手材料，它们指向同一个结论：**我们和高位系统的瓶颈不在同一处。**

先校正一处口径，否则下面三行会被读成"新 SOTA"：**SOTA 仍是 agentmemory V4 的 96.20%**（单次确定性运行、
Claude Opus 4.6 作答、GPT-4o 判分，§2 表里的 C 级），Mastra OM 在 GPT-5-mini 读数下是 94.9%。下面这个
RemLabs 的 94.6% 与 Hindsight 的厂商自报 94.6% 同档，**都不构成新 SOTA**；它之所以值得单列，是因为它是
公开材料里**唯一同时给出五个分项**的读数，而分项才是能和我们逐项对表的东西。

| 来源 | 公开读数 | 分项 | 它自己的失败归因 |
| --- | --- | --- | --- |
| RemLabs（2026） | **94.6%（473/500）** | SSU 100 / SSA 100 / SSP 93.33 / KU 100 / TR 92.48 / **MS 88.72** | "the vast majority are retrieval failures" |
| Reverie（2026，论文） | — | 27 道错 | TR 10 道（fragment gaps）、**MS 12 道**（"items described with different vocabulary"） |
| 本站 `41284575092` | 89.80%（449/500） | IE 95.7 / ABS 100 / **MR 77.5** / **TR 94.1** / KU 86.5 | **枚举**：22 道稳定错里 22 道的答案等于它自己 Step 1 的行数 |

三件事值得单独记下来：

**一，我们的 TR 已经高于 RemLabs（94.1 对 92.48），而 MR 低 11.2 点。** 所以"整体差 4.8 点"不是一
个均匀差距，是**两个方向相反的差距**：TR 我们领先，MR 我们落后。任何"整体提 5 点"的计划都必须先说
清它改的是哪一边，否则就是把 TR 的优势和 MR 的劣势当成一个数。

按同一口径，我们与各家整体的差是：**agentmemory V4 96.20% 差 6.40 pt**、Mastra（GPT-5-mini）94.9%
差 5.1 pt、RemLabs 94.6% 差 4.8 pt；领先 Raw-RAG 87.5%（+2.30）与 memoricai 85.8%（+4.00）。
**不是 SOTA**，SOTA 竞品是 **agentmemory V4**。

（分项一律取 `41284575092` 四次重复的平均：MR 93.75/121、TR 119.5/127、IE 143.5/150、KU 62.25/72。
单次运行的 MR 是 93/121 = 76.9%，与平均差 1 题——本文件其余各节引用单次读数时会写明是哪一次。）

**二，他们的失败是检索，我们的失败不是。** RemLabs 说"27 道错里绝大多数是检索失败——信息在库里但
没被翻出来"。本轮的读数是**相反的**：MR 的 22 道稳定错里 **18 道的 gold 数字就在送进去的窗口里**
（`AUDIT-MR-ENUMERATION.md` §3）。同一份 benchmark、同一个分项、同一类问题，两边的瓶颈在不同层。

**⇒ 所以他们的解法不能照抄。** 他们推的是"加检索路径、加 rerank、加实体图"，而在我们的读数上，那
三者对准的是**已经填满的那一格**。

**三，Reverie 论文里有一句反例，正好给这条推论做了独立验证。** 原文：*"We tested several retrieval
augmentations (session expansion, temporal range retrieval, pre-computed date arithmetic, entity graph
traversal for counting queries) that **uniformly degraded performance**, consistent with context
pollution."* 另一份公开的 LoCoMo 复现记录给了同方向的两个数：为 "how many" 放宽检索把 43 道计数题
的 F1 从 **43.3% 压到 38.0%**，还把一道正确的弃权翻成了自信的错答。

**这两条与我们的 18/22 是同一件事的三种测法。** 检索已经不是瓶颈时，继续加检索只会加污染。

> **给我们的直接结论**：MR 的下一步不是"找得更多"，而是"从已经找到的东西里数得更准"。这也解释了
> 为什么 thinking 在 TR 上 **+22**、在 MR 上只有 **+1**——它帮的是"逐次取针"，不是"对着一份长清单
> 数到底"。

另有一条机制层面的文献值得引用：arXiv `2609.38958`（2026-09-30）用 NIAH 计数任务证明，reasoning
模型的计数优势来自**在思考轨迹里逐条枚举**（targeted retrieval），而非一次性广泛注意；把它轨迹里
的表示清空，精确计数准确率从 **97% 掉到 1%**，而清空 prompt 里的记录反而没有影响。**枚举不是脚手
架，是机制本身**——这条支持我们继续在"枚举"这一层做增量，而不是回到检索层。

## 3. 一个系统能被读成多少种分数

`node tools/competitor-ledger.mjs --spread` 的原样输出：

```
Mem0            LongMemEval  spread 45.4  (49 .. 94.4)
Zep / Graphiti  LoCoMo      spread 30.9  (63.83 .. 94.7)
Zep / Graphiti  LongMemEval  spread 19.0  (71.2 .. 90.2)
Supermemory     LongMemEval  spread 18.5  (66.07 .. 84.6)
full context    LongMemEval  spread  2.0  (60.2 .. 62.2)
```

注意 Zep 出现两行：它在两个数据集上各有自己的跨度，而 `LongMemEval` 的 19.0 是本节表格里要读的那个数
（LoCoMo 的 30.9 对应 §2 备注里那条「同 harness 低 30.9 点」）。**同一个系统在不同数据集上跨度不同，这本身就是 §8 要求第二个数据集的理由之一。**

| 系统 | 读数（同一数据集 LongMemEval-S） | harness 数 | 跨度 |
|---|---|---|---|
| Mem0 | 94.4 / 93.4 / 56.0 / 49.0 | 4 | **45.4** |
| Zep | 90.2 / 79.8 / 71.2 | 3 | **19.0** |
| Supermemory | 84.6 / 66.07 | 2 | **18.5** |
| full context（无记忆） | 62.2 / 60.2 | 2 | 2.0 |

Mem0 一行是四个读数，因为它有**两种口径 × 两种部署**：自报（94.4 自托管配置、93.4 新版）与
复现（56.0 托管服务、49.0 开源自托管）。把这四个数平均成"Mem0 是 73.6 分"没有任何含义——
**这不是同一件事的四个测量，这是四件不同的事**。台账把它们放在同一个 `system` 下是为了算出这个
45.4，而 `deployment` 字段是为了记住它们不是一件事。

最后一行是让前几行可读的东西：**`full context` 只有 2.0 点**，而它是一个完全没有记忆机制的系统
——整份 haystack 塞进 prompt。这是**效应量的地板**：任何记忆系统的跨度都应该对着 2.0 读，而不是对着 0 读。
Mem0 的 45.4 是地板的 22 倍，Zep 的 19.0 是 9.5 倍。

工具还区分另一种跨度，本表暂时没有实例但规则要在：**同一个 harness 下的两个读数是一个版本差异，
不是 harness 效应**（`version difference, not a harness effect`），并且这类行会被排在跨 harness 的行
**之后**——因为读者会把第一行当成最大的发现，而版本差异不是本文在说的事。

二十六道里有八道读了；七道是**枚举差一个成员**（五道少一、两道多一），一道是单位聚合错。

这个诊断在 `§13.96` 就写下过，当时三次提示词侧尝试都没能推动它，于是把力气转向了窗口机制。
窗口机制现在结案（ceiling = 2 道，`§13.161.8`）。而 MR 这边是 **20 道净差，且这 20 道已经
被本仓自己的组件答对过**——同样的 haystack、同样的读者、同样的裁判。

**这是本臂迄今最大的机会，且不需要发明任何新东西**：需要找的是参照做了而记忆臂没做的那件事。

## 9. 检验方法与验收标准

| 项 | 检验方法 | 验收标准 |
|---|---|---|
| 台账完整性 | `node tools/competitor-ledger.mjs --check` | 每条有 `source`；同 harness 组内答题模型与裁判唯一；`harness` 类至少覆盖 3 个系统 |
| 可比性判定 | `--gap <score>` | 同组才给名次；无同组时列出**所有**并列最近组及差字段，且**不打印名次** |
| 我们 vs 竞品（同 harness） | `competitor-retrieval.yml` 的 `sut=` 臂，`infer` 开关入产物 | 两臂同回答模型、同裁判、同 roster；报告必须打印 `infer` 值 |
| MR 缺口诊断 | 对 26 道逐条分类（差一/单位/弃答/其他），四类计数之和 = 26 | 主导类命名一个机制；该机制的登记写在这份普查**之后** |
| MR 修复 | 重派后看 discordant 对 | ≥10 道移出"仅参照对"，"仅我方对"增长 ≤2；总分 +1.5 pt 以上；其他能力掉 ≤2 道 |
| token 轴 | 产物已带 `promptChars` 与 `evidenceTurns` | 报告必须给均值与 p95；不得只给"预算上限内" |
| 延迟轴 | 待建（本轮未做） | 未建前不得在任何对比中使用延迟一词 |

## 10. 这份文档本身的可证伪点

**第二，"换模型值多少分"这件事，只有两家敢给数。** 这正是我们此前缺的那块外部先验。

### 1.9.3 这个先验对我们意味着什么，以及我们怎么用

本轮之前，`PREREGISTRATION` §13.211.3 对这个增量写下的预测是 **MR +8 / TR +4**，依据是 MR 丢分的形状
（22 道稳定错题的答案全等于它自己 Step 1 的行数）。找到上面两组数据之后，这个数字**在任何公开实测
里都找不到支撑**，因此本轮在开跑**之前**把它改注册为 **MR/TR +1 到 +3**，并把原数字原样留在文档里。
理由很简单：**在看到数据之前改预测是科学，在看到数据之后改预测是另一件事**，两者必须能被读者区分。

更重要的是，这次改注册把一个"押方向"的实验变成了一个"**分诊**"的实验：

| MR 变化 | 读作 | 下一个增量 |
| --- | --- | --- |
| **≥ +4** | reader 是这个窗口下的真约束，契约在饱和它 | 让契约随 reader 档次切换（`model-portability.ts` 已经在分桶），比较单位从"reader"变成"(reader, 契约)" |
| **±4 内** | reader 不是约束，损失在**清单**里 | P2 的引文级 grounded 枚举 |
| **≤ −4** | 第二个 reader 在这个任务上更差 | 这是关于 LoCoMo 的 MR 形状（28/28 错题都是数值 gold，是算术题不是召回题）的发现，不是一次失败的派发 |

三条路都通向下一件具体的事，**没有一条是"再跑一次"**。这就是我们与 §1.9.1 那五家的方法论差别：他们
公布一个数，我们公布一个数**和它证伪自己的条件**。

### 1.9.4 不能从这张表推出来的东西

必须写清楚，否则 §1.9.2 会被当成背书：

- **mem0 换的是抽取模型，我们换的是 reader。** 抽取决定"记住了什么"，reader 决定"从记住的东西里怎么
  答"。同一条 1.2 点宽的前沿带**不能**直接搬到 reader 上——它只说明"同档模型互换的效应量级是 1–3 点"，
  这是**量级先验**，不是点预测。
- **分数不可直接相减。** mem0 的 92.5% 是 LoCoMo 1,540 题、自家判分；我们的 89.80% 是 LongMemEval 500
  题、`exactMatchScorer` + 弃权感知口径。89.80 与 92.5 之间的 2.7 点**不是差距**，是同名不同物。
- **Roampal 的 85.8% 是修正版 LoCoMo 的非对抗子集**，与原始 LoCoMo 也不可比。

真正可以相减的只有同一数据集、同一判分器、同一 harness 下的两次运行——这正是 `datasetFingerprint`
（§13.210）和 `reader=` 行（§13.212）存在的理由：**让"可相减"成为一个可检查的属性，而不是一句承诺**。

## 1.10 每答一题花多少 token：一张我们自己最难看、也最有用的一张表

**结论先给：** 在最弱的能力（多会话推理 MR）上，我们自己的**简单管线用 1,330 token 打赢了我们 14,106 token 的
记忆臂，领先 8.2 个点。** 这不是"证据不够"，是"证据没有排序"。

### 1.10.1 同一份产物里的两条臂，同一个模型，同一个判分器

`41284575092` 的 `usageBySide` 把两条臂分开记账，这是一张此前没有任何竞品表能提供的对照——**同一进程、同一
reader、同一 500 题、同一判分器，只有管线不同**：

| 臂 | prompt token / 题 | 完成 token / 题 | 缓存命中 | 总名册 | MR |
| --- | --- | --- | --- | --- | --- |
| `reference-pipeline`（简单检索 + 小窗口） | **1,330** | 39 | 81.7% | — | **85.1%**（103/121） |
| `cortex-memory`（48,000 字符窗口，会话边界） | **14,106** | 1,144 | 90.2% | **89.80%** | 76.9%（93/121） |
| `cortex-memory`（96,000 字符） | 23,700 | 1,182 | 90.8% | 90.45% | 80.2%（97/121） |

读法有三层，缺一层就会得出错误结论：

1. **总体我们赢**（89.80% 对基线在很多能力上接近 0，见 §1.10.3），**MR 我们输**，而且是 10 道题、10.6 倍 token。
2. **加预算能补一点**（MR 93 → 97），但要 1.7 倍 token——这就是本轮拒绝 96,000 的全部算术。
3. **简单臂的 1,330 token 里没有任何"记忆结构"**：它不画会话边界、不做多步枚举。它赢在**窗口小、每一条都
   与问题相关**。

### 1.10.2 和竞品的 token 账放在一起

口径必须先说清楚：**数据集不同、判分器不同，分数不可直接相减**；token 数才是可比的量级，而且各家都公布了它。

| 系统 | 数据集 | 分数 | prompt token / 查询 |
| --- | --- | --- | --- |
| **Cortex（记忆臂 48k）** | LongMemEval-S 500 | **89.80%** | **14,106** |
| Cortex（记忆臂 96k） | LongMemEval-S 500 | 90.45% | 23,700 |
| **Cortex（自家简单臂）** | LongMemEval-S 500 | MR 85.1% | **1,330** |
| Mem0（2026-10 BYOK） | LoCoMo 1,540 | 92.5% | 6,956 |
| Memori | LoCoMo | 81.95% | **1,294** |
| Mastra（Observational Memory，gpt-5-mini） | LongMemEval | **94.87%** | 未公布 |

三个可以直接下的判断：

- **我们的 token 成本是 Mem0 的 2.0 倍、Memori 的 10.9 倍**，而 Mem0 的分数比我们高 2.7 点（不同数据集，
  但方向上不利）。所以"用更多上下文换准确率"这条路，我们已经走到收益递减区。
- **Memori 用 1,294 token 拿到 81.95%**，和我们自家 1,330 token 的简单臂是同一个量级——**这一档是"便宜"的
  真实水位**，而不是我们 14,106 token 才该到的地方。
- **Mastra 94.87% 没有公布 token 数**，所以"它是不是靠更长的上下文"这个问题，现在无法回答；这正是 §1.9.1
  那张"谁点名了模型/谁公布了成本"的表要追踪的第三列。

### 1.10.3 为什么这张表比分数表更有用

因为它把下一个增量的**形状**定死了：

- 如果 MR 的缺口是"证据不足"，加预算应该线性地补——实测 48k→96k 只补 4 道题（且均值在噪声带内）；
- 如果缺口是"证据太多、排序不对"，那么**同样的 token 成本下把该有的那条排上去**就能补——而房间里此刻
  **85.3% 的已送达轮次与问题零实词重合，占 65.5% 的字符**。

第一条已经被本轮否掉，第二条因此成为唯一还有依据的方向，登记为 `PREREGISTRATION` §13.213.7，判据是
**在 48,000 的 token 成本不变的前提下恢复那四道题中的至少三道**。

> **这个判据在下一轮被部分否掉（§13.214）。** "同样的 token 把该有的那条排上去"预设那条**在**排序池里、
> 只是排得靠后。`10d9b85a` 的两条决定性金标 `goldRanks = -1`——它们不在池里，重排构造上够不着。方向没有错，
> 但机制换了：该修的是**同一段会话内选哪 167 轮**，不是给 256 宽的池子重新排序。§1.11 给出这条修正的算术。

### 1.10.4 不能从这张表推出来的东西

- **不能推出"应该退回简单管线"**：它在 IE 上只有 2/150、KU 上 0/72，总体是 0 分边缘。它的 MR 优势来自窗口小，
  而不是来自管线更聪明；把它的窗口放大到 175 轮，MR 会不会掉，没人测过。
- **不能推出"我们的 token 花得冤枉"**：14,106 里有 90.2% 是缓存命中，实际计费按 DeepSeek 的缓存价只有名义值
  的约三成；把它和 Mem0 的 6,956 直接按价格比会高估 2 倍以上。
- **不能跨数据集比分数**：89.80 是 LongMemEval-S 500 题、`exactMatchScorer` + 弃权感知；92.5 是 LoCoMo 1,540
  题、Mem0 自家判分。两者之间没有可减的量。

### 1.11 加预算买到的三分之一，是排序没提供的证据

§1.10 的结论是"用更多上下文换准确率已经走到收益递减区"。本轮把这句话量化成了两条可以引用的读数，它们来自
**修正后的**金标账（`--pool` 的合计此前算错，见 §13.214：48,000 被切掉的是 **707** 而不是 654，从池外送进来的
是 **53** 而不是 0；96,000 是 **296** 与 **185**）。

| 量 | 48,000 | 96,000 | 变化 |
| --- | --- | --- | --- |
| 金标轮次 | 7,516 | 7,516 | — |
| **排序从未浮出** | **361** | **361** | **0** |
| 被预算切掉 | 707 | 296 | −411 |
| 从池外送进来 | 53 | 185 | +132 |
| 已送达 | 6,501 | 7,044 | +543 |

**第一条：排序的触达在两次运行里都是 361，一位不差。** 把预算翻倍，排序浮出的东西一个没变，变的只是 prompt
装得下多少。所以"再加一倍上下文"这条路径，本质是**分配**而不是**信号**——它不可能改善我们与 SOTA 之间那个
6.40 点的差，因为那个差是"该有的证据有没有被找到并排在前面"，不是"房间有多大"。

**第二条：多给的房间买到的 543 条金标里，132 条（24.3%）来自排序池之外。** 也就是四次里有一次，房间捞到的是
排序**没找到**的东西。这一点对竞品比较有一个直接含义：**任何"纯检索 + 重排"的系统，在同样的预算下也捞不到
那 132 条**——不是因为它们实现得差，而是因为它们的窗口与候选池是同一个集合。我们能做到，是因为会话选择与
排序池是两个不同的宇宙（`--pool` 的 "beyond the pool" 列就是这件事的度量）。

反过来看，这也是我们比竞品贵的原因之一：**已送达的证据里有 2.6%（185/7,044）落在排序之外**，48,000 下是
0.8%（53/6,501）。把这些砍掉会省钱，也会把那一档分数砍掉——所以正确的做法不是砍，而是**让排序覆盖到它**，
这正是 §1.10.3 那条修正后的方向。

一个必须留着的边界：**24.3% 是"多给房间买到的"里面的比例，不是我们总证据里的比例**。后者是 185/7,044 = 2.6%。
把前者当成后者，会把"排序的缺口"高估近十倍——这也正是这一节存在的原因：同一份产物，两种口径，差一个数量级。

### 1.12 我们有"池"和"房间"两层，竞品通常只有一层——而这一轮发现瓶颈在池

§1.11 把"多给的房间买到三分之一池外证据"写成了我们的结构特点。这一轮把它拆得更细，因为它对竞品比较有一个
直接后果：**同一个"k 太小"的症状，在两层结构和一层结构里意味着完全不同的东西。**

#### 两层与一层

我们的检索链是两段：

```text
语料 ──(embedding, top-k)──▶ 池（relevanceTopK = 256） ──(按分数取前缀, 字符预算)──▶ 窗口（48,000 字符 ≈ 167 轮）
```

竞品的链通常是一段：`retrieve top-k ──▶ prompt`，k = 5…20，检索结果全部进窗口。Raw-RAG 的公开配置是
`k = 15`、256/32-token 窗口；Mem0 一类系统的 `top_k` 默认同量级。

一层结构里，"k 太小"和"窗口太小"是**同一个问题**，因为 k 就是窗口。两层结构里它们是**两个问题**，而且可以
分别失败：

| 失败 | 表现 | 修法 |
| --- | --- | --- |
| 池窄 | 金标从未进入候选，`goldRanks` 里是 `-1` | 提高 `relevanceTopK` |
| 窗口小 | 金标在池里但排在前缀之外 | 提高 `maxPromptChars` |

#### 这一轮的读数说瓶颈在池，不在窗口

`10d9b85a` 在 48,000 下的四元组：`total 11 / pool 9 / carried 9`。**池内九条全部送达**——窗口一条没切。
96,000 多买的两条是 `goldRanks = -1`，即**排在第 256 名之外**，靠装完所有打过分轮次之后的剩余房间才捎上。

而 96,000 那个更宽的房间也确实在买别的东西：§13.214.2 的 543 条金标增量里，**132 条（24.3%）来自池外**。
两个读数指向同一件事——**我们的窗口已经比池更宽，所以"加房间"买到的越来越是池外证据，而不是池内更好的
排序。**

同类系统的对照：

| 系统 | 池宽 | 窗口 | 谁更宽 |
| --- | --- | --- | --- |
| 我们（`41284575092`） | `relevanceTopK` 256 | ≈167 轮 / 48,000 字符 | **池更宽**（256 > 167） |
| 我们（96,000 那一侧） | 256 | ≈232 轮 | **窗口更宽**（232 ≈ 池） |
| Raw-RAG（公开配置） | `k = 15` | 256/32-token 窗口 | 同一个集合 |
| Mem0 一类 `top_k` 默认 | 5…20 | 全部入窗 | 同一个集合 |

**在 96,000 下我们的窗口已经追平了池宽**，而池宽是 256。这意味着再往上加预算，买到的是"排名 256 之后的
轮次"，也就是排序认为最不相关的那些——§1.11 的 24.3% 就是这件事的价格。

#### 所以竞品比较的正确读法变了

公开分数表（§1.1）里，agentmemory V4 的 96.20% 用的是"six-signal retrieval"，Mastra 94.9% 用的是观测式
记忆，MemCog 的 92.48% 用 2–3 步 ReAct 检索。这些系统的共同点不是"窗口更大"，而是**检索召回更宽或更深**。

而我们的短板在 MR（77.5 对 RemLabs 88.72，差 11.2 点），MR 恰恰是"证据散在多段会话里"的能力——它最吃的
就是召回宽度，而不是窗口。

于是这一轮给出的方向不是"再加预算"（§13.213 已经拒绝 96,000：+61.7% token 换 +3.25 在噪声带内），而是
**`relevanceTopK` 256 → 512**：不增加一个 LLM token，只让排序多看 256 个候选。登记的预测是 `MR` 至少 +3，
否证条件是 `MR` 移动 < 2 或 `offered / turns` 下降。

#### 一条不能推的结论

"池更宽就应该更好"不能从这张表推出来。池宽 512 会让更多轮次拿到分数，而那些分数**都很低**——它们仍然排在
所有高分轮次之后，只是不再共享同一个地板值。真正被改变的是"这些轮次之间的**相对**顺序"：从到达顺序变成
按分排序。这一步的价值取决于低分区间的分数是否有区分度，而这正是接下来要测的东西，不是可以从竞品数字里
读出来的。

## 1.12 同一个系统、同一个模型、同一批 500 题，差了 15.4 分

这一轮把竞品表补齐时发现，**我们表里最大的那个数根本不在表里**。

| 来源 | 系统 | 读数 | 说明 |
| --- | --- | --- | --- |
| 第三方独立比较 | Supermemory | **81.6%** | GPT-4o reader，同一批 500 题，A 级 |
| 厂商自己的对比页 | Supermemory | **97.0%** | GPT-4o reader，同一批 500 题，分项 97/100/95/100/95/96 |
| 厂商另一篇 | Supermemory | 84.6% | GPT-5 reader |

**四读，跨度 31 点。** 同系统、同 benchmark，最强的两次读数用的是**同一个 reader 模型**，仍然差 15.4 点。
差的不是模型，是 harness 与 reporting。

这一条比表里任何一行都重要，因为它改的不是排名，而是**"该追谁"这个问题的答案**：

| 我们与谁比 | 数 | 差 |

#### 我此前把 SOTA 说窄了

前几轮报的"最高 96.20%（agentmemory V4）"是**我们表里**的最高，不是**公开**的最高。表的缺口是
Supermemory 的 97%——一个我们早就知道存在、也早就在文档里讨论过其 98.6/97.2 两行的系统，只是没把它的
GPT-4o 单答案行登进来。**这不是别人改了数字，是我们查得不够。**

台账已补 `supermemory-published/gpt4o-97` 一条，`acceptance.ts` 的 S1 竞品行现在同时有 81.6（A）与 97.0（C），
并有一条测试防止任何一方被删掉或两者被"整理"成一个数。

#### 但 97 不能当靶子

它缺四项：judge 未点名、harness 细节未公布、单次运行、无重复。而**它自己**在另一个 harness 里是 66.07。
把 97 当目标去追，追的是一个 reporting 差异。

所以对外的口径要分两层，两层都必须说：

1. **对同级**（A 级、可复现）：我们落后 memoricai **2.3 点**。这是唯一一个"差距可以被机制解释、也
   可以被我们自己的 harness 复现"的目标。
2. **对全榜**：公开最高是 **Supermemory 97%（自报）**，其后 agentmemory V4 96.2%、Agent Zero 95.6%。
   我们 89.8%（实验配置）／83.5%（注册配置）。**cortex 不是 SOTA。**

#### 这改了下一轮做什么

原计划是"`relevanceTopK` 256 → 512，预测 MR +3"。现在先做两件更便宜的事：

| 顺序 | 动作 | 理由 |
| --- | --- | --- |
| 1 | 读注册配置的锚点读数（`41488630010`） | 所有偏离定价的基准 |
| 2 | `thinking` 单变量 | Supermemory 的 97% 用 8 个提示变体并行；Mastra 同系统换 reader 从 84.23 到 94.87。**reader 这一轴的公开证据比检索这一轴强得多** |

而是要问：多变体归并（`majority`，97.2）值不值它花的 token。这已登记为池宽之后的候选。
