# 竞品分析：谁在同一个赛道上，以及哪些数字可以放在一起

> 本文的每一个数字都能在 `AgentiX-E/cortex` 的 `tools/competitor-ledger.json` 里找到同名条目，
> 由 `node tools/competitor-ledger.mjs` 生成表格、`--check` 校验、`--gap` 判定我们能否与之排名。
> **台账是数据，本文是读法。** 两者冲突时以台账为准，并且这条冲突本身是一条缺陷。

## 0. 一句话结论

LongMemEval-S 上公开可查的数字从 **51.8 到 94.4**，跨度 42.6 点，而这个跨度里**大部分不是系统差异**：
同一个 Zep 被三份来源读成 90.2 / 79.8 / 71.2，同一个 Mem0 自报 94.4、同 harness 读成 56.0。
所以我们**不宣称任何跨来源排名**，只做三件事：登记可比条件、在自己 harness 内比较、把可复现的对手
拉进自己的 harness 跑。

## 1. 可比性是一个六元组，不是一个数据集

两个数字可以放在一起排序，当且仅当它们在下列六项上全部一致：

```
dataset | variant | scoring | answer model | judge | harness
```

- 前两项说**问了什么**；
- 第三项说**一次预测怎样变成一个分数**——一条答案，还是 k 条里对一条就算对，还是 k 条投票；
- 中间两项说**谁答、谁判**；
- 最后一项说**谁的流水线决定了什么进入答题模型**——检索、截断、什么叫"答对"都在这里。

`harness` 必须进键，而不是从中间两项推出来：两个 harness 可以有相同的答题模型和裁判，
却在检索深度、截断策略、判正规则上完全不同。`scoring` 进键的理由是同一个理由往上提一层：
**同一个 harness 可以对同一批系统同时印出一列单答案和一列 k 中之一**，那是两个问题。

`--gap 83.0` 在 51 条台账上给出的结果是**没有可比组**，并点名 26 个并列最近的组**差的是同一组字段**：

```
83 has no comparable group.
  26 group(s) are equally near, none shares all six fields, and every one differs in the same
  3 field(s): answerModel, harness, judge.
```

这个"没有"就是诚实答案；换成"83.0 排第二"就是把 harness 的事实读成系统的事实。

### 1.1 `scoring` 是第五个字段缺的那一项，它的证据是一次 1.4 分之差

Supermemory 在 2026 年 3 月公布过两个数，同一篇博客、同一批 500 题、同一批阅读器与搜索代理：

| | 配置 A | 配置 B |
|---|---|---|
| 分数 | **98.6** | **97.2** |
| dataset / variant | LongMemEval / S | 同左 |
| 答题模型 | 同左 | 同左 |
| 裁判 | 同左 | 同左 |
| harness | 同左（同一团队、同一篇发布） | 同左 |
| **分数怎么来的** | **8 个专门化提示变体各答一次，任一对即算对** | **12 个变体投票归并成一条答案** |

六个字段里前五个完全相同，两个数字却差 1.4 点。把它们排序，排的是"给八次机会能到多少"对
"给十二次机会归并成一条能到多少"，读出来的却会像是系统差异。

**这正是最危险的一类行**：五元组的设计原则一直是"宁可把可比的表拆开，不可把不可比的表合并"，
而这一行错在相反方向——**两个数字可以在五项上全同却仍不可比**，也就是说五元组不只是粗，
它是**不完备的**，而不完备恰好在两个数字看起来最接近时隐身。真正差得远的行（7B 阅读器 38.2
对前沿模型 95.8）从来不在危险里，因为答题模型那一项早已把它们分开。

中文报道在 2026 年 3 月传过的"99% 刷爆 SOTA"就是这一行的 98.6 四舍五入，同时有三件事成立：
①它是"八中之一"而不是准确率；②厂商在同一篇里说明这**不是**他们的生产引擎，生产引擎是本台账
已登记的 84.6（`supermemory-published/gpt5`）；③至少一份转述把这次发布描述为**戏仿**——
针对"记忆基准能被做成什么样"。三条都不是删掉这一行的理由，都是这一行必须带 `scoring`、`kind`
和 `note` 的理由。台账不裁决厂商是否在开玩笑，它只保证：**不管对方发布了什么，都不能被顺手和
我们的数字排在一起。**

### 1.2 这个告诫本来就在文档里，只是文档管不了它

`cortex/docs/SOTA-LANDSCAPE.md` §2 的 Supermemory 行一直挂着这句注：

> advertised ~99% is an 8-variant ensemble

也就是说这件事**早就知道、写得对、而且写在册**。它**做不到**的是任何事：不能被检查、不能被印在
分组旁边、拦不住 `--gap` 把这一行报成"近"，更不能在下一行忘了写时被发现。这就是**告诫**与
**条件**的区别，也是这一轮以改 schema 而不是补一段话收尾的原因。

一般形式：**只活在一份文档里、而不活在消费这个数字的产物里的限定条件，会在第二个消费者那里丢失。**
本仓已经撞过四次同一形状——覆盖率注解 gate 看不见、`wired` 标志消融跑器从不读、总体没人事先点名、
现在是评分规则。四次的修法都是把限定条件搬进**做决定的那件东西**里。

加字段只有在字段有活干时才值得，所以同一轮把让它有活干的行也加了：

| 系统 | 分数 | scoring | 登记它的用途 |

| PlugMem | 90.2 | `single` | 台账里**代码可获取**的最高分（Apache-2.0，arXiv:2603.03296），唯一能被换成一次测量而不只是引用的竞品数 |
| MEMTIER | 38.2 | `single` | 唯一的 7B 阅读器行，让 57 点的阅读器效应留在同一张表里可见 |

- **MemCog 的表是拼的，只有它自己那一行是现测的。** 论文写明 baseline 行来自 Latimer et al. (2025)
  与 Sen et al. (2026)，不是重跑。于是它印的"95.80 对 Mastra 85.71"不是配对差——Mastra 自报

  这是 §3 那个模式第三次被独立确认，也是第一次拼装在论文里被写明而不是被推断。
- **PlugMem 复刻的是一个写入路径主张，而这正是本仓最近六十步在做的事。** 它的机制是**在摄入时**
  把命题（关于世界的事实）与处方（关于行为的指令）分开，再按高层概念与意图路由检索，最后把召回
  单元压成一句任务指令。前一半就是这个臂反复没能否掉的零假设：**记忆系统写什么比怎么排序更重要**。
  PlugMem 是那个主张带着代码站在 90.2 的地方。

### 1.4 换模型这一轴上的竞品与文献：一个控制实验、一个网关机制、一份八态 taxonomy

前三节讲的是「谁的分数高」。这一节讲的是另一条轴，而它此前完全没有出现在本文件里：**用户把
cortex 接到自己的模型上之后，会发生什么**。这一轴上的对手不是记忆系统，是网关与测量框架。

#### 一、唯一一份控制实验（arXiv:2609.05339）

**Goyal & Ray, *Does Your Agent's Memory Survive a Model Upgrade? A Controlled Study of Memory
Portability*, 2026-09-04, 18 页, under review, cs.AI / cs.CL / cs.IR。** 同一段历史四种存法，48 段
合成历史 + 随机答案码（所以预训练里答不出来）、每题 160 问、**精确打分，全程不引入 LLM judge**、
两个 <10B 开源模型、**双向**换模型：

| 存法 | 换 writer 后 | 备注 |
| --- | --- | --- |
| LC-RAW（逐字长上下文） | 基线 | 与本 arm 同形：原始轮次，无存储 |
| KG-fixed（固定 schema 图） | **+0.0004 ± 0.0020** | 不确定度是效应的五倍，即「没测到位移」 |
| NOTES（模型压缩笔记） | **+9.91 / −13.28**，按方向 | 多数 agent 框架的默认存法 |
| RAG 全量重嵌 | 可得 **+11.90** | |
| RAG 50/50 混合索引 | **+4.96** | 放弃大部分收益，而**每次调用都成功** |

诊断分解同样是可借用的方法：NOTES 的亏空 **80%（0.467±0.014 / 0.584±0.013）发生在写入阶段**，
RAG 的亏空 **81%（0.364±0.012 / 0.450±0.012）发生在检索阶段**——同一个症状，两个不同的产地。
修复侧：**只靠存储修复在 48 个用例里全部达不到 90% 恢复目标**；保留原始历史后，一个方向上
48 例恢复 34 例。

对本产品的三条直接结论写在 §7.0 / 白皮书 §6.1.7.6：**方向是主导变量而我们方向盲**；
**embedding 是比 reader 更硬的锁定**；**保留原始历史这条我们已经满足**（artifact 保留 `turns`）。

#### 二、唯一一个把「降级」做成产品的对手：LiteLLM health-check routing

它不是记忆系统，但它是 `DegradationGuard` 最近的一个已上线同类机制：后台循环探活、失败节点移出
路由池、`allowed_fails_policy` 按错误类计数、`health_check_ignore_transient_errors` 忽略 429/408，
**冷却到期自动放回**。差异就是本设计的全部立足点：

| | LiteLLM | `DegradationGuard` |
| --- | --- | --- |
| 观测对象 | 存活（401/404/5xx、超时、`max_tokens=1` 完形） | 合规（空答案、回声、无法识别的弃权） |
| 能得出的结论 | 这个端点挂了 | 这个 reader 产不出解析器要读的东西 |
| 恢复 | 冷却后自动 | **按构造没有** |
| 粒度 | deployment | reader（按路由） |

它的双向恢复对它要回答的问题是对的；本设计要回答的是另一个问题，而**四个信号里没有一个能说出
「这个 reader 的输出又变得可读了」**，所以自动回升会是「对着正在修的信号做优化」。

#### 三、唯一一份把「静默失败」列全的 taxonomy：Datasumi 的八态

`valid` / `schema_invalid` / `malformed_json` / `provider_refusal` / `content_filtered` /
`truncated` / `tool_call_instead_of_result` / `timeout`。它的核心论断与本项目独立得到的结论一致：

> **一个把所有情况都转成 HTTP 200 加一个空对象的网关，把它们藏起来不给所有人看，包括它的运营者。**
> Compatibility proxy 换来的是「纸面上的可移植性，回归由客户发现」。

对照本设计的四个信号，八态里的映射是：`provider_refusal` / `content_filtered` → `parse-failed`；
`timeout` → `deadline-exceeded`；`schema_invalid` / `malformed_json` → `parse-failed`；
`tool_call_instead_of_result` 不适用（本 arm 无工具）。**真正缺的是 `truncated`**，而它恰恰是最
容易静默扣分的一态：在输出上限被截断、但前段已经有可解析答案的回复，会被当成一个正常答案计分。

#### 四、judge 的可靠性文献，是任何「通过 judge 测出来的换模型效应」的上界

- 同输入成对判定翻转率 **11–14%**，六家 judge、三家 provider、29 个任务，**跨代未改善**
  （Yagubyan，GroundLM 2026）；约需 **11 次重复**才能稳定一个判定。
- 预注册审计 52,988 次请求：同窗口 Spearman **0.400**（门槛 0.90），次日逐字节重放 0.78（门槛
  0.99），**四家 provider 中位 0.74–0.88，无一家达到 0.99**；换 provider 不修复。
- 21 家 judge、约 541,000 次判定：test–retest >0.95 与位置偏置 >0.10 **同时存在**（「一致地错」）；
  exact match 与 Cohen's κ 之间 **33–41 pp** 的虚高。

cortex 的第一档打分是**精确匹配**而不是 judge，同 prompt 翻转 **4.8%**（§13.194.4），比上述数字
好一个量级——这正是该项研究把 judge 完全排除在外的同一个设计选择。**但第二档是 judge，而任何
通过第二档读出的换模型效应都继承那 11–14%。**

#### 五、这一节对竞争定位的影响

**零。** 它不改变任何对外数字，也不改变「我们不是 SOTA」这个判断。它改变的是**锁定叙事**：在
「换模型后还能用」这条轴上，行业里能被引用的证据只有上面这些，而**没有一家记忆系统公布过自己的
换模型可移植性**——它们公布的是 LoCoMo / LongMemEval 的分数。这是本项目可以做第一的地方，而且
它恰好是用户提的四条要求里最难的那条。

### 1.5 同一个阈值，能恢复时安全，锁存时有害——而竞品全都落在能恢复那一侧

§1.4 把 LiteLLM 当成最近邻。这一轮量出一件更要紧的事：**两家的阈值看起来是同一个数，风险却不在
一个量级，差别只有一条——恢复。** LiteLLM 的 `allowed_fails_policy` 计满即把节点移出路由池，
**冷却到期自动放回**；`DegradationGuard` 降档后没有任何方法回去。于是同一个「N 次失败」的规则，
在前者是「换个节点，一分钟后再试」，在后者是「这个部署从此改用更小的上下文预算」。

把这件事算出来，是本轮最有价值的一个数字。设每窗触发概率为 `p`、一次评测跑 25 个窗口（500 题）：

| 每窗触发率 | 单窗即锁存 | 要求连续两窗 | 差额 |
| --- | --- | --- | --- |
| 5.0%（设计容差） | **72.26%** | **5.58%** | 13.0× |
| 13.0%（实测离散度） | 96.92% | 30.80% | 3.1× |
| 30.0% | 99.99% | 84.17% | 1.2× |
| 95.0%（每call都失败） | 100.00% | 100.00% | 1.0× |

**一个按 5% 每窗校准、一次动作即永久的闸门，会在一次评测里误伤 72% 的正常部署。** 竞品没有踩到
这个坑，不是因为它们的统计学更好，而是因为**它们的动作可撤销，于是误报的价格是分钟级的**。
可撤销把「假警报」从产品事故降级成运维噪声，所以它们可以只数次数。

这一条改写了本节的定位叙事：**「我们的守门器更严格」不是卖点，「我们知道锁存让阈值不能是同一个
数」才是。** 有恢复的动作只需校准检出延迟；无恢复的动作还必须校准**累计**误报，而累计误报是
`1 - (1 - p)^n`，随部署时长单调上升，任何「每窗 5%」的说法都盖不住它。

补救办法不是把阈值调高（那会同时废掉检出），而是**要求持久化**：一窗触发只是上膛，连续两窗才
动作。代价精确到可报价——每个真坏掉的 reader 多花 20 次调用（40 而非 20），而每 call 都失败的
reader 在 25 窗内的检出概率仍是 **100%**。这条改动落在 `GUARD_PERSISTENCE = 2`。

文献侧借的是 SPC，不是竞品：控制图用**平均运行长度**（ARL = `1 / p`）标定，而定义它的每一份材料
都同时警告运行长度分布高度右偏、只看 ARL 会误导。`1 / p = 20` 窗读起来像「每 20 窗一次」，实际是
「活过 20 窗的概率 27.7%」。**锁存型报警是引用 ARL 不只是不精确、而是方向反了的那一类。**


### 1.6 同一个 benchmark，5 分钟和 4 小时测的不是同一个量

本轮的问题是一个运行跑了四个多小时是否正常。查竞品时撞见一件更要紧的事：**在同一个
LongMemEval 上，公开数字的墙钟从 5 分钟到"数小时"都有，而那不是一个工程水平差，是三个不同
的测量。**

| 来源 | 墙钟 | LLM 调用 | 指标 |
| --- | --- | --- | --- |
| MemPalace（ChromaDB raw） | **约 5 分钟** | **0** | Recall@5 **96.6%** |
| Awareness Memory（daemon 路径） | **35 分钟** | **0** | Recall@5 **96.0%**（4.2 s/题） |
| Haki 公开 harness | "**several hours** and a few USD" | 500 × ~40 次抽取 + 作答 + judge | QA 准确率 |
| 本仓 | **300–335 分钟** | 4000 次 reader + judge | QA 准确率 **89.80%** |

前两行是**检索召回**：把 500 题的 haystack 建成索引，看标注会话有没有进 top-5，**一次 LLM 都
不调用**，所以 4.2 秒一题是必然的。后两行是**端到端问答**：检索 + 组 prompt + reader 作答 +
判分，每题 1.76–5.02 秒×8（2 arms × 4 repetitions）。

**所以 96.6% 与 89.80% 之间那 6.8 点不是能力差，是任务差**，把它们并排放进一张没有口径列的
表，是这一节存在的原因。Awareness 自己的榜已经标了这句警告——"MemPalace 96.6% is Recall@5 only,
not QA Accuracy"——说明这个混淆在公开榜上是真实发生的，不是假想。

三条结论：

1. **4 小时是端到端评测的正常量级，不是我们的缺陷。** Haki 公开 harness 对同一数据集的措辞是
   "expect several hours"，且明确把那当作预期而非异常。我们 306–335 分钟的差别来自 repetitions
   （4 次，用于区分处理效应与采样噪声），而 Haki 单次作答。**四倍重复换来的是"差异是处理的还是
   采样的"这个问题的答案**，这个问题上公开榜大多数数字根本没回答。
2. **快，靠的是不调用 LLM。** 任何把墙钟压到分钟级的方案，压掉的都是 reader 调用——也就是被测
   对象本身。这不是优化，是换题。
3. **对标时必须写口径。** 我们对外报 89.80% 是 QA 准确率（`41284575092`，四次 89.40–90.40%）；
   按同一口径的 SOTA 是 agentmemory V4 的 96.20%（481/500，Claude Opus 4.6 作答、GPT-4o 判分、
   seed 42），差 **6.40 pt**。同一口径下我们 **领先 Raw-RAG 的 87.5% 2.30 pt、领先 memoricai 的
   85.8% 4.00 pt**——这两家此前都在本仓所有历史产物之前。Recall@5 的 96.6% 不与任何 QA 数字可比。

### 1.7 工程侧的两条可直接抄的做法

**一，`num_concurrent` 的默认值是 1。** lm-evaluation-harness 的 API 后端把并发做成了显式参数，
**默认串行**，文档推荐 2–4（理由是避免触发限流）。本仓的评测循环同样串行——**这不是落后，是这一类
harness 的常态**，因为瓶颈在 provider 的往返而不在本地算力。差别在于它们有一个我们没有的东西：
`--use_cache`（SQLite 响应缓存），崩溃重跑不必重新付费。

**这一条我们不该抄，而且理由要写下来。** 在 `temperature: 0` 下缓存第二个 repetition 的响应会
让 artifact **无法区分"确定性 reader"与"重放"**——而四次重复存在的唯一目的就是回答这个问题
（run `40722772896` 的四个总分是 407 / 414.5 / 414.5 / 423，不是同一个数）。缓存在这里是
**改变被测对象的变更**，不是性能开关，需要注册而不是提交。

**二，数据集按内容钉住。** Haki 的 harness 在每次运行前校验 sha256，文件不同就**拒绝运行**。本仓
的 workflow 下载 `resolve/main`——一个**可变指针**，且不做任何校验。上游改一个字节，同名的两次
运行就是两个总体，而 artifact 不会说。**本轮修了一半**：artifact 现在带
`datasetFingerprint`（`sha256:<hex>`，渲染在数据集名正下方），所以两次运行能不能比是**可查的**，
不依赖任何人事先记过哈希。**另一半没修**，而且不能从这里修——拒绝需要在文件上取到期望值，环境里
没有该文件，现在写任何摘要都是猜。代价必须说清：**已归档的十七份产物（含 89.80% 那份 headline）
永远不会有摘要**，所以本仓任何数字都无法回溯到产生它的那个文件；能力只从下一次派发开始。


### 1.8 一个 94.6% 的公开高位，以及它为什么不能照抄

本轮挖到三份对本项目**直接可用**的一手材料，它们指向同一个结论：**我们和高位系统的瓶颈不在同一处。**

先校正一处口径，否则下面三行会被读成"新 SOTA"：**SOTA 仍是 agentmemory V4 的 96.20%**（单次确定性运行、
Claude Opus 4.6 作答、GPT-4o 判分，§2 表里的 C 级），Mastra OM 在 GPT-5-mini 读数下是 94.9%。下面这个
RemLabs 的 94.6% 与 Hindsight 的厂商自报 94.6% 同档，**都不构成新 SOTA**；它之所以值得单列，是因为它是
公开材料里**唯一同时给出五个分项**的读数，而分项才是能和我们逐项对表的东西。

| 来源 | 公开读数 | 分项 | 它自己的失败归因 |
| --- | --- | --- | --- |
| RemLabs（2026） | **94.6%（473/500）** | SSU 100 / SSA 100 / SSP 93.33 / KU 100 / TR 92.48 / **MS 88.72** | "the vast majority are retrieval failures" |
| Reverie（2026，论文） | — | 27 道错 | TR 10 道（fragment gaps）、**MS 12 道**（"items described with different vocabulary"） |
| 本站 `41284575092` | 89.80%（449/500） | IE 95.7 / ABS 100 / **MR 77.5** / **TR 94.1** / KU 86.5 | **枚举**：22 道稳定错里 22 道的答案等于它自己 Step 1 的行数 |

三件事值得单独记下来：

**一，我们的 TR 已经高于 RemLabs（94.1 对 92.48），而 MR 低 11.2 点。** 所以"整体差 4.8 点"不是一
个均匀差距，是**两个方向相反的差距**：TR 我们领先，MR 我们落后。任何"整体提 5 点"的计划都必须先说
清它改的是哪一边，否则就是把 TR 的优势和 MR 的劣势当成一个数。

按同一口径，我们与各家整体的差是：**agentmemory V4 96.20% 差 6.40 pt**、Mastra（GPT-5-mini）94.9%
差 5.1 pt、RemLabs 94.6% 差 4.8 pt；领先 Raw-RAG 87.5%（+2.30）与 memoricai 85.8%（+4.00）。
**不是 SOTA**，SOTA 竞品是 **agentmemory V4**。

（分项一律取 `41284575092` 四次重复的平均：MR 93.75/121、TR 119.5/127、IE 143.5/150、KU 62.25/72。
单次运行的 MR 是 93/121 = 76.9%，与平均差 1 题——本文件其余各节引用单次读数时会写明是哪一次。）

**二，他们的失败是检索，我们的失败不是。** RemLabs 说"27 道错里绝大多数是检索失败——信息在库里但
没被翻出来"。本轮的读数是**相反的**：MR 的 22 道稳定错里 **18 道的 gold 数字就在送进去的窗口里**
（`AUDIT-MR-ENUMERATION.md` §3）。同一份 benchmark、同一个分项、同一类问题，两边的瓶颈在不同层。

**⇒ 所以他们的解法不能照抄。** 他们推的是"加检索路径、加 rerank、加实体图"，而在我们的读数上，那
三者对准的是**已经填满的那一格**。

**三，Reverie 论文里有一句反例，正好给这条推论做了独立验证。** 原文：*"We tested several retrieval
augmentations (session expansion, temporal range retrieval, pre-computed date arithmetic, entity graph
traversal for counting queries) that **uniformly degraded performance**, consistent with context
pollution."* 另一份公开的 LoCoMo 复现记录给了同方向的两个数：为 "how many" 放宽检索把 43 道计数题
的 F1 从 **43.3% 压到 38.0%**，还把一道正确的弃权翻成了自信的错答。

**这两条与我们的 18/22 是同一件事的三种测法。** 检索已经不是瓶颈时，继续加检索只会加污染。

> **给我们的直接结论**：MR 的下一步不是"找得更多"，而是"从已经找到的东西里数得更准"。这也解释了
> 为什么 thinking 在 TR 上 **+22**、在 MR 上只有 **+1**——它帮的是"逐次取针"，不是"对着一份长清单
> 数到底"。

另有一条机制层面的文献值得引用：arXiv `2609.38958`（2026-09-30）用 NIAH 计数任务证明，reasoning
模型的计数优势来自**在思考轨迹里逐条枚举**（targeted retrieval），而非一次性广泛注意；把它轨迹里
的表示清空，精确计数准确率从 **97% 掉到 1%**，而清空 prompt 里的记录反而没有影响。**枚举不是脚手
架，是机制本身**——这条支持我们继续在"枚举"这一层做增量，而不是回到检索层。

## 3. 一个系统能被读成多少种分数

`node tools/competitor-ledger.mjs --spread` 的原样输出：

```
Mem0            LongMemEval  spread 45.4  (49 .. 94.4)
Zep / Graphiti  LoCoMo      spread 30.9  (63.83 .. 94.7)
Zep / Graphiti  LongMemEval  spread 19.0  (71.2 .. 90.2)
Supermemory     LongMemEval  spread 18.5  (66.07 .. 84.6)
full context    LongMemEval  spread  2.0  (60.2 .. 62.2)
```

注意 Zep 出现两行：它在两个数据集上各有自己的跨度，而 `LongMemEval` 的 19.0 是本节表格里要读的那个数
（LoCoMo 的 30.9 对应 §2 备注里那条「同 harness 低 30.9 点」）。**同一个系统在不同数据集上跨度不同，这本身就是 §8 要求第二个数据集的理由之一。**

| 系统 | 读数（同一数据集 LongMemEval-S） | harness 数 | 跨度 |
|---|---|---|---|
| Mem0 | 94.4 / 93.4 / 56.0 / 49.0 | 4 | **45.4** |
| Zep | 90.2 / 79.8 / 71.2 | 3 | **19.0** |
| Supermemory | 84.6 / 66.07 | 2 | **18.5** |
| full context（无记忆） | 62.2 / 60.2 | 2 | 2.0 |

Mem0 一行是四个读数，因为它有**两种口径 × 两种部署**：自报（94.4 自托管配置、93.4 新版）与
复现（56.0 托管服务、49.0 开源自托管）。把这四个数平均成"Mem0 是 73.6 分"没有任何含义——
**这不是同一件事的四个测量，这是四件不同的事**。台账把它们放在同一个 `system` 下是为了算出这个
45.4，而 `deployment` 字段是为了记住它们不是一件事。

最后一行是让前几行可读的东西：**`full context` 只有 2.0 点**，而它是一个完全没有记忆机制的系统
——整份 haystack 塞进 prompt。这是**效应量的地板**：任何记忆系统的跨度都应该对着 2.0 读，而不是对着 0 读。
Mem0 的 45.4 是地板的 22 倍，Zep 的 19.0 是 9.5 倍。

工具还区分另一种跨度，本表暂时没有实例但规则要在：**同一个 harness 下的两个读数是一个版本差异，
不是 harness 效应**（`version difference, not a harness effect`），并且这类行会被排在跨 harness 的行
**之后**——因为读者会把第一行当成最大的发现，而版本差异不是本文在说的事。

二十六道里有八道读了；七道是**枚举差一个成员**（五道少一、两道多一），一道是单位聚合错。

这个诊断在 `§13.96` 就写下过，当时三次提示词侧尝试都没能推动它，于是把力气转向了窗口机制。
窗口机制现在结案（ceiling = 2 道，`§13.161.8`）。而 MR 这边是 **20 道净差，且这 20 道已经
被本仓自己的组件答对过**——同样的 haystack、同样的读者、同样的裁判。

**这是本臂迄今最大的机会，且不需要发明任何新东西**：需要找的是参照做了而记忆臂没做的那件事。

## 9. 检验方法与验收标准

| 项 | 检验方法 | 验收标准 |
|---|---|---|
| 台账完整性 | `node tools/competitor-ledger.mjs --check` | 每条有 `source`；同 harness 组内答题模型与裁判唯一；`harness` 类至少覆盖 3 个系统 |
| 可比性判定 | `--gap <score>` | 同组才给名次；无同组时列出**所有**并列最近组及差字段，且**不打印名次** |
| 我们 vs 竞品（同 harness） | `competitor-retrieval.yml` 的 `sut=` 臂，`infer` 开关入产物 | 两臂同回答模型、同裁判、同 roster；报告必须打印 `infer` 值 |
| MR 缺口诊断 | 对 26 道逐条分类（差一/单位/弃答/其他），四类计数之和 = 26 | 主导类命名一个机制；该机制的登记写在这份普查**之后** |
| MR 修复 | 重派后看 discordant 对 | ≥10 道移出"仅参照对"，"仅我方对"增长 ≤2；总分 +1.5 pt 以上；其他能力掉 ≤2 道 |
| token 轴 | 产物已带 `promptChars` 与 `evidenceTurns` | 报告必须给均值与 p95；不得只给"预算上限内" |
| 延迟轴 | 待建（本轮未做） | 未建前不得在任何对比中使用延迟一词 |

## 10. 这份文档本身的可证伪点

**第二，"换模型值多少分"这件事，只有两家敢给数。** 这正是我们此前缺的那块外部先验。

### 1.9.3 这个先验对我们意味着什么，以及我们怎么用

本轮之前，`PREREGISTRATION` §13.211.3 对这个增量写下的预测是 **MR +8 / TR +4**，依据是 MR 丢分的形状
（22 道稳定错题的答案全等于它自己 Step 1 的行数）。找到上面两组数据之后，这个数字**在任何公开实测
里都找不到支撑**，因此本轮在开跑**之前**把它改注册为 **MR/TR +1 到 +3**，并把原数字原样留在文档里。
理由很简单：**在看到数据之前改预测是科学，在看到数据之后改预测是另一件事**，两者必须能被读者区分。

更重要的是，这次改注册把一个"押方向"的实验变成了一个"**分诊**"的实验：

| MR 变化 | 读作 | 下一个增量 |
| --- | --- | --- |
| **≥ +4** | reader 是这个窗口下的真约束，契约在饱和它 | 让契约随 reader 档次切换（`model-portability.ts` 已经在分桶），比较单位从"reader"变成"(reader, 契约)" |
| **±4 内** | reader 不是约束，损失在**清单**里 | P2 的引文级 grounded 枚举 |
| **≤ −4** | 第二个 reader 在这个任务上更差 | 这是关于 LoCoMo 的 MR 形状（28/28 错题都是数值 gold，是算术题不是召回题）的发现，不是一次失败的派发 |

三条路都通向下一件具体的事，**没有一条是"再跑一次"**。这就是我们与 §1.9.1 那五家的方法论差别：他们
公布一个数，我们公布一个数**和它证伪自己的条件**。

### 1.9.4 不能从这张表推出来的东西

必须写清楚，否则 §1.9.2 会被当成背书：

- **mem0 换的是抽取模型，我们换的是 reader。** 抽取决定"记住了什么"，reader 决定"从记住的东西里怎么
  答"。同一条 1.2 点宽的前沿带**不能**直接搬到 reader 上——它只说明"同档模型互换的效应量级是 1–3 点"，
  这是**量级先验**，不是点预测。
- **分数不可直接相减。** mem0 的 92.5% 是 LoCoMo 1,540 题、自家判分；我们的 89.80% 是 LongMemEval 500
  题、`exactMatchScorer` + 弃权感知口径。89.80 与 92.5 之间的 2.7 点**不是差距**，是同名不同物。
- **Roampal 的 85.8% 是修正版 LoCoMo 的非对抗子集**，与原始 LoCoMo 也不可比。

真正可以相减的只有同一数据集、同一判分器、同一 harness 下的两次运行——这正是 `datasetFingerprint`
（§13.210）和 `reader=` 行（§13.212）存在的理由：**让"可相减"成为一个可检查的属性，而不是一句承诺**。

## 1.10 每答一题花多少 token：一张我们自己最难看、也最有用的一张表

**结论先给：** 在最弱的能力（多会话推理 MR）上，我们自己的**简单管线用 1,330 token 打赢了我们 14,106 token 的
记忆臂，领先 8.2 个点。** 这不是"证据不够"，是"证据没有排序"。

### 1.10.1 同一份产物里的两条臂，同一个模型，同一个判分器

`41284575092` 的 `usageBySide` 把两条臂分开记账，这是一张此前没有任何竞品表能提供的对照——**同一进程、同一
reader、同一 500 题、同一判分器，只有管线不同**：

| 臂 | prompt token / 题 | 完成 token / 题 | 缓存命中 | 总名册 | MR |
| --- | --- | --- | --- | --- | --- |
| `reference-pipeline`（简单检索 + 小窗口） | **1,330** | 39 | 81.7% | — | **85.1%**（103/121） |
| `cortex-memory`（48,000 字符窗口，会话边界） | **14,106** | 1,144 | 90.2% | **89.80%** | 76.9%（93/121） |
| `cortex-memory`（96,000 字符） | 23,700 | 1,182 | 90.8% | 90.45% | 80.2%（97/121） |

读法有三层，缺一层就会得出错误结论：

1. **总体我们赢**（89.80% 对基线在很多能力上接近 0，见 §1.10.3），**MR 我们输**，而且是 10 道题、10.6 倍 token。
2. **加预算能补一点**（MR 93 → 97），但要 1.7 倍 token——这就是本轮拒绝 96,000 的全部算术。
3. **简单臂的 1,330 token 里没有任何"记忆结构"**：它不画会话边界、不做多步枚举。它赢在**窗口小、每一条都
   与问题相关**。

### 1.10.2 和竞品的 token 账放在一起

口径必须先说清楚：**数据集不同、判分器不同，分数不可直接相减**；token 数才是可比的量级，而且各家都公布了它。

| 系统 | 数据集 | 分数 | prompt token / 查询 |
| --- | --- | --- | --- |
| **Cortex（记忆臂 48k）** | LongMemEval-S 500 | **89.80%** | **14,106** |
| Cortex（记忆臂 96k） | LongMemEval-S 500 | 90.45% | 23,700 |
| **Cortex（自家简单臂）** | LongMemEval-S 500 | MR 85.1% | **1,330** |
| Mem0（2026-10 BYOK） | LoCoMo 1,540 | 92.5% | 6,956 |
| Memori | LoCoMo | 81.95% | **1,294** |
| Mastra（Observational Memory，gpt-5-mini） | LongMemEval | **94.87%** | 未公布 |

三个可以直接下的判断：

- **我们的 token 成本是 Mem0 的 2.0 倍、Memori 的 10.9 倍**，而 Mem0 的分数比我们高 2.7 点（不同数据集，
  但方向上不利）。所以"用更多上下文换准确率"这条路，我们已经走到收益递减区。
- **Memori 用 1,294 token 拿到 81.95%**，和我们自家 1,330 token 的简单臂是同一个量级——**这一档是"便宜"的
  真实水位**，而不是我们 14,106 token 才该到的地方。
- **Mastra 94.87% 没有公布 token 数**，所以"它是不是靠更长的上下文"这个问题，现在无法回答；这正是 §1.9.1
  那张"谁点名了模型/谁公布了成本"的表要追踪的第三列。

### 1.10.3 为什么这张表比分数表更有用

因为它把下一个增量的**形状**定死了：

- 如果 MR 的缺口是"证据不足"，加预算应该线性地补——实测 48k→96k 只补 4 道题（且均值在噪声带内）；
- 如果缺口是"证据太多、排序不对"，那么**同样的 token 成本下把该有的那条排上去**就能补——而房间里此刻
  **85.3% 的已送达轮次与问题零实词重合，占 65.5% 的字符**。

第一条已经被本轮否掉，第二条因此成为唯一还有依据的方向，登记为 `PREREGISTRATION` §13.213.7，判据是
**在 48,000 的 token 成本不变的前提下恢复那四道题中的至少三道**。

> **这个判据在下一轮被部分否掉（§13.214）。** "同样的 token 把该有的那条排上去"预设那条**在**排序池里、
> 只是排得靠后。`10d9b85a` 的两条决定性金标 `goldRanks = -1`——它们不在池里，重排构造上够不着。方向没有错，
> 但机制换了：该修的是**同一段会话内选哪 167 轮**，不是给 256 宽的池子重新排序。§1.11 给出这条修正的算术。

### 1.10.4 不能从这张表推出来的东西

- **不能推出"应该退回简单管线"**：它在 IE 上只有 2/150、KU 上 0/72，总体是 0 分边缘。它的 MR 优势来自窗口小，
  而不是来自管线更聪明；把它的窗口放大到 175 轮，MR 会不会掉，没人测过。
- **不能推出"我们的 token 花得冤枉"**：14,106 里有 90.2% 是缓存命中，实际计费按 DeepSeek 的缓存价只有名义值
  的约三成；把它和 Mem0 的 6,956 直接按价格比会高估 2 倍以上。
- **不能跨数据集比分数**：89.80 是 LongMemEval-S 500 题、`exactMatchScorer` + 弃权感知；92.5 是 LoCoMo 1,540
  题、Mem0 自家判分。两者之间没有可减的量。

### 1.11 加预算买到的三分之一，是排序没提供的证据

§1.10 的结论是"用更多上下文换准确率已经走到收益递减区"。本轮把这句话量化成了两条可以引用的读数，它们来自
**修正后的**金标账（`--pool` 的合计此前算错，见 §13.214：48,000 被切掉的是 **707** 而不是 654，从池外送进来的
是 **53** 而不是 0；96,000 是 **296** 与 **185**）。

| 量 | 48,000 | 96,000 | 变化 |
| --- | --- | --- | --- |
| 金标轮次 | 7,516 | 7,516 | — |
| **排序从未浮出** | **361** | **361** | **0** |
| 被预算切掉 | 707 | 296 | −411 |
| 从池外送进来 | 53 | 185 | +132 |
| 已送达 | 6,501 | 7,044 | +543 |

**第一条：排序的触达在两次运行里都是 361，一位不差。** 把预算翻倍，排序浮出的东西一个没变，变的只是 prompt
装得下多少。所以"再加一倍上下文"这条路径，本质是**分配**而不是**信号**——它不可能改善我们与 SOTA 之间那个
6.40 点的差，因为那个差是"该有的证据有没有被找到并排在前面"，不是"房间有多大"。

**第二条：多给的房间买到的 543 条金标里，132 条（24.3%）来自排序池之外。** 也就是四次里有一次，房间捞到的是
排序**没找到**的东西。这一点对竞品比较有一个直接含义：**任何"纯检索 + 重排"的系统，在同样的预算下也捞不到
那 132 条**——不是因为它们实现得差，而是因为它们的窗口与候选池是同一个集合。我们能做到，是因为会话选择与
排序池是两个不同的宇宙（`--pool` 的 "beyond the pool" 列就是这件事的度量）。

反过来看，这也是我们比竞品贵的原因之一：**已送达的证据里有 2.6%（185/7,044）落在排序之外**，48,000 下是
0.8%（53/6,501）。把这些砍掉会省钱，也会把那一档分数砍掉——所以正确的做法不是砍，而是**让排序覆盖到它**，
这正是 §1.10.3 那条修正后的方向。

一个必须留着的边界：**24.3% 是"多给房间买到的"里面的比例，不是我们总证据里的比例**。后者是 185/7,044 = 2.6%。
把前者当成后者，会把"排序的缺口"高估近十倍——这也正是这一节存在的原因：同一份产物，两种口径，差一个数量级。

### 1.12 我们有"池"和"房间"两层，竞品通常只有一层——而这一轮发现瓶颈在池

§1.11 把"多给的房间买到三分之一池外证据"写成了我们的结构特点。这一轮把它拆得更细，因为它对竞品比较有一个
直接后果：**同一个"k 太小"的症状，在两层结构和一层结构里意味着完全不同的东西。**

#### 两层与一层

我们的检索链是两段：

```text
语料 ──(embedding, top-k)──▶ 池（relevanceTopK = 256） ──(按分数取前缀, 字符预算)──▶ 窗口（48,000 字符 ≈ 167 轮）
```

竞品的链通常是一段：`retrieve top-k ──▶ prompt`，k = 5…20，检索结果全部进窗口。Raw-RAG 的公开配置是
`k = 15`、256/32-token 窗口；Mem0 一类系统的 `top_k` 默认同量级。

一层结构里，"k 太小"和"窗口太小"是**同一个问题**，因为 k 就是窗口。两层结构里它们是**两个问题**，而且可以
分别失败：

| 失败 | 表现 | 修法 |
| --- | --- | --- |
| 池窄 | 金标从未进入候选，`goldRanks` 里是 `-1` | 提高 `relevanceTopK` |
| 窗口小 | 金标在池里但排在前缀之外 | 提高 `maxPromptChars` |

#### 这一轮的读数说瓶颈在池，不在窗口

`10d9b85a` 在 48,000 下的四元组：`total 11 / pool 9 / carried 9`。**池内九条全部送达**——窗口一条没切。
96,000 多买的两条是 `goldRanks = -1`，即**排在第 256 名之外**，靠装完所有打过分轮次之后的剩余房间才捎上。

而 96,000 那个更宽的房间也确实在买别的东西：§13.214.2 的 543 条金标增量里，**132 条（24.3%）来自池外**。
两个读数指向同一件事——**我们的窗口已经比池更宽，所以"加房间"买到的越来越是池外证据，而不是池内更好的
排序。**

同类系统的对照：

| 系统 | 池宽 | 窗口 | 谁更宽 |
| --- | --- | --- | --- |
| 我们（`41284575092`） | `relevanceTopK` 256 | ≈167 轮 / 48,000 字符 | **池更宽**（256 > 167） |
| 我们（96,000 那一侧） | 256 | ≈232 轮 | **窗口更宽**（232 ≈ 池） |
| Raw-RAG（公开配置） | `k = 15` | 256/32-token 窗口 | 同一个集合 |
| Mem0 一类 `top_k` 默认 | 5…20 | 全部入窗 | 同一个集合 |

**在 96,000 下我们的窗口已经追平了池宽**，而池宽是 256。这意味着再往上加预算，买到的是"排名 256 之后的
轮次"，也就是排序认为最不相关的那些——§1.11 的 24.3% 就是这件事的价格。

#### 所以竞品比较的正确读法变了

公开分数表（§1.1）里，agentmemory V4 的 96.20% 用的是"six-signal retrieval"，Mastra 94.9% 用的是观测式
记忆，MemCog 的 92.48% 用 2–3 步 ReAct 检索。这些系统的共同点不是"窗口更大"，而是**检索召回更宽或更深**。

而我们的短板在 MR（77.5 对 RemLabs 88.72，差 11.2 点），MR 恰恰是"证据散在多段会话里"的能力——它最吃的
就是召回宽度，而不是窗口。

于是这一轮给出的方向不是"再加预算"（§13.213 已经拒绝 96,000：+61.7% token 换 +3.25 在噪声带内），而是
**`relevanceTopK` 256 → 512**：不增加一个 LLM token，只让排序多看 256 个候选。登记的预测是 `MR` 至少 +3，
否证条件是 `MR` 移动 < 2 或 `offered / turns` 下降。

#### 一条不能推的结论

"池更宽就应该更好"不能从这张表推出来。池宽 512 会让更多轮次拿到分数，而那些分数**都很低**——它们仍然排在
所有高分轮次之后，只是不再共享同一个地板值。真正被改变的是"这些轮次之间的**相对**顺序"：从到达顺序变成
按分排序。这一步的价值取决于低分区间的分数是否有区分度，而这正是接下来要测的东西，不是可以从竞品数字里
读出来的。

## 1.12 同一个系统、同一个模型、同一批 500 题，差了 15.4 分

这一轮把竞品表补齐时发现，**我们表里最大的那个数根本不在表里**。

| 来源 | 系统 | 读数 | 说明 |
| --- | --- | --- | --- |
| 第三方独立比较 | Supermemory | **81.6%** | GPT-4o reader，同一批 500 题，A 级 |
| 厂商自己的对比页 | Supermemory | **97.0%** | GPT-4o reader，同一批 500 题，分项 97/100/95/100/95/96 |
| 厂商另一篇 | Supermemory | 84.6% | GPT-5 reader |

**四读，跨度 31 点。** 同系统、同 benchmark，最强的两次读数用的是**同一个 reader 模型**，仍然差 15.4 点。
差的不是模型，是 harness 与 reporting。

这一条比表里任何一行都重要，因为它改的不是排名，而是**"该追谁"这个问题的答案**：

| 我们与谁比 | 数 | 差 |

### 1.13 四家都把"限流"写进了系统，只有我们把它写成了一条时间轴

本轮不是为了分数去挖竞品，而是因为一件很具体的事：我们两次冒烟都死在 `429 code 1302`，`retryAfterHonoured: 0`，
八次尝试、`0 s was left`。要判断"这是我们写得差还是 provider 太紧"，只能去看别人怎么处理同一件事。

#### 四家的做法

| 系统 | 机制 | 参数/默认 | 限的是什么 | 出处 |
| --- | --- | --- | --- | --- |
| Zep / Graphiti | `asyncio.Semaphore` 包住 episode 摄取的每次 LLM 调用 | `SEMAPHORE_LIMIT`，**默认 10，官方说"故意压低"** | **在途请求数** | Graphiti quickstart 与 Zep 工程文档（社区转述） |
| Mem0 v3 | 抽取从 `1 + N` 次压到 **1 次**；嵌入批处理 + 逐条 fallback；`add()` 异步化以"削 rate limit 的峰" | 无显式间隔参数 | 调用**次数**与**突发形状** | Mem0 v2→v3 复盘（LongMemEval 67.8 → 93.4，LoCoMo 71.4 → 91.6，均为其自报） |
| GraphThrift（Graphiti 外挂） | 计量 + 批处理 + 去重预过滤 + 缓存 + 提示压缩，**并用评测闸门拦截掉质量的优化** | 安全档 −47% 成本、−40% 调用、−24% 延迟，三元组 F1 不变；激进档（抽取路由到小模型）−97% 成本但 F1 0.93 → 0.75，**闸门拒绝** | 成本，且以质量闸门为条件 | Apache-2.0 工具，自带 23 条测试与在线演示 |
| **cortex（本轮之后）** | 进程级 `RequestGate`，按间隔发槽位；梯子每次尝试前预约；节流不计入重试预算 | `CORTEX_LLM_MIN_INTERVAL_MS`，默认**不设** | **请求起始速率** | 技术设计 §22 |

#### 两条可以直接抄的

1. **Semaphore 是并发上限，不是速率上限。** Graphiti 把在途数压到 10，是因为一次 episode 要做抽取、实体消解、
   关系更新，单次动辄十几秒——**在途 10 已经等价于每秒不到一次**。我们的读者是单次几十秒的思考型调用，同一思路
   在宽度上就等价于 `workers`。它能治"一次发太多"，治不了"稳定地每秒发一个而对方只允许每分钟十个"。后者需要
   的是间隔，这正是我们加的 **另一种** 原语。**两者不互相替代**，而我们此前一个都没有。
2. **把降本做成"必须过闸门"的动作**（GraphThrift）。它最有价值的不是那 47%，而是它把"这个优化安不安全"从
   主观判断变成了可复现实验：成本 −97% 但 F1 −0.18 的配置被**自动拒绝**。这与需求 #8 的要求是同一件事，
   而我们目前的评测管线已经具备做这个闸门的全部零件（配对 McNemar + 逐题向量 + 花费分臂）。

#### 一条必须诚实说的

Mem0 v3 自报 LongMemEval **93.4**、LoCoMo **91.6**，且把提升归因于一次调用完成抽取而非 `1+N`。这两个数字都
高于我们 A 级口径下的 **83.9**（`41488630010`，`featureAggregate.avg` 0.8390）。按本文件的分级，它们是
**C 级**（自报、reader/judge 形式未公开到可复现的程度、且 v3 的实现细节在其 OSS 分支上晚于该声明），因此不进
A 级表——**但"低于 93.4"这个事实不会因为分级而消失**，它只是暂时不可比。这也是 §1.12 末尾那条线（多变体归并）
为什么排在我们自己的池宽之后：抄机制要先能测它。

**第二，Mastra 自己公开的读者轴跨度（GPT-4o 84.23 → GPT-5-mini 94.87，一个记忆层不动，+10.64）比
Maximem 公开的（gpt-5.4 95.2 / Gemini 3.8 Flash 95.6，+0.4）大 26 倍，而这个差是可解释的**：
检索已经把证据放到位时，读者没什么可补；读者能补 10 分时，说明检索没放到位。**这条对我们不友好但必须写下来**：
我们的读者轴跨度是 +6.25（思考开关，prompt 逐字节相同），落在"检索还有余量"那一侧，与 90.15 的位置一致。

#### 一篇把这件事讲成"src-aug"的论文：Memory Tax（arXiv 2610.34073）

同一周出现的这篇（UIUC / 清华 / 人大 / Waterloo）把 11 个开源记忆系统与**朴素两轮 chunk RAG** 在三个
基准 × 三个骨干上对打，LongMemEval-s（Qwen3.6-27B 骨干）的结果是：

| 方案 | 分数 |
| --- | ---: |
| **朴素两轮 RAG** | **81.4** |
| A-Mem | 79.4 |
| LightMem | 78.8 |
| MemOS | 76.6 |
| SimpleMem | 73.6 |
| MemoryOS | 73.4 |
| OpenViking | 41.0 |

11 个全部输给朴素 RAG。论文的框架不是"记忆没用"，而是**净值 = 记忆收益 − 记忆税**，税有三处：
改写丢事实（OpenViking 38% 的事实根本没生成记忆单元）、改写后首轮召回不如原始分块、构造模型与问答
模型不一致时的抖动。它自己的解法叫 **src-aug**：记忆库照用，**同时保留一条回到原始历史的检索通道**，
两路候选合并重排。

**这条对我们的含义是：我们从一开始就在 src-aug 那一侧**——cortex-memory 的证据是原始轮次，不是抽取
出来的记忆单元（`relevanceUnits=turn`，`maxTurnChars=400` 只是截断，不做改写）。这解释了为什么我们在
**没有任何抽取管线、没有离线建库成本**的前提下拿到 90.15，而那些有抽取管线的系统在同一骨干上落在 73–79。
它也把 §1.16 上面那个上下文表格变成一个**可以在同一机制上修的问题**：我们读得多，不是因为需要那么多，
而是因为没有按题决定需要多少。

#### 本轮据此改了什么优先级

原来的下一步是"追 MR 的机制与池深"（§14.31 第六、七节）。现在它在前面加了一步，并且这一步**同时
满足第 8 条要求（不降指标地降 token）**：

| 优先级 | 方向 | 依据 | 判据（先写） |
| --- | --- | --- | --- |
| **P1** | 每题证据预算**自适应**（按该题自己的检索结果定宽度，而非固定 48,000） | Perpetuity 92.4→94.0 走的就是这一步；本仓 24k→48k 只 +0.60 | 总体 ≥ 90.15 **且** 每题证据 token 中位下降 ≥ 30% |
| P2 | MR 的计数契约（§14.32 已定位：28 道错题都是"已作答"，`recover` 只作用于"已拒答"的 10 道） | 满额约 +4.4 分总体 | MR ≥ 96/121 |
| P3 | 池深 512 的四条预测（§13.234，测量已存在，见 §14.33） | — | §13.234 原样四条 |

**这不是"SOTA 又远了"，而是"我们一直在错的那条轴上加油"。** 前排四个系统里有三个（Perpetuity、
Mem0、Maximem）读的上下文都不超过 7.4K；我们用 14.1K 换到 90.15，说明我们买到的是"读得多"，
不是"读得准"。

### 1.17 第一篇可以和我们正面对表的学术基线：Raw-RAG 87.53，我们 90.15

§1.14–1.16 的表格是厂商自报，条件各不相同，只能作参照。本轮挖到一篇**同基准、同题数、公开读者与判分**
的第三方工作，它是本仓第一次可以**逐题对表**的对象。

> **Is Complex Agentic Memory Always Needed? Naive RAG Is Stronger Than We Thought**（arXiv **2610.30755**，
> 2026-10-22）。Raw-RAG = 原始历史切 256-token 窗口（32 重叠）→ 稠密检索召回 **128** → cross-encoder
> **重排取 top-15** → 扩回完整轮次交给读者。没有抽取、没有摘要、没有图、没有 UPDATE/DELETE。

#### 1.17.2 它推翻了我上一轮的一句话：每题上下文我们并不算多

§1.16 写的是"我们比排在前四的系统每题多读 1.9–3.9 倍上下文，分数低 4 分，这是一个方向性的错误"。
论文 Table 20 给了 LongMemEval 上同一基准的证据 token 实测：

| 基准 | 题数 | 均值 | **中位** | P95 | 最大 |
| --- | ---: | ---: | ---: | ---: | ---: |
| LongMemEval | 500 | 11,355.6 | **11,248.5** | 13,915.3 | 27,375 |

我们的证据侧是 46,834 字符 ≈ **11.7K tokens**（不含指令块与问题）。**同一个基准上，最强的公开朴素
基线读 11.2K，我们读 11.7K，差 4%。** 所以"我们读得太多"这句话在**同基准可比**的对象上不成立；它只在
和厂商自报的 3.6K/6.8K/7.4K 相比时成立，而那些数字的取得条件没有一份是公开到可复现的。

这不是把 §1.16 抹掉，而是把它降级：**"读得多"是一个与厂商数字的对比，不是与基准的对比。** 真正成立的
那一半是：同样的 11K 上下文，我们能到 90.15，而同等上下文的朴素基线到 87.53——**同样多的钱，我们买到的
准确率高 2.6 分。**

#### 1.17.3 论文自己的消融，把一个我们一直缺的机制标成了最大项

Table 5（MemoryAgentBench，GPT-4o-mini，Total 基线 48.32）：

| 变体 | Total | Δ |
| --- | ---: | ---: |
| Raw-RAG 默认 | 48.32 | — |
| **去掉重排（reranker）** | **44.40** | **−3.92**（pHolm=0.0012） |
| 去掉轮次去重 | 45.93 | −2.39 |
| 加摘要增强 | 42.51 | −5.81 |
| 加图扩展检索 | 42.54 | −5.78 |
| 加原子事实抽取 | 28.70 | **−19.62** |

两条对我们的直接含义：

1. **重排是唯一一个"加上就赚、去掉就赔"的组件**，量级 3.92 分，比任何"记忆管理"机制都大一个数量级。
2. **一切"记忆管理"都是负的**：原子抽取 −19.62、摘要 −5.81、图 −5.78。我们一个都没做，这是架构上
   被第三方独立验证的一次。

检索深度也有实测：只给 1 条证据 −11.73；final-k 取 5/10/30/60 差异在 1.3 分以内；**top-120 −14.57**。
也就是说**深度在 5 到 60 之间几乎不重要，重要的是重排是否把对的放进了那 5–60 条**。

#### 1.17.4 它把"覆盖率"讲成了第一性原理，而我们刚把覆盖率做成了仪器

论文的核心论点是：**瓶颈在证据获取（evidence access），不在记忆编码。** 它的证据是覆盖率与利用率
的方差对比——系统间覆盖率 19.07%–45.29%（MemoryAgentBench）、35.69%–76.35%（MEME），而利用率
65%–90%，差一个数量级。

我们把同一件事做成了可复算的仪器（`tools/evidence-depth.py`，内部 §13.239）：按路由统计"池内金标
落在交付深度之内的比例"。**我们的覆盖率是 69.7%–100%，五条路由里三条在 84% 以上。**

这个对比的意义是**方向性的**：论文说的那个"覆盖不足"的区间（19%–76%）我们已经走出了，而我们还差
4 分——所以**剩下的 4 分不在覆盖率上，在排序质量上**。同一份数据支持这个结论：我们的池内金标
**中位排名 134（池 418）**，即排序只把中位金标从"随机 209"提到"134"，而它却必须靠"读得深"来弥补。
论文的 −3.92 消融说的就是这件事。

#### 1.17.5 重排不是新杠杆：我们测过，而且它的天花板由覆盖率决定

读到 Table 5 的第一反应是"重排是最大的正项，应当立刻上"。**第一反应是错的**，理由在本仓自己的记录里：

- **重排已经实现并测过。** `docs/VERDICT-B1-RERANKING.md`：交叉编码器重排，运行 `35624110842`，
  150 题，**+1.33 pp（131/150 对 129/150），McNemar p=0.7539**，判定为**"按功效不足而无法定论"**。
- **论文的 3.92 来自一个覆盖率低得多的语料。** 同一篇论文给的覆盖率是 MemoryAgentBench
  **19.07%–45.29%**、MEME 35.69%–76.35%；而我们的覆盖率是 **84.2%–100%**（§1.17.4）。重排能修的是
  "对的证据在池里但排到后面"，池里覆盖率只有两三成时它有大活可干，覆盖率九成时它剩下的活就是
  最后几名。**同一条机制在两个覆盖率区间上的期望收益不能互相搬运。**
- **而且功效算不过来。** B1 的不一致对是 10/150（6.7%）；在 500 题上约 33 对，按 McNemar 精确检验
  p<0.05 需要约 23/10 的劈分，对应总体效应 **≈2.6 分**。也就是说 500 题能分辨的是"三个点以上"，
  而 B1 测到的是 1.33——**再跑一次 500 题仍然是功效不足，只是更贵。**

所以重排从"P1"退回"已测、天花板受限、不再投入"。真正被这轮数据推到台前的不是它：

#### 1.17.6 真正的 P1：MR 的提示词形状，而不是它的检索

同一个产物里有一行比较此前没有被当作杠杆读：

| arm | 读者 | 窗口 | MR |
| --- | --- | --- | ---: |
| `reference-pipeline`（同一产品的记忆臂关闭） | **同一个 DeepSeek** | **更小** | **86.78%** |
| `cortex-memory`（注册臂） | 同上 | 检索窗 | **76.86%** |

**同一个读者、同一批 500 题、同一个判分器，用一个更小的窗口，高出 9.92 分。** 这一行排除了三个
我们一直在花钱的轴：不是读者（同一个）、不是覆盖率（§13.239.2 显示把 MR 推到 100% 只值约 +7 且
正在测）、不是预算（对方的窗口更小）。**剩下的是提示词形状**——参考管线把两步问成"先列、后算"，
而记忆臂自 §13.34 起要求一个列表。

**但"把参考管线的契约搬过来"这条已经被测过，而且是反向的——本节的初稿就写错了这一点，必须记下来。**

内部 §13.123.4 登记了 `ask=silent`，运行 `40792853362` 的读数是：**MR 87 → 61，掉 26 题**，总体
83.4–84.8% → 78.6–81.0%。两个子群把归因钉住了：

| MR 子群 | 题数 | 对照正确 | silent 正确 | 差 |
| --- | ---: | ---: | ---: | ---: |
| 交付轮次逐字节相同 | 66 | 48 | 31 | **−17** |
| 多交付一轮（指令变短买到的） | 55 | 39 | 30 | −9 |

三分之二的损失发生在**读到的证据完全相同、只有指令变了**的题上。错答形状是**少加**而不是弃答：
`25 + 40 + 120 = 185` 变成 `65`，`17 天` 变成 `10`。内部 §13.127.5 的诊断是：**写出来的列表就是
Step 2 用来计数的那个状态，不写出来的列表不是列表**——Step 1 的输出无处安放，"数识别到的条目"就
变成了"数记得住的条目"。

**而那次实验抄的是杂交体，不是参考管线。** 它抄了"只写最终答案"的隐私条款，却保留了自己那句"可以
跨会话合并证据"和"走遍 prompt 打印的每一个会话"的 Step 1。参考管线的 Step 1 是 **identify**，不是
逐会话 enumerate，而且它从不要求读者把三十个会话端在工作记忆里。

所以真正没被测过的变体是**整体搬迁**：`identify` 而非 `enumerate` + 只写最终答案 + 一行 `Answer:`
前缀 + 无解释。它与 `silent` 的差别恰好就是 §13.127.5 指出的那个原因，因此它不是重复实验。

| 优先级 | 方向 | 依据 | 判据（先写） |
| --- | --- | --- | --- |
| 进行中 | 每路由证据预算（`multi-session:55000,flat:36200`） | 内部 §13.239：MR 满覆盖 84.0% vs 部分 65.2%（2.3 SE） | MR ≥ 96/121、总体 ≥ 90.15、均值 prompt ≤ 46,630 |
| **P1** | **参考管线 ask 的整体搬迁**（`identify`+只写答案+`Answer:` 前缀）；**不是** `ask=silent`（`40792853362`：MR −26，已退役） | 同读者、更小窗口，参考管线 MR 86.78% vs 本臂 76.86% | MR ≥ 96/121，且 IE/TR/ABS/KU 在噪声带内 |
| P2 | MR 的计数契约（28 道错题都是"已作答"） | 内部 §13.233 | MR ≥ 96/121 |
| 已测/受限 | 重排（B1：+1.33，p=0.75，天花板由覆盖率决定） | §1.17.5 | — |
| 已退役 | 池深 512/1024、预算 24k→48k→96k | §13.238 / §14.31 | — |

**顺序在这一轮被改了两次，两次都是被数据改的**：上一轮把"降 token"提到 P1（依据是厂商自报的
3.6K/6.8K/7.4K），这一轮把它降级——同基准的可比对象读 11.2K，我们不超标；而 §1.17.5 又拦下了一个
看起来最像"最大正项"的机制。两次改动的共同点是：**先找同条件的数字，再排优先级。**

### 1.18 2026-11-04 复扫：LongMemEval 已经不能区分系统了，而能区分的那个台子露出了我们真正的短板

#### 一、三个排行榜都不独立，且它们衡量的是报告质量

这一轮的复扫先确认了一件比分数更重要的事：**这个领域最常被引用的三个"榜"都由参赛者自己建。**

| 榜 | 谁建的 | 建它的动机（原文措辞） |

| OmniMemEval | MemOS 的作者 | 自家在 LoCoMo 与 LongMemEval 表上领先 |
| MemoryBench | Supermemory | 只是一个 harness，**不发榜** |

LongMemEval 官方仓**没有任何排行榜**。所以"某系统 94.6%"这类数字的流通路径是：厂商自测 → 厂商博客 →
被二手文章当作第三方。**我们引用时必须每次都带这一句**（01 §B.6 的补记已按此降级过一次）。

**这张表里最该看的一列不是 92.08，是 28.17。**

#### 四、28.17 这个数字对我们意味着什么

在最难的规模上，连 BEAM-10M 目前第一的系统，多会话推理也只剩 28%。而**多会话推理恰好是我们唯一显著
输给自己对照的能力**：

| arm | 读者 | 窗口 | MR |
| --- | --- | --- | ---: |
| `reference-pipeline`（记忆臂关闭） | 同一个 DeepSeek | **更小** | **86.78%** |
| `cortex-memory`（注册臂） | 同上 | 检索窗 | **76.86%** |

两件事合起来的判断：**MR 的难点是规模，不是提示词。**

- 我们 MR 的池内金标交付率是 **94.8%**，但那是 **46,264 字符 / 174 轮深度**换来的，而 LongMemEval-S
  的一段历史只有约 115K 字符。
- 在 10M 规模上，"174 轮"连零头都不是。**在 LongMemEval 上把 MR 从 93 推到 96 是值得走完的最后一
  公里；把 MR 的机制搬到 10M 才是真正的下一步。**

这不是"换个基准刷分"，而是**我们所有 MR 结论都建立在一个 115K 字符的台上**，而该台已饱和。继续在
它上面优化 1 个点，已经接近在测噪声。

#### 五、两条可以直接借的机制（本轮新增，都指向第 8 条：降 token 而不降分）

| 论文 | 机制 | 数字 | 与我们的关系 |
| --- | --- | --- | --- |
| AgentIR（arXiv **2605.25092**） | 置信度触发的**级联检索**：先在 BM25/SIMD 子strate 上判"够不够"，够就跳过 dense | LongMemEval 上 **63% 的查询跳过 dense，延迟 2.67× 降低，LLM-judged 准确率持平** | 我们把每路由宽度当唯一杠杆（§13.239），而这只杠杆的价格已被测到"每翻倍 0.6 分"。**级联是同一预算下换更多覆盖率的路子，而不是再加预算。** |
| All-Mem（arXiv **2603.19595**） | 在线/离线解耦 + 拓扑演化 + 拓扑感知检索 | LongMemEval-S **60.20** vs Mem0 55.80（4o-J） | 在低端读者下与 Mem0 的**相对**差 +4.4，说明拓扑对"多会话聚合"有独立贡献——正是 MR 的失败形状 |

AgentIR 那条尤其值得记：**它证明"少读"可以不掉分，前提是知道什么时候可以不读。** 我们现在的做法是
每条路由固定宽度，读多少与题目难度无关。置信度级联把"读多少"变成"先问够不够"。

#### 七、后记（同日，实验回来之后）：28.17 这个数字的解读被我们自己的数据支持了

§1.18 四写下的判断是"MR 的难点是规模，不是提示词"。当天晚些时候 `41773546221` 回来，它把这句话的
**另一半**也钉住了：

| | 注册臂 | 重分配臂 |
| --- | ---: | ---: |
| MR 交付深度 | 174 轮 | **198 轮** |
| MR 池内金标交付 | 94.8% | **96.4%** |
| MR 满覆盖题数 | 75 | **82** |
| 满覆盖准确率 | 84.0% | **89.0%** |
| **全 121 题准确率** | 76.86% | **76.03%** |

**在 115K 字符的台上，覆盖率已经买到 96.4%，准确率不动。** 所以 MR 缺的不是"再多一点上下文"，也不
是"再深一点的选择"——在 LongMemEval-S 的尺度上，检索侧能给的东西已经被拿完了。

而 BEAM-10M 上 past.dev 的 multi-session **28.17%**，说明同一件事在更大的尺度上会**更糟**：那里的多会
话不是"证据没到"，是"证据到了也组织不起来"。

两件事合起来给出一个可执行的分工：

| 尺度 | MR 的主要矛盾 | 对应的动作 |
| --- | --- | --- |
| 115K（LongMemEval-S） | **读**：证据已到，组织与计数出错 | 提示词形状（参考管线 `identify` 契约，§1.18 五的 P1） |
| 10M（BEAM） | **组织**：跨会话聚合与顺序 | 拓扑/时序结构（All-Mem 2603.19595 一类），不是更宽的窗口 |

**这条分工是本节最有用的一句话**：它让"要不要做 10M"从"要不要刷另一个榜"变成"我们的 MR 机制在哪
个尺度上失效"——而这两个尺度需要的机制不同。

### 1.19 2026-11-04 复扫之二：这个领域刚刚把"准确率"换成了"准确率 × 每查询 token 数"，而这一列我们最难看

#### 一、先修一个名词陷阱：「BEAM」现在指两个东西

| 名字 | 是什么 | 出处 |
| --- | --- | --- |
| **BEAM（基准）** | 100 段单用户对话、2,000 探针、10 能力、100K→10M | ICLR 2026，arXiv **2510.27246** |
| **BEAM（方法）** | Bayesian-style Evolutionary Agentic Memory，把记忆价值当上下文条件化的信念 | arXiv **2610.25119**（2026-10） |

本文件此前所有「BEAM」都是前者。**今后每次出现都必须带限定词**，否则两篇论文的引用会互相污染——这是本仓第一次遇到同名词，也是第一次需要这条规则。

#### 二、我们这个领域刚刚换了记分板：五维，其中两维是成本

Mem0 在 **2026-10-02** 发布了《State of AI Agent Memory 2026》，它做的事比它自己的分数更重要：把评测框架从单一准确率改成**五维**——

| 维度 | 测什么 | 为什么这一维会进来 |
| --- | --- | --- |
| BLEU | 与金标的 token 级相似度 | 传统 |
| F1 | 回答 token 上的精确率/召回 | 传统 |
| LLM score | 裁判的二值正确性 | 我们的主指标 |
| **token consumption** | **每次查询消耗的 token 总数** | "一个准确率 96 但每题 26,000 token 的系统不是生产可用的" |
| **latency** | 检索 + 生成的实际耗时 | 同上 |

**这句话必须原样记住：** *"A system that scores well on accuracy but requires 26,000 tokens per query is not production viable."* 说这话的公司自己在 LongMemEval 上是 **94.4 @ 6,787 token/查询**。

#### 三、我们被这句话点名了，而我们的数字是 11.5K

我们注册臂的均值 prompt 是 **46,125 字符/题**。按 4 字符/token 折算是 **≈ 11,500 token/查询**。

| 系统 | LongMemEval-S | 每查询 token | 口径 |
| --- | ---: | ---: | --- |
| Mem0（2026-04 算法，自报） | **94.4** | **6,787** | 平均每次检索调用的 token |
| **cortex（注册臂 `41546569106`）** | **90.15** | **≈11,500** | 每题 prompt 字符 ÷ 4，含指令与证据块 |
| 差值 | −4.25 | **+4,700（1.7×）** | — |

**这不是一个可以解释掉的口径差。** 我们的 46,125 是**送到读者面前的整个 prompt**，Mem0 的 6,787 是它"每次检索调用的平均 token"——两者都是"回答一道题要付多少 token"的量级估计，而且我们的指令块（§13 的 ask 契约、证据块头、abstention 指令）**同样是花钱买的**。

诚实的结论有三条：

1. **在准确率上我们与 Mem0 差 4.25 点，在 token 上我们多花 1.7 倍。** 两个方向都不利。
2. **但 Mem0 的 94.4 是自报、不可复现**，而同一个 Mem0 OSS 被第三方在 500 题上复现到 **32.4**（本文件 §1.16 的 [B] 行）。所以"94.4 @ 6,787"这个组合本身没有被独立验证过。
3. **我们的 90.15 是公开提示词 + 官方 judge + 4 轮，token 数可以从产物逐题重算。** 在五维记分板上，我们是**唯一一列可核对的**，而这一列现在不利。

**这条比"还差 6.25 点"更值得写进下一步计划**：LongMemEval-S 已经饱和，再抠准确率是测噪声（§1.18）；而 token/查询这一维**还有 1.7 倍的空间，且不需要换数据集**。

#### 四、past.dev 的 BEAM 明细公开了，它把我们 MR 的判断钉死了

past.dev 把评测脚手架开源，逐题结果可查，因此它的四档是可核对的（本文件 §1.18 只列了 100K 与 10M）：

| 规模 | past.dev | 此前最佳 | 备注 |
| --- | ---: | ---: | --- |
| 100K | **92.08** | 86.2 | |
| 500K | **89.63** | 80.1 | |
| 1M | **90.65** | 79.1 | 高于 500K，非单调 |
| 10M | **85.03** | 68.0 | |

而 BEAM 论文自己的基线数字是：**把完整历史塞进上下文，在 1M 规模上准确率至多 25.9%。**

把三个数字放在一行：**全上下文 25.9 → 此前最佳 79.1 → past.dev 90.65（1M）**；**而多会话推理在 10M 只有 28.17%**。这三个数合起来说明一件事：**规模加大时掉的不是"找到"，是"组织"**——这与我们 `41773546221` 的读数（交付 96.4% 金标、满覆盖 89.0%、全线仍 76.03%）是同一个判断在两种尺度上的复现。

### 1.20 本文件 §1.18/§1.19 引用过的一个解释是错的，数字仍然成立

本文件对参考管线（`natural-language-memory.ts`，`benchmark.yml` 那条臂）有两条读数，都来自我们自己的产物，不来自任何厂商：

| 读数 | 值 | 出处 |
| --- | --- | --- |
| 同读者、同 500 题、同判分器，**窗口更小**，MR | **86.78%** | 每个 `cortex-memory` 产物里的 `reference-pipeline` 臂 |
| 上下文规模 vs 我们的 | **小 4%**，总分高 **+2.6** | Raw-RAG 论文的 87.53 对注册臂 90.15 |

第一条**数字没问题，解释错了**。本文件此前跟着内部记录把它解释成"它的 prompt 更沉默"，理由是一句在源码里能逐字找到的话：

```
Work in two steps, but write ONLY the final answer.
Keep those notes to yourself; do NOT write them out.
```

这句话属于 `conInstruction`，而 `conInstruction` 的 docblock 自己写着它服务的是**单会话**阅读提示——四个调用点是 `buildQaPrompt`、`buildPreferencePrompt`、`buildKnowledgeUpdatePrompt`、`buildTemporalQaPrompt`。多会话走 `answerSessions` → `buildAggregationQaPrompt`，Step 1 是：

```
Step 1 — Enumerate every item matching the question's EXACT action, one per line:
  - <item> | <exact action verb from the question> | <session date>
```

**它是写清单的。** 所以"参考管线的优势是沉默"这句话，把一个正确引用到的句子，放在了一条它不描述的路径上。

对竞品分析而言，这件事的教训不是关于参考管线的，而是关于**本文件所有"机制归因"列**的：

> 一个公式或一句 prompt 可以在源码里逐字验证，同时仍然与你要解释的那个数字无关。可验证性不是相关性。

本文件因此收紧一条读法（不是收紧任何数字）：

| 行 | 之前 | 之后 |
| --- | --- | --- |
| 参考管线 MR 86.78% | 机制：沉默的两步 | 机制：**未确定**。它与我们的差异在枚举的**结构**（三段 schema、四种 Step 2 形态、具名 `Answer:` 终止符、不同的弃答许可），这些差异一项都没被单独测过 |
| 本文件任何"它靠 X 赢"的列 | 引文即可 | 引文 + **该引文所在函数的调用点** |

第二行是新增的验收标准，且它已经被实现：`ask-verbatim.test.ts` 的前两条断言把"参考管线的 ask 是沉默的"变成会红的用例。也就是说，这一条不是承诺，是已安装的检查。

#### 1.20.1 这对榜单意味着什么，以及不意味着什么

**意味着**：我们与参考管线之间那 9.92 分，其候选解释从"一个已被否证的假设"回到"一个从未被实际下发过的契约"。这在流程上比数字更重要——一条被误判为"已退休"的轴重新变成可花的钱。

**不意味着**：86.78 这个数有任何变化，它仍然是我们自己产物里的 `reference-pipeline` 臂、同读者同判分器、窗口更小。也**不意味着**我们从参考管线学到了什么新东西——恰恰相反，本轮确认的是**我们一直没抄到它**。

#### 1.20.2 与 §1.19 的 token 列的关系

§1.19 把"每查询 token"列为最难看的一列（我们 ≈11,500 对 Mem0 6,787）。这一节不改变那一列，但给出了它的一条**排他约束**：60 题确认产物 `41845802020` 的 `prompt-overhead` 报指令块中位占 prompt 的 **1.3%**。所以"降 30% token"不可能来自改提示词；它只能来自**决定发多少证据**的机制，也就是 §1.19 列出的那一族（AgentIR 的级联、T2Mem 的测试时装配、MetaMem）。

这两条合起来是本文件目前最有用的一对结论：**准确率的剩余空间在契约里，token 的剩余空间在检索预算里，两者不在同一个地方。**

### 1.21 参考管线的 MR 从今天起是可归因的：同契约、同读者、同判分器

本文件 §1.20 结尾留了一个未完成的句子：*"我们与参考管线之间那 9.92 分，其候选解释从'一个已被否证的假设'回到'一个从未被实际下发过的契约'"*。本轮那个契约下发了（`41860773768`，`ask=verbatim`，参考管线聚合契约整体搬迁，逐行相等断言），于是那一行从"待测"变成"有读数"。

#### 1.21.1 三行数字

| 跑 | 全部 121 | 全带 | 部分带 | 平均窗口深度 |
| --- | ---: | ---: | ---: | ---: |
| 我们，`operands+operand-gap`（`41546569106`） | 76.86% (93) | 75 @ 84.00% | 46 @ 65.22% | 175.2 |
| 我们，`verbatim`（`41860773768`） | **79.34% (96)** | **75 @ 89.33%** | 46 @ 63.04% | 174.1 |
| **参考管线**（同产物内的 `reference-pipeline` 臂） | **85.95% (104)** | — | — | 更小 |

**"全带"** 的定义是：每一条被检索到的金标（rank ≥ 0）都落在窗口内。这个口径原本由一段未提交脚本定义（内部记录 §13.243.2），本轮恢复并固化为 `readout-arm-run.py --split`；它在注册臂与再分配跑上逐位复现，所以这一列与历史可比。

#### 1.21.2 这一列改变了什么，没改变什么

**改变了**：在证据完整的那 75 道题上，我们读 **89.33%**，参考管线在同路线读 **85.95%**。而同读者、同判分器、**从这一跑起还同契约**（§1.20 记录的那次更正就是这个）。也就是说：

> 此前"我们 MR 输给它"是不可解释的 —— 候选解释包括它的提示词、它的证据、它的会话原子分配。现在提示词被拉平了，而在它无法拉平的那一半（证据完整度）上，**我们不输**。

**没改变**：总体 79.34% 对 85.95% 仍是 **−6.61 分、8 道题**。这 8 题全部住在"部分带"（46 题里我们 63.04%），而参考管线**不产生这一带**——它按会话检索、按会话截断，一道题要么整段拿到要么没有。

所以剩下这 8 题的正确名字是：**我们的证据比它碎**，不是我们的读者比它差。

#### 1.21.3 顺带纠正本文件一处会误导的表述

§1.18 与 §1.19 把"每查询 token 11,500 对 Mem0 6,787"列为最难看的一列。本轮另外量出一个必须与它并列的数：**在 prompt 完全未变的 479 道题上，读者的正确性翻转率是 1.9%**（`temp=0`，IE 1 / KU 1 / TR 7 / ABS 0）。这不是竞品数据，但它决定了竞品数据的读法：

> 一条 121 题路线上的单次派发，噪声底是 **±2.3 题**。任何小于 2 题的"领先"或"落后"都不该被写进竞品对比表。

本文件此前没有这条下限，而 Mem0 的 6,787 与该下限无关——它是量级差（1.7×），不是噪声带里的差。

#### 1.22.2 一个新出现的可比性陷阱：**可达率的分母单位不同**

ContextStream 公布的是"**每道题至少一个答案所在会话到达读者**：491/500 = 98.2%"。我们的 67.8%（任意深度）与 46.6%（当前预算）是 **turn 级**：要求**每一个**金标轮都进窗口。

> 会话级可达与轮级可达不是同一个量，差着一个数量级的严格度。把 98.2% 与 67.8% 并排，等于用别人的粗尺子量我们的细活。

#### 1.22.4 一条需要打折接受的"零 LLM"基线

MemPal 公布：**原样存文本 + ChromaDB 默认 embedding，LongMemEval 96.6% R@5，不用任何 LLM**；加 Haiku 重排后 100%。它自己的方法学注脚说明了折扣：**n_results=50、每题只有 30–50 个会话，所以 R@5 在这种语料上测的是排序质量，不是大海捞针**。

这句话把它的意义限定得很死：它证明的是"在会话数少于 50 的语料上，稠密检索已经接近饱和"，而 LongMemEval-S 的 haystack 是中位数 115k token、每题上百轮。**如果这条成立，它对我们的"池子缺失"是一个反证**：同样的稠密检索在我们的 500 题上 missing 161 题（32.2%），在它那里几乎不 missing。差别只可能在两处——embedding 模型（Chroma 默认 vs 智谱 embedding-3），或者单元（会话 vs 轮）。**这两处都可以在不调用任何 LLM 的前提下做对照实验**，这是它给我们的唯一可用之处。

### 1.23 可达率这条可比性陷阱，用我们自己的产物了结了：同粒度下我们是 100%

#### 1.23.1 §1.22.2 提的那个问题，现在有答案

上一节记过一条不可比：ContextStream 公布 *"每道题至少一个答案所在**会话**到达读者：491/500 = 98.2%"*，我们的 67.8% 是 **turn 级、且要求每一个金标轮**。当时写的是"我们量不出来"。

产物里其实有答案：`goldOverlap.carried >= 1` 就是"至少一个金标轮到了读者"，而这是会话级的自然代理。`41860773768` 上：

| 量 | 单位 | 本次 |
| --- | --- | ---: |
| 每个金标轮都交付 | turn，全量 | 51.0%（255/500） |
| 每个金标轮都被检索到 | turn，全量 | 67.8%（339/500） |
| **至少一个金标轮交付** | **会话级** | **100.0%（500/500）** |
| 交付金标轮 / 命名金标轮 | turn | 86.47%（6,499/7,516） |

三行必须一起读，否则每一行都会骗人：

1. 用**他们的尺子**，我们是 100%，高于他们公布的 98.2%。所以"会话级到达"这一栏我们不落后，而且在 DeepSeek 这个更弱的读者上。
2. 用**我们的尺子**（每个金标轮），我们是 51.0% / 67.8%。这才是产品实际面对的困难，也是我们所有"检索缺失"叙事该用的分母。
3. 两个数不是同一条轴的强弱，是**两条不同的轴**。公布 98.2% 而同时 500/500 的我们，说明这个指标在一套 haystack 上百轮的语料上几乎不区分系统——它对"系统能不能找到东西"这件事的分辨率，远低于它的数字给人的印象。

#### 1.23.2 它对"聚合"这个机制的判断意味着什么

上一节说领先者在 MS/KU 上用的是聚合，并把它列为我们最可能被机制修复的单栏。这次读数给了一个更强的理由，也让这个理由更窄：

- 强理由：**没有一道题是"什么都没检索到"**。所以 MS/KU 的损失不是"检索不到"，而是"检索到了一个集合里的一个成员"。这恰好是聚合要解决的问题，而不是换 embedding 要解决的问题。
- 更窄：既然会话级到达已经 100%，那么**再提高召回（换更大的池、换 embedding、换单元）在这条轴上的上限是 0**——它已经满了。能动的只有"到了之后，读者看到多少、以什么形状看到"。

这同时给 §1.22.4 里 MemPal 那条"零 LLM、Chroma 默认 embedding、96.6% R@5"一个更清楚的解读：它测的是**会话/块级**的召回，而那一层在我们这儿已经饱和。它的 96.6% 与我们的 100% 不矛盾，也不构成威胁——它们各自说明的是同一件事：**稠密检索在这个语料上早就够用了，不够用的是把一堆到了的碎片拼成答案。**

#### 1.23.3 本轮不打折也不加码的结论

| 判断 | 依据 |
| --- | --- |
| 会话级到达：**不是**我们的短板 | 500/500 = 100.0%，对 ContextStream 的 98.2%（Opus 5.5 读者） |
| turn 级全覆盖：仍是短板，且是产品面对的轴 | 51.0%（全交付）/ 67.8%（全检索到） |
| MS/KU 的损失性质被改名 | 不是"检索不到"，是"集合只到了一个成员"→ 聚合类机制 |
| 总体排名不变 | 我们 90.40%，榜首 98.4%（Recallium，Opus 5.5）／96.8%（ContextStream，官方判分） |

### 1.24 2026-11-05 二次复扫：三条结构性发现，其中一条直接给了下一机制的名字

#### 1.24.1 新增的可比条目

#### 1.24.2 发现一：**"逐轮原样 + 写时不调模型"已经被公开数据证明是能打的**

Turnbook 与 CoD 两家都是**不做写时抽取**的路线，分别报 91.8% 与 86.6%。Turnbook 自己的失败分析是这段里最值钱的一句：

> 它的 41 个 miss 里有 **33 个**是"需要合并多个会话"、"需要对日期推理"或"需要某个改过口的事物的最新值"的题。

这三类正是我们的 MR、TR、KU。也就是说：**"原样保留"这条路线的天花板，不在检索，而在这三类题的证据组织**——与我们在 §1.23 用自己产物得出的结论（会话级到达 100%，缺的是把到了的碎片拼起来）是同一个结论，来自两个互不相关的团队。

同一条路线上还有一条反向证据（Redis 团队 2026，500 题、模型裁判）：**只用提炼记忆 71.2%，原始片段与提炼事实一起 86.1%**，差 14.9 点。它说明提炼不是免费的，而且代价主要在"名字、日期、具体措辞"这些被摘要吃掉的东西上——与 Turnbook 的 33/41 完全对应。

我们这条线的约束比它们更紧（**每题 0 次新增调用**），而它们证明了这个约束不必牺牲竞争力：Turnbook 是 0 保存 token 拿到 91.8%，CoD 是 0 抽取拿到 86.6%。

#### 1.24.3 发现二：一个"学习式重排"值 ≈5 点，且恰好作用在跨会话上

Turnbook 公布的单变量消融：装上学到的重排器 **91.8%**，换成朴素 rank fusion **87.0%**（其中 380 道从未用于调参的题上 91.1% vs 86.8%）。它自己的注解是：**"它在答案跨多个会话的地方帮助最大。"**

我们的 MR 是 121 题、全带 86.67%、room-cut 为 0。也就是说 MR 上唯一还能动的杠杆就是**选择顺序**，而这条外部证据说这个杠杆值 4.8 点、且正落在 MR 这种题上。这比"再换一个 embedding"有依据得多。

我们已有一条同类机制在册（`retrieval-hybrid` 的 reciprocal-rank 融合 + 可选 cross-encoder 重排），但 §1.17 的 S7 条目测的是"同一 128 宽池子加不加 cross-encoder"，值 3.92 点。**两个独立来源给出同一个量级（3.9 / 4.8），可以当作先验。**

#### 1.24.4 发现三：CoD 把我们刚测出来的缺口写成了一个可执行的算法

这是本轮最有用的一条。CoD 的做法（arXiv:2611.02480，逐字摘要）：

> 在**不变的逐轮记忆**之上做查询时的证据组织：给定一个较宽的候选池，按**查询相关性**、**相对已选锚点的词面多样性**、**新覆盖的查询词**三者分配一个固定的锚点预算，然后**确定性地恢复每个被选锚点所在会话的邻域**。这条链只服务当前查询，底层记忆不动。

对应到我们已经测出来的事实：

| 我们的读数 | CoD 的对应设计 |
| --- | --- |
| MR 的 room-cut 是 0（房间从不切金标） | 问题不在预算大小，在**预算花在哪** |
| 会话级到达 100%（集合在池子里） | 池子够了，缺的是**从池子里选谁** |
| 那 145 道"缺一个金标"的题桶内低 10–17 点 | 缺的是**集合的其它成员**，而它们与问题词面不相似 |
| 每题 0 次新增调用 | CoD 全程无 LLM，纯确定性 |

**它不是我们要打败的系统**（86.6% 低于我们 90.40%），它是**我们要复刻的机制**。判据也要照这个写：不是"超过 86.6%"，而是"在同一套 500 题、同一读者、同一判分器下，MR 的 37 道 undecidable 里有多少被这一机制救回来"。

#### 1.24.5 读者轴再确认一次，并带上价格

Garry Tan 用**同一套记忆系统**换读者：particle-1 91.4%、GPT-6.1 Sol 92.8%、Opus 5.5 94.8%。与 Recallium 的 90.2 → 98.4 是同一个现象，幅度 3.4 到 8.2 点。

同一份对比还给了单价：**每个正确答案 Opus 5.5 为 $0.0993、GPT-6.1 Sol 为 $0.0381、particle-1 约为 Opus 的 1/23**。这给我们 P3（第二家 provider 全量复现）加了一条判据：换读者要同时报 Δ 准确率**与** Δ 每题成本，否则"强模型更好"这句话没有产品含义。

#### 1.24.6 本轮结论

| 判断 | 依据 |
| --- | --- |
| 我们的架构路线（逐轮原样、写时不调模型、0 新增调用）**不是落后路线** | Turnbook 91.8%（0 保存 token）、CoD 86.6%（0 抽取）都在这条线上 |
| 我们的短板与它们的短板**是同一个** | Turnbook 33/41 miss、CoD 的论文动机、我们的 MR/KU，三者都是"跨会话证据组织" |

## 1.25 CoD 的 +1.86 点落在我们自己的噪声带里：机制同族，效应同阶

### 1.25.1 论文正文的四个数，不是一个数

此前（§1.23）我们引用 CoD（arXiv:2611.02480）时只有一个数：LongMemEval-S 86.6%。把正文读完，它是四个数，而且**四个数回答四个不同的问题**：

| 指标 | 数值 | 它回答的问题 |
| --- | ---: | --- |
| LoCoMo 全量 1,986 题 | **76.3%** | 完整管线在这套题上的绝对水平 |
| LoCoMo 非对抗 1,540 题 | **82.2%** | 去掉对抗题后的水平（对抗题 23.6% 是错答） |
| LongMemEval-S 500 题 | **86.6%**（433/500） | 换 benchmark 的可迁移性 |
| **只改分配规则的配对差** | **+1.86 点**（74.5 → 76.3），会话簇 95% CI **[0.59, 3.15]** | **这套机制本身值多少** |

第三行和第四行必须分开读，因为**它们的差值不是机制的贡献**。86.6% 与 76.3% 差 10.3 点，来自不同 benchmark、不同题数、不同答案模型；CoD 自己把机制效应单独测成 +1.86 点，这个做法比多数厂商页面诚实。

而 +1.86 点这个数字，对我们有直接后果。

### 1.25.2 同族机制的效应量与我们的噪声底同阶

我们在 500 题上实测的噪声底是 **±1.6 点**（同配置两次派发，16 题翻转，§13.255.3）。CoD 报告的机制效应是 **+1.86 点**，置信区间下界 **0.59**。

换算到我们的题数：1.86 点 ≈ **9.3 题**，CI 下界 0.59 点 ≈ **3 题**。我们的噪声带是 **±8 题（1.6 点）**。

也就是说：

> **即使我们完整复刻 CoD 的分配规则并得到它报告的那个效应量，单次派发也读不出来。**

这不是说 CoD 弱，是说**效应量与测量精度同阶**——这正是我们把门 3 写成"三次派发合并 ≥21/27"而不是"单次 ≥21/27"的原因，也是 §13.255.6 那条"任何单次非配对差异低于 1.6 点不设结论"的来源。两条约束是独立得出的（我们自己的重跑、CoD 的配对 CI），却给出同一个量级，这提高了双方的可靠性。

### 1.25.3 CoD 的四个设计维度，我们差在哪一格

论文表 1 用四个维度定位七个系统（"无生成式语义记忆 / 固定查询流程 / 集合感知分配 / 源上下文恢复"），CoD 是唯一四项全中的：

| 系统 | 无生成语义记忆 | 固定查询流程 | 集合感知分配 | 源上下文恢复 |
| --- | :---: | :---: | :---: | :---: |
| LoCoMo dialog RAG | ✓ | ✓ | ✗ | ✗ |
| SeCom | ✗ | ✓ | ✗ | ✗ |
| SetR | – | ✓ | ✓ | ✗ |
| CueMem | ✗ | ✓ | ✗ | ✓ |
| ReFind | ✓ | ✗ | ✗ | ✓ |
| Chronos | ✗ | ✗ | ✗ | ✓ |
| **CoD** | **✓** | **✓** | **✓** | **✓** |

我们目前的注册配置在这张表上是 **✓ ✓ ✗ ✓**：无生成语义记忆（逐轮原样存）、固定查询流程（0 LLM 调用）、源上下文恢复（`expandContextWindowBySession` 的会话完成，在准入层）。

**唯一缺的那一格是"集合感知分配"**——即候选之间互相看，而不是各自打分。这一轮 §13.256 实现的正是这一格：锚点选择用"相对已选锚点的词面新颖度"与"新覆盖的问题词"，两者都只有集合存在时才有定义。

值得注意的是 **ReFind 与 Chronos 的第三格也是 ✗，而它们的第四格是 ✓**——"恢复源上下文"这一格单独存在、不等于集合感知分配。这解释了为什么我们的 `session-fill` 规则（按会话最大分填充）在 §13.31 之后仍然停在原地：它恢复了会话，但没有让候选互相看。

### 1.25.4 换成强模型值几点：两个来源给出不同答案

用户要求"实测强模型应更好"，此前我们只有一个来源：Recallium 换读者（GPT-4o 90.2 → Opus 5.5 98.4，**+8.2 点**）。

Agent Zero Memory（arXiv:2608.29606）给出了第二个、更系统的来源。它固定 substrate、只换 backbone，在 LongMemEval 上跑八个模型：

| 事实 | 数值 |
| --- | --- |
| 八个 backbone 的准确率跨度 | **92.20% – 95.60%（3.40 点）** |
| 最准配置 | gpt-5.5，95.60% |
| 最快配置 | glm5.2fast，93.00%，中位 **6.16 s** |
| 最便宜配置 | deepseek-v4-pro，92.20%，**$0.001768/查询** |
| 便宜 20 倍的代价 | **3.4 点** |
| 每美分准确率点数 | opus4.8 **18.0** → gpt-5.5 27.5 → glm5.2 88.0 → deepseek-v4-pro **521**（19×） |

两个来源的对比本身就是结论：

| 来源 | 换模型带来的变化 | 说明 |
| --- | ---: | --- |
| Recallium（GPT-4o → Opus 5.5） | **+8.2 点** | 同一套记忆、不同读者，判分器不同 |
| Agent Zero（8 个 backbone） | **3.40 点** | 同一管线、同一判分，只换主模型 |

**换模型值多少，取决于换的是哪一对、以及判分器是否跟着换。** 这对我们的 P2（第二家 provider 全量复现）是一个具体的设计约束：如果只换答模型而判分器不变，预期差异是**几点的量级**，不是十几点；而如果连判分器一起换，差异会混入判分器方差——已知约 **10%**（见 §1.25.5）。

同时它给了我们一个此前没有的"如果强模型只有几分钱价值"的答案：deepseek-v4-pro 的 **$0.001768/查询** 与 gpt-5.5 的约 20 倍差，落在 3.4 点上。**我们的读者档（DeepSeek）正好是那个最便宜的端点**——这把"我们不是总体 SOTA 但成本效率高"从一句辩解变成了一个可引用的坐标。

### 1.25.5 同一家厂商的两个数字差 13.8 点

Supermemory 在 Agent Zero 的表 3 里是 **85.20%**（LongMemEval），在 2026 年 3 月的一篇第三方汇总里是 **~99%**（"ASMR 多 agent 编排"）。

差 **13.8 点**。不是不同 benchmark，是同一 benchmark 的同一列。

同时一篇独立分析（jakecuth.com 的 agent-memory 图谱）给了两条我们此前只能推断的事实：

1. **oracle ceiling 是 82.4%**（gpt-4o，只给证据会话）；而 Mastra 用 GPT-4o 报 **84.23%**——**高于 oracle**。这不必然是错，但它说明"oracle"在这个 benchmark 上不是上界而是一个配置，任何引用 oracle 作为分母的句子都要说明是哪一版。
2. **"多数引用的分数用 LLM 判分，判分提示词不同会带来约 10% 的摆动"**。

10% 的判分摆动，对我们是 50 道题。这就是我们从第一天起只用**自有判分 + 自有读者 + 自有产物**做 A/B 的原因，也是 §1.24 那张 A/B/C 三级口径表的必要性：**跨来源比较的唯一可靠用法是量级参照，不是名次。**

### 1.25.6 这一轮从竞品那里实际拿走了什么

## 1.26 公开数字的"分母"是什么：区间跨题算的，不是跨跑算的

这一轮我们犯了一个错，值得记在竞品分析里，因为它和竞品怎么报数是同一个问题。

### 1.26.1 我们犯的错

我们把 500 道题放在一起做配对符号检验，得到 **5 胜 18 负（p=0.0106）**，据此判定机制造成回归。产物自己的字段说：其中 **13 个不一致对发生在提示词一个字节都没变的题上**。未变的字节不可能被处理改变——那 13 对是读者与判分器的漂移。

归因之后，可归给机制的是 **−0.80 点**，落在我们 ±1.6 点的噪声带以内。

### 1.26.2 竞品的区间是跨题算的

| 系统 / 报告 | 公开的效应量 | 区间（若给出） | 区间跨什么 |
| --- | --- | --- | --- |
| Chain on Demand（arXiv:2611.02480） | 只改分配规则 74.5% → 76.3%（**+1.86**） | 95% CI **[0.59, 3.15]** | **会话簇**（bootstrap over sessions），不是重复跑 |
| Agent Zero（arXiv:2608.29606） | LongMemEval 8 个 backbone 92.20–95.60 | 无 | 8 个模型之间 |
| Recallium | GPT-4o → Opus 5.5 **+8.2** | 无 | 一次替换 |
| Supermemory | 同一 benchmark 两处报 **85.20%** 与 **~99%** | 无 | 两个来源之间 |

四行的共同点是：**没有一行把"重复跑同一份输入"当成方差来源。** CoD 的区间最严谨，它跨的是会话簇——回答"这个效应对不同的题稳健吗"，不回答"换个时间点再跑一次还是这个数吗"。

这不是他们的疏漏，是成本：跨跑方差要跑两遍全量，而全量一次是几百到几千美元。

### 1.26.3 于是公开数字不能回答的那个问题

对我们这种效应量级（1–3 点）的机制，"这个数稳不稳"比"这个数多大"更关键：

| 问题 | 谁能回答 | 我们的读数 |
| --- | --- | --- |
| 效应跨题稳健吗 | CoD 的会话簇 CI | 已报 |
| 同配置再跑一遍还是这个数吗 | 跨跑对照 | 16 题翻转 = **±1.6 点** |
| 其中多少来自读者/判分器 | 提示词等价比 + 重判 | **3.49%** 未变群体翻转率 |
| 处理到底改了多少题 | 提示词摘要 | **128/500 = 25.6%** |

最后一行是这一轮最有用的一条：**一个机制只改了四分之一的题，那么在四分之三的题上做配对检验，量到的必然是漂移。** 任何"只换一个组件"的 A/B 都有这个形状——包括 §1.25.4 那 3.40 点的"只换 backbone"。

### 1.26.4 我们因此改了什么

1. **配对检验必须与"字节是否改变"的切分并列出现。** 只报一个 p 值，等于把漂移算进效应。
2. **判据的单位要和判据的宽度匹配。** 第一遍的遍间跨度（MR 6–7 题）比门宽（±5）还大，那这个门就不是门。
3. **跨来源比较只作量级参照。** Supermemory 那两个数（13.8 点差）已经演示过：同一 benchmark 不同来源的差距，可能比任何机制效应都大。

### 1.26.5 这一条对 SOTA 主张的意义

我们的总体不是 SOTA（Recallium 98.4%、ContextStream 96.8%、agentmemory 96.2%、Mastra 94.87%、Mem0 94.4%），同口径内我们最高。这一轮之后，这个句式要再加一句：

> 同口径内我们最高，**并且我们报的是四遍均值 + 可归因群体**——这两个数在我们的效果量级上是唯一能站住的口径。

那句话不是修辞。上表四行里没有一行给出跨跑方差，而我们从这一轮开始必须给，因为我们做的是 1–3 点的机制。

### 1.27.1 Redis 的复现报告：同一条链路复现出的 86.5%

Redis（2026-09-21）发表的不是自己的分数，而是一份**把别人也跑一遍**的报告：500 题 LongMemEval-S、统一的 gpt-4o 读者、统一的官方判分提示词、统一记录 ingest 与 query 两侧的 token，然后把自己和第三方系统放进同一张表。

### 1.27.2 Mastra Observational Memory：机制细节，以及它真正的自变量

公开的机制描述（2026 年多篇二手与一手材料一致）：

- 两个后台 agent。**Observer** 在未观察消息累积到 **30k token** 时，把原始消息压成带日期与时间戳的观察条目；**Reflector** 在观察条目累积到 **40k token** 时合并、去重、删过时项。
- 条目是**纯文本日志**而不是结构化对象，用 🔴/🟡/🟢 标优先级，让语言模型直接读到权重，同时人可读。
- 上下文分成前段（观察日志，追加式、稳定）与后段（原始消息）。前段稳定 ⇒ **前缀可缓存** ⇒ 厂商宣称 4–10× 的输入成本下降。压缩比：文本类 3–6×，工具密集类 5–40×（后者厂商自述为轶事，非标准化测量）。
- 分数：gpt-4o **84.2%**，gpt-5-mini **94.87%**。同一套记忆，只换读者，**+10.6 点**。

第三行那个 +10.6 是这份材料里最该被单独拿出来的一条，因为它和我们自己的四次测量是同一个轴：

| 实验 | 变化 | 效应 |
| --- | --- | ---: |
| Mastra（厂商自己的消融） | GPT-4o → GPT-5-mini，记忆不变 | **+10.64** |
| Recallium（厂商自己的消融） | GPT-4o → Claude Opus 5.5，检索不变 | **+8.2** |
| 本仓（2026-10-28） | `deepseek-chat` → `deepseek-v4-pro`，其余不变 | **−7.20** |
| 本仓（`41546569106`） | 两路由 `thinking`，提示词逐字节不变 | **+6.25** |

四行里三正一负，轴是同一个。所以"我们落后 4.25 点是因为读者不够强"这句话在我们自己的数据上是**被否证过的**：我们花过那笔实验并且输了 7.20 点。这条轴买的是**契约遵从**，不是参数量——而这正好解释本轮 §13.261 的发现：同一份字节，读者自己改判 12 个 MR 题。

| 竞品事实 | 我们的读数 | 下一步 |

## 1.28 三条新证据，合起来指向同一个结论：瓶颈在聚合，不在读者

### 1.28.1 《Beyond Retrieval: Evidence Access and Event Aggregation in Agent Memory》（arXiv 2610.19474，2026-10-14）

这是目前与我们的失败形态**逐字对应**的一篇。它的主张分两半：

1. **访问**：记忆在问题出现之前写入，必然要猜什么会重要；所以它保留轨迹原文（source-addressable、无损），只在提问时决定展示什么（**deferred evidence selection**），且全程不调用模型。
2. **聚合**：它引入**聚合负载**这个量——答案要合并的事件数。受控探针上，把完整历史直接交给长上下文读者，**14 个事件时 100% 正确，53 个事件时降到 80%**；在 AMA-Bench 上以编译期推导的负载做代理，轨迹记忆从 1–5 个事件时的 **77.1%** 掉到 100 个事件以上的 **10.0%**。

它的解法叫 **TallyMem**：把"决定数什么"和"数"分开。事前用轨迹建一本事件账本；提问时由模型写一份**事件规格**（scope / predicate / operation），再由**确定性执行器**在账本上求值，返回结果与它用到的 step id。规格支持 count / list / first / last / grouping / timeline。

数字：99 个 held-out MINTEval 仓库上**精确匹配 +13.8 点**（三个读者都涨），受控探针 **+11.0**，完整 AMA-Bench 路由后 69.8% → 71.1%。而且它自己说，做完确定性聚合之后，**残余系统错误的最大一类是事件选择**。

> 三段话里有两段直接命中我们本轮的两个观测：(a) `0a995998` 的 Step 1 只列出 2 项而金标是 3，是选择错误；(b) `6d550036` 把 5 个候选按过窄的动词全排除、答 `0` 而金标是 `2`，也是选择错误；(c) 我们离线量过的"数读者自己的清单"15 破 1 修，正是因为它把 scope / predicate / operation 这三件事压成了一个固定操作。

### 1.28.2 Oolong（arXiv 2511.02817）：聚合是独立能力，而且前沿模型也不及格

Oolong 的设计出发点与 §1.27 的 Redis 报告相反：它认为检索式长上下文评测让模型可以把绝大部分上下文当噪声忽略，于是构造了**必须逐块分析再全局聚合**的任务（计数、用户交叉引用、时序、分布性问题）。

关键数字与结论：

- **没有任何模型在 128K 上超过 50%**（GPT-5、Claude Sonnet 4、Gemini 2.5 Pro 都在 50% 以下）；
- 55K → 175K，所有模型掉 20–30 点；
- **消融：把黄金标签直接给到每个样本，只涨 0.79–10.9 点**——所以瓶颈不是逐块分类，而是"定位相关片段 + 正确合并"；
- 真实数据上的高频失败：token 预算耗尽、说话人混淆、密集交错下的枚举错序、**计数上的过度聚合/幻觉**。

这条对我们是一句冷水也是一句指路：**"把窗口做宽"不是聚合问题的解法**。我们的 `maxPromptChars=48000`、`promptChars` 中位 46,816、会话级可达 500/500 = 100%，这些都在"访问"这一侧，而 Oolong 说的瓶颈在另一侧。

### 1.28.3 内在自我修正的负结果：我们的 −15.7 点不是异常，是被反复测到的现象

| 来源 | 结论 |
| --- | --- |
| Huang et al., ICLR 2024《Large Language Models Cannot Self-Correct Reasoning Yet》 | 无外部反馈的内在自我修正不可靠，且会把**本来正确**的答案改错 |
| ACL 2025《Understanding the Dark Side of LLMs' Intrinsic Self-Correction》 | 自我修正后准确率普遍下降；Llama-3.1-8B **−20.4 点**，**58.8% 的正确答案被推翻**；归因是 **prompt bias**——模型把注意力放到精炼提示上、忽略原问题。缓解：**在精炼提示里重复原问题**，+3.2–4.9 点，推翻率降 5.3–10.9 点 |
| arXiv 2601.00828（2026-01）《Decomposing LLM Self-Correction》 | **Accuracy-Correction Paradox**：弱模型内在修正率 26.8%，强模型 16.7%；并且**给出错误位置提示会让所有模型变差** |

我们这一轮的数字（`42054107910`）：审计覆盖 118 题、469 次咨询、178 次改答（37.9%），配对的 118 题上 **4 涨 22 落**，MR **−15.7 点**；22 个被改坏的答案**全部**变成裸整数，17 个金标本就不是计数。

三件事因此变成有来源的判断而不是我们的孤例：

1. **"再问一遍让它自查"这条路的期望值接近零甚至为负**，我们已经用自己的数据复现了文献的效应量与方向；
2. **重复原契约是最便宜的缓解**——这正是我们新指令里"保持首轮的形式""未改动就逐字重复"两句话在做的事，也与该论文的缓解手段同源；
3. **强模型不一定更会自查**（2601.00828 的悖论），这解释了 §1.27.2 里我们自己的 −7.20 点读者轴结果，也说明"换个更强的读者"不是答案。

### 1.28.4 合起来：我们的下一根轴是事件规格，而不是更好的提示词

| 证据 | 对我们的含义 |
| --- | --- |
| TallyMem：确定性执行 +13.8，残余错误是选择 | 聚合要交给确定性执行器；但要先有**账本**和**规格**，否则就退化成我们量过的 15 破 1 修 |
| Oolong：前沿模型 128K 不足 50%，瓶颈是定位 + 合并 | 加宽窗口无效；要减少读者必须一次合并的事件数 |
| 自我修正三条负结果 | 第二阶段"复核"不产生净收益；价值在**第一阶段的抽取**与**确定性聚合** |
| 我们自己的 20 个满证据失败（14 个 MR，其中 12 个是选择/合并错误） | 与 TallyMem 的残余错误类别完全重合 |

一句话：**竞品与文献在同一个方向上收敛——把"数什么"写成可执行规格、把"数"交给执行器。** 这与 §1.27 的 Redis 结论不矛盾：Redis 说"再加一支证据形态（抽取事实）"，TallyMem 说"再加一个确定性执行器"，两者都不是"换更强的读者"。

## 1.29 修正 §1.28.4：轴是两条，而"够不着"那条更大也更便宜

§1.28.4 用四组证据得出"下一根轴是事件规格"。本轮的量把这个结论**切开**了：事件规格对，但它只覆盖失败的一半，而另一半是检索从不曾提供证据。

### 1.29.1 我们自己的分解（`42013256884`，零模型调用）

| 能力 | n | 证据完整 | 正确率 | 证据残缺 | 正确率 | 可达空间 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `MR` | 121 | 87 | **83.9%** | 34 | **64.7%** | +6.5 |
| `KU` | 72 | 5 | 100% | 67 | 86.6% | +9.0 |
| `TR` | 127 | 90 | 97.8% | 37 | 86.5% | +4.2 |
| `IE` | 150 | 75 | 94.7% | 75 | 96.0% | −1.0 |

`MR` 的 26 个失败分成 **12 残缺 / 14 完整**。§1.28.4 的"事件规格"对的是那 14 个；那 12 个是检索形状的，事件规格碰不到。

更锐的一层：**241 个残缺题里 133 个的金标转从未成为候选**（`pool < total`）。排序在池内怎么改都送不到。

### 1.29.2 三篇 2026 下半年的工作，正好对这条

**《Relevance Is Not Sufficiency》（arXiv 2610.09348）** 把检索重新表述成"构造充分记忆集"，并给出两个可测代理：**Gold Hit** 与 **Turn Hit**。机制是 **BFR（Budgeted Flat Reconstruction）**：先用 Formal Concept Analysis 把问题分解成信息需求、选一个共同覆盖的紧凑子集，再**反复获取未见记录**（更深的文本检索、互补的实体/会话视图），预算耗尽即停。LongMemEval-S 上报 **72.4% → 82.2%** 判分、**Turn Hit 91.4%**。

它有一句话几乎是我们 `pool < total` 的英文原文：

> "Improving selection within the initial candidate pool cannot recover evidence that was never retrieved."

**《What Eviction Destroys》（arXiv 2609.08279）** 给的是仪器而不是机制：**restore counterfactual**——把该题金标证据重新注入读时上下文、重跑**同一个读者**，按"恢复后是否变对"×"证据是否被驱逐"分成 recoverable / irreversible / residual。80k top-k 预算下不可逆占比 **0.67–0.73**（FIFO / 随机 / 冗余感知），LLM-importance 0.60；8k 下 **1.00**。它还明确：recoverable 在 top-k 下存在、在强制金标注入下**按构造不存在**，所以跨预算的"预算-准确率"结果**不可比，除非报检索制度**。

**xMemory /《Beyond RAG for Agent Memory》（Hu et al. 2026）** 反对的是检索单位：转级相似度在对话上会坍缩到一个密集区域，于是它先解耦成 component、再用四级层次自上而下取覆盖。它对我们的直接含义是**反面的**：把 `top-k` 调宽会填进近重复项——这正是 §13.257 已经量过的位移损失（更小的加宽就丢了 8 道 MR）。

### 1.29.3 与 §1.28 的关系，以及为什么不是推翻

| §1.28 的结论 | 本轮的量 | 新读法 |
| --- | --- | --- |
| TallyMem：确定性执行 +13.8，残余是选择 | 我们的 30 道计数型题里仍是 7 选材 / 2 聚合 | **保留**，但它只作用于 30 题，上限 MR +17.4 / 总体 +4.2 |
| Oolong：加宽窗口无效，瓶颈在定位与合并 | 133 题的金标转**从没进过池** | **部分修正**：加宽 *窗口* 无效是真的；加宽 *池* 是另一件事，且它没被识别为"加宽"而是"从没拿到" |
| 自我修正三条负结果 | 修好的审计遍净值 **+0**、翻转率 **3.20×** | **强化**：不发布，默认保持 `bare` |
| 我们的 20 个满证据失败 | 现在是 **14 满证据 + 12 残缺** | **切开**：事件规格对 14 个，检索对 12 个 |

一句话：**§1.28.4 没说错，只说了小的那一半。** 而且小的那一半是"贵"的一半——它要账本、要规格、要执行器；大的那一半要的是"把该拿的拿到"。

### 1.29.4 我们的口径与它们的口径不可直接比

必须写下来，否则下一次会有人把 90.2% 与 82.2% 并排放：

| 量 | 我们 | 它们 |
| --- | --- | --- |
| 判分 | **精确匹配**（trim/lower/压空白后字符串相等） | LLM judge |
| 覆盖 | `carried / total`，**转级**，48,000 字符预算后 | Turn Hit，转级；Gold Hit 会话级 |

所以"我们比 BFR 高 8 点"或"低 8 点"都是假陈述。可比的是**机制**：它们把"没有的证据"当成要主动取回的东西，我们把它当成检索返回的结果。

### 1.30.1 §1.29.1 的"133 题"是真的，而它已经被修掉了——修掉之后什么也没发生

`goldRanks` 与 `goldDelivered` 按同一组金标转对齐，于是 500 题上的 7,516 个金标转每次运行都恰好落在三种状态之一：

| 金标去向 | `42013256884`（k=256） | `42161343457`（k=512） |
| --- | ---: | ---: |
| 到达读者 | 6,476 | 6,522 |
| **排序从未 surfaced**（`rank = −1`） | **264** | **2** |
| 进池、被预算切掉 | 732 | **992** |
| 从池外溢出到达（§13.214 制度） | 44 | 0 |

池宽翻倍把信号侧的失手从 264 压到 **2**，几乎清零。**而被它救回来的 262 个金标转，一个不剩地被预算重新切掉**——切掉的从 732 涨到 992，净到达只多 46 个。

这是本战役最干净的单变量结果。信号问题与分配问题**不是同一个缺陷的两种描述**，而是两个缺陷：第一个已经关掉，关掉它的动作等量转化成第二个。此后任何人说"检索找不到证据"，都要对照这次运行——在那里这句话已经不成立了。

它同时**退役了 §1.29.1 与 §22.28.1 的那条读数**：133 在 k=256 下为真，在 k=512 下是 2。宽度没提升准确率，不是因为读数错了，而是因为预算正站在它身后。

### 1.30.2 宽度是免费的，这是第二个发现而不是脚注

处理组 5,671 次调用对对照 5,668；**prompt token 31,047,070 对 31,076,815**——池子翻倍，token 少了 29,745。预注册给的上限是 +22%，实际花了 −0.1%。

原因是 §22.25 记过一次的那个区分：**offer 不是 delivery**。一道残缺 `MR` 题上，被准入的 offer 是 `evidenceChars = 64,665`，交付的证据是 `promptChars = 45,741`，整条提示词 `deliveredPromptChars = 47,786`，上限 48,000。池子想涨多少涨多少，交付字节由预算钉死，排序只决定**是哪一些字节**。

所以宽度这条轴在**成本**和**效果**上同时收口：它既不该为 token 背锅，也没买到准确率。

### 1.30.3 预算不是"差一转"，是差 2.1 到 6 倍

`tools/evidence-depth.py` 把 `goldRanks` 变成一条覆盖-深度曲线，对运行没用过的深度也算得出来，因为曲线是**选择**的性质、不需要一次调用。

| 路由 | 交付深度 | 字符/转 | 该深度覆盖 | 到 95% 的 room | 到 99% 的 room | 倍数 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| multi-session | 175 | 254 | 90.8% | 63,700 | 100,000 | **2.1×** |
| temporal | 182 | 250 | 88.0% | 70,500 | 104,900 | **2.2×** |
| knowledge-update | 62 | 717 | 78.3% | 143,400 | 239,500 | **5.0×** |
| flat | 61 | 723 | 84.7% | 152,600 | 290,000 | **6.0×** |
| abstention | 72 | 596 | 66.4% | 178,900 | 250,400 | **5.2×** |

缺的金标**不在切口附近**。`multi-session`——余量最大、残缺最多的那条——最后 9 个点的覆盖在 2.1 倍预算之外；`flat` 在 6 倍之外。一个只把接下来几转提前的排序碰不到它们，因为**没有"接下来几转"**：曲线在切口之后按构造变平。

连同 §1.30.1，第二条轴也收口了。买预算是把 prompt token 从 31.0M 推到 65M–190M 之间；诊断的预注册上限是 +22%。这件事没有任何一个版本是付得起的，也没有任何一个版本是被测过的。

### 1.30.4 于是只剩一个该测的问题，而它不是机制

两条轴都被量死了——池子里没有失手，预算在 2.1–6 倍之外——而**两条封闭都没有说金标还回去有没有用**。这正是 arXiv 2609.08279 的 restore counterfactual 要答的，也是 §13.267 注册的那件仪器：

- 如果还回去之后错误答案变成正确答案的比例高，轴是**证据密度**（在 48,000 字符里装下更多 offer），预算原地不动；
- 如果比例低，读者用不上给它的证据，在此之前任何搬动证据的轴都一文不值。

第二个先验不是零。§13.265.6 在这群题上量过一次操作，结果是**修 0 破 10**；而 `multi-session` 上 `accFull = 90.6%` 对 `accPart = 66.7%` 是两个**人群**的差，不是"加一转"的效应。

### 1.31.3 干预的代价：158–1,195 字符

restore 反事实的人群在 `42177443765` 上是 **11 对**（12 失败 / 22 成功 / 1 配不上），而把一道题缺的金标原文还回去要 **158–1,195 字符，占 48,000 预算的 0.33%–2.49%**。

**没有任何一个版本的干预是贵的，也没有任何一个版本是被预算挡住的。** 所以反事实的结果只会是两种之一，没有灰色地带：缺的那一转要紧（→ 集合级选择是正确方向），或者不要紧（→ 读者用不上证据，其余轴作废）。

一句新增的口径约束：**"108/108 装得下"必须连带条件引用**——`top_k = 256`、且只覆盖 `ABS`/`IE`/`KU`。把它读成"cortex 的证据充分性没问题"是错的，那两族没测。

## 1.32 空房间表把战场重新划了一遍：预算轴关闭，"顺序"成为唯一剩下的机制

`42190193540`（`top_k = 512`，`1369fb8f`，与参考 `5492088d` `top_k = 256` 之间只差六个文档与工具文件、`packages/` 一行未动）把 room 表的两行空白填上了，而填出来的数字是零。

| 能力 | n | 全到 | 残缺 | 缺的转在池内 | 装得下 | **房间外** |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `ABS` | 30 | 2 | 28 | 27 | 25 | **2** |
| `IE` | 150 | 75 | 75 | 75 | 75 | **0** |
| `KU` | 72 | 5 | 67 | 67 | 67 | **0** |
| `MR` | 121 | 89 | 32 | **31** | **31** | **0** |
| `TR` | 127 | 93 | 34 | **34** | **34** | **0** |

### 1.32.1 这否证了谁，支持了谁

**它否证了三类竞品方向在本题上的相关性**，而且是否证在"约束根本不在那里"这一层：

- **预算/摘要类**（Mem0 的 summarisation、Letta 的 eviction、Zep/Graphiti 的时序图压缩）解决的是"窗口装不下"，而 room = 0 说这些题**装得下**。它们在这个残差上不会有收益，不是因为做得不好，而是因为它们在解一个不存在的约束。
- **"再加宽一点"**（MemCog 的 92.5% 走的是更强 reader + 更长上下文）在这一族上同样不成立：`offered` 已经是 31/32 与 34/34，池里已经有了。
- **这一点同时把 §13.268 的深度曲线解释清楚了**：99% 覆盖要 2.1–6.0 倍预算，那不是"再多买一点"，而是换一个预算量级；而 room 表说，即便一分钱不加，剩下的失败也不在"没地方放"上。

**它支持的是 BFR 那一支**（arXiv 2610.09348）。BFR 的判分口径是"答案所需的信息集合是否被覆盖"，其机制核心是 **FCA 充分子集**：在候选集合里选出一个**能覆盖需求**的最小子集，而不是按逐条相关性取前 k。cortex 的残差形状正好落在这个定义里——缺的那一转排在 382 位，预算买 175 转，装得下、在池里、就是没被选中。

| 判据 | cortex 残差 | 逐条打分（当前实现） | 集合级目标（BFR 的 FCA 分支） |
| --- | --- | --- | --- |
| 池内是否含齐 | 31/32、34/34 | 是 | 是 |
| 是否装得下 | 31/31、34/34 | 是 | 是 |
| 被选中 | 否 | 逐条相关性排序取前 k | 求覆盖需求的子集 |
| 能表达"需求已满足" | — | **不能** | 能 |

一行注记：`turn` 级的 `recall_all@10 = 88.3%` 与这里的 51.8% 交付完整率**不可相减**——前者是会话级、无 48K 预算、无 reader 的检索口径。

### 1.32.2 是否 SOTA：仍然不是，而这一轮把差距定位到了机制种类

| 量 | cortex | 领先者 | 差 |
| --- | --- | --- | --- |
| `MR`（自身配对口径） | **76.03%（`top_k=512`）– 80.17%（`top_k=256`）** | 同制品参考管线 84.30% | **−4.13 至 −8.27 点 = 5 至 10 题**；两个宽度读数互相矛盾（+0.83 与 −4.13，合并 p≈0.63），所以报一条带而不是一个点 |
| `MR`（公开最高） | — | **MemCog** 92.5%（arXiv 2605.28046） | 口径不同，不可相减 |
| 证据充分性（`fits` 率） | **96.9%（MR 31/32）/ 100%（TR 34/34）** | BFR 的 Turn Hit 91.4% | **不可比**：cortex 这一列是"若完美选择则可交付"，BFR 是"实际交付且被 reader 用上" |
| 交付完整率（转级、48K 预算） | 51.8%（259/500） | 公开 `recall_all@10` 88.3%（会话级、无预算） | 不可比 |

必须写下来的一条：`fits` 是**上界**，不是成绩。把它当作"cortex 证据充分性 SOTA"是这一类比较里最容易犯的错，而 §13.265.6 已经量过一次同形状的干预"修好零题、弄坏十题"。

### 1.32.3 与 MemCog 的差距现在可以拆成两层

MemCog 的 92.5% 与 cortex 的 76.03% 之间隔着 reader 与上下文长度两件事，而这一轮把"上下文"这一层从借口变成了测量：`offered`/`fits` 说上下文**不是**这里的瓶颈。所以若两者用同一 reader 重测而差距仍在，它只可能来自**选择**或**reader 的用法**，这正是 restore 反事实要分开的那两件事。

## 1.33 反事实把"一次性重排"这条路定了价：3.31 点，而距离是 6–9.5 点

`42219514040` 把 22 道题的缺失金标还回去重问，八门全过：**4/12 转化、1/10 弄坏（修正后 0/10）、残差 0.67–0.73**。

### 1.33.1 定出来的价

| 人群 | 数量 | 什么能修 | 对 `MR` 的上界 |
| --- | ---: | --- | ---: |
| 证据残缺、还原后变对 | 4 | 一次性选择/重排 | **+3.31 点** |
| 证据残缺、还原后仍错 | 8 | 上游没有 | 0 |
| **证据完整、仍然答错** | **17** | 只有读者 | **+14.05 点** |

`MR` 的 29 道失败里，**17 道金标全在窗口里**。这条比例把 `MR` 的性质改了：它不是检索问题，在三分之二的失败上它**是阅读问题**。

### 1.33.2 它否证了哪一支，又**没有**否证哪一支

| 竞品方向 | 这一跑说了什么 |
| --- | --- |
| **BFR 的 FCA 充分子集**（arXiv 2610.09348） | **部分否证**。它属于"一次性从候选集里选出覆盖需求的子集"，而一次性选择的天花板被量成 3.31 点。它的判分口径（Turn Hit 91.4%）仍然是对的度量，但机制价值在这一族上有限 |
| **Mem0 的 summarisation / Letta 的 eviction**（预算与压缩） | **无关**。§1.32 的 room = 0 已经说这些题装得下 |
| **MemCog 的 2–3 步 ReAct 检索**（arXiv 2605.28046，92.5%） | **没有被否证，而且这一跑说明了它为什么可能有效**。多步检索不是"重排一个窗口"，是**在部分答案的条件下改变下一次要看什么**——它绕过的是"一次决定看什么"这个约束本身。这是本战役尚未测量的一族 |
| **Raw-RAG**（arXiv:2610.30755，87.5% 总体） | **支持**。带时间戳、分块、稠密检索、重排，不做抽取不做改写，就到 87.5——比本臂高 9 点，而它没有任何"记忆结构"。这与本跑"读者侧承重"的结论同向 |

### 1.33.3 一个必须写下来的数字对照

本臂与参考管线的差，在**同一个 DeepSeek 读者、同一批 500 题、同一个判分器**上，是 5.99 点（`top_k=256`）到 9.50 点（`top_k=512`），而参考管线的窗口**更小**。这意味着这道差的来源可以逐个排除：

- 不是读者（同一个）；
- 不是语料（同一批）；
- 不是判分（同一个）；
- 不是窗口大小（参考的更小）；
- 剩下的是 **prompt 契约**，以及它决定了模型写什么、按什么格式写、写到哪一行算完。

`§13.246` 已经点明三处具体差异：枚举 schema（`item | verb | session date`）、Step 2 的算术指令、以及 `Answer:` 终止符。下一跑就是只搬这三处的消融（§13.277）。

### 1.33.4 是否 SOTA：不是，而本轮把距离的来源从"机制种类"改成了"契约"

| 量 | cortex | 领先者 | 差 |
| --- | --- | --- | --- |
| `MR`（四遍均值，`top_k=512`） | **76.45%** | 同制品参考管线 **85.95%** | **−9.50 点 = 11.5 题** |
| `MR`（四遍均值，`top_k=256`） | **79.34%** | 同制品参考管线 **85.33%** | **−5.99 点 = 7.25 题** |
| `MR`（公开最高） | — | **MemCog** 92.5% | 口径不同，不可相减；其机制族本战役未测 |
| 证据充分性（实际转化率） | **25%–33%**（3/11 或 4/12） | BFR Turn Hit 91.4% | 定义不同，不可相减 |
| 证据充分性（上界 `fits`） | MR 31/32、TR 34/34 | — | 上界，不是成绩 |
| 交付完整率（转级、48K） | 51.8% | 公开 `recall_all@10` 88.3% | 不可比 |

一句话：**cortex 现在落后 6–9.5 点，而这 6–9.5 点里检索最多解释 3.31 点。** 这就是下一轮为什么改打契约，而不是继续在检索上找机制。
