> **阅读约定**：本文件只写**已被证据支持**的内容。未运行的部分明确标注「未运行」，

## 1. B2 实测：这是本轮最重要的数字

### 1.1 实测结果

Run `35498421148`（commit `16ca1ea`），`LIMIT=60`，43 道可答题，
DeepSeek + Zhipu GLM embedding-3，temperature 0：

| k | recalled | recall | ceiling | gain |
|---|---|---|---|---|
| 1 | 12 | 27.91% | 93.02% | **65.12%** |
| 3 | 24 | 55.81% | 93.02% | 37.21% |
| 5 | 27 | 62.79% | 93.02% | 30.23% |
| 10 | 33 | 76.74% | 93.02% | 16.28% |
| 20 | 39 | 90.70% | 93.02% | **2.33%** |
| 50 | 40 | 93.02% | 93.02% | 0.00% |

### 1.2 按预注册读法得出的结论

观察到的形态是 **`gain` 大且 `ceiling` 已平坦** —— 预注册表的**第 1 行**。
对应行动：**执行 B1 的 A/B，不要加宽池。**

三条必须分开陈述的事实：

**一、`ceiling` = 93.02%（43 道可答题中的 40 道）。** 剩下 3 道（6.98%）的答案回合
**根本不在池内**，任何重排都够不到。这是诚实的地板，不是可以实现的目标。

**二、`gain` 从 65.12% 衰减到 2.33%。** 重排能占据的空间，只在「上下文窗口相对答案
排名**很窄**」时才是大的；到了系统实际工作宽度，这份空间**已经被宽度本身吸收掉大半**。

**三、cortex 在可用宽度上没有广度问题。** 这条**关闭了**「加召回通道」这一类提案的方向。
今后任何此类提案，必须针对剩下的 **6.98%** 论证自己，而不是针对 `recall@5`——
那是一个截断点，不是上界。

### 1.3 为什么预注册是必要的

单看 `recall@5 = 62.79%`，读起来像「管线丢了三分之一的证据」，足以支持加池**或**加重排，
二者不可区分。曲线同时给出了**上界**（93.02%，证据其实在）与**排序欠账的真实位置**
（在 k ≤ 10，而非在工作宽度）。

**如果先读数字再定读法，这个 62.79% 会被用来支持一个错误的方向。**

### 1.4 口径警示

60 题分层抽样，不是全量 500。3 道不可达题占 43 的 6.98%，换样本会以约 2.3pp 步进移动。
**曲线形态**（gain 陡降、ceiling 平坦）在此分辨率下稳健；**具体 ceiling 值不稳健**，
对外引用前必须以 `LIMIT=0` 重读。

### 2.2 产物取出通路：三个 Azure 存储账号，与一个被解释清楚的死路

沿用上一轮的结论（artifact API 302 → `*.blob.core.windows.net`），本轮发现**主机名与账号
必须一一对应**，pin 错账号会得到 `AccountNotFound` 而非 403：

| 用途 | 主机 | 可用 IP |
|---|---|---|
| 运行产物（artifact） | `productionresultssa3` | `57.150.27.1` |
| 运行产物（历史） | `productionresultssa1` / `sa15` | `20.209.226.1` / `20.209.113.193` |
| 运行日志（**运行中**作业） | `productionresultssa16` | **不可达——见下** |

**沙箱的 DNS 把所有 `*.blob.core.windows.net` 解析到 `198.18.x.x`（RFC 2544 合成段）**，
必须逐个 pin 到真实 IP。各 `sa*` 是**不同账号**，用 `sa3` 的 IP 访问 `sa16` 会被拒。

#### 死路解析：`sa16` 不是 IP 找错了，而是那个账号在作业运行期间不公开

上一轮把「日志主机不可达」记为**未闭合缺口**。本轮把它查清了，结论**不是**网络问题：

| 作业 | 状态 | 日志主机 | 可公开取回 |
|---|---|---|---|
| `106057222316` | 已完成 | `sa3` | ✅ |
| `106045650999` | 已完成 | `sa1` | ✅ |
| `105795543701` | 已完成 | `sa15` | ✅ |
| `106077768627` | **运行中** | `sa16` | ❌ |

**区分「真 Azure 错误」与「陈旧主机名」的对照实验**：`sa3` 返回
`InvalidQueryParameterValue`（账号存在时的真实前端响应），而 `sa16` 返回带真实
`RequestId` 的 `AccountNotFound`。**两者都是真实的 Azure 响应**——第二个账号在公开侧
**确实不存在**。

**结论（运维层面，非代码层面）**：**运行中的作业无法通过此 API 取实时日志**；进度只能读
步骤列表，日志在作业完成后才可取回。**产物集不受影响**——产物写入公开账号，全程可下载，
这正是本轮所有测量结论从未受影响的原因。

**教训**：`AccountNotFound` 读起来像**权限或凭据问题**，会把人引向「找正确的 IP」。
但对照组证明它是**账号在运行期不可见**。**遇到看起来像权限的错误，先构造一个「本应成功」
的对照组，再决定追哪个方向。**

### 2.3 A2 全量：**运行成功，但测量结果不可取回**

这是本轮**唯一一个没有任何办法用代码修复的失败**，因此必须写得比代码 BUG 更清楚。

A2 全量重测（`LIMIT=0`）在 run `35502712132` 上**跑绿了**——所有步骤通过、报告已生成。
但取产物时得到：

| 探测的主机 | 形态 | 结果 | 判读 |
|---|---|---|---|
| `productionresultssa3` | 有真实 Azure 前端响应 | `409` | 账号存在，但**没有这份产物** |

**对照实验（同一次调查内完成）**：更早的 run `35502712132` 之外，`35498421148` 的产物在

#### 2.3.2 第二次与第三次重派发：**两种不同的失败，不该被合并**

重派发并非一次就好。三轮尝试各有各的失败，且**前一轮都不可能暴露出后一轮的原因**：

| # | run | commit | 结果 | 原因 |
|---|---|---|---|---|
| 1 | `35510619912` | `fe0daa7` | 绿，产物不可取 | 路由到 `sa16`（账号不存在） |
| 2 | `35516440181` | `05eec97f` | **失败** | 格式门禁（`prettier --check`），与 A2 无关 |
| 3 | `35516794168` | `9eb6b7ee` | **绿，产物仍不可取** | 路由到 `sa18`（解到不可公网到达的地址） |

**`sa18` 与 `sa16` 是两种不同的失败模式**，必须分开记录：

**先把三个主机的三层行为分别测出来**（TCP / TLS / HTTP 各测一次，避免把「某一层挂了」
误写成「整个主机不可达」）：

| 主机 | DNS 解析 | TCP 443 | TLS 握手 | HTTP 响应 |
|---|---|---|---|---|
| `productionresultssa3` | `57.150.27.1`（真实） | ok（0.00s） | **ok** —— 真实 `*.blob.core.windows.net` 证书，TLS 1.3 | `400`（缺查询参数的正常 Blob 应答） |
| `productionresultssa16` | `20.209.113.193`（真实） | ok | ok | `404 AccountNotFound` |
| **`productionresultssa18`** | **`198.18.0.53`**（RFC 2544 合成段） | **ok（0.00s）** | **失败：握手期即关闭** | **从未到达** |

**这份表格更正了我先前写下的「`000`/超时」。** 实测的 `sa18` 失败**不是**路由黑洞：
TCP 连接**是成功的**（0.00s，与 `sa3` 无异），失败发生在**握手阶段**。两个独立 TLS 栈
给出一致的错误：

| 工具 | 报错 | 耗时 |
|---|---|---|
| Python `ssl` | `SSLZeroReturnError: TLS/SSL connection has been closed (EOF)` | 立即 |
| `curl`（OpenSSL 后端） | `(35) SSL_ERROR_SYSCALL`，`http_code=000` | **恰好 5.001s**（硬超时） |

两者都指向同一件事：**连接被接受，然后 TLS 不被允许协商。** 这是**沙箱出口代理拦截**
的特征，而不是 DNS 或 Azure 侧的问题。对照组 `sa3` 在**同一次检查中**完成了完整 TLS 1.3
握手并拿到真实证书与 `409`，证明出口、凭据、TLS 能力全部正常。

> **为什么这个更正有价值**：把 `sa18` 写成「解析到不可公网到达的地址 / 超时」，
> 会让人以为修 DNS 或 pin IP 有用。实测否定了这条路——**同为 Azure 真实 IP 的 `sa3`
> 与 `sa16` 都通，`sa18` 的地址段与握手行为才是变量。**
> 精确到「TLS 层被拦截」，才能得出唯一正确的处置：**重派发，等一个可用主机。**

其余两点仍成立：

1. `sa18` 的合成解析**不是沙箱 DNS 造成的**——该主机名本身解析进保留段；
   pin 已知可用 IP 也没用（返回 `404`），其它 Azure IP 返回 `400`。
2. **对照组依然成立**，变量仍然只是**主机分配**。

> **两种模式的共同点是：都只能靠重派发解决，且都在读者唯一会看的地方沉默**——
> 运行是绿的、产物在 API 里列着且未过期、而数字已经没有了。

#### 2.3.3 第四次重派发：**第一个真正带上了第二个出口的运行**

前三轮里有一轮**不是**因为路由失败的（第 2 轮是格式门禁），这暴露了一个更基本的问题：
**重派发只有在「已知新一次尝试里不包含那个原因」时才是修复，否则只是重掷。**

第 4 轮因此改为在 **`a7e846d1`** 上派发（run `35523328949`）——它同时包含格式修复与
§2.4 的第二个数据出口，是**第一个「路由失败也无法静默销毁数字」的运行**。

> **一个必须写清楚的前提，而不是一句安慰**：**只有派发在该 commit（含 sink）之后的运行，
> 才有这个出口。** 落在 sink 之前的运行没有——见 §2.4 的更正。

#### 2.3.4 为什么这与上一轮的日志主机问题**不是同一件事**

两者都是「主机不可达」，但根因不同，处置也不同：

| | 上一轮：日志主机 | 本轮：产物主机 |
|---|---|---|
| 主机 | `sa16` | `sa16` |
| 现象 | 作业运行中取日志 | 作业完成后取产物 |
| 判读 | **设计如此**：运行期日志不公开 | **路由事故**：产物落到了不存在的账号 |
| 影响 | 无法看实时日志 | **测量数据不可恢复** |
| 处置 | 等作业完成 | 重派发 + 增加数据出口 |

**表面相同的症状，根因完全不同。** 这正是为什么诊断必须写到「哪个账号、什么响应、对照是什么」，
而不能停在「网络不通」。

#### 2.3.5 第五种失败：沙箱当前的出口状态**不是**「网络不通」，而是按**主机名**的解析拦截

这一条是**本轮最后发现的、也是最精确的一条**，而且它推翻了我此前对这一状态的描述用语。

本轮末尾沙箱无法推送（`api.github.com` 返回 `000`、恰好 5.001s）。此前我把它记为
「沙箱整体出口故障」（`OPS-SANDBOX-EGRESS-STATE.md` §2 的 condition A）。**逐主机实测后，
这个描述是错的**：

| 主机 | 解析到 | 结果 |
|---|---|---|
| `api.github.com` | `198.18.0.15` | `000` @ 5.001s |
| `github.com` | `198.18.0.14` | `000` @ 5.001s |
| `codeload.github.com` | `198.18.0.35` | `000` |
| `objects.githubusercontent.com` | `198.18.0.40` | `000` |
| `registry.npmjs.org` | `198.18.0.13` | `000` @ 5.001s |
| `pypi.org` | `198.18.0.4` | `000` @ 5.001s |
| `files.pythonhosted.org` | `198.18.0.41` | `000` |
| `www.google.com` | `198.18.0.8` | `000` |
| — | — | — |
| `example.com` | 真实 | **`200` @ 0.57s** |
| `www.baidu.com` | 真实 | **`200` @ 0.03s** |
| `open.bigmodel.cn` | 真实 | **`200` @ 0.10s** |
| `api.deepseek.com` | 真实 | **`401` @ 0.21s** |
| `api.cohere.com` | 真实 | **`403` @ 1.06s** |
| `api.voyageai.com` | 真实 | **`404` @ 1.01s** |

**规则在所有测过的主机上无例外：凡解析进 `198.18.0.0/15` 的名字一律黑洞；
凡解析到真实地址的一律可用。**

三点推论，每一点都改变了处置：

1. **这是解析层条件，不是网络层条件。** `198.18.0.0/15` 是 RFC 2544 基准测试段，
   **在公网不可路由**，所以解析到它的名字**任何客户端都到不了**，与客户端做什么无关。
   **同一时刻** `example.com` 0.57s 返回 `200`、`api.deepseek.com` 完成 TLS 握手返回 `401`，
   证明沙箱出口本身是**健康的**。**「沙箱没有网络」是错的描述**，而任何「等网络恢复」的
   流程都在等一个不是问题的东西。
2. **不是路由故障。** TCP 对合成地址 `0.00s` 就连上了（代理本地接受），
   所以重试、重解析、改请求体都不会有用。
3. **它按名字施加，因此对调用方「间歇」而对每次检查「确定」。**
   同一个进程一分钟前能取 `pypi.org`，解析器改口后就不行。

> **合成段地址本身就是诊断结论。** 一个 `000` 是含糊的；
> 一个「解析进 `198.18.0.0/15` 的名字上的 `000`」不含糊。
> **先读解析结果，再把 §2.3.2 的分层分析当作确认而不是主证据。**

**处置不变但理由被修正**：仍然是**不重派发**（重派发跑在 GitHub runner 上、本来就不受这里影响，
而**取产物**那一步照样会失败）。修正的只是**诊断**：

| 我以为 | 实测 |
|---|---|
| 「出口挂了」 | 出口是好的；一组名字被解析到不可路由段 |
| 「等网络恢复」 | 网络是好的；等的是解析器改答案 |
| 「沙箱没有互联网」 | 同一时刻可证伪（`example.com` `200`） |

**一秒钟的自检，在任何 `000` 被解读之前先跑：**

```sh
getent hosts api.github.com   # 合成段 => 解析层拦截
getent hosts example.com      # 真实段 => 沙箱本身出得去
```

而是**让数字不依赖那一条通路**。

| 项 | 内容 |
|---|---|
| 实现 | `tools/benchmark-summary.py`（8,210 字节） |
| 输出目标 | `$GITHUB_STEP_SUMMARY`（GitHub 原生 UI，**不经 Azure blob**） |
| 接线 | `benchmark.yml` 末步，`if: always()` |
| 测试 | 13 个，以**子进程**方式运行真实脚本（非 mock） |
| **生效前提** | **派发的 commit 必须包含 `98e4a3a` 或之后** |

#### 2.4.1 更正：这个出口**保护不了它落地之前就已经派发的运行**

我此前在 `OPS-UNFETCHABLE-ARTIFACT.md` 里写过「第二个出口让同类失败不再致命」。**对
run `35516794168` 而言这是假的**：它派发在 `9eb6b7ee` 上，而那个 commit **早于 `98e4a3a`**。
该运行的任务**只有 15 个步骤，没有任何 job summary 步骤**——已用运行步骤列表与该 commit 的
workflow 文件双重核对。

所以正确的表述是一个**前提条件**，而不是一句安慰：

> **只有派发在含 sink 的 commit 上的运行，才有这个出口。**
> 已经在飞的运行不会追溯获得它。

这与本仓库缺陷日志里的其余条目**同型**：**把一次修补假定为可追溯生效**。
同样的问题在别处也出现过（修复注解假定能追溯改善已有读数），所以值得单独列出来。

> **推广**：「我加了防护」和「这个失败不会再发生」是两句不同的话，
> 中间差着一个**时序条件**。写下前者时必须补上后者。

**关键设计约束（全部有测试锚定）**：

1. **渲染器永不允许抛异常**。整个脚本是 `if: always()` 的最后一步，它如果在
   benchmark 失败时崩掉，会把一次「有数据的失败」变成「没数据的失败」。
2. **`null` 必须渲染成 `n/a`，绝不允许渲染成 `0`**。这与 §3.9 的重读缺陷同源：
   `JSON.stringify` 会把 `NaN` 写成 `null`，而把 `null` 印成 `0` 会**把一个
   「确定性实验没有 p 值」伪造成「p = 0」**——后者是学术不端级别的误读。
3. **召回曲线是顶层 list，不是 object**。首版实现打印
   `_Unexpected top-level type: list_` 并**静默丢掉整张表**——与 §3 的完整缺陷同型：
   **渲染器在遇到不认识的输入时选择沉默，而沉默读起来像「本来就没有数据」**。
   已按文件名匹配并接受顶层 list，并加测试。

> **一个失败的路由 + 一个独立的出口 = 数据仍然是数据。**
> 这是本轮唯一一个把「把运维失败转化为架构改进」的改动。

### 2.5 **A2 全量测量已收口**：run `35523328949` 的发布级 N=500 结果

这一节补上了此前一直缺的那块：**在含第二个出口的 commit 上完成的、可取的、发布级测量**。

#### 2.5.1 通路：产物通过 DoH 解析取回，而不是通过本地 DNS

先说清楚**这次是怎么取到的**，因为它同时是本轮 §2.3.5 诊断的直接应用。

产物下载 302 跳转到 `productionresultssa10.blob.core.windows.net`，而该名字被解析到合成段。
Azure blob 的 SAS 签名**绑定主机名**，所以把 `sa3` 钉到它自己的真实地址返回 `400`、
钉到 `sa16` 的地址返回 `404 AccountNotFound`——**任何别的 Azure 端点都不会接受这个请求**。
因此需要一个「取回该主机真实地址」的办法：本地解析器给不出，公共 DNS（8.8.8.8 / 1.1.1.1）
也被拦截，但 **`dns.alidns.com` 的 DoH JSON API 可达**，它返回完整 CNAME 链直至 A 记录：

```
productionresultssa10.blob.core.windows.net
  -> blob.blz25prdstrz09a.store.core.windows.net
  -> blob.blz25prdstrz09a.trafficmanager.net
  -> 20.209.226.1 / 20.209.226.129 / 20.209.227.33
```

取回结果：**4,056,049 字节，与 API 报告的产物大小逐字节一致**，21 份报告全部完整。

> **这不是「绕过」，是把诊断用对了。** §2.3.5 的结论是「本地的**解析答案**是错的，
> 而网络本身是好的」；既然如此，正确动作就是**自己给出正确的答案**，
> 并且把每一次替换**记录在日志里**，使「经替换取回」与「正常解析取回」在事后可区分。

| `benchmark-ablation-skipped.json` | **`[]`** | 跳过记录为空，说明本轮**没有任何臂因为输入不足而被跳过** |
| `benchmark-mr-retry` 触发计数 | control **0**，treatment **16 / 500 = 3.20%** | 300 题时是 3/200 = 1.50%，扩容后触发率翻倍且 control 仍为 0 |

**retry 臂在 N=500 上仍然 Δ = 0.00%（McNemar p = 1，Cohen's d = 0）**，
而触发率从 1.50% 升到 3.20%。**这仍然不是证伪**：16 次触发对 500 题的分辨率不够，
但比起 3/200，它已经是一个**有内容可读的计数**。

> **纪律（延续 §3.12）**：**`controlFires == 0` 而 `treatmentFires > 0` 是仪器有效的证据；
> Δ = 0 且 p = 1 是「效应不可见」的证据。两者同时成立时，结论只能是欠功率。**

#### 2.5.6 一个必须**上报**的回归：conjunction 臂 −1.67%

| 项 | 数值 |
|---|---|
| 题数 | 180 |
| baseline | 96.11% |
| feature | 94.44% |
| Δ | **−1.67%** |
| 不一致对 | b✓f✗ = **4**，b✗f✓ = **1** |
| McNemar p | 0.375（**不显著**） |
| cohort | **7/7（complete）** |

**cohort 是完整的**，所以这**不是** §3.6 那类「因输入不足而比较了不同人群」的缺陷——
它是一次真实的、人群可比的负增量。

> **纪律**：**即使 p = 0.375 不显著，也不应把它读作「没有影响」而搁置。**
> 不显著在这里的含义是**这 180 题分辨不出 1.67 个百分点**（4 vs 1 的不一致对），
> 不是「效应为零」。**一条负向点估计 + 完整 cohort，应当触发一次针对性复核，
> 而不是被 p 值挡掉。**

## 3. 本轮发现的 BUG：守卫的爆炸半径

这是**靠运行发现、而非靠读码发现**的缺陷——因为代码单独看是正确的。

### 3.1 现象

Run `35498421148` 在 11 分钟时失败：

```
conjunction ablation cohort is incomplete: 1/7 present, missing 6456829e_abs,
edced276_abs, e5ba910e_abs, gpt4_70e84552_abs, gpt4_c27434e8_abs,
gpt4_fe651585_abs. ...
    at runQueryExpansionDecompositionAblation (runner.ts:831:11)
    at main (bench/run.ts:397:37)
```

**守卫是正确的，且必须继续保持响亮。** R4 的 P2/P3 是针对**七个特定题目**预注册的；
`LIMIT=60` 的分层抽样只保留了 6 个控制中的 1 个，对这个子集打分就等于**用同一个名字
发布另一个实验**。拒绝执行是对的。

### 3.2 真正的问题

守卫的**判决**对，**在程序中的位置**不对。

`bench/run.ts` 在 conjunction 臂之前已经写好了其余全部报告，`main().catch` 只在最后
才持久化 embedding 缓存。于是这个 throw 一路把它们全部带走了：

| 后果 | 细节 |
|---|---|
| 主报告丢失 | `benchmark-report.md` / `.json` 在 08:08 已写盘，但未作为成功产物留存 |
| Markdown 报告丢失 | 同上 |
| embedding 缓存未持久化 | 11 分钟的付费嵌入调用无法被下次运行复用 |
| workflow 红 | `Run benchmark` = failure，读起来像「什么都没产出」 |

产物集之所以还保住了更早的报告，只是因为 `Upload benchmark report` 用了 `if: always()`
——这是**意外的第二道防线**，不是设计。

**缺陷类别**：一个前置条件检查被放在它所保护的工作**之后**，而程序在失败处理时会丢弃
已完成的工作。守卫是为了防止一个错误数字，结果它防掉了整个数字集。

### 3.3 修复（两部分，刻意分开）

**3.3.1 `bench/run.ts` 捕获守卫。** conjunction 臂包在 `try`/`catch` 中。守卫照旧抛出，
消息照旧进 stderr（`conjunction ablation skipped: ...`），其余报告与缓存**存活**。
这次跳过是被**记录**的，不是被**隐藏**的。

**3.3.2 `src/ablation-skip.ts` 记录原因。** 结构化记录——臂名、原始原因、缺失的
cohort 成员 id、分母——每次运行都写入 `benchmark-ablation-skipped.json`，**包括空数组**。

理由：没有它，一个找不到 `benchmark-conjunction-ablation-report.json` 的读者，
无法区分「因已声明的理由被拒绝」与「崩溃」或「从未接线」。产物集现在能解释自己的缺口。

### 3.4 为什么**没有**把守卫降级

最省事的修法是默认 `requireCohortCoverage: false`。这是**错的**：那正是守卫要防的
**空洞通过**——在 `LIMIT=60` 下 P3 退化为一个 0/1 的界，其单侧 95% 上界是 95%，
即**它不可能失败**。现在把严格行为暴露为 `REQUIRE_CONJUNCTION_COHORT`（默认 0），
使这个取舍**显式**，而不是用一个缺陷换另一个缺陷。

### 3.5 测试抓出的两个实现缺陷

**缺陷一（解析错误）。** `parseMissingCohortMembers` 最初用 `/\bmissing\s+([^.]*)\./`。
一个针对**非 cohort 错误**的测试当场拒绝了它：

```ts
parseMissingCohortMembers('the response is missing content.')
// 期望 [] — 实际得到 ['content']
```

未加锚定的模式会把**任何含 "missing" 一词的句子**当成 cohort 缺失，于是一个 provider
错误会被记录成「缺失名为 `content` 的题目」。改为锚定守卫自己的措辞
—— `present, missing <ids>.` ——既更精确，也自我说明。

**缺陷二（死分支）。** `match[1] ?? ''` 分支不可达（`match` 非空时该捕获组必然存在）。
已替换为直接断言 + 注释说明为何不需要回退，而**不是**用 `v8 ignore` 盖住死代码：
解析器里一条不可达分支，会掩盖未来某个把该组删掉的模式改动。

### 3.6 第二个 BUG：修复本身引入的覆盖度侧信道

**这是三个缺陷里最严重的一个，因为它把一个响亮的失败换成了一个安静的错误数字。**

`fe0daa7` 同时做了两件事：包裹 `try`/`catch`（对），以及把 `requireCohortCoverage`
默认翻成 `false`（错）。后者使欠覆盖的 cohort **成功**而非抛出。验证该修复的运行
`35502712132` 产出：

```
benchmark-conjunction-ablation-report.md    <- 存在，渲染为普通报告
cohortCoverage.present: ["80ec1f4f_abs"]
cohortCoverage.missing: 6 of 7
cohortCoverage.ratio:   0.1428
```

对这份 Markdown **全文件 grep** `cohort|coverage|incomplete|missing` → **零命中**。
**一个 1/7 的 cohort 产出了一份看起来完全正常的 35 题消融报告。**

| | 修复前 | 第一次修复后 |
|---|---|---|
| 运行结果 | 红 | **绿** |
| 报告保留 | 无 | 全部 |
| **错误实验风险** | **可见**（运行响亮地死了） | **静默**（报告看起来完整） |

### 3.7 根因

```ts
return { report, markdown: formatAblationReport(report), coverage };
```

`formatAblationReport(report)` 只拿到 `report`，而 `report` 不含覆盖度。**信息在返回点
存在，却与它所限定的东西分离了。** 覆盖度不是关于报告的元数据，**它是报告含义的一部分**。

### 3.8 修复（`0e2c30e`）

1. `AblationReport.cohortCoverage`（可选）——把覆盖度放进报告内部；
2. `runner.ts` **在格式化之前** 附加它，使渲染器**不可能**在没有覆盖度的情况下渲染数字；
3. banner 打印在**结果之上**——印在三张 Wilson 区间表**下面**的警示，是没人会读的警示；
4. `bench/run.ts` 直接序列化报告，消除第二条可能与覆盖度不一致的路径。

**已用真实产物端到端验证**：把 run `35502712132` 的 `benchmark-conjunction-ablation-report.json`
重新喂给修复后的渲染器，输出：

```
> **COHORT INCOMPLETE — read these numbers with care.**
> This arm's pre-registered predictions name 7 specific questions.
  **1/7 (14.29%) are present**; ...
> Missing: 6456829e_abs, edced276_abs, e5ba910e_abs,
           gpt4_70e84552_abs, gpt4_c27434e8_abs, gpt4_fe651585_abs
```

### 3.9 第三个 BUG：报告无法从 JSON 重读（`c17cf88`）

**靠重渲染一份真实的归档产物发现** —— 即任何读产物集的人都会做的那件事。

```
TypeError: Cannot read properties of null (reading 'toExponential')
    at formatAblationReport (report.ts:124)
```

**根因**：JSON 无法表示 `NaN` 与 `±Infinity`，`JSON.stringify` 把两者都写成 `null`。
而单次运行的消融**正好产生这两个值**：

| 字段 | 内存值 | 原因 | `JSON.stringify` 后 |
|---|---|---|---|
| `ablation.pValue` | `NaN` | Welch 跨运行 t 检验需要 `runs ≥ 2` | `null` |
| `ablation.effectSize` | `±Infinity` | 两臂从未分歧 | `null` |

渲染器用 `Number.isNaN(ab.pValue)` 做守卫。**这个守卫对该输入是错的**：
`Number.isNaN(null)` 是 `false`，因为 `null` 不是 `NaN` 这个值，它是另一个值。于是
`null` 走了数值分支并抛出。effect-size 路径连守卫都没有，直接落到 `null.toFixed(3)`。

**为什么现有测试看不见它**：所有 `formatAblationReport` 的测试都在**内存中**构造报告，
其中 `pValue: Infinity` 与 `effectSize: -Infinity` 是真实数字。专门测试这两个值的用例
**通过**，因为它们从不序列化。**只测内存对象的测试套件看不见序列化缺陷**，无论它对渲染
函数的覆盖多完整。

**噪声的一半比崩溃的一半更危险**：用 `?? 0` 之类的朴素修法会把 `null` effect size 渲染成
`0.000`，读作**「无效应」**；而真相是**无限效应**（两臂在每一题上都不同）。
**静默地反转一个结论，比一个堆栈跟踪更糟。**

**修复**：两个带显式 `null` 处理的小格式化器。`null` 被**显式检查**，而不是折进
「非数字」测试里——原缺陷恰恰是「把两者当作同一件事」的假设，替换实现不该换一种拼法
重述它。effect-size 的回退值是 `'n/a'` **不是 `0`**：这是正确性要求，不是风格选择。

**验收**：`report-json-roundtrip.test.ts`（6 测试）用真实归档产物中**逐字**的 `ablation`
对象；决定性用例不是手工造的 `null`，而是**真正产生它的那一对 `JSON.stringify`/`JSON.parse`**。

### 3.10 缺陷三的规模：不是边缘情况，而是**全部**

上一轮把「其他报告是否有同类问题」列为**已知缺口**。本轮将它闭环，而答案**比缺口本身更糟**。
把 13 份已完成运行的 `benchmark-*-ablation-report.json`（覆盖 conjunction / MR / MR-retry /
TR / TR-coverage / TR-window / KU-bitemporal 七个臂）**全部重读并重渲染**：

| 指标 | 值 |
|---|---|
| 审计报告数 | 13 |
| 含 `null` 数值字段 | **13（100%）** |
| 旧表达式可渲染 | **0** |
| 修复后可渲染 | **13** |

**反事实验证同样重要**（在新旧代码上都通过的审计**证明不了任何事**）：把**修复前**的表达式
`Number.isNaN(p) ? … : p.toExponential(3)` 直接作用于同样 13 份真实文件 → **13/13 全部抛错**。

**原因是结构性的，不是偶然的**：单次运行的消融——即**除主基准臂之外的所有臂**——在**每一个臂**
上都会为 `pValue` 产生 `NaN`，因为 Welch 跨运行 t 检验需要 `runs ≥ 2`。**所以每一份持久化报告
按构造就是不可渲染的。** 之所以一直没被发现，只是因为渲染器恰好在序列化**之前**运行，
而唯一存在的执行路径**从不读回自己的输出**。

> **这条缺陷的教训已经超出这个 bug 本身**：一个「永远在写、从不读回」的数据通路，
> **它的可读性从未被任何测试或运行触及**。这比「某个字段错了」严重得多——它意味着归档件
> 的**可信度从未被验证过**。

### 3.11 第四个 BUG：侧信道的**第二个实例**（本轮）

上一轮在修复文档里声明了一个**未审计缺口**：「其他消融臂的 `{ report, markdown, ...extras }`
是否同类侧信道」。本轮把它审计完，**答案是「有」** —— 缺口声明是准确的，闭环它不是形式主义。

**审计范围：`runner.ts` 的全部 9 个消融函数与 9 个返回点**（逐一读码）：

| # | 函数 | 行 | 是否计算了额外值 |
|---|---|---|---|
| 1 | `runEmbeddingBenchmark` | 120 | 否 |
| 2 | `runNaturalLanguageBenchmark` | 178 | 否 |
| 3 | `runMrAggregationAblation` | 252 | 否 |
| 4 | `runTemporalEngineAblation` | 311 | 否 |
| 5 | `runDeterministicCoverageAblation` | 389 | 否 |
| 6 | `runTimeWindowAnnotationAblation` | 471 | 否 |
| 7 | `runBitemporalKnowledgeUpdateAblation` | 532 | 否 |
| 8 | `runAbstentionRetryAblation` | 685 | **是 — `retryFires`** |
| 9 | `runQueryExpansionDecompositionAblation` | 867 | **是 — `coverage`** |

**9 个里 7 个干净。** 缺陷的必要条件是「函数计算了一个**限定结果的值**，然后把它返回在报告
旁边」；那 7 个臂除报告外不计算任何东西，**因此没有东西可泄漏**。真正计算的 2 个，正好就是
`0e2c30e` 和本轮修掉的两个。

**第二个实例的实证**：`runAbstentionRetryAblation` 计算 `retryFires` 并返回在报告旁边。
Markdown 通过返回点的字符串拼接拿到小节，JSON 通过 `bench/run.ts` 的 spread 拿到。把真实归档的
`benchmark-mr-retry-ablation-report.json` 重新喂给渲染器：

```
has "Abstention-retry fires": false
```

**为什么这比「少一张装饰表」严重**：该臂已发表的结果是**零结果**，而源码注释写明，
计数器是唯一能区分「**功能正常但在它帮不上的数据集上**」与「**功能从未接线**」的东西。
删掉小节，这个歧义就完整地回来了。

**修复**：`retryFires` 成为 `AblationReport` 的字段，在格式化**之前**附加；
`formatRetryFireSection` 改为委派给唯一实现 `retryFireLines`，不再持有表格的第二份副本。

### 3.12 修复之后才能读到的事：该臂其实是**欠功率**的

修好之后才能渲染归档件，**这是第一次能把这个臂的计数器与它的准确率数字一起读**：

| 字段 | 值 |
|---|---|
| `controlFires` | 0 |
| `treatmentFires` | **3** |
| `questions` | 200 |
| treatment 触发率 | **1.50%** |

两条结论：

1. **实验有效。** control 可证明为 0，说明 `enableAbstentionRetry: false` **确实**到达了
   retry。此前这是**假设**，现在是**检查过的事实**——而这正是把该臂的零结果与
   「空操作」区分开的断言。
2. **该臂功率极弱。** 200 题触发 3 次，Δ accuracy 最多只能移动 1.5 pp，观测到的零结果被
   这个上界框住。**这次消融没有证明 retry 无效，它证明了 retry 几乎不运行。**
   这是两个结论，下一步动作完全不同，而只有计数器能区分它们。
   **这就是该小节是承重结构而非装饰的具体理由。**

于是渲染器增加了**第三个判决分支**。一个零结果有三种成因，各有不同的应对：

| 计数器状态 | 打印的判决 | 正确的下一步 |
|---|---|---|
| `controlFires > 0` | `INVALID EXPERIMENT` | 修 flag 接线；结果作废 |
| `treatmentFires === 0` | `INERT — never fired` | 找会产生裸弃权的总体 |
| `0 < treatmentFires <= 2` | `INERT — under-powered` | 机制是好的；**别去找接线 bug** |
| `treatmentFires >= 3` | *（无警示）* | 读 delta |

**中间两档必须区分。** 把「触发过一次」并进「从未触发」，会让下一轮去找一个**不存在的接线
bug** —— 这恰恰是计数器要防的误读，所以**渲染器本身不能犯这个错**。

### 3.13 为**缺陷类别**加回归守卫（而非为两个实例）

修两个实例**并不会让这个模式变得非法**，而这一类已经复发过一次。下一轮新写的第 10 个臂
能通过本文件此前的全部测试。于是改为断言**结构不变量**：
**渲染器输出的每一个小节，都必须能仅凭报告对象得到** —— 通过「JSON 往返之后再渲染」来检查，
这里正是所有归档件所处的状态，也正是两个缺陷显形时的状态。

### 3.14 四个缺陷的共同成因（第五、第六个另立一节）

四个都不是「代码写错了」，而是**边界处的假设**：

| # | 边界 | 错误假设 |
|---|---|---|
| 1 | **位置** | 「检查放在哪里都一样」 |
| 2 | **返回值** | 「限定结果的信息可以放在结果旁边」 |
| 3 | **表示** | 「内存里的值和写盘读回的值是同一个值」 |
| 4 | **类别** | 「修掉这两个实例，这个模式就不会再来」 |

**统一纪律**：任何「降级但不失败」的路径，必须同时**产出可见的警示**，否则它比失败更糟。
已固化为 `AblationReport.cohortCoverage` + 报告顶部 banner，以及
`AblationReport.retryFires` + 报告底部三档判决。

### 3.15 第五个 BUG：覆盖率门禁**本身在读噪声**

这是本轮唯一一个**不属于 §3.14 那张表**的缺陷——前四个在测量**产品**，
这一个在测量**测量工具**。

**现象**：`cortex-core` 的覆盖率在同一条 commit、同一份代码上反复运行得到多个不同数字。
在**受控条件**下（单进程、串行、无同工作区并发负载）跑 12 次：

| 已覆盖 / 总数 | 覆盖率 | 出现次数 |
|---|---|---|
| 777 / 789 | 98.48% | 2 |
| 779 / 789 | 98.73% | 3 |
| 781 / 789 | 98.99% | 4 |
| 783 / 789 | 99.24% | 2 |
| （另见）785 / 789 | 99.49% | 1 |

**五个不同结果，跨度 0.76pp。分母在 12 次运行中恒定不变，只有分子在动。**

> **分母恒定是决定性的。** 如果代码在变，分母会变。分母不变而分子变，
> 说明**被测代码没变，测量者对它的判定在变**。

需要说明的是：我此前把波动幅度记为 **±0.5pp**。那是我在看到 98.47 / 98.73 / 98.98
三个值时**从数据反推的**，而不是测出来的——真实跨度是 **0.76pp**。
**把观测到的范围当作「误差」，本身就是在给噪声编一个它没有的上界。**

**这条必须写下来。** 这个数字此前出现过两次（98.22 → 98.98、98.73 → 98.98），

### 3.18 我在这里的第一个根因结论是**错的**，以及它是怎么被推翻的

**第一个版本的结论**（已写进仓库、附带验收表）是：

> 这些守卫经复算确实不可达（连分数在 56 组 `(x, df)` 上复算，观测到的最小 `|c|`/`|d|`
> 约 0.81，而阈值是 `1e-30`，**差 29.9 个数量级**）；因此注解是对的，
> 缺陷在于 v8 对 ignore 提示的**施加是非确定性的**。

**第二半句从来没有被证明过。** 我是从「注解（我以为）是对的」+「数字在动」
**推出**了「所以是施加过程的问题」。这是从一个结论出发的推理。

**第一半句是假的。** 我用了**抛错哨兵法**重新测可达性：把每个守卫体换成 `throw`，
跑真实测试套件。真正不可达的守卫会让套件保持全绿；可达的会当场失败并报出自己。
**这个方法不涉及任何计数器、不涉及任何覆盖率机制**，所以仪器本身不可能与结论混淆。

| 守卫 | 行号 | 哨兵结果 |
|---|---|---|
| 循环前 `\|d\| < 1e-30` | 181 | **可达——6 个测试失败** |
| 循环内 `\|d\| < 1e-30` | 191 | **可达——6 个测试失败** |
| 循环内 `\|c\| < 1e-30` | 196 | **可达——6 个测试失败** |
| 循环内 `\|d\| < 1e-30` | 204 | **可达——6 个测试失败** |
| 循环内 `\|c\| < 1e-30` | 209 | **可达——6 个测试失败** |

**五个守卫全部可达，全部被现有测试触发。** 注解所陈述的理由是**假的**。

**哨兵的补充证据（本轮复现）**：这五个守卫**不需要专门的构造输入**就已经被现有测试
覆盖——单次调用 `studentTCdf(±Infinity, 10)` 即可穿过全部五个。这与 §3.18 的哨兵结论
一致，但把「可达」的门槛降到了**一个普通的既有测试**：

```
studentTCdf(Infinity,  10)  → 1
studentTCdf(-Infinity, 10)  → 0
```

也就是说，注解所声称的「unreachable via valid inputs」在**符号取值**上就不成立：
`±Infinity` 是合法的 `number`，而它恰好是最容易进入这些守卫的输入。

#### 3.18.1 「可达」不等于「承重」——一个必须一起说清的区分

把**五个守卫体全部删除**、只保留其外的算术，重跑同一组输入：

| 版本 | 输出 |
|---|---|
| 原实现（含 5 个守卫） | `[1, 0, 0, 0.5, 0.9842765778816955]` |
| 删除全部 5 个守卫 | `[1, 0, 0, 0.5, 0.9842765778816955]` |

**逐位相同。** 所以正确的描述是双重的：

> 这些守卫**可达**（可达性由哨兵法与 `±Infinity` 路径双重确证），
> 但在当前输入域上**不承重**（删除后输出不变）。

这两句必须一起出现，否则会各自误导：只说「可达」会让人以为删掉会破坏数值正确性；
只说「不承重」会让人以为「不可达」的注解只是措辞不当。
**事实是：注解的理由是假的，删掉它们数值上安全，但删掉的理由不是「不影响数值」，
而是「它们本该被测试覆盖，而注解让这件事不被看见」。**

#### 3.18.2 我的计数器探针为什么会给出相反的答案

**因为探针本身就在制造它要测的那个现象。** 往守卫体里加一条语句，会改变 v8 的
基本块结构，而这条新语句会被归因到**另一行**。

这一点可以直接演示。只给 181 行插桩：

```ts
181|   } globalThis.__G181 = (globalThis.__G181||0)+1;    // 写在 181 行
```

计数器报告 **20000 次命中**。但那 20000 次属于 **178 行的 `if` 被求值**，
不属于 **181 行的 body 被进入**。算术可以验证：扫描调用 `studentTCdf` 恰好 20000 次，
而 `|d| < 1e-30` 对这 20000 个输入**一次都不成立**。

> **一个用来测量「归因错位」的仪器，自己发生了归因错位，
> 就会确认你原本相信的任何事情。**

**这是本轮最重要的方法学教训，也是为什么 §3.18 单独成节：**
我此前那版结论之所以能带着一张验收表进仓库，不是因为写得不够小心，
而是因为**我用一个会扰动被测对象的仪器，去测量那个对象。**

### 3.19 修正过程中挖出的四个**真实**缺陷

#### 3.19.1 `math/ot.ts` 的收敛分支从未被测试（已修）

`sinkhorn` 里的 `converged = true; break;` 两条语句**没有任何测试执行过**：
现有每一次调用要么耗尽 `maxIter`，要么参数选得让收敛永远不成立。
补一个断言「收敛出口确实被走到」的测试即可闭合。`math/ot.ts` 现在 **100% 覆盖**。

#### 3.19.2 `sinkhorn` 的收敛检测器是**失效的**（已修，真实 BUG）

修 §3.19.1 时发现，收敛检测根本没在工作：

```ts
const uPrev = u;          // 引用，不是拷贝
for (...) {
  u[i] = ...;             // 原地修改 uPrev 指向的同一个数组
}
let maxDiff = 0;
for (let i = 0; i < m; i++) {
  const d = Math.abs(u[i]! - uPrev[i]!);   // u 在和自己比
  ...
}
if (maxDiff < tol) { converged = true; break; }
```

`uPrev` 是 `u` 的**别名**，而 `u` 被原地修改，所以 `maxDiff` **恒等于 0**。
于是 `maxDiff < tol` 恒真，`sinkhorn` **永远在第 1 次迭代返回 `converged: true`**——
包括那些根本没收敛的输入。

**决定性证据是 `tol = 0`：**

| 调用 | `iterations` | `converged` | 判读 |
|---|---|---|---|
| `tol = 1e-300` | 1 | **true** | 真实残差不可能满足 `maxDiff < 1e-300` |
| `tol = 0` | 1000 | **false** | `0 < 0` 为假，所以 `maxDiff` 恰好是 0 |

**`tol = 0` 失败而 `tol = 1e-300` 通过，只可能是 `maxDiff` 恒为 0。**
修复：`const uPrev = Float64Array.from(u)`。

**严重性：潜伏，未激活。** `docs/AUDIT-CODE-VS-DOCS.md` 已记录 `sinkhorn`
**导出但从未被调用**，所以产品侧没有消费过这个错误答案。但它会在
`ARCHITECTURE.md` 所述的 optimal-transport distillation 路径接线的**那一刻**转为激活，
并且表现为一个**静默的**「已收敛」——而它并不收敛。

#### 3.19.3 `logGamma` 对**所有负非整数输入**返回 NaN（已修，真实 BUG）

追 §3.18 的「守卫既然可达，是什么把它们带到的」这个问题，一路追进了
`logGamma` 的反射分支：

```ts
return Math.log(Math.PI / Math.sin(Math.PI * z)) - logGamma(1 - z);
```

恒等式是 `ln(pi / |sin(pi z)|)`。**绝对值是承重的，而它被漏掉了。**
`sin(pi z)` 在 `(-1, 0)`、`(-3, -2)`…… 上恒为负，于是 `Math.log` 收到负数，返回 `NaN`。

对 `math.lgamma`（C 库）实测：

| `z` | 期望 | 修复前 | 修复后 |
|---|---|---|---|
| `-0.5` | 1.265512123484645 | **NaN** | 1.2655121234846451 |
| `-0.25` | 1.5895753125511862 | **NaN** | 1.589575312551186 |
| `-0.75` | 1.5757045971498589 | **NaN** | 1.5757045971498587 |
| `-2.5` | -0.05624371649767457 | **NaN** | -0.056243716497675456 |
| `-1.5` | 0.8600470153764812 | 0.8600470153764792 | 0.8600470153764792 |

**它为什么没被测试发现——而原因不是「没人看」。** 仓库里**确实有**一个名为
`logGamma reflection formula handles z < 0.5` 的测试。它断言的是 `z = 0.3` 与 `z = 0.7`，
**两个都是正数**，因此从来不走它名字所指的那个分支。而 `-1.5` 又是好的，
因为 `sin(-1.5 * pi)` 恰好是 `+1`。

> **抽查落在错误的半周期上，与「测试名字描述的代码它根本没碰」，看起来都是健康的。**

**严重性：对统计量潜伏，对公开 API 是坏的。** `logGamma` 从包索引导出。
内部调用只传正数（`df/2`、`0.5`、`n - k >= 1`、`k + 1 >= 1`），所以下游结果从未出错——
而这正是它可以长期不被发现的第二个原因。

#### 3.19.4 `regularizedIncompleteBeta` 在收敛域**之外**求值连分数（已修，真实 BUG）

连分数只在

```
x <= (a + 1) / (a + b + 2)
```

内收敛；域外必须用互补恒等式 `I_x(a, b) = 1 - I_{1-x}(b, a)`。**这个分支不存在**，
于是每当 `x` 接近 1，程序就在求一个发散级数。

`binomialCdf` 传入的是 `x = 1 - p`，所以一个小的 `p` 会把它推得很深：

| 调用 | 精确值（二项 pmf 求和） | 修复前 | 修复后 |
|---|---|---|---|
| `binomialCdf(2, 40, 1e-6)` | 0.9999999999999901 | **0.9694** | 0.9999999999999901 |
| `binomialCdf(2, 10, 1e-12)` | 1 | **6.6e-5** | 1 |
| `binomialCdf(3, 100, 0.02)` | 0.8589615633982938 | 0.8589615633983717 | 0.8589615633982832 |

三点使它比「一个数错了」更糟：

1. **它是静默的。** 返回的是看似合理的数值，不是 `NaN`，没有任何信号。
2. **误差在函数最确定的地方最大。** 小的 `p` 意味着 CDF 基本就是 1，而塌陷正好发生在这里。
3. **它破坏了单调性。** `binomialCdf(k, 40, 1e-6)` 在 `k = 2` 给 `0.9694`、在 `k = 3` 给
   `0.99999`——**CDF 递减是自证无效的。**

**修复本身里还有一个陷阱。** 自然的修法是递归到互补参数对上。若用**非严格**比较
（`x >= 阈值`），程序会**在自己的不动点上无限递归**：当 `a == b` 时映射把
`(a, a, x)` 送到 `(a, a, 1 - x)`，于是 `x == 0.5` 映射到自身。`studentTCdf(t, 1)`
恰好落在这里，因为 `a = df/2 = b = 0.5` 且 `t = ±1` 时 `x = 1 / (1 + t*t) = 0.5`——
栈溢出。**抓到它的是密集网格的性质测试，不是任何点检查。** 比较必须**严格**。

**严重性：激活的。** `binomialCdf` 是真实的统计输出，而单调性是调用方有权假定的唯一性质。

### 3.21 关于「注解其实在藏什么」——这是本节最该被记住的一句话

把六个 `c8 ignore` 全部移除、只跑真实测试套件，得到：

```
真实覆盖率（无注解、当时 1156 个测试）：789 / 795 = 99.25%
```

**在这一测量成立的修订版上，注解藏的不是「不可达的代码」，而是「可达且未被测试的代码」。**
四个循环守卫体从来没有被测试进入过，但它们**可以被**进入，
而注解让这件事不会作为缺口显示出来。

> **一个写着「不可达」的注解，如果代码其实可达，那么它不是文档，是遮蔽。**
> `c8 ignore` 是一句关于代码的断言；**断言为假时，它的危害比没有它更大**，
> 因为它同时压制了缺口告警和后续的复核动机。

**但这句话只对那个修订版成立。** §3.21.1 与 §3.21.2 记录了接下来的事情：
两个无关 bug 修复让守卫真的变成不可达，而最初的哨兵证据本身带着一个假阳性。
「遮蔽」这个结论因此被限定为**历史判断**，不是当前状态。

#### 3.21.1 **但是**：修完 §3.19.3 / §3.19.4 之后，那五个守卫真的变成不可达了

这一段是本轮最值得保留的观察，因为它让「注解是假的」这个结论**不能**被简单收尾。

改完 `logGamma` 的反射符号与 `regularizedIncompleteBeta` 的互补分支之后，
用**同一套抛错哨兵**、在**同一形态的测试套件**上重测：

```
五个守卫全部替换为 throw  →  124 个测试全部通过（套件保持全绿）
```

也就是说，**注解文字「unreachable via valid inputs」现在是成立的，而它写下时是假的。**
两个说法都不需要对方是错的：原作者断言它，实测否证它，随后两个**毫不相关**的
bug 修复又让它意外地成立。

> **注解是关于「某个修订版代码」的断言，不是耐久事实，而且没有任何机制会重新评估它。**
> 一次后续修复可以让一条假注解变真——同样的机制也可以让一条真注解变假——
> 而全程没有任何信号。
>
> 这正是 `coverage-annotations.test.ts` 存在的理由：它**不**去验证理由是否为真
> （那是散文，无法机检），它保证的是**集合不能悄悄变化**，
> 于是任何新增或删除都必须经过一次复核。

**方法注记**：这次哨兵重测差点给出错误结论。第一次尝试把插桩后的文件留在了工作区，
随后一次 `git stash` 周期**静默地恢复了修复前的源码**，于是第一次读到的是
「没有任何变化」——而原因完全不是它看起来的那个。重测前先把原始源码另存并
在前后都断言 `SENTINEL` 计数为 `0`，才算干净。

#### 3.21.2 **哨兵实验本身有一个假阳性**，以及修好之后的干净重测

3.21.1 的那次重测**自己也带着一个缺陷**，而它比前一个更值得记：把某个守卫

```ts
/* c8 ignore next -- defensive guard, unreachable via valid inputs */
if (Math.abs(d) < 1e-30) {
  d = 1e-30;
}
```

**连同注解一起**替换成 `throw` 版本时，恰好有**一个**测试失败——
`coverage-annotations.test.ts` 里的「注解集合被钉住」。那个测试断言的是注解**文字**
仍然存在，所以**删掉注解它就会失败，与守卫是否被执行毫无关系**。
如果照字面读，「一个守卫 ⇒ 一个失败测试」看起来像是「守卫可达」的证据；
实际上它只是「注释被改了」的证据。

修正后的实验**保持全部六行注解逐字节不变**，**只替换被守卫的语句体**，
于是失败的唯一可能原因就是那段语句体真的被执行了：

| 被替换为 `throw` 的守卫体 | 注解文字是否保留 | 失败测试数 |
| --- | --- | --- |
| `welchTTest` 的 df 守卫（第 76 行） | 6/6 保留 | **0** —— 127/127 全通过 |
| `betaContinuedFraction` 的 `d` 初值（第 204 行） | 6/6 保留 | **0** —— 127/127 全通过 |
| 循环内两个 `d` 守卫 | 6/6 保留 | **0** —— 127/127 全通过 |
| 循环内两个 `c` 守卫 | 6/6 保留 | **0** —— 127/127 全通过 |

四次运行在当前修订版上**全部保持全绿**，这是**不依赖计数器归因**的可达性证明：
**被执行到的路径上放一个 `throw`，测试套件不可能通过。**

这同时**修正了先前那个数字**。§3.18 记录的「每个守卫 6 个测试失败」，是在一次
**没有单独保护注解文字**的运行中测得的，因此其中有多大比例属于同一个假阳性，
已无法从当时的记录中分离。诚实的表述只能是：

| 修订版 | 守卫体 | 注解文字 | 失败测试数 | 判定 |
| --- | --- | --- | --- | --- |
| §3.19.3 / §3.19.4 修复**之前** | `throw` | **被删除** | 1（注解钉住测试） | 结论不可采信 |
| §3.19.3 / §3.19.4 修复**之前** | `throw` | 保留 | 未重测 | —— |
| §3.19.3 / §3.19.4 修复**之后** | `throw` | 保留 | **0** | 不可达 |

只有「之后」那一行在方法上是端到端干净的，而注解的真假只能建立在它上面。
「之前」那一行因此被降级为**不可采信**而不是被重述——它所处的修订版已不在树中，
重建它需要回退两个互不相关的 bug 修复。

> **哨兵实验有两个扰动旋钮，两个都必须按住。** 语句体必须变（那是探针），
> 而**其他任何东西都不能变**。这里注解注释就是一个没被承认的第二个旋钮，
> 而它恰好被接到一个「一拧就红」的测试上。

### 3.22 修复暴露出的两个缺陷类别，以及把它们泛化后的第二次命中

修完 §3.19.3 / §3.19.4 并不是终点。那两个缺陷**存活下来的原因是同一个**，
而一旦把这个原因命名出来，就**第二次**命中了它。

#### 3.22.1 一个「以分支命名的测试，从不进入该分支」

`logGamma` 的反射分支挂着一个叫
`logGamma reflection formula handles z < 0.5` 的测试，
而它断言的是 `z = 0.3` 与 `z = 0.7` —— **两个都在直接路径上**。
指向该分支的唯一线索就是它自己的名字，而**名字不是生成器**。
这就是 NaN 能存活的原因：那个测试**看起来**恰好覆盖了出问题的那个分支。

现在 `branch-coverage.test.ts` 用**生成式锚点**覆盖整条非整数轴，
而不是八个手挑的点——因为第一次失败的就是那张表：

```ts
const nearPole = (z: number) => Math.abs(Math.sin(Math.PI * z)) < 1e-6;
fc.assert(
  fc.property(fc.double({ min: -50, max: 50, noNaN: true }), (raw) => {
    const z = Math.round(raw) + 0.37;   // 构造上就是非整数
    fc.pre(!nearPole(z));                // 极点处返回 Infinity 是合法的
    ...
  }),
  { numRuns: 400 },
);
```

#### 3.22.2 一个「内部硬编码了参数的性质测试」

第二个实例更糟，因为它**本身就是一个性质测试**，因此看起来是这类检查的**强形式**。
`binomialCdf` 的单调性测试写的是 `fc.property(n, k, ...)`，
随后却从**外层作用域**取了 `p = 0.5`，从未把 `p` 作为生成输入。

而 `p = 0.5` 恰是 §3.19.4 缺陷**不可能发生**的那个值：
它让 `x = 1 - p = 0.5` 落在连分数的收敛域**内部**。
仓库里其余全部 `binomialCdf` 断言用的是 `p = 0.5`、`0` 或 `1` ——
逐一枚举是 **11 处、2 处、0 处**（那两个 `0`/`1` 在进入连分数之前就被钳位短路了）。
**没有任何一个测试曾在它出错的区间里求值过。**

修法是生成那个真正重要的参数：

```ts
fc.double({ min: Number.MIN_VALUE, max: 1, noNaN: true })
```

用 `Number.MIN_VALUE` 而不是随便一个「很小的数」：
误差随 `p` 缩小而放大，而**最小可表示正数**正是它最糟的地方。

**验证新测试不是装饰**：把修复回退、一次只回退一个缺陷，再跑新测试：

| 注入的缺陷 | 变红的测试数 |
|---|---|
| 从 `logGamma` 反射分支移除 `Math.abs` | **3** —— 含生成式锚点 |
| 从 `regularizedIncompleteBeta` 移除互补分支 | **5** —— 含两个生成式锚点 |

两个缺陷现在都被**多于一个独立测试**捕获，且至少有一个断言的是
**对生成输入成立的性质**，而不是某个常量。

> **性质测试的强度等于它的生成器。** 一个 `fc.property` 的自由变量
> 随即被外层作用域的常量盖掉，**比没有性质测试更弱**——
> 因为它读起来像一个普遍成立的断言。
> 加性质测试时要问的是：**「它要失败的话，必须出现什么输入？而生成器会产生它吗？」**

### 3.23 第七个 BUG：召回曲线的分母**静默缩小**

这是本轮最新的一个，也是**唯一一个不以异常或失败测试现身的**——
它是在核对 A2 全量产物时，把每个能力项的数字与其自身报告对照才发现的。

#### 3.23.1 现象

`benchmark-recall-curve.json` 的每一个百分比都是对 **428** 个问题算的，
而 `benchmark-report.json` 的准确率是对 **500** 个问题算的。
两个文件都没有说它们的分母不同。

```
curve n = recalled / recall = 142 / 0.331776 = 428.00
500 - 428 = 72
```

同一轮运行的 `benchmark-diagnostics.json` **同时记录了两个数**：

```json
{ "totalQuestions": 500, "answerableQuestions": 428, ... }
```

也就是说，产物**知道**分母是 428，也**记下了**它是 428。
没有任何产物记下的是：**哪 72 个被丢掉了、为什么**。
唯一的痕迹是控制台里的一行 `n=`，而那一行印的是**采样数**而不是**测量数**：

```
k      recall   ceiling  gain     (n=500 sampled questions)
```

**这一行就是缺陷的签名**：在基于 428 算出的表格旁边写着 500。

#### 3.23.2 一个排除条件，三种互不相干的成因

`computeRecallCurve` 在答案集为空时排除该问题：

```ts
if (answerTexts.size === 0 || context.length === 0) {
  continue;
}
```

而空答案集有三种成因，只有第一种是设计意图：

| 成因 | 含义 | 排除它是否正确 |
|---|---|---|
| `abstention` | 正确答案就是拒答，证据轮**按设计**不存在 | **正确** —— 它不含检索信号，这是已文档化的规则 |
| `derived` | 问题**可回答**，但答案是**从证据中算出**的，而非陈述在证据里 | **不应静默** —— 这是从分母里移走了一个真实问题 |
| `no-flag` | 问题可回答，但没有任何轮被标记 | **不正确** —— 这是数据/加载器问题，是纯粹的测量损失 |

文档只描述了第一种。`docs/MEASURE-B2-RECALL-CURVE.md` §2.3 的全文说的都是
弃权问题被排除——这是**真的**，也因此被读成了**完整的**。
它从未提到 72 个里有 42 个属于它没有命名的那一类。

#### 3.23.3 那 72 个为什么是 `derived`，以及这才是关键

LongMemEval-S 的 KU 答案是聚合值与更新后的值：

```
'25 minutes and 50 seconds (or 25:50)'   'four'      'the suburbs'
'$400,000'   'Three times a week.'   'Yes.'   '10-12 hours'
'Friday'   'Paris'   'under my bed'   'seven'   '220'
```

72 个里有 66 个短于 30 个字符。这些是读者**从**证据里**产出**的答案，
不是**出现在**证据里的文本。评分路径能正常处理它们——阅读器从四处跑步记录
合成出 "four"——但曲线用的是**逐字文本匹配**，而这个合成值匹配不上任何一轮。

**因此曲线在结构上对准确率第二差的那个能力项是盲的。**
`ceiling = 96.26%` 是关于 IE/MR/TR/ABS 检索的陈述，
它**没有**说 KU 的证据是否可检索，因此**不得**被当作它说了。

> **一个中间的错误假设，记录在此以免被下一个读者重新合并。**
> 早先一轮曾检验「KU 答案是否逐字出现在检索上下文里」，测得 **73.6% 是**。
> 表面上这与本节矛盾，实际不然：**「出现在某个检索块的某处」**
> 与**「是某个被标记 `has_answer` 的轮的文本」**是两个不同的谓词。
> 前者是对拼接串做子串检查，后者才是曲线实际执行的成员测试。
> 正是那个子串结果让错误解释显得可信。

#### 3.23.4 修复：让短fall 自我披露，而不是改变排除规则

对 `abstention` 排除是正确的，对 `derived` 是可议的。
**缺陷是沉默**，所以修的是沉默。

`computeRecallCurve` 现在返回记录而不是裸数组：

```ts
type RecallCurveResult = {
  points: RecallCurvePoint[];
  considered: number;                       // 分母，被明确说出来
  excluded: RecallCurveExclusion[];         // 每一个被丢掉的，附成因
};

type RecallCurveExclusion = {
  questionId: string;
  reason: 'abstention' | 'derived' | 'no-flag';
};
```

分类的顺序承载语义，三处细节是承重的：

1. **`!hadContext` 返回 `null`** —— 没有 user 轮的实例本就无可检索，
   它不是答案集问题，把它算作短fall 会用从来就不可测的问题去灌水短fall。
2. **弃权先判** —— 它是唯一一个「空答案集是预期行为」的情形，
   因此绝不能被打成数据缺陷。若先判 `derived`，每轮运行都会把 30 个弃权问题
   报成缺陷，从而把真正是缺陷的那 42 个埋掉。
3. **`question_id` 是可选字段，读取必须守卫** —— 未守卫的版本在测试第一次跑到
   没有 id 的实例时就抛了 `Cannot read properties of undefined (reading 'endsWith')`。
   这是**测试套件抓出来的，不是看代码看出来的**。
   无法命名的问题仍然被报告（`questionId: ''`），而不是让整个测量崩掉。

三个消费方现在都把它说出来：

| 消费方 | 修改前 | 修改后 |
|---|---|---|
| `benchmark-recall-curve.json` | 裸数组 | `{points, considered, excluded[]}` |
| 控制台（`bench/run.ts`） | `n=500 sampled questions` | `n=428 of 500 sampled questions` + 按成因的明细 |
| job summary（`tools/benchmark-summary.py`） | 只有表格 | 表格 + `Covered **428** questions` + `Excluded **72** (derived 42, abstention 30)` |

summary 同时接受两种形状：旧产物是裸数组，而
**一个在写入方改形状后就停止渲染的 summary，比渲染一张旧表格更糟**。

#### 3.23.5 验证

两半都各自回退过一次并重跑，这是把测试与装饰区分开的检查：

| 注入的缺陷 | 结果 |
|---|---|
| 恢复 `computeRecallCurve` 里的静默 `continue`（不上报 `excluded`） | **5 个失败** / 40 |
| 从 summary 渲染器移除 `curve_denominator` 调用 | **1 个失败** / 15 |

两处随后都恢复，并由 `diff` 确认**逐字节一致**后才重跑门禁。

`recall-curve.ts` 的覆盖率达到 **100 / 100 / 100 / 100**，
从修复刚落地时的 96.66 / 91.30 提升上来。中间那两个缺口是**真实缺口**而非噪声：

| 缺口 | 为何存在 | 补的测试 |
|---|---|---|
| `derived` 分支 | 没有任何测试构造出「有标记但不产出答案文本」的情形 | 用一条携带 `has_answer` 的 **assistant 轮**——它在构建答案集之前就被丢弃，于是标记存在而贡献为零 |
| `haystack_sessions ?? []`（两处） | 所有测试都提供了 sessions | 完全不带该键的实例，分别经由 `computeRecallCurve` 与导出的 `classifyExclusion` |

#### 3.23.6 这是第几个「测量**静默收窄了自己的范围**」的缺陷

| 文档 | 收窄方式 |
|---|---|
| `FIX-COHORT-COVERAGE-SIDE-CHANNEL.md` | 覆盖率被返回在报告**旁边**，于是 1/7 的队列读起来像普通结果 |
| `AUDIT-PERSISTED-NULLS.md` | 序列化时 `NaN` → `null`，于是损失与取值无法区分 |
| `FIX-COVERAGE-GATE-NOISE.md` §12.2 | 性质测试内部硬编码参数，于是生成器看起来覆盖了它其实钉死的参数 |
| **本文档 §3.23** | 分母静默缩小，于是基于 428 的 ceiling 与基于 500 的准确率并列 |

共同结构是：**产物内部自洽，对外误导**。没有抛异常，没有测试失败，
每个文件里的每个数字都正确。错误在于**它邀请读者去做的那次比较**。

共同修法也一样，而且不是「更小心一点」：**让仪器报告它自己施加的边界**。
`considered` 与 `excluded[]` 不是为了测量自身而加的诊断——
它们是「一个可被核对数字」与「一个只能被信任的数字」之间的差别。

#### 4.4.2 一个技术更正：rerank 既不是 LLM 也不是 embedding

| | 编码方式 | 输出 |
|---|---|---|
| **embedding**（bi-encoder） | question / passage **各自独立**编码 | 向量，靠余弦比较——**无法表达交互** |
| **rerank**（cross-encoder） | `question</s></s>passage` **拼成单序列联合**打分 | **相关性标量** |
| **LLM** | 自回归 | token 序列 |

DeepSeek **未发布**任何名为 Reranker 的精排模型，也**不提供**独立 `/rerank` 接口
（由其 endpoint 清单 + 检索双重确认；早先用无效 token 探 `/v1/rerank` 得 401 的探测
**无效**，因为对一条肯定不存在的路由同样得 401——先鉴权后路由，401 对「路由是否存在」
零信息量，已废弃该方法）。

**但这不是阻塞。** rerank 的本质是一个**打分函数**，不是一套协议。把 DeepSeek 接成
**LLM caller** 即可复用其 secret——这正是 `LLMReranker` 的由来，也是用户那个问题的
直接答案：**可以复用，且已实现。**

#### 4.4.5 一个自己写出来、又自己推翻的测试（值得记录）

新增的 `runRerankAblation` 需要证明「baseline 真的没有拿到 reranker」。我先后写了两版

v3 的数字是**实测**的（正确实现 2 次、缺陷实现 4 次），不是推出来的——中途我曾把另一个
更小 probe fixture 上测得的「1 / 2」套到正式 fixture 上，断言立刻变红，才发现**实测值
必须按 fixture 记录**。

> **这一节的意义**：一个「通过的测试」与一个「能发现 bug 的测试」是两回事。前两版都
> 通过了，也都毫无价值。**唯一的判别手段是主动注入缺陷**，这也解释了为什么本仓库
> 每一轮都要做注入验证。

#### 4.4.6 B1 首次实测：判决是「未决」，且实测过程本身抓出一个真实 BUG

按用户指令**自主派发 workflow 取一手数据**，不再靠推演。派发 `35624110842`：
`completed/success`，15/15 步全绿；artifact `10654395809`（1,298,259 字节）已**逐字节**取回。

**读数严格按预注册顺序（`§5.3`，写在看到数据之前）。**

| 项 | 预注册规则 | 实测 |
|---|---|---|
| 精度 Δ | 未预测 | **+1.33 pp**（86.00% → 87.33%） |
| McNemar p | 未预测 | **0.7539，不显著** |
| 规则 1：`fallbacks` | 非 null 且非零 → 不能出判决 | **`null`** —— 见下 |
| 规则 2：`abstentionShift` | 非零 → Δ 被混淆 | **+2.00 pp，已混淆** |
| 规则 3：MR/TR 配对而非合计 | — | MR **0 vs 0**；TR 2 vs 0 |

**判决：不成立、也不否定，而是「本轮无法区分」。** 三条理由各自独立：

1. **Δ 被弃权移动混淆。** 预注册规则是分类式的：shift ≈ 0 才可归因于「读了不同证据」，
   非零即**混淆**。实测 **+2.00 pp**（弃权率 16.67% → 18.67%），故走第二行。
   `AUDIT-B1-HITS0-READ-SITES.md` 早已定位机制：`571` 与 `1009` 两处仍从
   `hits[0].score` 读弃权置信度，故「只改排序」的阶段照样改了**何时拒答**。
2. **n 太小，p≥0.05 只能读作「欠功率」。** 预注册原文即写明「**Underpowered, not
   refuted**」，实测正是如此。MR=22、TR=21 题，需 6:0 才达 p<0.05。
3. **预注册的验收标准本身不成立。** 标准要求 **MR 与 TR 同向移动**，实测 **MR 0 vs 0**
   ——**一个字都没动**。这一条与显著性无关，是直接失败。

**结论：不启用 rerank 默认开启。** 唯一有动量的 TR（+9.52 pp）恰是弃权置信度读自
`hits[0].score` 的能力，即这个动量至少部分来自混淆而非特性本身。

**实测抓到的新 BUG（本轮真正产出）：回退计数器在工厂边界处不可达。**

上一轮刚建的 `readRerankFallbacks` 从工厂返回的函数上读 `fallbackCount`/`bucketCount`，
用来区分「重排无效果」与「重排从未运行」。实测结果为 `null`。探针确认：

```
PROBE llm    fallbackCount: undefined   readRerankFallbacks: null
PROBE local  fallbackCount: undefined   readRerankFallbacks: null
PROBE openai fallbackCount: undefined   readRerankFallbacks: null
```

根因：`buildReranker` 结尾是 `return new LLMReranker({ llm }).score`，而 `.score` 是
**实例绑定的箭头函数**——它带着计数器的闭包，却不带 getter。于是三个 provider 全部返回
`null`，**每一次真实运行都会打印「该 reranker 不暴露计数器」**，正是计数器要防的那种
静默未知，只不过方向相反：不是「误报为零」，而是「永远无可知」。

修复：把计数器以**实时 getter** 投影到返回的函数上（而非快照——快照能通过构造期断言，
却会在任意次失败后仍报 `0/0`，是同一个静默未知换了个更难察觉的形状）。

| 验证手段 | 结果 |
|---|---|
| 先写 7 条测试（TDD），跑 | **3 红** |
| 注入缺陷（回退修复） | **4 红**，24 绿 |
| 恢复后重跑 | 28 全绿 |
| 注入 `fetchFn` 的端到端实调用 | `bucketCount: 2`、`fallbackCount: 2`、`scores: []` |

最后一条最关键：它用真实适配器走真实请求路径，喂一个 200 但内容不可解析的响应，再从
**工厂返回的那个函数**上读计数。「空分数数组 + 两个非零计数」正是此前与「成功但无变化」
无法区分的那个签名。

## 5.1 一个会让负面结论不可证伪的缺口

`LLMReranker` 在某个 bucket 解析失败时返回**短数组**，`rerankHits` 读短数组为失败并
**返回输入序**。这是正确的失败语义——给失败的 bucket 填一个中间分会**用编造的分数重排候选**。
但它有一个在 adapter 存在之前不可见的测量后果：

> 若**所有** bucket 都失败，feature 臂与 baseline 臂**行为完全相同**，消融报告输出 `0.00 pp`。
> 这与「rerank 试过了但没用」是**同一个数字**。

也就是说，B1 的负面结论本来**不可证伪**：「rerank 没帮助」与「rerank 从未运行」是同一份输出。
§7 那条「记录结果，包括负面结果」的验收标准，在能区分这两者之前是无法执行的。

**修复**：`LLMReranker` 暴露 `fallbackCount` / `bucketCount`（跨调用累计，因为检索管线
每轮调用一次 `score`），`runRerankAblation` 通过一个**结构化读取**（`readRerankFallbacks`）
把读数带进报告，bench 入口把它打印在 delta 旁边。

| 读数 | 含义 |
|---|---|
| `fallbacks: null` | reranker 不暴露计数器（普通 `RerankScoreFn`）。delta 无法归因。 |
| `fallbackCount === 0` | 每个 bucket 都解析成功。delta 度量的是 reranker 本身。 |
| `fallbackCount > 0` | reranker 对部分 bucket **弃权**，即它比预期**更保守**，delta **低估**了 feature。 |

**`null` 而非 `0` 是刻意的**：伪造的 0 是把一个未测量的数字摆在已测量的数字旁边。
半 instrumented 的情形同理——非有限计数器返回 `null`，而不是在合理数字旁渲染 `NaN`。

**为什么用结构化读取而不是扩展 `RerankScoreFn`**：`(pairs) => Promise<number[]>` 被
`/rerank` HTTP 客户端、本地 cross-encoder、LLM adapter 三者共同实现；把计数器塞进契约
会迫使**不可能以这种方式失败的实现**也背负它们用不上的记账。

**注入验证**：移除 `this.fallbacks += 1` → `llm-reranker.test.ts` **3 条精准变红**，已逐字节恢复。

## 5.2 试着自己跑一次，发现了与 rerank 无关的真实缺陷

写这份文档需要反复跑门禁，而门禁**两次**报告了一个不存在的缺陷。追它的过程产出了一个
与重排毫无关系、但会咬到任何改动导出签名的人的真实发现。

`bench/run.ts` 用**自己的包名**导入本包：

```ts
import { runRerankAblation, /* ... */ } from '@agentix-e/cortex-eval';
```

在 `moduleResolution: NodeNext` 下，包对自身名字的解析走 `package.json#exports` →
`dist/index.d.ts`。**所以 bench 的 typecheck 读的是构建产物，不是它旁边的源码。**
CI 先 build 后 check，因此一直免疫；本地则表现为：

```
bench/run.ts(518,39): error TS2339: Property 'fallbacks' does not exist on
  type '{ report: AblationReport; markdown: string; abstentionShift: number; }'
```

`fallbacks` 在 `runner.ts` 里、在返回类型里、是正确的。报错却指向同样正确的 `bench/run.ts`。
**错的是 `dist/index.d.ts`——它是改动前的陈旧副本**，而输出里没有一个字提到这一点。

**两次修复尝试，第一次是错的，已回退**：先加了 `paths` 别名把包指向自身源码。
`paths` 在 `NodeNext` 下**不覆盖 self-name 解析**。它看起来对，为它写的测试也通过了
（那些测试只断言配置文本），直到做了一个真正的实验——**覆盖 `dist/index.d.ts` 后重跑
bench typecheck，仍报 `TS2306`**——才证明这个别名是**惰性的**。

**有效的修复是一个字符的意图**：

```json
"typecheck": "tsc -p tsconfig.json --noEmit && tsc -p tsconfig.bench.json"
```

`--noEmit` 就是缺陷本身。它宣称在类型检查，却**不动下一条命令要消费的产物**，
于是第二次调用编译的是某个无关 `build` 最后写下的 `dist`。

**由实验而非推理验证**（因为第一次尝试修复也是错的）：早期草稿删了 `--noEmit`，
但编译器**仍然跳过 emit**——`incremental: true` 加上未过期的 `tsconfig.tsbuildinfo`
让它相信没有东西变过。删掉 build-info 后 `dist` 被重建（**16 字节 → 5657 字节**），
机制得到确认。

**回归守卫**：`dataset.test.ts` 中一对断言——一条钉住顺序，一条钉住源码调用里不含
`--noEmit`。两条都**在把 `--noEmit` 注入回去时确认变红**。

**与既有纪律的关系**：§5.1 和 §5.2 都不是靠读码发现的，都是靠**运行**发现的。
§5.2 尤其是「本地门禁若是 CI 门禁的真子集」这条纪律的镜像——这次不是子集问题，
而是**两条路径读的是不同的东西**，于是本地报告了 CI 永远不会报告的错误。

### 7.1 关于第 4 项的一个后续判断（改变了下游规划）

§3.12 读出的 **1.50% 触发率**（`treatmentFires: 3` / `questions: 200`，`controlFires: 0`）
改变了对这个臂的看法，必须进入下一轮规划：

- 该臂的零结果**不是**关于 retry 有效性的证据，它被 1.5 pp 的上界框住；
- 因此 roadmap 中任何以「retry 已证伪」为前提的条目都需要**重新表述**
  （已在 `07-sota-roadmap.md` §9.3 落地）；
- **但也不能反向解读为「retry 有希望」**——3 次触发同样支持不了正向结论。
  **欠功率的零结果约束的是我们的认知，不是产品的质量。**
- 唯一可执行的推论是：**若要让这个臂可判决，瓶颈在「产生裸弃权的总体」，不在 retry 本身。**
  这与 §3.12 的判决表一致，也是为什么渲染器要区分「从未触发」与「欠功率」。

> 这条判断的价值不在结论，而在**它是由仪表读数驱动的**：如果没有那个计数器，
> 这个臂会以「零结果」被归档，而「零结果」会被读成「已证伪」。

> **纪律**：第 13 项在任何情况下都**不得**先于第 8–12 项。B3 是成本 × 通道数的架构级改动，
> 而 B1 的 A/B 尚未取得任何实测数据。在仪器刚读出第一个数字时投入架构级改动，
> 正是本仓库历史上多次回滚的模式。

> **本轮新增纪律之一**：**修复必须被验证，而不能被假定。** 第 2 项正是「验证第 1 项的修复」
> 才发现的缺陷——如果不验证，一个 1/7 cohort 会以正常报告的形式进入文档。

> **本轮新增纪律之二**：**「重新运行一次就好了」是危险信号。** 覆盖率读数此前两次波动
> 都被我用「缓存过期」解释掉（§3.16），第三次才去查，而它是真缺陷。
> **需要重跑才能正常的数字，本身就不是证据。**

> **本轮新增纪律之三**：**凡是「降级但不失败」的路径，都必须留下可见痕迹。**
> `sa16` 路由失败是一次**绿了但读数丢了**的运行——如果它没有在产物取出阶段暴露，
> 这份「全绿」会被当成一次成功的 N=500 测量写进报告。

> **本轮新增纪律之四（最贵的一条）**：**当测量不稳定时，先检查「你用来解释它的工具」
> 是否稳定。** 第 7a 项的教训：我用一个**会扰动被测对象**的探针去证明那些行不可达，
> 而探针本身制造了它要测的归因错位，于是它确认了我原本相信的结论。
> **结论被写进仓库并附了一张验收表**，直到换成不扰动的抛错哨兵才被推翻（§3.18）。
> **推论：任何「我测过」的结论，都必须同时交代「用什么测的」；
> 而「用什么测的」本身也可能是个错误答案。**

> **本轮新增纪律之五**：**说「某主机不可达」之前，必须分层测到位。**
> §2.3.2 的更正：我把 `sa18` 写成「不可公网到达 / 超时」，
> 而实测是 **TCP 通（0.00s）→ TLS 握手期被关闭**。
> 「不可达」是结论，不是测量；**TCP / TLS / HTTP 三层必须各自给出一次读数**，
> 否则处置方向会错（前者会让人去修 DNS 或 pin IP，而正确处置是重派发）。
> **推广：一次失败要写到「哪一层失败」，而不是「失败了」。**

> **给下一轮自己的提醒**：上一轮把「沙箱内不可执行」误判成「不可执行」，代价是整整一轮
> 实测被推迟。**先验证执行环境的边界，再声明 blocker。**
>
> **本轮的对应提醒**：五个缺陷里**没有一个**是靠读码发现的。凡「写盘 → 读回」「降级但不
> 失败」「前置检查与它所保护的工作」「测量工具与被测对象」这四类边界，
> **必须用运行或重读来验证**，读码不可替代。
