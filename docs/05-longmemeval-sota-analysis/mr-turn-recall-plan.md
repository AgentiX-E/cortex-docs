## 1. 原本坏在哪里

`retrieveTopKSessions` 用一个会话**各轮向量之均值**来代表该会话。一个问题的证据通常是长会话
中的某一短轮，因此每一个无关轮都会把质心拖离查询。

在被遗漏的 19 个证据会话上实测：

| 量 | 值 |
|---|---|
| 每会话轮数 | 11.1 |
| 每会话 token 数 | 1,582 |
| answering turn 中的 token 数 | 90 |

离线归因（上一次迭代）已确认这些遗漏是**系统性的，而非 top-k 边界问题**：14 个部分召回
问题中只有 1 个在 8 次运行间翻转，且 18 个被遗漏会话中有 0 个达到那些*被*召回会话的词汇
重叠度第 25 百分位。因此修复必须是排序，而非容量。

## 2. 我不得不撤回的一个论断

我最初报告轮次级评分带来 **3.22 倍提升**。那个数字来自一个词袋余弦代理，它是有长度偏置的：
余弦会除以 `sqrt(|doc|)`，因此一个短轮仅凭长度就能压过一个长会话。在基于它继续之前，我跑了
一个长度对照。

`mr_turn_length_control.py`，对每个被遗漏会话计算四个分数：

| 分数 | 定义 | 均值 |
|---|---|---|
| `s_sess` | `cos(q, whole session)` | 0.0256 |
| `s_turn` | `max_i cos(q, turn_i)` | 0.0806 |
| `s_rand` | `cos(q, random window, same length as the best turn, drawn outside it)` | **0.0073** |
| `s_head` | `cos(q, first-turn-length window)` | 0.0616 |

**长度偏置被证伪。** 一个长度匹配的随机窗口得分是整个会话的 0.28 倍——远*低于*它，而非
高于它。仅凭短本身并不会抬高分数。增益来自**定位到相关片段**：最佳轮比长度匹配的随机窗口高出
**11.10 倍**。

对该量级能迁移到稠密嵌入的独立佐证：对 `n` 个互相正交的轮取均值池化，会把质心的投影缩小
约 `1/sqrt(n)`。当 `n = 11.1` 时，这相当于 **3.33 倍**，而实测的原始提升为 **3.15 倍**。

### 第二处更正

我曾把机制描述为*"一个离题的头部稀释了质心。"* 数据却表明并非如此：在排名前 10 的案例中
有 7 个 `s_head == s_turn` 完全成立，即 answering turn **就是**第一轮。真正的机制仅仅是：
一段约 90 token 的片段丢失在一个约 1,582 token 的会话之中。只有少数案例确实存在真正离题的
头部。同一个修复，不同（且现在正确）的理由。

## 3. 参数的可行性

`mr_turn_feasibility.py` — 若一切都按最佳轮评分，一个被遗漏会话相对于那些*被*检索到的会话
会排在哪里：

```
competitive with retrieved (>= median best-turn): 18/19 (95%)
rank among retrieved: median 4.0   within top-3: 9/19   within top-5: 16/19 (84%)
```

上下文预算（`turn_recall_ab.py` §3，121 个 MR 问题）：

```
sessions/question : median 12   p90 17   max 33
chars/question    : median 13,001   max 18,168   (budget 20,000)
clipped by budget : 0/121
```

最坏情况下的余量为 1,832 字符 ≈ 1.9 个会话，中位数 ≈ 7,000 字符 ≈ 7 个会话。多出的三个
会话在最极端的问题之外处处都放得下，而在该问题处一次部分裁剪的代价约为三个中的一个。

## 4. 设计

在 `retrieval.ts` 中新增原语 `retrieveSessionsByTurns`：将每一个轮索引到一个携带其所属
会话的 id 之下，按查询检索各轮，把每次命中归因到其会话，以各会话的**最佳**轮为其打分。

四个特性使其风险较低：

| 特性 | 为什么重要 | 如何得到保证 |
|---|---|---|
| **零边际嵌入成本** | 该变更不得抬高 API 开销 | 轮向量就是 `buildSessionIndex` 已经计算并均值池化的同一批向量；二者都命中共享缓存 — 由测试断言 |
| **严格可加** | 不能丢失基线已有的证据 | 手头的会话在设上限*之前*被排除，且结果是追加、绝不重排序 — 由测试断言 |
| **弃权不受影响** | `hits[0].score` *就是*弃权信号 | 轮余弦高于质心余弦，因此按分数合并会把一个新增会话提升到 `hits[0]`；追加则保住它 — 由测试断言，且 `sessionAbstainThreshold` 置于两个分数带之间 |
| **有界** | 上下文不得爆炸 | 至多 `turnRecallSessions`（3）个额外会话 |

搜索深度为 `turnRecallTurnsPerQuery = 50`。一次搜索无论如何都会给每个被索引的轮打分，因此
深度是**免费**的；它之所以重要，是因为已检索会话的轮占据了排名的顶部，而浅搜索只会返回已经
在手的会话。一个测试锁定了这一点：在深度 5 时该通道不增添任何东西，在深度 6 时它找到目标。

默认值仅对 MR 路径开启。`answerSessions` 被独占路由到 MR（`benchmark.test.ts` 断言了这一
点），因此 IE / TR / KU / ABS 是干净的阴性对照。`turnRecallSessions: 0` 为该 A/B 禁用该
通道。

## 6. A/B 设计 — 主要端点是确定性的

一个证据会话是否被检索，完全由嵌入余弦决定，且提供方在每次运行前均已在 temperature 0 下
验证为确定性。因此证据召回**没有采样方差**：每臂一次运行即可精确测量它。相比之下，准确率
位于运行级别约 ±1.6pp 的实测噪声下限之上，仅作为描述性估计报告。

- **主要（确定性）：** 证据召回完整的问题，以及恢复的会话数。对不一致对做 McNemar。
- **次要（受噪声下限约束）：** 各能力准确率、弃权，配合精确置换检验。
- **守卫项：** 仅可加（回归是相对于臂内不稳定基线而言，而非零——查询扩展由 LLM 生成，
  即使在 temperature 0 下每次运行也会翻动几个问题）；非 MR 零效应；预算裁剪。

`analysis/turn_recall_ab.py <root>` 已就绪，并已针对 `ab_deriv` 做过冒烟测试；在该处两臂
均无此通道：它正确地报告 0 个改善、0 个超出基线的回归，且所有守卫项 PASS。

该冒烟测试还在我自己的脚本中抓到了**三个测量缺陷**（轮前缀正则中一个未闭合的 `{2`、
把会话当作轮来计数、以及把逐会话截断误认为聚合截断）——这也正是我发现早先那次
"0/121 处于预算上限"的检查在测量错误对象的方式（它检查的是已经截断过的输出）。更正后的
检查以正确的理由确认了同一个结论。

## 7. 阻塞项 — 已解决

沙箱曾失去出站网络：DNS 把 `github.com` 解析到 `198.18.0.0/15` 黑洞段，TLS 握手被终止，
且 `pypi.org` / `huggingface.co` 不可达。

根因：`/etc/hosts` **在每次工作区重启时被重置**，而 GitHub 直连 IP 映射只持久化在
`~/.user_hosts` 中。该工作区曾重启，因此 `/etc/hosts` 恢复为出厂文件、DNS 落入黑洞。将
`~/.user_hosts` 中的七条 `github.com` / `*.githubusercontent.com` 记录重新追加后，出站立即
恢复（`api.github.com -> 200`）。

这是一个**反复出现**的故障模式：任何沙箱重启之后，都要重新追加那些行，否则 DNS 会静默返回
黑洞地址。

## 9. 发现并修复的测量缺陷（会话计数）

`ctx_sessions` 数的是以空行分隔的块。但一个会话自身的轮中含有空行——多段落的助手回复——
因此计数被抬高了。在上一次迭代的对照臂上实测：

| | 均值 | 最大 |
|---|---|---|
| 朴素块计数 | 18.62 | 157 |
| 真实会话数 | 3.41 | 13 |
| 多计 | 15.21，出现在 349/470 条记录上（74%） | |

现在，一个块仅当其**首行带有轮前缀**时才计为一个会话；续块以散文开头，会被跳过。修复后的
数字与 `DEFAULT_SESSION_TOP_K = 10` 一致（中位数 10，最大 13），而修复前的数字并非如此。

该缺陷从未触及主要端点——证据召回是直接把证据指纹与检索到的字符串做匹配——只影响描述上下
文大小的统计量。但修复前的数字会让"新增会话数"读起来比实际大 5.5 倍。

## 10. 发现并修复的测量缺陷（静默的运行名冲突）

`DATA` 是一个以**运行目录名**为键的扁平字典，横跨两臂。两个同名运行会坍缩成单一数据集，
随后分析就在把一个东西与其自身比较——报告出一个与"该变更什么都没做"无法区分的完美零结果。
这由下方的功效检查发现（两个合成臂都被命名为 `run_1`）。现在会硬性 `SystemExit`，而非静默
归零。

## 11. 功效检查 — 端点被证明是敏感的，而不仅是对的

一个零效应冒烟测试只能证明脚本在什么都没发生时读出零；一个永远读出零的坏端点也能通过它。
因此 `ab_power_check.py` 注入一个*已知*效应：它取一个真实对照运行，为每个受影响的 MR 问题
追加一个真正缺失的证据会话（使用与分析相同的指纹测试——精确匹配是错误的，因为已检索的会话
已经过截断、绝不会逐字出现），并检查脚本恰好恢复出那个数目。

| 变体 | 注入 | 检出 | 回归 |
|---|---|---|---|
| 无 20k 预算（端点敏感性） | 15 | **15** | 0 |
| 带 `truncateText(.., 20_000)`（按已交付版本） | 15 | **15** | 0 |

15 个改善 → 12 个问题达至证据完整，McNemar p=6.1e-05。

由此得到两点：

- **这 15 个受影响问题相互吻合**，与早先根因分析中独立发现的 15 个证据不完整问题一致——
  两种不同方法在"奖品规模"上取得一致。
- **20k 聚合预算在这里没有任何代价。** 对照上下文中位数为 13,001 字符，因此多出一个会话
  处处都放得下。（多出三个会话则不然：最坏情况的问题只有约 1,832 字符的余量，因此真实的
  A/B 在该处至多能恢复 3 个名额中的约 2 个。功效检查只注入一个会话，所以它有意不压测那个
  情形。）
