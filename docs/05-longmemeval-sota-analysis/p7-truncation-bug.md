# P7 —— `truncateSession` bug：真实、已修复，且在此数据集上几乎惰性

**状态**：已修复并验证（`pnpm check` 通过，671 项测试，覆盖率
99.89 / 98.66 / 100 / 99.89）。**“这解释了 MR 平台期”这一主张是错的，已在 §3 中撤回。**
被取代的文档保留为 `p7-truncation-bug-superseded.md`，以使该错误留在记录中。

## 1. 该 bug（真实）

`truncateSession` 在第一个大到放不下的用户回合处停止：

```ts
if (used + turn.length > maxChars) { truncated = true; break; }
```

`break` 抛弃了每一个剩余回合，包括那些每个只花 200 字符、本仍能放下的
助手开头。该函数自己的文档字符串说它“保持每个用户回合完整并限制助手回合” ——
`break` 做的恰好相反，而如果循环无法越过一个超大回合继续，`ASSISTANT_HEAD_CHARS`
就毫无意义。实现与契约相矛盾。没有测试捕获到它。

## 2. 修复

在 `natural-language-memory.ts` 中做两遍：

- **第 1 遍**选择哪些用户回合存活，跳过超大回合而非停止。
- **第 2 遍**按顺序输出，且仅当
  `used + head + suffix[i+1] <= maxChars` 时才接纳一个受限的助手开头，
  其中 `suffix[i+1]` 是仍将到来的被保留用户回合的总大小。
  因此一段冗长的回复永远无法挤掉那些它只为其提供上下文而存在的事实。
- 一个其最小用户回合仍超出预算的会话将保留不了任何事实，因此回退到
  `truncateText`。

TDD：先写 5 项测试，全部 5 项对旧实现失败，之后全部通过。
它们覆盖：保留多个用户回合、预算确实被花费、短回合在更早的超大回合之后存活、
助手开头不挤掉之后的用户回合，以及无用户回合可放下的回退。

## 3. 已撤回：“该框架丢弃了其预算的 84%”

被取代的文档报告 **316 个金标准会话中 0 个**完整抵达，且字符数的中位
**2000 中的 325**（2.2%）存活，并把责任归给 `break`。**那个测量是错的。**

原因：`answerSessions` 在*检索之前*剥离助手回合：

```ts
const factSessions = sessions.map((session) => session.filter((t) => !isAssistantTurn(t)));
```

但诊断中的 `answer_sessions_content` 存储的是**未过滤**的主体。
用完整主体去匹配渲染后的框架，会在第一个助手回合处断裂 ——
这就是为什么“存活的字首”总是约 283 字符，恰好一个回合长。流水线是好的；
比较不是。

更正后（`mr_attribution_v2.py`，它先过滤助手回合）：

| 证据状态 | n | 正确 | 准确率 |
|---|---|---|---|
| PRESENT | 115 | 101 | **87.8%** |
| MISSING | 6 | 1 | **16.7%** |

不是 22 个 MISSING，而是 **6** 个。检索占 **19 个错误中的 5 个（26%）**，
而非最初报告的 42%。**抽取是主导项：19 个中的 14 个。**

## 4. 已更正：该修复几乎不移动 MR

以流水线实际截断的形式（助手回合已剥离，预算 2000），在 316 个金标准会话上
重放两种实现：

| 指标 | 之前 | 之后 |
|---|---|---|
| 超出预算的金标准会话 | 60 / 316（19%） | — |
| 保留的用户回合 | 1752 / 1832 | 1757 / 1832 |
| 丢失的用户回合 | 80 | **75** |

1832 个中恢复了 5 个回合 —— 0.3%。原因是结构性的：
LongMemEval-S 的用户回合是同质的（约 270 字符），因此贪心首次适配
已经接近最优。`break` 只在一个大回合后面跟着小回合时才有害，
而本数据集很少产生这种情况。

**结论：修复是正确的，但它不是 MR 平台期。** 该平台期是抽取问题。

## 5. 剩余的错误实际在哪里

在证据完整在场的 14 个错误中：

| 失效模式 | n | 例子 |
|---|---|---|
| 少数（枚举过少） | 4 | `3→2`、`3→2`、`3→2`、`2→1` |
| 多数（枚举过多） | 3 | `3→4`、`4→5`、`4→6` |
| 求和错误 | 2 | `$3,750→$8,750`、`$720→$200` |
| 证据在场却弃权 | 3 | `UNANSWERABLE`、GPA、页数 |
| 评分产物 | 1 | 见 §6 |
| 歧义 | 1 | `100→300 points` |

多数与少数一样常见，这排除了“检索漏掉了一项”的说法。模型枚举了错误的集合。

## 6. 新线索：评判器不遵循官方协议

案例：金标准是 `'11 days (or 12 days, if April 15th to 22nd is considered as 8
days)'`，预测是 `'12 days'` —— 被评为**错误**。金标准明确认可 12。

`judge.ts` 要求：

> “判断预测答案是否与标准答案语义等价。”

官方 LongMemEval 评判器的要求实质上更宽松：

> “如果回答**包含**正确答案，请回答 yes。[…] 如果回答等价于正确答案
> **或包含所有中间步骤**以得到正确答案，你也应回答 yes。”

我们要求的是**等价**；官方要求的是**包含**，并明确计入中间步骤。
我们还省略了官方协议按问题类型添加的时间性差一容差，
以及知识更新的“更新后的答案取代之前的”条款。

后果：我们的准确率是在一把比已发布基准所用**更严格**的尺子上测量的，
因此它与已发布的 LongMemEval 数字不可直接比较。这是一个独立于任何模型改动的
效度问题。

**尚未据此采取行动。** 改动评判器会改变数字，因此在采纳任何东西之前，
必须把它作为一次消融，在相同的预测上对照当前评判器来测量。
