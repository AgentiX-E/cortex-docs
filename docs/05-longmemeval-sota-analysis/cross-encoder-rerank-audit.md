# 交叉编码器重排 — 深度审计（P1）

**日期：** 2026-09-06
**目标：** 评估在刚落地的 RRF 融合之上叠加交叉编码器重排阶段的可行性与 ROI，
且须在 cortex 的约束下（TS monorepo、DeepSeek LLM + Zhipu 嵌入、无默认本地模型运行时）。

---

## 1. 重排为何存在（前沿证据）

双编码器为*召回*而检索（正确答案位于 top-K 的某处）；交叉编码器为*精确率*而重排
（正确答案排在第 1 位）。NeuroLink 的基准（500 条查询，RRF top-20 → top-5）是最干净的
公开数字：

| 策略 | Precision@5 | 延迟 | 每次查询成本 |
| --- | --- | --- | --- |
| 不重排（仅 RRF） | 0.71 | 0 | $0 |
| 批量 LLM（列表式） | 0.85 | 180ms | $0.0005 |
| LLM 重排（逐候选） | 0.88 | 420ms | $0.002 |
| Cohere Rerank | 0.90 | 130ms | $0.001 |
| **本地交叉编码器** | **0.91** | 95ms | $0（本机） |

AgentOS（LongMemEval-S 85.6%）搭载了一条三阶段链路——本地交叉编码器（120→30）→
Cohere（30→15）→ LLM 评判（15→5）——并带有优雅降级。

## 2. cortex 的当前状态

- **没有重排阶段。** `retrieveSessionsForQuestion`（MR）与 `retrieveTopKByQueries`
  （单会话）止步于 RRF 融合 + 轮次召回追加；`answerSessions` 直接把有序命中截断后
  塞进提示词。
- **已有一个 transformers.js 接缝。** `cortex-llm` 提供了 `TransformersEmbedding`，
  带有惰性的 `@xenova/transformers` 导入与可注入的 pipeline 工厂——但它**只**是
  *feature-extraction* pipeline；**没有交叉编码器 pipeline**，也没有重排器。
- **LLM 接口是够用的。** `complete` / `completeStructured` 可以在不引入新依赖的前提下
  运行一个列表式 LLM-as-reranker。

## 3. 方案权衡

| 方案 | 精确率 | 成本 | 新依赖 | 契合度 |
| --- | --- | --- | --- | --- |
| **批量 LLM 列表式重排**（DeepSeek 在一次调用中对有序候选列表打分） | 0.85 | +1 次 LLM 调用 / 题（约 3-4K tok） | 无 | ✅ 复用 DeepSeek |
| LLM 逐候选重排 | 0.88 | +N 次 LLM 调用 | 无 | ⚠️ 昂贵 |
| 本地 ONNX 交叉编码器（Transformers.js） | 0.91 | 模型下载 80-560MB + CPU 推理 | 扩展现有接缝 | ⚠️ 重，新 pipeline |
| Cohere Rerank API | 0.90 | 按调用计费 | 新密钥 | ❌ 新供应商 |

## 4. 诚实的 ROI —— 这可能不是正确的下一个目标

有三点事实支持谨慎：

1. **RRF 已捕获了大部分精确率增益。** RRF 通过修复跨通道融合把 MR 从 75.21% 提到
   79.55%（+5.25/运行）。重排是在已融合排序之上的*第二*轮精确率处理——其边际增益小于
   第一轮。
2. **LongMemEval-S 的 MR 大多是单一事实。** NeuroLink 的 +0.14-0.20 提升是在一个带有
   否定/冲突问题的困难技术语料上测得的；该基准的 MR 计数/聚合问题这类病态较少
   （DCG 的负面结果已表明多重证据技巧无法迁移）。
3. **TR 是更大的开放缺口。** TR 处于 73-75%，而 HydraDB 为 90.97%——一个约 15pp 的
   窟窿，重排并不能填补（那是时序图 / 时间感知检索的缺口，不是精确率缺口）。

**判决：** 交叉编码器重排在这里是*真实但二阶*的杠杆。其置信度最高的形态（本地 ONNX）
与 cortex 的零本地模型哲学冲突，并给基准引入 80-560MB 下载 + CPU 推理；其最廉价的形态
（批量 LLM 列表式）是一个约 0.85 精确率的启发式，大概只能买到 ≤+1-2pp 的 MR，代价是
每题 +1 次 LLM 调用。

> **判决更新（2026-09-22，实测）：上述「≤+1-2pp」的上界也未能落实。** 管线已接线并可
> 派发（`benchmark.yml` 透传 `CORTEX_RERANK` / `RERANK_*`，LLM 形态复用 chat 凭据，
> **零新增 secret**）。两臂实测（n=150，托管端点，`temperature=0`）：
>
> | 臂 | Δ | McNemar p | `abstentionShift` |
> |---|---|---|---|
> | 无保护 | **+1.33 pp** | 0.7539 | +2.00 pp（Δ 被混淆） |
> | 钉住前 N 个 hit（关闭混淆通道） | **−1.33 pp** | 0.7539 | +0.67 pp |
>
> **符号相反、幅度相同、p 相同** → 该量级即噪声。且预注册的「MR 与 TR 同向移动」
> 在两臂上都失败：MR 分别**动 0 与动 −1**，TR 两臂都恰好 **+2** —— **只有 TR 动、MR 不动
> 或倒退，正是预注册要排除的形态**。**正确读法是「n=150 下未测到效应」（欠功率，
> MR=22/TR=21 题，需 6:0 才达 p<0.05），而非「已证伪」**——但它足以否决默认开启。
>
> 对照臂的 `fallbacks = {fallbackCount: 0, bucketCount: 300}` 确认 300 个 bucket 全部
> 真实打分、零次弃权，因此这条负结论**可证伪**：它不是「重排从未运行」伪装成的零效应。
> 详见 `09-progress-and-delivery-report.md` §4.4.6 / §4.4.8。
>
> **对本审计建议的影响**：§5 的 P1（批量 LLM 列表式重排）**前提不成立**——它是「仅当
> 探针显示 MR precision@k 是约束瓶颈时才做」，而这里 MR 实测零移动。P0（面向 TR 的
> 时间感知检索）**因此成为唯一未被实测否定的路径**，优先级上升。

## 5. 建议（P0 → P2）

| # | 举措 | 理由 |
| --- | --- | --- |
| **P0（建议改为执行此项）** | **面向 TR 的时间感知 / 时序图检索**——把 cortex-core 已有的双时态事实 + 关联图接入 TR 检索路径 | 直击 ~15pp 的 TR 缺口（最大的单一窟窿），使用 cortex 已拥有的原语 |
| P1 | **批量 LLM 列表式重排**（仅 MR），先以小型 A/B 为闸门 | 便宜、无新依赖；仅当探针显示 MR precision@k 是约束瓶颈时才做 |
| P2 | 经由现有 transformers 接缝的本地 ONNX 交叉编码器 | 精确率最高，但依赖更重 + 需要模型下载；推迟到 P0/P1 穷尽之后 |

如果用户仍想在时序检索之前做重排，具体的 P1 规格为：新增
`rerankSessions(query, hits, llm)`，返回由单次列表式 DeepSeek 调用重新排序后的命中；
将其插入 `retrieveSessionsForQuestion` 与 `answerSessions` 之间；以列表式排序单元测试
+ 变异测试（删除重排必须使测试失败）做 TDD；在 MR 机制端点上做 A/B。
