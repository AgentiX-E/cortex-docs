# P5 —— MR 聚合守卫，重新定量

**判决：** MR 聚合守卫（`mr-cot-aggregation` 对 `mr-legacy-aggregation`）
是**真实且巨大的**，而它是本项目中对噪声底施加的每一项更正都存活下来的唯一守卫。
其增量为 **121 道中的 +42 至 +50 道题（+34.7 至 +41.3 pp，均值 +45.8 道 / +37.8 pp）**，
对照的是 **13 道题**的 MR 范围内运行间噪声底。在最小的观察增量上，
它以 **3.2 倍**的幅度越过其噪声底。

`p5-verdict.md` 和 `p5-pairing-verdict.md` 附在 MR 上的“14 q / 11 pp”那个数字
**根本不是 MR 的数字**。把它沿产物追溯，它是 **TR 引擎**守卫
（`tr-llm-temporal` → `tr-deterministic-temporal`，127 中的 83 → 97，14/127 = 11.0 pp），
它在八次单独的以 TR 为重心的运行中都以恰好那个增量出现。我从那些判决中把它带了过来
而没有核实；两者都错了，§6 记录了更正。

MR 守卫的效应远比 14 道题大。正确引用它应是
**121 道中的 +42 至 +50 道（+34.7 至 +41.3 pp）**。

---

## 1. MR 范围的噪声底，是测得的而非继承来的

总体噪声底（11 道 / 2.20 pp）是在 500 道题的评分样本上测得的。
MR 守卫是在 121 道题上评分的，因此总体噪声底并不支配它。
我直接测量了 MR 范围的噪声底，使用的是与总体噪声底同源的、位于 `2c2c635` 的
四次同配置运行，并用到 MR 消融报告已经携带的 `featureCorrect` 向量。

`featureCorrect` 按 `sampleInstances` 顺序产出，因此这些向量在同配置运行之间
按位置对齐。除非每个向量都恰好是 121 长，否则脚本会拒绝比较，
这样一旦错位就会大声失败，而不是静默地连接错误的题。

**MR 范围的流动：6 个运行对上为 8–13 道题（均值 10.2，sd 1.57）。** 因此支配
MR 守卫的噪声底是 **13 道题**，取观察到的最大值而非均值 —— 守卫必须在最坏情况上取胜，
因为守卫是在单次运行上被评估的，无法知道它落在极差的哪一点上。

### 为何我不使用增量噪声底（8）

增量序列的极差为 8，而逐题流动的极差为 13。增量是两个噪声量之差，
因此它的极差应*大于*任一成分，而非更小。它没有更大，意味着这四次运行恰好产出了
比其底层逐题流动所暗示的更接近的增量 —— 这是这特定四个值的一次巧合，
而非结构性事实。

我使用逐题流动（13），因为它是保守的选择，且它是具有直接可解读含义的量：
它是一次重跑所能移动的题数。使用更小的增量极差，会让噪声底因一次有利的抽取
而变得乐观。

## 2. 这里的流动是信号，不是噪声

MR 流动（50–62）远高于 MR 噪声底带（8–13）。这不是矛盾 ——
它是一个各实验臂提示词不同的消融所应有的形态。

两个 MR 实验臂在构造上渲染不同的提示词（`buildLegacyAggregationQaPrompt`
对 `buildAggregationQaPrompt`）。约 45% 的 MR 题收到的答案在两个实验臂之间不同，
因为这些提示词确实指示了不同的行为 —— CoT 提示词强制“先枚举再计数”，
配以交换规则和显式计数单位规则，而遗留提示词要求内联计数。
一个大的不一致计数，配以一个大的、同向的净增量（每一次运行中都是 46–56 修复
对仅 3–6 破坏），正是真实处理效应的样子。对比 KU 守卫，那里净 +2 坐落在 6 的流动上，
并未越过其 3 的噪声底。

## 3. `20592f2` 会改变 MR 比较吗？不会 —— 且我是验证的，不是假定的

这重要到值得测试，因为若答案缓存修复改变了 MR 消融，
上面的历史 MR 噪声底就在测量一个与当前不同的配置，无法比较。

它没有改变。一个针对 `runMrAggregationAblation` 的探测，使用计数 LLM，
显示该消融恰好发出 **3 次 LLM 调用：1 次查询扩展 + 2 次聚合**，
且两个聚合提示词是不同的。对给 MR 实验臂单独的答案缓存的构建
（模拟 `20592f2` 之前的行为）运行同样的探测，得到**相同的 3 次调用和相同的
2 个不同聚合提示词**。

原因是结构性的：

- MR 实验臂**本就共享**查询扩展缓存。其键是
  `` `${promptBuilder.name}:${question}` ``，且两个实验臂都使用同一个默认
  `buildQueryExpansionPrompt`，因此它从未被重新查询。
- 两个聚合提示词在每一道题上都**逐字节不同**，因此新共享的答案缓存对 MR
  从不命中。共享在这里是一次空操作。

所以 §1 中的 MR 噪声底对当前代码以及它据以测量的代码都有效，
且该修复的真正效应仅限于那些提示词逐字节相同的实验臂
（TR 引擎、TR 窗口、TR 覆盖、KU 双时间）—— 正是 `report-runner.test.ts` 中
变异测试所失败的那一组。

MR 测试现在断言的较弱性质才是诚实的那个：MR 实验臂不共享任何提示词，
因此共享缓存不可能把它们坍缩成一次调用、使消融什么都测不到。

## 4. 范围与局限

- **n = 4 次运行。** 噪声底是四次观察上的一个极差，而非一个拟合的分布。
  第五次运行可能把它拓宽；增量的 3.2 倍余量足够大，适度的拓宽不会推翻判决。
- **噪声底是在修复前的运行上测得的。** §3 确立了该修复不改变 MR 消融，
  因此这是可靠的 —— 但它可靠是*因为 §3*，而不是因为这些运行同期。
- **`featureCorrect` 是一次按位置的连接。** 它是本分析中唯一一处位置是正确的键，
  且它受守卫保护：脚本拒绝比较不全是 121 长的向量。
- **第 4 次运行在这里不是离群点。** 不同于总体序列（那里丢掉第 4 次运行会把极差
  从 11 坍缩到 3），MR 序列是平的：四次运行中有三次特征正确为 98，
  且增量极差不依赖于任何单次运行。

## 5. 这改变了什么

MR 守卫是本项目中测得的最强结果，无需进一步验证即可报告。
下一个问题不是 MR 是否有效，而是**它为何停在约 81%**（98/121）：在一个已经强制枚举的
提示词下，特征实验臂上仍有 23 道题是错的。那是一个能力上限问题，
而非测量完整性问题，且它是正确的下一个目标。

TR 引擎守卫（历史上 83 → 97）在
`requantify_guards.py` 中针对它自己的噪声底被重新定量，而 KU 守卫（+2，噪声底 3）
是唯一**没有**越过其噪声底的守卫 —— 它应被报告为未解决，而非作为一个正面结果。

## 6. 对我自己早先判决的更正

`p5-verdict.md` 和 `p5-pairing-verdict.md` 都把 MR 聚合守卫描述为
“14 q / 11 pp 的较大效应”，并在提议重新定量时引用了那个数字。那个标签错了两重。

**错误 1 —— 认错了守卫。** 14 q / 11 pp 是 **TR 引擎**的增量。它以
`tr-llm-temporal → tr-deterministic-temporal`、83 → 97 的形式出现在八次 TR 运行中
（`34028574903`、`34035358249`、`34035372339`、`34226960621`、`34226975988`、
`34140072057`、`34140111361`、`34171370206`）。本仓库中没有任何 MR 报告的增量是 14。
我从一份较早的摘要中继承了那个标签并重复了它，而没有打开产物，
这正是 P5 配对判决当初被写下来要制止的那种错误。

**错误 2 —— 被低估了 3.2 倍。** 真实的 MR 增量是 +42 至 +50 道，而非 14。
由于错误 1，那个数字从来就不是 MR 数字，所以它从来就不会吻合；
但实际后果是，一个我排在第二位的守卫，事实上是本项目中测得的最强效应。

**本分析还更正了：** TR 引擎守卫在当前代码上*小于* 14 道这个历史数字所暗示的 ——
四次同配置运行给出的增量是 127 中的 7、10、11、9（均值 9.25），而非 14。
历史上的 14 来自代码历史中另一个时点的以 TR 为重心的运行。对照
TR 范围的噪声底，这个守卫仍然真实（均值 9.25 道，对照约 4 的 TR 噪声底），
但引用它时应引用同批次的运行，而非更早的纯 TR 运行。
TR 范围的噪声底见 `p5-verdict.md`。
